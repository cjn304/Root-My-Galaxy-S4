## 1. 结论

**整条授权链在真机上跑通了**，不是推的：

```
su (uid 2000, shell 域)
  → 白名单未命中
  → ish 提权（uid0 + init_shell）
  → 建 socket /data/local/tmp/.su_sock
  → am start RequestActivity（带 socket 路径）
  → APK 连 socket，读协议帧，弹出授权界面
  → 用户点"允许"
  → APK 回写 "socket:ALLOW"
  → su 读到 → exec
  → uid=0(root) gid=0(root) context=u:r:init_shell:s0
```

界面实测内容（uiautomator dump）：


## 2. 三个必须先趟清的坑

### 2.1 `am start` 需要 uid 0，shell 会 SecurityException

```
java.lang.SecurityException: Permission Denial: starting Intent {
  cmp=me.phh.superuser/...RequestActivity } from null (uid=2000)
  not exported from uid 10198
```

RequestActivity 是 `exported=false`。AMS 的 `checkComponentPermission` 对
`uid == 0 || uid == SYSTEM_UID` 直接 GRANTED，所以**必须先 ish 再 am start**。
实测 uid 0 + init_shell 下 `am_rc=0`，界面正常弹出。

顺带证明 `init_shell` 能：exec `system_file`（am 脚本）、走 `service_manager find`、
binder call 到 system_server。

### 2.2 APK 不是"读 extra"，是"读 socket"

`RequestActivity` 只是壳，转发到 `MultitaskSuRequestActivity`。它只从一个 extra 拿东西：

```java
mSocketPath = intent.getStringExtra("socket");
mSocket = new LocalSocket();
mSocket.connect(new LocalSocketAddress(mSocketPath, Namespace.FILESYSTEM));
```

其余全部从 socket 读。协议（`su.c:write_data` + Java `DataInputStream`）：

```
重复：[4字节大端 nameLen][name][4字节大端 dataLen][data]
直到 name == "eof"
```

上限：`SU_PROTOCOL_PARAM_MAX=20`、`SU_PROTOCOL_NAME_MAX=20`。

su 侧发的帧：

```
version=1  binary.version=17  pid=<ppid>  from.name=app  to.name=root
from.uid=<caller>  to.uid=0  from.bin=/system/xbin/su
bind.from=  bind.to=  init=  command=<cmd>  eof=
```

APK 回写 11 字节：`socket:ALLOW` 或 `socket:DENY`。

### 2.3 socket 的域问题（enforcing 下的隐患）

```
untrusted_app → init_shell:unix_stream_socket  = accept,bind,connect,getattr,getopt,ioctl,read
                                                  ← 无 connectto、无 write
untrusted_app → untrusted_app:unix_stream_socket = 全套（connectto/read/write 都有）
```

su 提权后是 init_shell，它建的 socket 标签属于 init_shell，APK（untrusted_app）连不上。
**当前能跑是因为设备处于 permissive**（2a 的现状）。

enforcing 下的正解：fork 一个**保持 app 域**的子进程持有 socket，
主进程提权后通过匿名管道与它交换结果（管道 fd 的 read/write 不受 SELinux 检查）。

## 3. 与 phh 原设计的差异

| | phh 原版 | 我们 |
|---|---|---|
| 谁拉起 APK | daemon（root，常驻） | su 自己（ish 后 uid 0） |
| socket 持有者 | daemon（su_daemon 域） | su 主进程（init_shell） |
| 提权后执行 | setuid | 内核改 cred |
| 依赖 su 域 | 是 | 否 |

**不需要 daemon** 这一点被证实了：APK 只认 socket 路径，谁在下面接都行。

## 4. sqlite 已接入，闭环完成

`src/su_apk.c` 现在按三级顺序判定：

```
1. /data/system/su_allow 白名单（adb 手工加，最快）
2. su.sqlite 的 uid_policy（APK 记住的授权）
3. 都没有 → 弹窗
```

`db_check()` 照 `db.c` 的语义实现：

```c
select policy, until, command from uid_policy where uid=?
  command 为空 → 匹配所有命令
  until == 0 或 until > now → 有效
  policy == allow → 放行；deny → 拒绝；其余 → 弹窗
```

编译：`gcc -static -O2 -s -I. -DSQLITE_OMIT_LOAD_EXTENSION -DSQLITE_THREADSAFE=0
-DSQLITE_OMIT_WAL -o su su_apk.c sqlite3.c` → **753,912 B**。

**实测（数据库里已有 uid 2000 的 allow 记录）**：

```
$ /system/xbin/su -c id
uid=0(root) gid=0(root) context=u:r:init_shell:s0
rc=0
```

输出里**没有** `Starting: Intent` —— 没有弹窗，直接从数据库放行。闭环成立。

## 4b. 完整时序（实测）

```
第一次：
  su (uid 2000) → 白名单未命中 → 库无记录 → ish → 建 socket → am start
  → APK 弹窗 → 用户勾"永久记住" → 点"允许"
  → APK 写 uid_policy(2000, 0, 'allow', 0, '', 'com.android.shell', 'Shell')
  → 回写 socket:ALLOW → su exec → uid=0 ✓

第二次：
  su (uid 2000) → 白名单未命中 → 库命中 allow(until=0, command='')
  → 直接 exec → uid=0 ✓（无弹窗、无 am start）
```

## 5. 当前状态与剩余问题

| 项 | 状态 |
|---|---|
| APK | `me.phh.superuser` 已装，uid 10198 |
| `/system/xbin/su` | sqlite 版（753,912 B），`su_exec`，755 |
| `/data/system/su_allow` | `99999`（让 2000 走数据库/弹窗路径） |
| `uid_policy` | 1 条：uid 2000 / allow / until=0 / command='' |
| 模块 | 加载中，permissive |
| 屏幕 | `svc power stayon true` |

### 还没解决的三件

1. **enforcing 下的 socket 跨域**
   `untrusted_app → init_shell:unix_stream_socket` 无 `connectto`/`write`。
   现在能跑是因为 permissive。正解：fork 一个保持 app 域的子进程持有 socket，
   主进程提权后通过匿名管道交换结果（管道 fd 的 read/write 不查 SELinux）。

2. **2a 开机自动化**
   冷启动顺序仍是手工三步（`boot_stage.sh`）：bootmode → permissive → kernel 域 insmod。
   要写进 `init.sec.boot.sh`。

3. **真 app（uid 10xxx）的端到端**
   目前用 shell 的 uid 2000 + `ctx` 伪造 untrusted_app 域验证。
   域这一层是真的，uid 这一层没测——真 app 调 su 时会走完全相同的路径，
   只是数据库里要有一条属于它 uid 的记录。
