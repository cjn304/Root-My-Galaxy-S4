# P4.27 写别人 app 数据：fsuid + untrusted_app 双钥匙方案

日期：2026-10-22
目标：不再依赖 permissive，也能写任意 app 的 `/data/data/<pkg>`

---

## 一、问题：两把钥匙分别在两个域手里

策略实测（`sepolicy_parse.py` 查二进制策略）：

| 域 | DAC 钥匙 | SELinux 钥匙 |
|---|---|---|
| `init_shell` | ✅ uid0 + caps（setuid/setgid/fowner/chown/dac_override） | ❌ `app_data_file`：file 无 `write`，dir 无 `create/add_name/remove_name` |
| `untrusted_app` | ❌ capability 规则为空（无 `dac_override`） | ✅ `dir: create/add_name/search/write`，`file: create/write/append` |

没有任何单一域同时拥有两把钥匙。原来的做法是打开 `init_shell` 的
permissive bit（bit 986），靠 permissive 绕过 SELinux 检查 —— 能用，但
支撑它的是 permissive 而非策略，属于设计缺陷。

## 二、方案：一个进程里拼两把钥匙

`/system/xbin/appwrite`（700 root:root）：

```
1. 读源文件（还在 init_shell 域，任意路径都能读）
2. 写 /dev/ktool: "ctx u:r:untrusted_app:s0 <uid> <gid>"
      → 模块换 cred->security->sid = untrusted_app
      → 模块同时把 cred->fsuid/fsgid 写成目标目录 owner
3. open/write 目标文件
      DAC：fsuid == owner，0700 目录直接过（不需要 dac_override）
      SELinux：untrusted_app -> app_data_file:file write，策略允许
```

关键点：**两把钥匙都在内核里拼，不经过任何 capability 检查**。

## 三、踩到的三个坑（都很隐蔽）

### 坑 1：`ktool root` 不换 SELinux 域

`do_root()` 只做两件事：补满 4 组 caps、把 8 个 uid/gid 字段清零。
**它完全不碰 `cred->security`**，所以进程留在调用者的域里：

```
adb shell（shell 域）→ ktool root → 仍是 shell 域，只是 uid=0 + caps 满
boot 脚本（init_shell）→ ktool root → 仍是 init_shell 域
```

`shell` 域没有 permissive bit，策略也不给它 `setuid` capability，于是
`setfsuid()` 静默失败。

### 坑 2：`setfsuid` 失败是静默的

`sys_setfsuid()` 的失败路径是 `return old_fsuid;` —— **不设 errno**：

```c
	if (!ns_capable(ns, CAP_SETUID) && ...)
		goto error;      /* error: return old_fsuid; */
```

实测输出极具误导性：

```
setfsgid(10199)    -> ret=0 errno=0 (Success)
setfsgid(10199) #2 -> ret=0 errno=0 (Success)   ← 期望 10199，实际 0
/proc/self/status: Uid: 0 0 0 0                 ← fsuid 根本没变
```

第一版 appwrite 因此误报“成功”过一次：那次 `setfsuid` 恰好被
permissive 缓存条目放行。**结论：不要用 setfsuid 探测；要检查
`/proc/self/status` 第四列，或者干脆交给内核写。**

### 坑 3：清掉 permissive 会触发内核 BUG

`ktool unperm` 之后，已经被缓存的拒绝在审计时踩到：

```
kernel BUG at security/selinux/avc.c:158!          ← BUG_ON(tclass >= ARRAY_SIZE(secclass_map))
PC is at avc_audit_post_callback+0x104/0x108
Internal error: Oops - BUG: 0 [#5] PREEMPT SMP ARM
```

后果是**调用进程被 SIGSEGV 打死**（不是整机崩）。这是本内核审计路径的缺陷，
与我们的代码无关。处置：**不要在运行期 unperm 后继续跑业务命令**，
要么重启（缓存清空），要么压根不 unperm。

## 四、模块改动（v13）

`ktool_setctx()` 支持可选尾缀：

```
ctx <context>                只换域
ctx <context> <uid> <gid>    换域 + 内核直写 fsuid/fsgid
```

```c
	if (uid >= 0)
		new->fsuid = (uid_t)uid;
	if (gid >= 0)
		new->fsgid = (gid_t)gid;
	commit_creds(new);
```

只改 fsuid/fsgid，不改 uid/euid：文件 owner 由 fsuid 决定，DAC 判定也只看
fsuid，所以 `uid 仍是 0 + fsuid = 目标 owner` 就够，且保留 root 能力用于
读源文件。

`struct cred` 在本树用裸 `uid_t/gid_t`（不是 kuid_t），直接赋值即可；
`security` 偏移 0x58 已验证（换域生效就是证明）。

门禁保持不变：`ctx` 只有 `exe=/system/xbin/su` 或**已 uid0**的进程能过。
app 永远到不了 uid0，所以这条不放宽攻击面；而 su 授权的 app 本来就是 root。

## 五、真机验证（2026-10-22，冷启动后）

```
# 从 adb shell 起（shell 域，没有 permissive，也没有 setuid capability）
/data/local/tmp/ktool root /system/xbin/appwrite - /data/data/com.amaze.filemanager/aw_v13 < src
appwrite: dst dir /data/data/com.amaze.filemanager owner uid=10199 gid=10199, src 31 bytes
appwrite: OK 31 bytes -> /data/data/com.amaze.filemanager/aw_v13

# 结果
-rw------- u0_a199 u0_a199  u:object_r:app_data_file:s0  aw_v13
```

owner = 10199 = `u0_a199`，标签 = `app_data_file`，**全程没有动 permissive**。

对照（同一台机、早期无 permissive 时）：`init_shell` 直接 `echo > app_data_file`
→ `Permission denied`。

## 六、当前交付态

```
/system/bin/ktool        700 root:root     ← 门禁二进制，app/adb 都 exec 不了
/system/xbin/appwrite    700 root:root     ← 新工具
/system/lib/modules/ktool_mod.ko          ← v13（含 uid/gid ctx）
/dev/ktool               0666              ← 门禁在模块里
permissive               仅 init_shell（bit 986）1 个 type
内核模块                 ktool_enforce=1（只认 exe=/system/xbin/su）
```

实测：

```
sh -c 'echo ish > /dev/ktool'      → rc=1（DENY，exe=/system/bin/sh）
/system/xbin/su -c id（adb shell）  → 126 Permission denied
Amaze → gate exe=/system/xbin/su → ALLOW → ish uid0 ✅（弹窗正常）
```

## 七、遗留

1. **删除 / 重命名 app 文件**还没有对应工具（`appwrite` 只做写）。做法同理：
   同样 ctx 到 untrusted_app + fsuid，再 unlink/rename。需要时再加 `apprm`。
2. **`ktool sh` 的全开 permissive** 是历史遗留：它把 permissive_map 全开且
   重启不还原，容易污染 AVC 缓存（这次的坑 3 就是它留下的）。后续应改成
   只做 `do_root` + `ctx init_shell`。
3. **avc.c:158 的内核 BUG** 只在“已有缓存拒绝 + 审计”时触发，暂不处理，
   但要记住：诊断时不要随意 unperm。
