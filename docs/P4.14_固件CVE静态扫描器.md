# P4.14 — 内核固件镜像 CVE 补丁状态静态扫描器

> 目标：把 S4 上逐个 CVE 的**实测判据**，产品化为「不需要设备、只需要固件镜像」的扫描器。
> 这样评估 S5/S6（或任意新靶机）从「买设备试」变成「下载固件、跑脚本」。

---

## 1. 为什么需要它

S4 这一轮下来，补丁状态全靠两类证据：

| 类型 | 例子 | 成本 |
|---|---|---|
| 行为实测 | dirtycow 金丝雀跑 57 万次写 | 需要设备 + 时间，且失败≠有洞 |
| 静态反汇编 | `follow_page` 里找 `can_follow_write_pte` 三条件 | 需要设备才能拿到 `kernel.raw` |

关键发现：**静态判据才是主证据**——它证明的是"代码路径被改了"，而不是"这次没打中"。

推论：
- 三星连 2013 年的 S4、在 2017 年的构建里都 backport 了 dirtycow；
- 但 **CVE-2015-1805（2015-02 公开、修复 2015-04）在本机未修**；
- 两个方向都错 ⇒ **SPL 与真实补丁状态不相关**（不是"撒谎"，是"无信息"）。

**所以任何新机器都不能靠 SPL 推断，只能逐条扫。**

## 2. 工具：`src/cve_scan.py`

### 核心：通用 kallsyms 自解析（不依赖任何机型锚点）

以前 `kallsyms_extract.py` 里的 `ARR/NUM_SLOT/NAMES/MK/TT/TI` 是**硬编码偏移**，换固件就失效。扫描器改为自搜索：

```
1. 扫全镜像，找"非降序 u32"的最大 run（值落在 [base, base+24MB)）→ kallsyms_addresses
2. 紧随其后的 u32 == run 长度 → num_syms 槽（自动跳过 ≤48B 的零填充）
3. names = num_syms 槽 + 4 + 12B pad
4. markers = names 之后首个"升序 u32、首项为 0"的序列，项数 = ceil(num/256)
5. token_table = markers 末尾（再跳零填充对齐）
6. token_index = 其后 256 个严格递增的 u16
7. 按 kallsyms_expand_symbol 标准算法解压名字
   —— 注意：跳过的是第一个**字符**，不是第一个 token
      （内核 skipped_first 是字符级；首 token 可能是多字符如 "Ts"）
```

**自验证结果**（S4 `kernel.raw`，base `0xc0008000`）：

```
kallsyms: 63133 符号
  arr@0x840180   names@0x87dc10
  mk@0x937130    tt@0x937510   ti@0x937890
```

与项目里已验证的硬编码偏移 **完全一致**；导出表与 `kallsyms.txt` **地址集合相同**，仅 326/62325 条名字不同（同地址符号别名取了不同代表名，非错误）。

## 3. 判据表

| CVE | 静态判据 | S4 实测基准 | 扫描器输出 |
|---|---|---|---|
| CVE-2016-5195 (dirtycow) | `follow_page` 是否同时含 `FOLL_FORCE\|FOLL_COW`(0x4010) 与 pte dirty(0x80) 判定 | **FIXED** | FIXED ✓ |
| CVE-2015-1805 (pipe iov) | `pipe_iov_copy_from_user` 签名形态：4 参值传递 = 未修；5 参带 atomic 指针 = 已修 | **VULNERABLE** | VULNERABLE ✓ |
| CVE-2026-43499 (GhostLock) | `__list_del_entry` 失败分支是否 `udf`(ARM 的 BUG()) | **DEBUG-FATAL** | DEBUG-FATAL ✓ |
| CVE-2019-2215 (binder) | `binder_free_thread` 是否清 `t->from`（零寄存器写多偏移） | **FROM-CLEARED** | FROM-CLEARED ✓ |
| CVE-2015-3636 (PingPong) | `ping_rcv`/`ping_v4_unhash` 符号存在性 | 未测 | PRESENT（需进一步判引用形态） |
| 通用 | `vermagic`、`list_del corruption`、`CONFIG_SEC_DEBUG_LIST_PANIC` 等字符串 | — | 3 项命中 |

### 判据来源（都在设备二进制上验证过）

**dirtycow** — `follow_page` @ `0xc00dee8c` 反汇编：

```
c00def28:  tst  r7, #128        @ 0x80     ← pte_dirty 判定
c00def30:  movw r3, #16400      @ 0x4010   ← FOLL_FORCE|FOLL_COW
c00def34:  and  r3, r4, r3
c00def38:  movw r1, #16400      @ 0x4010
c00def3c:  cmp  r3, r1
c00def40:  beq  0xc00df05c
```

三条件齐全 ⇒ 修复已 backport。**注意 objdump 立即数打印成十进制，hex 在行尾 `@` 注释里**——正则必须两种形态都匹配。

**GhostLock** — `__list_del_entry` @ `0xc025cd68`：

```
c025cde8:  udf  #18            ← ARM BUG()，只在一致性检查失败时到达
c025ce0c:  b    0xc025cde8      ← 另一失败分支也跳到 udf
```

`udf` 出现即 FATAL（WARN 形态不会有 udf）。第一轮用 `b/wfi` 当"非致命分支"判成 MIXED 是**误判**——普通跳转指令到处都是，不能当 WARN 证据。

**binder** — `binder_free_thread` @ `0xc05154b8`：

```
c0515528:  str  r7, [r4, #16]   ← t->to_thread = NULL
c0515558:  str  r7, [r4, #24]
c051555c:  str  r7, [r4, #28]   ← t->from = NULL
```

r7 先置 0，再写 3 个不同偏移 ⇒ 清理 `from`/`to_thread` ⇒ **wake 路径证伪**。

## 5. 踩过的四个坑（都写进脚本注释了）

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | **objdump 不认 stdin** | `disasm()` 传 `-` 返回 0 条指令，**所有判决失效** | 先落盘临时文件再传给 objdump |
| 2 | **立即数是十进制** | 正则匹配 `#0x4010` 永远不中 | 同时匹配 `#16400` 与 `0x4010` |
| 3 | **kallsyms 有重复地址** | run 检测用严格 `>`，遇到别名就断，解析出 54 条假表 | 改成非降序 `>=` |
| 4 | **num_syms 槽有 12B pad** | 按"数组末尾即槽"算错位置，名字解压出来是乱码 | 数组后 ≤48B 内搜等于 run 长度的 u32 |
| 5 | **名字首 token ≠ 首字符** | 跳过整个 token 导致名字缺字（`stext`→`text`） | 解压后按**字符**去掉第一个 |

坑 3/4 叠加时最要命：能解析出"看起来合理"的 63133 条，但名字全是乱码。

## 6. 用法

```bash
python src/cve_scan.py <kernel.raw> [--base 0xc0008000] [--dump-syms kallsyms.txt]
```

- `<kernel.raw>`：从 `boot.img` 抠出的内核映像（非压缩的 raw）
- `--base`：内核虚拟基址（ARM 3.4 常见 `0xc0008000`，但必须按机型确认）
- `--dump-syms`：顺带导出符号表，便于人工核对

## 7. 边界与不可靠处

扫描器**不是**漏洞验证器，它只回答"补丁在不在"。已知不足：

| 不足 | 说明 |
|---|---|
| PingPong 判据太弱 | 只查符号存在性，没判 sk 引用形态，输出 `PRESENT` 而非 `VULNERABLE` |
| 依赖 kallsyms | 若固件裁剪掉 kallsyms（`CONFIG_KALLSYMS=n`）则退化为 UNKNOWN |
| 依赖 base 正确 | base 错了整个表就找错，目前靠人工指定 |
| 只有 5 个 CVE | 判据表需要随新 CVE 扩充 |

**它替代不了真机验证**，但能在一小时内砍掉 70% 的候选——剩下的才值得买机器上电。

---

## 8. 对 S5/S6 的直接用途

按上面的判据表，对 S5（klte, 3.4）/ S6（zeroflte, 3.10）：

1. samfw 拉官方固件（`tar.md5`）
2. 解 `boot.img` → 抠 `kernel`
3. `python src/cve_scan.py kernel.raw --base <该机型基址>`
4. 半小时出结论，再决定要不要买机器

**注意**：`--base` 必须按机型确认，不能直接抄 S4 的 `0xc0008000`。
