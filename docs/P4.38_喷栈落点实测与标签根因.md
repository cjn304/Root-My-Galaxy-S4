# P4.38 喷栈落点实测：harness 一直在空转（附 /dev/ktool 标签根因）

日期：2026-10-22
设备：GT-I9500 / ja3g / LRX22C.I9500ZSSHQD1 / 内核 3.4.5-6264821

## 一、这一轮最重要的结论

**`msgctl(msqid=0, IPC_SET, buf)` 在“id=0 的队列不存在”时返回 EINVAL，用户缓冲区没有
留到内核栈上；即便队列存在，IPC_OLD 的 0x3C 字节拷贝也会被紧接着的调用覆盖。**

三条实测（模块 `wfind` 在整页 8KB 内核栈里搜 4 字节图案 `0xcafe0000`）：

| 实验 | 条件 | 结果 |
|---|---|---|
| A | `msqid=0`，无该队列 | `msgctl` 返回 **-1/EINVAL**；整页栈 `hits=0` |
| B | `msgget(IPC_PRIVATE,0666)` 建出 id=0 后再 `msgctl(id, IPC_SET)` | 返回 **0**（成功） |
| C | 成功路径下再搜整页栈 | 仍 `hits=0`（IPC_OLD 变体） |

结合源码（`ipc/msg.c`）：

```c
static int msgctl_down(...)
{
    struct msqid64_ds uninitialized_var(msqid64);   /* msgctl_down 的帧 */
    if (cmd == IPC_SET) {
        if (copy_msqid_from_user(&msqid64, buf, version))   /* IPC_OLD 走这里 */
            return -EFAULT;
    }
    ipcp = ipcctl_pre_down(...);    /* 与 copy_msqid_from_user 同一个帧槽 */
```

`copy_msqid_from_user()` 的 `struct msqid_ds tbuf_old` 是**被调函数的局部变量**，
它返回后 `ipcctl_pre_down()` 立刻复用同一段栈 → 0x3C 字节的图案被覆盖。
只有 3 个字段（uid/gid/mode）被复制进 `msqid64`，那部分不含图案。

**所以 harness 的“喷栈”从设计上就没生效**，这解释了：

- `pass` 模式为什么死在 `_raw_spin_trylock` 且 `lock == 1`——waiter 根本没被改写过，
  `waiter->lock(+0x2C)` 是上一轮遗留值；
- 为什么 NOSPRAY 和 pass 死法类似；
- 为什么 probe 模式的 `0xdeadbeef` 铁证从来没出现过。

### 修法（二选一，需真机验证）

1. **改用 IPC_64**（`cmd = 1 | 0x100`）：`copy_from_user(out, buf, sizeof(*out))` 直接写进
   `msgctl_down` 自己的 `msqid64`（`msgctl_down` 的帧），syscall 返回后仍留在栈上。
   代价：长度变成 `sizeof(struct msqid64_ds)`（约 0x6C），覆盖范围比 0x3C 大，落点也要重算。
2. **让 T 在 A 的 msgctl 执行期间触发链走**（并发），而不是等 `sprayed` 之后再触发。
   这条更贴近“利用窗口”的原意，但同步难度高。

先用 `msgt4` 的两种模式（`./msgt4` = IPC_OLD，`./msgt4 6` = IPC_64）配 `wfind` 判定 1 是否成立。

## 三、/dev/ktool 标签：根因与修法（已改代码，待部署验证）

**症状**：`/dev/ktool` 与 `/dev/null` 一起变成 `u:r:system_server:s0`，`> /dev/null` 都被拒，
`su` 静默失效直到重启。

**根因**：老实现把 `/dev/ktool` 的 `i_security` **指针**指向 `/dev/null` 的 blob。
`isec->sid` 是 sidtab 的**序号**，策略一重载（Samsung SEPF 在 `mount -o rw,remount /system`
等时机重载）序号整体重映射，共享 blob 的两个 inode 一起变成别的类型。

**修法**：模块自己 `kmalloc` 一个 `inode_security_struct`，从 `/dev/zero` 的 blob 复制
（拿到正确的 sclass=10 与已初始化的 mutex），然后改回自己（inode 反向指针、list 自环、
sid），**每次 open() 用 `security_context_to_sid("u:object_r:null_device:s0")` 现算 SID 刷新**。
`/dev/null` 完全不受影响。

**另一个独立坑**：`miscdevice.mode = 0666` 只在 devtmpfs 首次建节点时经 devnode 回调生效；
反复 rmmod/insmod 后实测节点变成 **0600**，表现为 `can't create /dev/ktool: Permission denied`，
极易误判成 SELinux。现在模块在 init 里显式把节点 mode 设成 0666。

## 五、环境坑（记录备查）

- Android 5 的 toybox **没有** `sed/awk/tail/head/timeout/pkill`；脚本只能用 shell 参数展开。
- uid0 进程（shell 域）写 `/data/local/tmp` 会被已缓存的 capability 拒绝拦住 →
  取内核日志用 `adb shell "... cat /proc/last_kmsg" > 本地文件`，不要在设备上 `cp`。
- **不要把还带着悬空 `pi_blocked_on` 的线程 kill 掉**：`rt_mutex_adjust_prio_chain` 会

- 反复 panic 后设备偶发 adb `offline`，需要等它自己重启或物理断电重来。

## 七、补充：扫描法的可信度自检（必须看）

用已知值做对照：`wdump` 在 `0x1FE4` 打出 `be85b738`（pt_regs 里的用户寄存器），
再用 `wfind <pid> be85b738` 搜 → **hits=1，命中 0x1FE4**。说明

- `task->stack` 取的是对的（8KB 栈，pt_regs 在 `0x1FB8..0x1FFF`）；
- `probe_kernel_read` 对栈页可读；
- `wfind` 的比对逻辑正确。

但同一个进程（`/proc/<pid>/cmdline` 确认仍活着）刚调过 `poll(pfd, 32, 0)`（32 个 pollfd
= 256 字节，按内核源码应落在 `do_sys_poll` 的 `stack_pps` 上），`wfind 0xcafe0000`
在 0..0x4000 全范围仍是 **hits=0**。

结论：**“搜残留”这套方法目前并不可靠**——syscall 返回后那些栈槽可能已经被
返回路径或后续调用覆盖。因此：

- “harness 用 msqid=0 且队列不存在 → EINVAL”这一点是**硬结论**（返回值直接测到）；
- “IPC_OLD/IPC_64 的拷贝能否留到 syscall 之后”**尚未定论**，需要换验证手段：
  让 T 在 A 的 msgctl **执行期间**触发链走（并发窗口），或在 `msgctl` 里用
  `wfind` 在*系统调用进行中*采样（需要另一个线程持续扫描）。

下一步建议：直接改 harness 为并发触发（T 在 A 进入 msgctl 前后紧贴着跑），
用 `pass` 模式下 `waiter->lock == fake_lock` 是否成立来判定，而不是靠残留扫描。

## 八、更正与新增实测（P4.39）

### 8.1 撤回：“喷栈空转”这个判决证据不足

`msgctl` 返回 EINVAL 只说明返回值，不说明没拷贝（拷贝在 `ipcctl_pre_down` 之前）。
我拿“事后搜残留”去定罪，方法本身不成立。**新版实测证明了这一点**：

```
pollblock: 30 个 pollfd，poll(fds,30,-1) 停在内核里
wfind cafe0004 → HIT off=1c04，随后 cafe0008/cafe000c/... 每 8 字节一个，完整
```

- 阻塞期间：`do_sys_poll` 的 `stack_pps` 在 **base+0x1C00**，240 字节图案完好；
- 之前 `poll(pfd,32,0)`（**已返回**）搜不到任何图案 → **syscall 返回后那段会被覆盖**，
  “事后搜残留”只对阻塞型调用有效。

所以 `msgctl` 到底有没有拷、拷到哪，目前**仍是未定值**，只能靠效果判据或停在里面测。

### 8.2 8 字节平移：这条批评成立

实测 `pi_blocked_on = base+0x1DF8`，而 `E = base+0x1FB8`，所以

```
waiter = E - 0x1C0        （不是 P4.13 的 E - 0x1B8）
lock   = waiter + 0x2C = E - 0x194
task   = waiter + 0x28 = E - 0x198
```

我上一轮把它说成“确认 `stack_top-0x208`”，措辞掩盖了“旧表要整体 +8”这件事。

### 8.3 但 `buf[0x00] → lock` 这一步推不出来

它要求 msgctl 的拷贝基 D = 0x194。而现有模型里 D 是 **0x190**（独立常数，不是从
waiter 推的）。两者只能二选一：

| 若 D = | 拷贝覆盖 waiter 的 | lock 是否可达 |
|---|---|---|
| 0x190 | waiter+0x30 .. +0x67 | **不可达**（lock 在 +0x2C，比基址高 4 字节） |
| 0x194 | waiter+0x2C .. +0x63 | 可达，`buf[0x00]` = lock |

也就是说：**要么 buf[0] 命中 lock，要么整个窗口都够不着 lock，不存在 buf[0x0C] 那种中间态。**
D 必须实测，不能靠平移推。而 msgctl 不阻塞 → 只能换载体。

### 8.4 新载体：poll 阻塞（240B）+ 把 futex 帧加深

| 载体 | 栈上字节 | 能否停住 | 实测深度 |
|---|---|---|---|
| `poll(fds,30,-1)` | 240 | ✅ | **base+0x1C00**（已验证图案完整） |
| `msgctl` | 56 | ❌ 立即返回 | 未定 |
| `semtimedop`（64 ops） | 384 | ✅ | 未测（>0x1A00） |

poll 的落点 0x1C00 与 waiter 的 0x1DF8 差 **0x1F8**。所以做法是：
**在 futex 调用外面套一层带 0x1F8 局部数组的函数**，把 waiter 整体压到 ~0x1C00，
让它和 poll 的 240 字节窗口对齐（`lock` 落在 buffer+0x24 附近）。

这样喷栈就变成“阻塞中写入”，不存在返回覆盖问题，也不需要 msgctl 了。

### 8.5 纪律补充

- 判据一律用**效果**（`waiter->lock == fake_lock`），不用残留；
- 实验前先确认没有线程卡在 PI 环里；
- 后台进程用 `(trap '' HUP; exec ...) </dev/null` 拉起，别让 adb 会话语义决定寿命。

## 九、新载体落地：`semop` 阻塞态实测（P4.40，本轮最有用的一张表）

`semtimedop` 在这台机上不可用（`nsops` 超 `semopm` 或 timeout 语义问题，实测立即返回），
但 **`semop` 会真的阻塞**（`/proc/<pid>/stat` 状态 `S`），且 `sembuf[32]` 走 `fast_sops`
留在栈上。把标记放 `sem_op`（`sem_num` 必须全 0，否则内核在阻塞前就判 EINVAL）：

```
wfind16 <pid> 0101  →  HIT16 off=1df0     (标记 = ops[1].sem_op，位于数组基址+8)
⇒ 数组基址 = 0x1DE8
```

`wdump` 交叉验证（6 字节步进完全吻合）：

```
1de8: ffff0000   ops[0] sem_num=0 sem_op=0xffff(-1) flg=0
1df0: 00000101   ops[1] sem_op=0x0101
1df4: 01020000   ops[2] sem_op=0x0102
1df8: 00000000
1dfc: 00000103   ops[3] sem_op=0x0103
```

### 9.1 与 waiter 的相对关系（都是"基址+偏移"，同一线程）

| 项 | 偏移 |
|---|---|
| `semop` 的 `fast_sops` 数组 | **base + 0x1DE8**（32 项 × 6 = 192 字节，覆盖到 +0x1EA7） |
| futex waiter | **base + 0x1DF8** |
| ⇒ 数组覆盖 | waiter−0x10 .. waiter+0xAF ✅ **完全覆盖 waiter 结构** |

### 9.2 字段映射（关键：lock 正好落在 ops[10] 的起始）

| waiter 字段 | 地址 | 数组内偏移 | 对应 sembuf |
|---|---|---|---|
| `list_entry.prio` | +0x00 | 0x10 | ops[2] 字节 4-5 |
| `node_list.next/prev` | +0x0C/+0x10 | 0x1C/0x20 | ops[4] 字节 4-5 .. |
| `pi_list_entry` | +0x14 | 0x24 | ops[6] 起 |
| `task` | +0x28 | 0x38 | ops[9] 字节 2-5 |
| **`lock`** | **+0x2C** | **0x3C = 10×6** | **ops[10].sem_num（低16） + ops[10].sem_op（高16）** |

### 9.3 约束与对策

内核在阻塞前会**校验所有 `sem_num`**（实测 `sem_num=0xDEAD` 直接 EINVAL 返回），
所以每个 sembuf 的前 2 字节必须是 0。落到 `lock` 上就是：

```
lock = (sem_num << 0) | (sem_op << 16)   且 sem_num 必须为 0
⇒ lock 的低 16 位恒为 0 ⇒ fake_lock 必须 64KB 对齐（mmap 后按 0x10000 对齐即可）
```

同理 `waiter+0x20`、`+0x26` 等位置的**低 16 位也被强制为 0**，做 plist 自指时要按这个
约束选地址（或改用另一条 6 字节相位不同的路径）。

### 9.4 由此得到的正确利用顺序

```
1) A: futex WAIT_REQUEUE_PI  →  waiter 建在 base+0x1DF8，返回后 pi_blocked_on 仍悬空
2) A: semop(semid, ops32)    →  数组落在 base+0x1DE8，ops[10] 写入 fake_lock（64K 对齐）
                                semop 阻塞（状态 S），数据常驻，不存在"返回即覆盖"问题
3) T: 加锁触发 rt_mutex_adjust_prio_chain
       → 读 A->pi_blocked_on = 0x1DF8 → waiter->lock = fake_lock  ✅
```

这条路径**不需要 msgctl，也不需要猜 D**——落点是实测的，且是阻塞态写入。

## 十、里程碑：`waiter->lock == fake_lock` 已被实测证实（P4.41）

用 `sem_spray`（新 harness，semop 载体）跑 probe 模式：假锁的 `wait_list.node_list.next`
故意放 `0xdead0000`。设备 oops，现场：

```
kernel BUG at kernel/rtmutex_common.h:74!        <- rt_mutex_top_waiter 的 BUG_ON(w->lock != lock)
PC is at rt_mutex_adjust_prio_chain+0x428/0x42c
r8 : b6f30000      <- ★ 我们的 fake_lock（64KB 对齐，正是 mmap 出来的地址）
r2 : dead0000      <- ★ 我们塞进假 wait_list.next 的野指针
r10: c3c9fdf8      <- 链里用的 stack 指针
```

**`0xdead0000` 只存在于我们的假锁里，链条把它读出来了** ⇒
`waiter->lock` 确实被 `sembuf[10]` 改成了 `fake_lock`，且链走真的用了它。

这一步同时验证了三件事：
1. `semop` 阻塞态确实把数组留在 `base+0x1DE8`；
2. `lock` 落在 `ops[10]` 起始（0x3C = 10×6）这条映射正确；
3. `pi_blocked_on` 在 futex 返回后仍指向 `base+0x1DF8`，链走读得到。

## 十一、下一个卡点：`plist_del` 需要 entry 地址，而用户态不知道

链走接着要执行 `plist_del(&waiter->list_entry, &lock->wait_list)`，`CONFIG_DEBUG_LIST=y`
会做：

```c
prev->next == entry && next->prev == entry      // entry = waiter + 0x0C（内核栈地址 0xc…）
```

问题在于 `waiter->node_list.next` 的编码被 sem 载体钉死了：

| 字段 | 数组偏移 | 可控范围 |
|---|---|---|
| `node_list.next`(+0x0C) | 0x1C | 低16 = `ops[4].sem_flg`（自由），**高16 = `ops[5].sem_num` 必须 0** ⇒ 只能 `0x0000XXXX` |
| `node_list.prev`(+0x10) | 0x20 | `ops[5].sem_op`+`sem_flg`，**32 位全可控** |
| `prio_list`(+0x04) | 0x14 | 32 位全可控（可做自环，让 plist_del 跳过重排分支） |

### 11.1 可行解法：把假链表放到用户态低地址

ARMv7 没有 PAN/SMAP，内核在 SVC 模式直接解引用用户地址是允许的（`copy_from_user`
就是干这个的）。所以：

```
mmap(0x0000E000, 2 页, MAP_FIXED)      // 低 16 位地址，正好塞得进 next 的 16 位
  *(u32*)0x0000E000 = entry            // prev->next == entry
  *(u32*)0x0000F004 = entry            // next->prev == entry
waiter->node_list.next = 0x0000F000    // 只用低 16 位
waiter->node_list.prev = 0x0000E000    // 32 位全可控
waiter->prio_list.next = prev = &waiter->prio_list   // 自环，让 plist_del 跳过重排
```

这样 `list_del` / `list_add` 的两个 DEBUG_LIST 检查都能过，写操作全落在我们自己的页里，
链走就能一路走到 `wake_up_process(waiter->task)`（task 我们填成 `init_task`，无害）。

### 11.2 唯一缺的东西：`entry` 的值

`entry = task->stack + 0x1E04`，是内核栈地址，用户态不知道。两条路：

1. **模块协助（推荐）**：harness 进 semop 阻塞后把 tid 写到 `/data/local/tmp/sem.tid`，
   外部跑 `echo "waiter <tid>" > /dev/ktool` 拿到 `stack`，算出 entry 写回文件，
   harness 读文件后填进用户页再放 T。
2. **自我泄漏**：让 A 先触发一次可控的 `%p` 打印（`die()` 的 `stack limit`），
   从 dmesg 读回——但那条路要一次 oops。

### 11.3 纪律确认

probe 那次是 **BUG（udf）而不是 page fault**，说明链走在 `rt_mutex_top_waiter` 就停了，
没有走到 `plist_del`；机器随后靠 softlockup 重启。每次实验仍等于一次重启。
