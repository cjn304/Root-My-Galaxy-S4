`e3023e04 = waiter + 0x0C = entry_node`，是**内核栈地址**。

T 仍然阻塞（A 还持 u4），`owner=0` 说明链走走了 `if (!rt_mutex_owner(lock))`
分支并释放了假锁 —— 与源码路径推演一致。

**没有 BUG、没有 panic、没有锁泄漏。**

## 二、这一版的关键改动：先泄漏，后喷栈

P4.43 失败的那次：

```
PC is at __list_del_entry+0x38
r0 = d0bcfdfc   (entry = waiter+0x04, prio_list)
r2 = 0000d000   (next = 我们设的常数)
r3 = 00000000   (prev = 0)   ← 崩在这里
```

原因：`prio_list.prev` 落在 `ops[4].sem_num | ops[4].sem_op<<16`，
而 **`sem_num` 必须为 0**（内核在阻塞前逐个校验），所以
`prio_list.prev` 只能编码 `0xXXXX0000`（低 16 位恒 0）。
我填了 `0xD800`，实际落成 0。

**换个顺序就绕开了整个分支**：

| | P4.43 | P4.44 |
|---|---|---|
| 时序 | A 先 semop 阻塞 → 再泄漏 | A futex 返回 → 泄漏 → **再** semop |
| `prio_list.next` | 只能填常数 | **可以直接填 `&waiter->prio_list`（栈地址）** |
| `list_empty(&node->prio_list)` | 假 | **真** |
| plist_del 重排分支 | 进入（且需要 64KB 对齐的 prev） | **完全跳过** |
| 剩下要过的检查 | 4 个 list_del 检查 | 只剩 `node_list` 的 2 个 |

代价只是一次额外的 pipe 握手：A 在 futex 返回后阻塞在 `read(ack)`，
主线程泄漏 stack、算地址、填用户页、写 ack，A 才去 `build_sops()` 并调 semop。

这也顺带说明：**`waiter` 区在 semop 之前可以被任意覆盖**（A 在 `read` 里睡过），
semop 的 `fast_sops` 落点不受之前调用影响 —— 与 P4.40 实测的 `base+0x1DE8` 一致。

## 三、两条硬编码约束（都来自 `sem_num` 必须为 0）

`sembuf` 是 6 字节：`sem_num(2) | sem_op(2) | sem_flg(2)`，数组基址 = waiter − 0x10：

| waiter 字段 | 数组偏移 | sembuf 编码 | 可控性 |
|---|---|---|---|
| `prio` +0x00 | 0x10 | `ops[2].sem_flg \| ops[3].sem_num<<16` | 低 16 位 |
| `prio_list.next` +0x04 | 0x14 | `ops[3].sem_op \| ops[3].sem_flg<<16` | **32 位全可控** |
| `prio_list.prev` +0x08 | 0x18 | `ops[4].sem_num(0) \| ops[4].sem_op<<16` | 只能 `0xXXXX0000` |
| `node_list.next` +0x0C | 0x1C | `ops[4].sem_flg \| ops[5].sem_num(0)<<16` | 只能 `0x0000XXXX` |
| `node_list.prev` +0x10 | 0x20 | `ops[5].sem_op \| ops[5].sem_flg<<16` | **32 位全可控** |
| `task` +0x28 | 0x38 | `ops[9].sem_op \| ops[9].sem_flg<<16` | **32 位全可控** |
| `lock` +0x2C | 0x3C | `ops[10].sem_num(0) \| ops[10].sem_op<<16` | 高 16 位（所以 64KB 对齐） |

两条推论直接决定了地址布局：

1. **`lock` 必须 64KB 对齐** ⇒ `fake_lock` 从 mmap 结果向上取整到 0x10000 边界；
2. **`node_list.next` 只能 0x0000XXXX** ⇒ 假链表节点必须放在用户低地址。

## 四、低地址布局（踩过的两个坑）

| 地址 | 实测结论 |
|---|---|
| `0x0` 页 | **不可用**：`mmap(0)` 返回 EINVAL（errno=22），即使 uid0 + `CapEff=ffffffff`。`mmap_min_addr` 的保护不是仅靠 CAP_SYS_RAWIO 就能过的（SELinux `capability mmap_zero`） |
| `0x8000..0xFFFF` | ✅ 可用（`mmap_min_addr=0x8000` 之上，且低于 text） |
| `0x10000` 起 | ❌ **是程序自己的 text**（`readelf -l`：`LOAD 0x00010000`）。P4.43 用 `mmap(0xC000,0x14000,MAP_FIXED)` 直接把 text 清零，表现是「sg.log 已创建但 0 字节 + SIGSEGV」 |

最终布局：

```
0x0000_8000..0x0000_FFFF   用户页（mmap MAP_FIXED，32KB）
0x0000_9000                node_list.prev 指向这里 → *(0x9000) = entry_node
0x0000_A000                node_list.next 指向这里 → *(0xA004) = entry_node
0x0001_0000..             程序 text（不能碰）
```

## 五、现在的原语到底是什么

跑通的这条链给出的是：

```
plist_add(&waiter->node_list, &lock->wait_list)
  → *(lock+0x08) = waiter+0x0C      (栈指针)
  → *(lock+0x0C) = waiter+0x0C      (栈指针)
```

`lock` 目前指向我们自己的用户页，所以这两个写没有利用价值。
它的价值在于**链路本身被证明可走通且不崩**：从 `waiter->lock` 被替换，
到 `plist_del` 过 DEBUG_LIST，再到 `plist_add` 落笔，全程零 oops。

## 六、endgame 的硬约束（诚实评估，比 P4.13 时更清楚）

要把它变成"往内核写东西"，需要 `lock` 指向内核里的一个地址，且同时满足：

1. **`lock` 低 16 位 = 0**（64KB 对齐）—— 来自 `sem_num=0`；
2. `lock+0x00 == 0`（`raw_spin_trylock(&lock->wait_lock)` 要成功；
   若失败会 `goto retry` 无限重试，把 CPU 卡在中断关闭状态）；
3. `lock+0x08 / +0x0C` 自环（`wait_list` 空），否则 `plist_add` 走遍历分支，
   要额外满足排序条件；
4. `*(lock+0x28) == lock`（空表时 `rt_mutex_top_waiter()` 的
   `BUG_ON(w->lock != lock)`，w = (lock+0x08) − 0x0C = lock−0x04）；
5. `lock+0x10 == 0` 或 `!= top_task`（`rt_mutex_owner(lock) == top_task` 会提前返回）。

自然存在的内核对象几乎不可能同时满足 1+4。所以：

- **短期**：这是"验证成功"的成果，不是可用写原语；
- **可能的突破口**：`sem_num` 的上限由 `nsems` 决定。当前 `semget(..., 1, ...)`
  只有 1 个信号量，所以 `sem_num` 只能 0。若把 `nsems` 开到 `SEMMSL`
  （`/proc/sys/kernel/sem` 第二列，通常 32000 上下），`lock` 的低 16 位就能
  覆盖 0..32767，把"64KB 对齐"放宽到"低 15 位任意"——是否够用要看目标对象。

## 七、复现步骤

```sh
# 1) 加载带 waiter/kread/wfind 的调试模块（需要 permissive 一次）
/data/local/tmp/ktool permissive
/data/local/tmp/ktool flush
/data/local/tmp/ktool sh -c 'rmmod ktool_mod; insmod /data/local/tmp/ktool_mod_kr6.ko \
    ktool_enforce=1 ktool_target=ja3g:3.4.5-6264821'
/data/local/tmp/ktool restore          # 关 permissive

# 2) 跑（ktool root 的 exploit 是竞态，失败就重试，表现为 "kwrite uid fail"）
/data/local/tmp/ktool root /data/local/tmp/sem_ghost

# 3) 看结果
cat /data/local/tmp/sg.log
```

判据：`sg.log` 里 `[T] after : wait_list.next=` 的值等于 `[L] ... entry_node=`。

**跑完必须重启**：A 还阻塞在 semop、T 阻塞在 u4，且 A 的 `pi_blocked_on`
是悬空的——kill 这些线程会在 `rt_mutex_adjust_prio_chain+0x180` 冲空指针 panic。
