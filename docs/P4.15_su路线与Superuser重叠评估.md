# P4.15 — su 路线裁决：与 Superuser 的重叠、以及被忽略的第三条路

日期：2026-10-21
设备：GT-I9500 / 内核 3.4.5-6264821
起因：对「手动链 vs 代码地图」的批评，以及「要不要用 phh Superuser 官方 APK」

---

## 1. 结论

批评成立。但路线图里有两处事实错误、一处架构冗余：

| 判断 | 裁决 |
|---|---|
| 「A 段是资产，全靠手动，重启归零」 | ✅ 成立 |
| 「B 段是地图，一行代码没写」 | ⚠️ 部分不成立：**2a 已经写完并实测过三轮重启** |
| 「C 段是假设，开机钩子从没见过执行」 | ❌ **错**：P4.11 有 uid=0 + `u:r:init_shell:s0` + `exec patch already on` 的实测输出 |
| 「用 Superuser 官方 APK」 | ❌ 策略层跑不通，且**整条 daemon 链对本机是冗余的** |
| 「三个代码块：ish / 2a / su」 | ✅ 但 2a 只剩追加 `insmod` 两行；su 不需要 1 天 |

**被忽略的第三条路**：`/dev/ktool` 的标签是 `null_device`，而本机策略有一条

```
allow domain null_device:chr_file {append,getattr,ioctl,lock,open,read,write}
```

`domain` 是**所有域的根属性**。也就是说 **untrusted_app 可以直接写 `/dev/ktool`**。
phh 的 daemon + 抽象 socket + sqlite 授权库这三层，存在的唯一理由是
「su 二进制是 setuid root，需要一个常驻 root 进程替它提权」。

我们有内核模块能就地改 cred —— **daemon 层没有存在理由**。

---

## 2. 事实核查

### 2.1 2a 已经做完并实测过

P4.11 记录（2026-10-19）：

```
=== 2a auto start ===
uid=0(root) gid=0(root) context=u:r:init_shell:s0
permissive_map: node=c0b9ec3c highbit=1536
permissive_rc=0
c0012164 <= ea000047 (was 0a000002)
patch_rc=0
=== 2a auto end ===
```

载体是 `init.rc:939` 的 `service sec-sh /system/bin/sh /system/etc/init.sec.boot.sh`，
未改 boot.img、未改 init.rc。重启后 `ktool sh` 输出 `exec patch already on`，
证明补丁**是开机脚本打的**，不是本次手动打的。`warranty_bit=0`，TIMA `warranty okay d`。

**缺的只是**：在这个已验证的脚本末尾追加

```sh
insmod /system/lib/modules/ktool_mod.ko
chmod 666 /dev/ktool
```

和 `lkmauth_bootmode=2`（BSS 变量，需要在 insmod 前由 exploit 写入）。
这不需要半天，是 15 分钟 + 一次重启。

### 2.2 「init_shell 真机读 /data/data 没验证」——对，但验证成本是 5 分钟

2a 的 `sec-sh` **本身就是 uid=0 + init_shell**。不需要先写 `ish`：

```sh
ls -la /data/data > /data/system/dd.log 2>&1
cat /data/data/com.android.providers.contacts/databases/contacts2.db > /dev/null && echo READ_OK >> /data/system/dd.log
```

加两行、重启一次、看日志。这条一旦通过，「属性广播把 read 加回来了」这个
推导（P4.12 续十一，翻过一次烧饼）就从纸面变成事实。

### 2.3 「用官方 APK」在策略层不成立

phh 的 su 与 APK 之间的协议是：
- 抽象 unix socket，名字 `\0SUPERUSER`（`daemon.c:619`，不是文件路径）
- 数据库 `/data/data/com.koushikdutta.superuser/databases/su.sqlite`
- `su --version` 输出 `17 com.koushikdutta.superuser`

本机策略实测：

```
[2] untrusted_app 的 unix socket 目标
  DMM-daemon [unix_stream_socket]: connectto
```

**只有 DMM-daemon 一个**。没有 `su_daemon`，也没有 `su` 域：

```
su          = None
su_daemon   = None
superuser   = None
```

所以 phh 的 daemon 一起来就死在 `setfscreatecon("u:object_r:su_daemon:s0")`
和 `setexeccon("u:r:su:s0")` —— 这两个类型在本机 policydb 里根本不存在。

唯一能让它跑起来的办法是全局 permissive（2a 现在就是）。但那就等于
「用 permissive 掩盖一个策略缺失」，一旦 restore 或 2a 未执行就全崩。
这正是之前被批评过的「靠 permissive 装作可用」。

## 3. 策略证据链（enforcing 下成立，不需要 permissive）

| 步骤 | 规则 | 结论 |
|---|---|---|
| app exec `/system/xbin/su` | `allow untrusteddomain exec_type:file {execute,execute_no_trans,getattr}`，`su_exec ∈ exec_type` | ✅ 且**不换域**，留在 untrusted_app |
| file_contexts | `/system/xbin/su → u:object_r:su_exec:s0` | ✅ 已有条目 |
| su 写 `/dev/ktool` | `allow domain null_device:chr_file {...open,write}` | ✅ 全域可写 |
| 模块改 cred | 内核态，不过 SELinux | ✅ |
| 新域 exec 命令 | `init_shell → system_file:file {execute,execute_no_trans}` | ✅ |
| 新域读 app 数据 | `init_shell → app_data_file:dir/file {read,open,search}`（经 newAttr57 广播） | ⚠️ 需真机确认 |

整条链没有任何一环依赖 permissive。

### 5.1 ish 的实现（已写进 `kmod/ktool_mod.c`）

```c
static int ktool_ish(void)
{
	int (*ctx2sid)(const char *, u32, u32 *);
	struct cred *new;
	u32 sid = 0;
	char ctx[] = "u:r:init_shell:s0";
	char *sec;

	ctx2sid = (void *)kallsyms_lookup_name("security_context_to_sid");
	if (!ctx2sid) return -ENOSYS;
	if (ctx2sid(ctx, sizeof(ctx) - 1, &sid) || !sid) return -EINVAL;

	new = prepare_kernel_cred(NULL);      /* uid0 + full caps + 独立 security blob */
	if (!new) return -ENOMEM;

	sec = (char *)new->security;
	if (sec) {
		*(u32 *)(sec + 0) = sid;   /* osid */
		*(u32 *)(sec + 4) = sid;   /* sid  */
		*(u32 *)(sec + 8) = 0;     /* exec_sid */
	}

	commit_creds(new);
	return 0;
}
```

三个设计要点：

1. **必须查表**。`type value 986 != sidtab 索引`，硬编码会指向错误 context 甚至 panic。
   `security_context_to_sid` 没有 `EXPORT_SYMBOL`（已在 `services.c:1298` 核实），
   所以走 `kallsyms_lookup_name` 拿指针。
2. **必须用 `prepare_kernel_cred(NULL)` 而不是 `prepare_creds()`**。前者拿的是
   `init_cred` 的副本，`selinux_cred_prepare` 会给它分配**独立的** task_security_struct，
   改它不会污染全局；后者继承调用者（app）的 cred，带着 app 的各种标记。
3. **只改当前进程**。su 客户端自己 fork 出子进程、子进程自己写 `/dev/ktool`。
   跨进程改 cred（`root <pid>` 那条路）要处理 `get_task_struct`/`put_cred`/RCU，
   没必要。

### 5.2 su 客户端骨架

```c
/* /system/xbin/su，su_exec 标签，静态链接 */
int main(int argc, char **argv) {
    pid_t p = fork();
    if (p == 0) {
        int fd = open("/dev/ktool", O_WRONLY);
        write(fd, "ish", 3);          /* -> uid0 + init_shell */
        close(fd);
        for (int i = 3; i < 1024; i++) close(i);
        execvp(argv[1], argv + 1);
        _exit(127);
    }
    int st; waitpid(p, &st, 0);
    return WEXITSTATUS(st);
}
```

不到 30 行。加 `-c` 解析和 pty 也不会超过 300 行。

## 9. MLS 质疑的裁决：不成立，且有两条独立证据

质疑：app 跑在 `s0:c512,c768`，`/dev/ktool` 是 `s0`，`l1 eq l2` 不成立 → 写被 mlsconstrain 拒。
框架完全正确，但前提不成立。

### 证据一：`null_device` 本身就在 `mlstrustedobject` 里

```
null_device (v=377) attrs=['dev_type', 'mlstrustedobject', 'newAttr26',
                           'newAttr27', 'newAttr28', 'newAttr29', 'newAttr30',
                           'newAttr31', 'newAttr67', 'newAttr68']
mlstrustedobject 成员数 = 83
```

`mlstrustedobject` 就是 mlsconstrain 表达式里的豁免项（`t2 == mlstrustedobject`），
null_device 作为目标类型直接跳过 `l1 eq l2` 检查。

### 证据二：`binder_device` 与 `null_device` 的属性集逐项相同

```
null_device   (v=377)  attrs=[dev_type, mlstrustedobject, newAttr26..31, 67, 68]
binder_device (v=1076) attrs=[dev_type, mlstrustedobject, newAttr26..31, 67, 68]
ashmem_device (v=1309) attrs=[dev_type, mlstrustedobject, newAttr26..31, 67, 68]
```

**换标签是空操作**。三者在 AV 表里命中的规则集完全一样（都是从 `domain` / `dev_type` /
`mlstrustedobject` 展开），`untrusted_app` 对三者的 `chr_file` 权限都是
`append,getattr,ioctl,lock,open,read,write`。

### 旁证：该策略可能压根没启用 app 间 MLS 类别

```
file_contexts:1072   /data/data/.*    u:object_r:app_data_file:s0
```

标准 AOSP 4.4+ 是 `app_data_file:s0:c512,c768`。这里是裸 `s0`。
另外 `mlsfilewrite` / `mlsfileread` 两个类型在本策略里**不存在**，
说明 Samsung 编译的 mls 约束不是 AOSP 标准形态。

### 结论

`3b`（app 上下文验证）仍然值得做 10 分钟——它是端到端确认，不是推导。
但**不是阻塞风险**，也不需要换标签。

## 10. 更正：`service_manager find` 不是缺口，是我查错了 target

上一版本这里写「init_shell 只有 list 没有 find，am start 必被拒」。**这条是错的**，
和 P4.12 第 48 节同一个错法：target 选错。

原始规则（`sepolicy_rules.txt:14937`）：

```
allow domain service_manager_type:service_manager {find}
```

两道检查是分开的：

| 检查 | 规则 | target 是谁 |
|---|---|---|
| `list`（枚举所有服务） | `allow domain servicemanager:service_manager {list}` | `servicemanager`，context manager 进程的域 |
| `find`（按名字取服务） | `allow domain service_manager_type:service_manager {find}` | 服务本身的 type |

`service_manager_type` 有 **44 个成员**，含 `default_android_service`
（未单独标注的服务的默认类型，`activity` 就落在这里）、`system_server_service`、
`radio_service`、`keystore_service` 等。

`am start` 要的是 `getService("activity")` → 命中 `allow domain ... find` → **通过**。
上一版查 `init_shell → servicemanager` 看到只有 `list`，是因为 `servicemanager`
根本不是服务的 type，它是管理器自己的域。

**结论：find 全域放行。上一版给它的「架构约束」定性作废。**

## 10b. 但 `am` 是脚本这点你对了——而 phh 根本没 exec 它

`/system/bin/am` 在 5.0 上是 `#!/system/bin/sh` 脚本，file_contexts 里没有它的条目，
落在 `/system(/.*)?` 通用规则上。你的判断（app 域 exec 脚本大概率被拒）在方向上成立。

但 phh 的 `activity.c` 根本没碰这个脚本：

```c
#define AM_PATH "/system/bin/app_process", "/system/bin", "com.android.commands.am.Am"
```

它直接 `execv("/system/bin/app_process", {...})`，跳过 shebang、跳过 `/system/bin/sh`。
而：

```
/system/bin/app_process  →  zygote_exec        (file_contexts:911)
untrusted_app → zygote_exec:file  =  execute,execute_no_trans,getattr,ioctl,lock,open,read
untrusted_app → shell_exec:file   =  execute,execute_no_trans,getattr,ioctl,lock,open,read
```

`exec_type` 共 **184 个成员**（含 `shell_exec` / `zygote_exec` / `su_exec` / `install_recovery_exec`），
`allow untrusteddomain exec_type:file {execute,execute_no_trans,getattr}` 全部覆盖。

所以「方案 2：裸 binder」不需要单独做——`exec app_process` 本身就是裸 binder 启动器，
而且走的都是已允许的 exec_type。

## 10c. 撤回：`system_file` 一直存在，是解析器的别名折叠 bug（第三次）

上一版本在这里写「system_file 类型不存在，policy 与 file_contexts 不配套」。
**这条是错的**，而且是同一个 bug 的第三次复发。

### 根因

polycydb 的 type 符号表 `nprim=1343 / nel=1433`，多出来的 **90 条是 typealias**。
alias 与 primary **共享同一个 value**，而解析器写的是：

```python
types[val] = (key, prop, bounds)     # 后读到的 alias 直接覆盖 primary
```

于是 `925` 这个 value 最终留下的是最后一个 alias `dhcp_system_file`，
primary `system_file` 被盖掉 → 按名字查 `system_file` 返回 None → 误判为「类型不存在」。

这与 P4.12 §35 那次（`tname(tt)=='system_file'` 永远不匹配）是同一个错法，
当时按 value 925 绕过了，但**没有修根因**，所以第三次又踩到。

### 修复

```python
types_all.setdefault(val, []).append((key, prop))     # 保留全部名字
type_by_name[key] = val                              # 任意名字 -> value
if prev is None or ((prop & 1) and not (prev[1] & 1)):  # primary 优先
    types[val] = (key, prop, bounds)
```

### 自检结果（`src/sepolicy_selfcheck.py`，11 项全 PASS）

```
len(types)=1343  len(types_all)=1343  名字总数=1433  别名=90

  925  primary=system_file  prop=1
       aliases=['system_library_file', 'event_log_tags_file', 'dhcp_system_file']
  161  primary=su_exec
  377  primary=null_device
 1076  primary=binder_device
 1178  primary=shell
  986  primary=init_shell
```

### 矩阵重跑（走 value 925，不走名字）

```
kernel        -> system_file:file  execute,getattr,ioctl,lock,open,read
shell         -> system_file:file  execute,execute_no_trans,getattr,ioctl,lock,open,read
init_shell    -> system_file:file  execute,execute_no_trans,getattr,ioctl,lock,open,read
untrusted_app -> system_file:file  execmod,execute,execute_no_trans,getattr,ioctl,lock,open,read
system        -> system_file:file  execute,execute_no_trans,getattr,ioctl,lock,open,read
zygote        -> system_file:file  execute,execute_no_trans,getattr,ioctl,lock,open,read
```

**与 P4.12 的记录逐行一致**，没有新发现，P4.12 的结论不用重验。

### 顺带推翻一条：app 域连 `am` 脚本本身都能 exec

`untrusted_app → system_file:file` 有 `execute` **和** `execute_no_trans`。
`/system/bin/am` 落在 `/system(/.*)?` 通用规则上，标签就是 `system_file`。
所以「app 域 exec am 脚本会 EACCES」这个担心也不成立——
不只是 `app_process` 能跑，`/system/bin/am` 本身也能跑。

### 工具约束（防第四次）

任何 AV 查询的输出必须同时给出：
1. 命中的是**直接规则**还是**属性规则**；
2. 属性展开后的成员数；
3. target 的身份（域 / 服务 type / 属性），不能混。

名字只用于显示，查询一律走 value。

## 11. 「用官方 APK」——上一轮的判断错了，APK 不需要 daemon

上一轮说「APK 是 daemon 的前端，daemon 起不来 APK 就是空壳」。读完源码，这话是错的。

`db.c`（全文 105 行）说清楚 APK 的输入是什么：

```c
snprintf(query, sizeof(query),
    "select policy, until, command from uid_policy where uid=%d", ctx->from.uid);
sqlite3_open_v2(ctx->user.database_path, &db, SQLITE_OPEN_READONLY, NULL);
```

`activity.c` 说清楚 APK 怎么被唤起：

```c
#define ACTION_REQUEST "start", "-n", REQUESTOR "/" REQUESTOR_PREFIX ".RequestActivity"
#define ACTION_RESULT  "broadcast", "-n", REQUESTOR "/" REQUESTOR_PREFIX ".SuReceiver"
```

**APK 是 sqlite 的前端，不是 daemon 的前端。** daemon 只是「谁来读库、谁去 am start」
的载体。谁来做这两件事，APK 不关心。

实测参数（源码确认）：

| 项 | 值 |
|---|---|
| APK 包名（applicationId） | `me.phh.superuser`（`Superuser/packageName`） |
| 组件（类全名仍基于 manifest package） | `me.phh.superuser/com.koushikdutta.superuser.RequestActivity` |
| 数据库 | `/data/data/me.phh.superuser/databases/su.sqlite` |
| 表 / 列 | `uid_policy(uid, policy, until, command)`，policy ∈ allow/deny/interactive |
| su 版本串 | `17 me.phh.superuser` |

所以「强行用」的可行架构是：

```
su (untrusted_app 域, uid=app)
  ├─ fork 子进程: am start -n ...RequestActivity --ei uid ... --es command ...
  │    （app 域调 am 没问题，不需要 service_manager find）
  ├─ 主进程: echo ish > /dev/ktool         ← 提权到 init_shell
  ├─ 轮询 sqlite（init_shell → app_data_file:file 有 read ✅）
  └─ allow → exec；deny → 退出
```

三个未验卡点：
1. `init_shell → app_data_file:file` 有 `read,open,lock`，但 databases 目录 0700 要靠 `dac_override` 过 DAC；
2. sqlite 静态链接（NDK 有 `libsqlite3.a`，或直接用源码里的 `sqlite3/sqlite3.c`）；
3. APK 是否能在 5.0.1 装（2015 年 targetSdk，风险低）。

**代价**：+1 天（sqlite 集成 + am 协议调试 + 授权时序）。
**收益**：一个能弹窗、能记住选择的授权 UI。

判定：如果目标是「给自己这台机器用」——不值，白名单文件 2 小时。
如果目标是「能给别人装的 root」——值，但它仍依赖 1805 exploit 和 LKM 加载，
离「产品」还隔着 TIMA 记账和首启空窗两道坎。

## 12. 「S4 是单用户」的准确说法

Android 4.2+ 支持多用户：`/data/user/0`（机主）、`/data/user/10`（第二用户/访客），
每个 user 的 app 有独立 uid（`u0_a123` vs `u10_a123`）和独立数据目录。

su 必须知道「请求来自哪个 user」，才能找对授权记录。phh 用四档 `multiuser_mode`
（`owner` / `managed` / `user` / `none`），配置写在
`/data/data/me.phh.superuser/files/multiuser_mode`，路径模板是 `REQUESTOR_USER_PATH "/data/user/"`。

**S4 默认只有 user 0**（设置里没有「用户」入口），所以这套逻辑退化成「总是 0」，
不会触发分支。准确说法是「默认不触发」，不是「架构上不需要」——
一旦开了访客模式，`/data/user/10` 就会出现，那时才需要处理。

## 13. 残留风险

| 风险 | 影响 | 处置 |
|---|---|---|
| `init_shell` 无 `dac_read_search`，只有 `dac_override` | 0700 的 app 私有目录遍历可能失败 | 真机看 `ls /data/data/*/` 是否全通 |
| ish 后进程仍持有 app 的 fd 表 | 个别 fd 可能干扰 exec | su 客户端关 fd 3..1023 |
| 模块签名/TIMA 重复记账 | 反复重启可能触发 | 目前 1 次记录，warranty_bit=0；需长期观察 |
| 每次开机都要重跑 exploit（bootmode 在 BSS） | 首启 10–20 s 空窗 | 2a 里已解决；不足是 exploit 本身依赖 1805，若某次失败则无 root |
| AMS 侧对 `init_shell` 发起的 `startActivity` 可能拒绝 | APK 授权路径 | caller 没有 package identity；优先用 fork 保留原域身份 |

### 已划掉（曾经列为风险，实测/复核后不成立）

| 曾经的判断 | 为什么不成立 |
|---|---|
| MLS 约束拦 app 写 `/dev/ktool` | `null_device` ∈ `mlstrustedobject`（83 成员），约束豁免；且 `binder_device` 属性集与之逐项相同 |
| `service_manager find` 缺口 | `allow domain service_manager_type:service_manager {find}` 全域放行；`activity` → `default_android_service` |
| app 域 exec `am` 脚本被拒 | `untrusted_app → system_file:file` 有 `execute` + `execute_no_trans`（950 重修解析器后实测） |
| `system_file` 类型不存在 | 解析器别名折叠 bug，`925 = system_file` + 3 个别名 |
