## 2. 静态判据：kernel.raw 已含 FOLL_COW

`follow_page`（`0xc00dee8c`）反汇编：

```
c00def1c  ands  r2, r4, #1          ; flags & FOLL_WRITE
c00def24  beq   0xc00def8c          ; 不是 WRITE → 跳过
c00def28  tst   r7, #0x80           ; pte & L_PTE_RDONLY (0x80)
c00def2c  beq   0xc00def8c          ; 可写 → 跳过（can_follow_write_pte 返回 true）
c00def30  movw  r3, #0x4010         ; FOLL_FORCE(0x10) | FOLL_COW(0x4000)
c00def34  and   r3, r4, r3
c00def38  movw  r1, #0x4010
c00def3c  cmp   r3, r1
c00def40  beq   0xc00df05c          ; 两标志都置 → 进入 COW 检查
...
c00df05c  cmp   r0, #0              ; page 非空？
c00df064  ldr   r3, [r0, #4]        ; page->flags
c00df068  tst   r3, #1              ; PG_dirty
c00df06c  bne   0xc00def94          ; 不 dirty → 拒绝
```

三个条件（`pte_write` → `FOLL_FORCE|FOLL_COW` → `PageDirty`）齐全，
与上游 4.8 修复 `can_follow_write_pte()` 的语义一致。

`__get_user_pages` 里还有 `c00dff50 orreq r4, r4, #0x4000`，
即 `faultin_page` 中 `if (ret & VM_FAULT_WRITE) *fault_flags |= FOLL_COW;`。

**静态结论：dirtycow 修复已 backport。**

## 3. 行为级判据：金丝雀实测

`src/dirtycow_canary.c`：

- 目标 `/system/etc/security/otacerts.zip`（1898 字节，只读，日常不读，OTA 才用）
- `mmap(PROT_READ, MAP_PRIVATE)`
- 线程 1 反复 `madvise(MADV_DONTNEED)`
- 线程 2 反复 `pwrite(/proc/self/mem, marker, 1, map+offset)`
- 跑 10 秒后重新 `open + pread` 验证 page cache

结果：

```
mapped at 0xb6fd9000 (PROT_READ | MAP_PRIVATE)
offset=1897 orig=00 marker=ff

writes=573980  errors=0
readback: orig=00 now=00

*** FAILED: page cache 未变 —— 内核已包含 CVE-2016-5195 修复 ***
```

**57 万次写入全部返回成功（`errors=0`），但 page cache 一个字节都没变。**

这正是修复后的正确行为：
- `pwrite(/proc/self/mem)` 走 `FOLL_FORCE|FOLL_WRITE`
- `can_follow_write_pte` 因 `pte` 只读且 `PageDirty` 不满足而返回 false
- 内核分配 COW 私有副本，写入落在副本上
- **不污染 page cache**

如果未修，`pwrite` 会直接改 page cache，`readback` 会读到 `ff`。

## 4. 结论

**CVE-2016-5195 在本机不可利用。** 两层判据一致，但**权重不同**：

| 判据 | 权重 | 说明 |
|---|---|---|
| 静态（`follow_page` 反汇编三条件齐全 + `__get_user_pages` 的 FOLL_COW 置位） | **决定性** | 证明的是“代码路径被改了”——内核映像里存在 `can_follow_write_pte` 语义 |
| 行为（57 万次写、page cache 不变） | 辅证 | 见下方表述修正 |

**行为判据的正确表述**：`writes=573980 errors=0` 不是“利用没打中”——修复后 `pwrite(/proc/self/mem)` 走 `handle_mm_fault(FAULT_FLAG_WRITE)` → COW 副本，**写入本来就该成功**，只是落在私有页上。准确说法是：**每次写都被内核合规地导向 COW 副本，page cache 零污染**。这与“没打中”对内行是“证明修好了”和“证明没打中”的区别。

**对「SPL 2015-11 ⇒ 2016 年后 CVE 都没修」这一推断的修正**：
Samsung 在 2017-04 构建 I9500ZSSHQD1 时 backport 了 2016-10 的 dirtycow 修复，
但 `ro.build.version.security_patch` 仍标 2015-11-01。

**不是“SPL 撒了谎”，是“SPL 无信息”。** 同一台设备、同一个字符串，两个方向都错：

| CVE | 公开时间 | SPL=2015-11 的推断 | 实测 |
|---|---|---|---|
| CVE-2015-1805 | 2015-02 | 应该已修 | **未修**（SPL 高估） |
| CVE-2016-5195 | 2016-10 | 应该未修 | **已修**（SPL 低估） |

结论要比“这次推错了”狠一档：**这个字段在本项目里不该出现在任何推理链里**——写成“撒谎”会让人以为 SPL 是下界（实际只会更多），下次继续拿它推断；正确定性是**任何方向都不能推，只能逐条实测**。
