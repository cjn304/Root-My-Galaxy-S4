# P4.92 内存改策略：te_avtab 手术，让任意 app 在 0 permissive 下弹窗

日期：2026-10-24 ~ 10-25
对象：`kmod/ktool_mod.c`（新增 avtab 手术）、`avtab_query.py`、`avtab_walk.py`
结论：**成立并已在真机闭环**——冷启动后 permissive=0，Amaze 弹出授权框、允许后拿到 root 并列出 `/data/data`。

---

## 一、为什么要走这条路

`su`（fork 版）在 0 permissive 下有两处跨域，只能靠 permissive 放行：

| 位置 | 操作 | 审计证据 |
|---|---|---|
| 父进程（已 `ish` 成 init_shell） | 写 fork 前（untrusted_app）创建的管道 | `avc: denied { use } ... tclass=fd` |
| 子进程（untrusted_app） | 在 `shell_data_file` 目录里 `bind` socket | `avc: denied { create } ... tclass=sock_file` |

常规解法是 `supolicy --live` / `magiskpolicy --live`（SuperSU/Magisk 都这么干），
但本机 `security_load_policy` 被 Samsung 挂钩：写 `/sys/fs/selinux/load` 会触发
TIMA 对内核做完整性度量，度量失败 → trustlet 返回 -1 → `write` 永不返回
（P4.89 实测进程卡 D 状态，SIGKILL 无效）。**所以只能改内存里的策略表。**

改的是 `policydb.te_avtab`——判定路径 `context_struct_compute_av()` 每次都会查它，
只要节点在、哈希对，就等于多了一条规则。不经过 `load_policy`，不触发 TIMA。

## 二、结构布局与验证（先证明，再动手）

`security/selinux/ss/avtab.h`（32 位 ARM）：

```c
struct avtab_key  { u16 source_type, target_type, target_class, specified; };  // 8B
struct avtab_datum{ u32 data; };                                              // 4B
struct avtab_node { key; datum; struct avtab_node *next; };                   // 16B
struct avtab      { node **htable; u32 nel, nslot; u16 mask; };               // 16B
```

哈希：`(target_class + (target_type << 2) + (source_type << 9)) & mask`

`policydb` 布局按头文件顺序累加，`te_avtab` 落在 **+0x74**。三条独立事实互证：

1. `policydb+0x20` = **1343**（types）、`+0x10` = **86**（classes）——
   与 `sepolicy_parse.py` 解出的数量一致；
2. `te_avtab.nel` = **16072**，正好等于解析器统计的 allow/audit/transition 条目总数；
   `nslot` = 2048、`mask` = 0x7ff（2 的幂 - 1）；
3. 按内核哈希算 `(986,188,7)` → slot 1783，走桶链第 8 个节点：

```
[ 8] 0xcf97fc80  986 -> 188 cls= 7 spec=0x0001 allowed=0x00100020   <<< MATCH
```

`0x00100020` = dir 的 `search(1<<20) | setattr(1<<5)`，与解析器算出的
`init_shell -> app_data_file:dir {search,setattr}` **完全一致**。

工具：`avtab_query.py`（从 `sepolicy` 取 type/class/权限位）、
`avtab_walk.py`（按哈希走桶链核对节点）。

## 三、实现（`kmod/ktool_mod.c`）

新增两条命令，都只对 uid0 开放（门禁白名单里加 `avrule`）：

```
echo "avruleq <src> <tgt> <cls>"        > /dev/ktool   # 只查
echo "avrule  <src> <tgt> <cls> <mask>" > /dev/ktool   # OR 进已有节点 / 有序插入新节点
```

要点：

- **运行时自检**：`htable` 必须是内核指针、`nslot` 必须是 2 的幂、`mask == nslot-1`、
  `nel ∈ [1000, 300000]`；任一不满足就拒绝动手（宁可不改，也不能写错地方）。
- **必须有序插入**：`avtab_search_node()` 有 early-break（`src < cur->src` 就停），
  乱插会导致"插进去了但永远查不到"。所以按 `(src,tgt,cls)` 升序定位插入点。
- **无锁安全性**：判定路径只读；插入是"节点填满 → `smp_wmb()` → 一次 store 发布指针"，
  读者要么看到旧链、要么看到完整新节点；本机策略不会重载，不存在并发删除。
- **幂等**：同 key 已存在就 `datum.data |= mask`，重复加载不会重复插节点。
- **开机自动应用**：`ktool_init()` 里调 `p4k_apply_su_rules()`，先用
  `types==1343 && classes==86` 做闸门，换 ROM 后形状变了就只告警、不加规则
  （仍可用 `avrule` 手工加，type 值也可用 `av_app_type` 等模块参数覆盖）。

### 实际加的 4 条

| src | tgt | class | mask | 含义 |
|---|---|---|---|---|
| 986 init_shell | 809 untrusted_app | 8 fd | `0x1` | `use`：父进程用 fork 前的管道（含调用者 stdout） |
| 809 untrusted_app | 986 init_shell | 2 process | `0x4` | `sigchld`：子进程退出通知父进程 |
| 809 untrusted_app | 200 shell_data_file | 12 sock_file | `0x42c` | `create,write,setattr,unlink`（收窄后，见 §八） |
| 809 untrusted_app | 200 shell_data_file | 7 dir | `0x160004` | `write,add_name,remove_name,search` |

## 四、真机验证

### 4.1 热态（手工插入）

```
avrule 986 809 8 1        → OR/ADD
avrule 809 986 2 4        → ADD
avrule 809 200 12 43e     → ADD
avrule 809 200 7 160004   → OR 0x500013 -> 0x560017

avruleq 986->809:8   spec=0x1 allowed=0x1
avruleq 809->986:2   spec=0x1 allowed=0x4
avruleq 809->200:12  spec=0x1 allowed=0x43e   ← 当时是宽松值，收窄后为 0x42c
avruleq 809->200:7   spec=0x1 allowed=0x560017
```

清空白名单（`/data/system/su_allow` 为空）、permissive=0，然后启动 Amaze：
**授权弹窗出现**（截图：`src/w1.png`，标题「超级用户请求 / "Amaze"正在请求超级用户访问权限」）。
点「允许」后弹窗消失，随后 **Amaze 又发起第二次 su 请求**（说明它真的在执行 root 命令），
再点「永久记住 + 允许」，Amaze 顺利列出 `/data/data`。

期间审计里**没有** `fd use`、**没有** `sock_file create` —— 两处跨域都通了。

### 4.2 冷启动

新模块装进 `/system/lib/modules/ktool_mod.ko` 后重启：

```
[19.003] ktool: avrule 986->809:8   ADD 0x1   node=... slot=... nel=16073
[19.003] ktool: avrule 809->986:2   ADD 0x4   node=... slot=362 nel=16074
[19.031] ktool: avrule 809->200:12  ADD 0x43e node=... slot=1324 nel=16075   ← 收窄后为 0x42c
[19.058] ktool: avrule 809->200:7   OR 0x500013 -> 0x560017
[19.058] ktool: avrule: su 4 rules applied (app=809 ish=986 shd=200)
```

重启后 `permissive_map = 00000000 00000000`、`getenforce = Enforcing`，
`avruleq` 仍能查到；Amaze 点根目录图标直接列出 `/data/data`（`drwxr-x--x` 各 app 目录）。
——**规则随模块加载自动重建，重启不丢**。

## 五、安全性

四条规则都只对 `init_shell` / `untrusted_app` 这两个域开口，**不是 permissive**。
策略里现有 15157 条 allow，`untrusted_app` 直接规则 82 条；把 untrusted_app 标 permissive
等于让这 1343 个 type × 86 个 class 的所有检查全部放行，而我们只加了 **4 个三元组、12 个权限位**。

- `init_shell → untrusted_app:fd use`：**不授予任何文件访问**。源码里
  `file_has_perm()` 是"先查 fd use，再查 inode"：

  ```c
  if (sid != fsec->sid) {                       // 只在跨域时查
          rc = avc_has_perm(sid, fsec->sid, SECCLASS_FD, FD__USE, &ad);
          if (rc) goto out;                     // 拒了就结束
  }
  if (av) rc = inode_has_perm(cred, inode, av, &ad, 0);   // 文件权限照查不误
  ```

  所以它只取消"能不能用别人域的 fd"这道前置门，真正读写仍要过 inode 那一关
  （`app_data_file` / `shell_data_file` 各自的规则）。
  旁证：本机策略里本来就有 `allow system_server init_shell:fd {use}`（3520 行），
  这是域间 IPC 的常规写法，不是特权提升。
- `untrusted_app → init_shell:process sigchld`：`signal_to_av()` 里 **SIGCHLD 单独一个
  permission**，和 `sigkill`/`signal` 互不包含。作用只是子进程退出时内核给父进程送
  SIGCHLD 的检查——**不加也能跑**（`waitpid` 靠僵尸态返回，不依赖信号投递），
  加它是为了消掉每次 su 都刷一条审计。
- `untrusted_app → shell_data_file:{sock_file,dir}`：放宽的是 `/data/local/tmp` 的
  SELinux 技术限制，**DAC 仍是第二把锁**（实测）：

  | 路径 | 模式/属主 | app（other）能不能写 |
  |---|---|---|
  | `/data/local/tmp` | `drwxrwx--x shell:shell` | 否（other 只有 `--x`，只能穿行） |
  | `/data/local/tmp/sud` | `drwxrwxrwx shell:shell` | **能**（本来就是 0777，su 专用） |
  | `/data/data/com.android.shell` | shell 应用私有 | 否 |

  `shell_data_file` 只覆盖这两个路径（`/file_contexts` 里就两条）。
  **诚实说明**：SELinux 这一层是对整个 `shell_data_file` 类型放开的，真正挡住 app 的是
  `/data/local/tmp` 的 0771。如果哪天把它 chmod 成 0777，app 就能在里面建文件了——
  这是真实的、有限的纵深防御下降，不是零成本。
- 相比"把 untrusted_app 标成 permissive"（全机 app 免疫 SELinux，且 su 又把 caps 顶满，
  等于任意 app 一授权就是不受限 root），这个方案窄得多。

## 六、残留噪声（不影响功能）

| 审计 | 来源 | 影响 |
|---|---|---|
| `init_shell → app_data_file:file { setattr } name=su.sqlite-journal` | `db_check()` 以只读打开 su.sqlite，SQLite 发现残留的 hot journal 想清理（chmod/utimes/truncate 一族，审计只记 `{setattr}`） | 被拒 → `db_check` 当作"无记录" → 走弹窗。属**瞬时**：本次 boot 的 audit.log 里 app_data_file 相关拒绝为 **0** |
| `system_server → init_shell:process { sigkill }` | AMS 杀 app 时按**进程组**发 `kill(-pgid, SIGKILL)`，su 是 app fork 出来的、继承了同一个 pgid，于是连坐 | 拒绝后 su 逃过 AMS 的 kill，把当前命令跑完（或 90s alarm）自己退。**不是本次改动引入的**：策略里 `system_server → init_shell` 只有 `fd {use}`(3520) 和 `binder {call,transfer}`(3819)，从来没有 `process sigkill` |

两条都只是"想做的事被拒"，不是"多出来的权限"。sigkill 那条如果一定要消掉，
可以再加 `allow system_server init_shell:process sigkill`——但那是让 AMS 有权杀 root 进程，
收益（日志干净）不值这个代价，所以没加。

另：`SecurityLogAgent` 被重新启用后，会在锁屏弹一条「安全声明：检测到未经授权的动作」。
它是通知，不是复位；如果要安静，把该 app 再禁用即可。

## 七、与之前结论的关系

- P4.89「唯一可用的 AVC 复位通路是模块 avcflush」——仍然成立，本条没有改它。
- P4.88 §六「完全干净 == 重启」早已被 P4.89 推翻，本条不影响。
- 「0 permissive + 弹窗」以前靠 AVC 缓存残留（P4.89 三步实验），现在靠**显式规则**，
  不再依赖缓存，重启后依旧成立。
- `su` 的代码**没有改**；白名单机制仍然可用（`/data/system/su_allow`），
  只是不再是弹窗的前提。

## 八、收窄 sock_file 权限（两次误判的过程）

目标：把 `sock_file` 从 `0x43e`（create/read/write/getattr/setattr/unlink）收到最小集。
结论：**最小集是 `0x42c` = create(0x8) | write(0x4) | setattr(0x20) | unlink(0x400)**，
中间踩了两次，都是"少一位就整条链路断"，而且断法完全不同：

| 试的值 | 少了什么 | 现象 | 审计证据 |
|---|---|---|---|
| `0x418` | 漏 **setattr** | 弹窗**闪两下就退** | `denied { setattr } ... name="s9xxx" scontext=u:r:untrusted_app:s0` —— `chmod(sock,0777)` 被拒，socket 停在 0600，另一个 uid 的 APK 连不上 |
| `0x428` | 漏 **write** | 同样闪一下就走 | `denied { write } ... tclass=sock_file`，紧跟 `syscall=283`（= connect） |

第二条是关键教训：**Unix socket 的 `connect()` 在 SELinux 里查的是 `sock_file:write`**，
不是 `unix_stream_socket:connectto`（后者是 socket 对象那一层，域内自连本来就有）。
所以 `write` 不能删。`read` / `getattr` 才是真正多余的两位。

### 验证

1. 运行态 `avrule 809 200 12 4`（OR 进 write）→ `0x428 → 0x42c`，`ktool flush -y`；
2. 触发 Amaze：**弹窗稳定出现**（`src/z3.png`），点允许后 Amaze 列出 `/data/data` 296 项（`src/z6.png`）；
3. 把 `0x42c` 固化进 `p4k_apply_su_rules()`，重装模块并重启：
   `ADD 0x42c node=... slot=1324 nel=16075`，`avruleq 809->200:12 allowed=0x42c`。

### 顺带加的开关

```c
static int p4k_avrule_enable = 1;
module_param_named(avrule_enable, p4k_avrule_enable, int, 0444);
```

`insmod ... avrule_enable=0` 就完全不改策略（弹窗链路会退回 permissive 依赖态，
但至少出问题时有"一键不加载规则"的退路，不用重编）。

## 九、phh 那四个「超级用户访问权限」选项，对我们无效

现象：设置里有 禁用 / 仅限于应用程序 / 仅限于 ADB / 应用程序和 ADB 四档。

### 它存在哪、谁读它

- 存储：`su.sqlite` 的 `settings (key TEXT PRIMARY KEY, value TEXT)` 表
  （APK dex 里的建表语句就是这个），键 `superuser_access`，
  值为 `access_disabled` / `apps_only` / `adb_only` / `apps_and_adb`。
- 读取者：phh **原版** su 会在判定前读这张表；**我们的 su 只读 `uid_policy`**
  （`src/su_fork.c:77`），从不读 `settings`。

### 行为验证（决定性）

把设置改成 **禁用**、并把授权列表里的 Amaze 撤消干净，然后触发 Amaze 访问 `/data`：

```
设置 = 禁用  →  授权弹窗照样弹出（src/y2.png），点允许照样拿到 root
```

所以这四档对**当时的** su 是纯粹装饰：不拦弹窗、不拦授权、不影响任何判定。
（**已改造**：su 现在会读这张表并按档位判定，见 §十。）

### ADB 那一档更早就没入口

`shell` 域执行 `/system/xbin/su` 被 policy 拒绝（dontaudit：

```
/system/bin/sh: su: can't execute: Permission denied
```

），所以「仅限于 ADB」连调用都到不了，谈不上生效。

### 真正控制我们这套的两个开关

| 开关 | 位置 | 作用 |
|---|---|---|
| 白名单 | `/data/system/su_allow`（一行一个 uid） | 命中就**不问**直接放行；清空 = 每次问 |
| 记住选择 | `su.sqlite` 的 `uid_policy`（policy/until/command） | 弹窗里"记住选择"写进去的；"撤消超级用户权限"删的就是它 |

要"彻底不给 root"：清空 `su_allow` + 在 phh 里把所有已授权 app 撤消
（或者 `insmod ... avrule_enable=0` 让弹窗链路直接不通）。

## 十、让那四档真正生效（su 侧实现，2026-10-25）

### 10.1 语义

| 设置值 | 应用（uid ≠ 2000） | ADB（uid = 2000） |
|---|---|---|
| `access_disabled` | 拒 | 拒 |
| `apps_only` | 允许 | 拒 |
| `adb_only` | 拒 | 允许 |
| `apps_and_adb`（默认/读不到） | 允许 | 允许 |

root（uid 0）在 `main()` 里就跳过整段，不受这四档影响。
`su -v` 也在判定之前返回——所以设成"禁用"不会让 phh 的开机自检报"binary outdated"。

### 10.2 实现要点

- 新增 `db_setting()`：`select value from settings where key=?`，读 `superuser_access`。
- 新增 `access_allows(caller)`：`caller == 2000` 走 adb 位，其他走 apps 位。
- **判定必须放在 `ish` 之后**：`settings` 表在 APK 的私有目录里，
  以 app 身份读不到（DAC 是 660 别人的文件，SELinux 那层也没有跨 app 读），
  `init_shell` 才读得到。代价是"禁用"时进程仍会先提权到 root 再退出——不执行任何命令。
- 新增覆盖开关 `/data/local/tmp/su_access_mode`（整行一个值）：
  存在就优先于 APK 的设置。`/data/local/tmp` 是 `shell:shell 0771`，
  只有 adb shell / root 建得出来，app 建不了，所以不能用来提权。
  用途：不点屏幕就能切换和验证，APK 挂了也能控制。

### 10.3 实测矩阵

应用侧（Amaze，临时 trace 输出）：

```
access_disabled  → P2 mode=access_disabled allow=0   （此后无 P3/P4，直接退出）
apps_only        → P2 mode=apps_only       allow=1   → P3 whitelist=0 → P4 db=1 → 放行
adb_only         → P2 mode=adb_only        allow=0
apps_and_adb     → P2 mode=apps_and_adb    allow=1   → P4 db=1 → 放行
```

ADB 侧（`adb shell su -c ...`，以"授权界面是否出现"为信号）：

| 模式 | 弹窗 |
|---|---|
| access_disabled | 无 |
| apps_only | 无 |
| adb_only | **有** |
| apps_and_adb | **有** |

### 10.4 ADB 侧要额外三条策略（否则连 exec 都过不去）

| 规则 | 值 | 作用 |
|---|---|---|
| `shell → su_exec:file` | `0x22000` = execute + execute_no_trans | `shell` 域原本**不允许执行 su**（dontaudit，连审计都没有） |
| `init_shell → shell:fd use` | `0x1` | 父进程 ish 后要用 fork 前的管道（否则 socket not ready） |
| `shell → shell_data_file:sock_file` | `0x42c` | 子进程在 `sud` 里 bind socket |

**找 exec 最小集时踩的坑**：第一次写 `0x120012`，看着像
`execute|execute_no_trans|open|read|getattr`，实际算错了——`0x120012` 里
**没有 `execute`（0x2000）**，正确组合是 `0x122012`。因为 `dontaudit` 把拒绝
全盖住了，只能靠二分：最后确定只要有 **execute + execute_no_trans（0x22000）** 就够，
`open`/`read`/`getattr` 都不需要。

代价说明：这三条等于**让 adb shell 也能调起 su 的授权弹窗**（等价于"ADB root 可选"）。
不想要就在 `p4k_apply_su_rules()` 里删掉这一段，四档里的 adb 两档就只会拒。

### 10.5 现状

- `/system/xbin/su` = 753912 B，含四档判定；旧版备份 `/data/local/tmp/su_prev.bak`。
- 模块 152724 B，开机自动应用 **7 条**规则（4 条应用 + 3 条 ADB），
  `nel` 16072 → 16078；permissive=0 时全部可用。
- 覆盖文件已删除，当前由 APK 的 `settings` 表控制。

## 十一、四档真正生效（定位到 `persist.sys.root_access`）

### 11.1 之前为什么不生效（三个误判，按发现顺序）

| # | 误判 | 事实 |
|---|---|---|
| 1 | 以为设置在 `su.sqlite` 的 `settings` 表 | `su.sqlite` **没有** `settings` 表（只有 `android_metadata` / `uid_policy`） |
| 2 | 以为 `superuser.sqlite.settings` 是落点 | 该表存在但**长期 0 行**；我们手写一行进去，UI 仍显示旧值 → 不是它 |
| 3 | 以为设置只在内存里 | 反编译 `Settings.getSuperuserAccess()`：`SystemProperties.get("persist.sys.root_access")`，默认 3 |

真值与语义（Koush 原版）：

```
persist.sys.root_access = 0  禁用
                          1  仅限于应用程序
                          2  仅限于 ADB
                          3  应用程序和 ADB（默认）
```

设备实测该属性当前就是 `0`，与用户 UI 里选的「禁用」一致——**UI 的写入是成功的**，只是我们的 su 从来没读过它。

### 11.2 App 改档位的方式（决定了 su 必须留一条缝）

`Settings.setSuperuserAccess(int)` 反汇编：

```java
if (Process.myUid() == 1000) { SystemProperties.set(...); return; }
...
Runtime.getRuntime().exec("su")            // 不带参数！
    .getOutputStream().write("setprop persist.sys.root_access N".getBytes());
```

也就是说：**App 用 `su` 的 stdin 来 setprop**。因此 su 在"禁用"档下如果把无参调用一律拒掉，
用户就永远改不回来（死锁）。su 必须：
1. 识别 `caller == 管理App uid(10198)` 且**无参数**的调用；
2. 读 stdin 第一行，只有 `setprop persist.sys.root_access 0..3` 才执行；
3. 其它应用没有这条缝（uid 校验）。

### 11.3 属性写不进去的原因：property_service 的用户态 AVC

`shell` 域（`ktool root` 的上下文）执行 `setprop` 一直 `rc=0` 但值不变，审计：

```
avc: denied { set } for property=persist.sys.root_access scontext=u:r:shell:s0
     tcontext=u:object_r:system_prop:s0 tclass=property_service
```

关键点：**即使全量 permissive + flush 也不生效**，因为 property_service（init 进程）用的是
**用户态 AVC**，那条 deny 在很早以前就被缓存进 init 自己的哈希表，改 `permissive_map`
不会让它重算。

但 `init_shell` 是**全新条目**：加上

```
allow init_shell system_prop:property_service { set }
```

之后，`init_shell` 域 setprop **立刻成功**（`rc=0`，`getprop` 立刻变 3）。
数值：`init_shell=986`、`system_prop=342`、`property_service=84`、`set=bit1=0x1`。

这条已固化进模块的 `p4k_apply_su_rules()`（开机第 8 条规则）：

```
avrule 986->342:84 OR 0x1  (node ...)   ← 先 OR，说明 ROM 里本来就有部分位
```

### 11.4 su 侧实现

`read_access_mode()` 的取值顺序（前者优先）：

1. `/data/local/tmp/su_access_mode`（调试覆盖，只有 adb/root 建得出来）
2. **`/data/property/persist.sys.root_access`（正式来源）**
3. `superuser.sqlite.settings`（历史兼容）
4. 默认 `apps_and_adb`

`access_allows(caller)`：`0` 全拒 / `1` 只放非 2000 / `2` 只放 2000 / `3` 全放。

管理 App 的改档通道（`caller==10198 && argc<2`）在读 stdin 后**直接 exec**
（先 `close(p2c[1]) / waitpid` 让 socket 子进程立刻退出，避免残留 90s）：

```c
if (fgets(line, ...) && sscanf(line, "setprop persist.sys.root_access %d", &v) == 1
    && v >= 0 && v <= 3)
        execl(SHELL, "sh", "-c", line, NULL);
```

### 11.5 实测

| 状态 | 结果 |
|---|---|
| `prop=0`（禁用） | Amaze 拉根 → `RequestActivity=0`，dmesg 里 `gate ALLOW` + `ish uid0`（su 跑了，是它自己拒的） |
| 覆盖文件 `apps_and_adb` | 同一个 Amaze → `RequestActivity=13`，弹窗正常 |
| 冷启动后 `init_shell setprop 3` | `rc=0`，`getprop` = 3 → 规则在开机后依然有效 |
| `prop=3` 时 Amaze | 弹窗出现 |

### 11.6 现在怎么用

- 在 phh Superuser 里改「超级用户访问权限」→ su 立即按新档位判定，**不需要重启**；
- 改档位这条通道只认管理 App 的 uid（10198），别的应用拿不到 root shell；
- `adb_only` / `apps_only` 靠 `caller == 2000` 区分（adb shell 的 uid）；
- 覆盖文件 `/data/local/tmp/su_access_mode` 仍在，用于不点屏幕验证：

```sh
adb shell 'echo access_disabled > /data/local/tmp/su_access_mode'
adb shell 'rm -f /data/local/tmp/su_access_mode'      # 回到属性
```

### 11.7 补一条端到端验证（stdin 通道）

管理 App 的调用没法直接从 adb 模拟（uid 必须等于 10198），所以用一个测试构建
把 `SU_PKG_UID` 临时改成 2000，从 adb shell 走同一条代码路径：

```
$ echo 'setprop persist.sys.root_access 3' | su
rc=0                                   ← 命中 setprop 行，exec 成功
$ getprop persist.sys.root_access
3                                      ← 属性真的落了

$ (再触发 Amaze)  RequestActivity=13   ← 3 档放行、弹窗正常

$ echo 'setprop persist.sys.root_access 0' | su
rc=0 ; prop=0                          ← 同一通道改回禁用
```

换回生产构建（`SU_PKG_UID=10198`）后再试同一个管道：

```
$ echo 'setprop persist.sys.root_access 3' | su
su: access_disabled, deny uid 2000
rc=1                                   ← 缝只对管理 App 开，其它 uid 一样被拒
```

最终状态：`prop=0`（禁用）、Enforcing、`/system/xbin/su` 为生产版、
`su_path=/system/xbin/su`、无 `/data/local/tmp/su_access_mode` 覆盖文件。

## 十二、管理 App 的 uid 不写死 + ADB 档两处修复

### 12.1 10198 就是 `me.phh.superuser`

```
$ dumpsys package me.phh.superuser | grep userId
    userId=10198 gids=[]          ← u0_a198
    codePath=/data/app/me.phh.superuser-1

$ dumpsys package com.amaze.filemanager | grep userId
    userId=10199 gids=[...]       ← u0_a199，Amaze
```

### 12.2 改成运行时解析（重装会换 uid）

`u0_aXXX` 是安装时分配的，卸载重装可能变号；写死 10198 会让"改档位"的缝失效，
而它一旦失效、档位又刚好在"禁用"，UI 就再也改不回来了。所以：

```c
static int su_pkg_uid(void)
{
    /* stat 它的数据目录，取 st_uid；两个包名都试（phh 版 / Koush 版） */
    static const char *dirs[] = {
        "/data/data/me.phh.superuser",
        "/data/data/com.koushikdutta.superuser"
    };
    ...
    return SU_PKG_UID;      /* 兜底 10198 */
}
```

su 此时已经在 `init_shell`，读 app 目录没问题（§11 已验）。

拒绝信息也带上解析结果，便于现场核对：

```
$ echo access_disabled > /data/local/tmp/su_access_mode
$ su -c 'id'
su: access_disabled, deny uid 2000 (admin 10198)     ← admin 是 stat 出来的
```

### 12.3 ADB 档原来根本不能用（两处）

**① 协议把 ADB 请求标成了 `app`**

`child_sock()` 里 `from.name` 固定写 `"app"`，APK 按它区分来源。改成：

```c
write_frame(cfd, "from.name", caller == AID_SHELL ? "adb" : "app");
```

**② `adb_only` 档还去问 APK，APK 秒回 DENY**

实测（`prop=2`）：

```
$ su -c 'id'
Starting: Intent { cmp=.../RequestActivity ... }     ← 弹窗起了
su: denied (uid 2000, DENY)                          ← 但立刻被拒
```

「仅限于 ADB」的语义本来就是"ADB 可以、应用不行"，不该再问 APK。现在 uid=2000
在 `adb_only` 档直接放行（跳过白名单/弹窗）：

```
$ su -c 'id'
uid=0(root) gid=0(root) context=u:r:init_shell:s0
```

### 12.4 终态

| 项 | 值 |
|---|---|
| `persist.sys.root_access` | **2**（仅限于 ADB） |
| adb `su -c id` | `uid=0` / `init_shell`，无弹窗 |
| 应用（Amaze） | 被拒（不弹窗） |
| 覆盖文件 | 已删除，按属性判定 |
| `/system/xbin/su` | 753920 B（含 uid 动态解析、from.name=adb、adb_only 直通） |
