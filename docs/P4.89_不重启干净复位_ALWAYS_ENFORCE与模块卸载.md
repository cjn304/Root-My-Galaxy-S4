# P4.89 不重启的干净复位：ALWAYS_ENFORCE 真相与模块可卸载

日期：2026-10-24 19:30
对象：`src/ktool.c`、`kmod/ktool_mod.c`、`/system/bin/ktool`、`/system/lib/modules/ktool_mod.ko`

---

## 一、结论先行

| 问题 | 结论 |
|---|---|
| 前几轮“装不进 /system”的解释对不对？ | **方向对，根因说错**。不是“AVC 陈旧条目”，而是设备内核 `CONFIG_ALWAYS_ENFORCE=true`：全局 `selinux_enforcing` 对权限判定**完全无效** |
| `setenforce 0` 有用吗？ | **零效果**。`getenforce` 会显示 Permissive，那只是显示位；权限判定读不到它 |
| 不重启能干净复位吗？ | **能**，含模块卸载。内核状态可 100% 复位 |
| 什么消不掉？ | **审计/日志痕迹**（`audit.log`、`/data/log/avc_msg_recovery.log`）。记录本身不可逆 |
| 模块能卸吗？ | **能**，但要先 `pwn` + `flush`（SELinux 拒绝 `capability:sys_module`） |

**P4.88 §六 的“完全干净 == 重启”是错的，已在本轮推翻。**

## 二、根因：CONFIG_ALWAYS_ENFORCE

### 三条独立证据

**① 内核自己打的审计记录**

```
type=1404 audit(...:12): config_always_enforce - true; enforcing=1 old_enforcing=1
```

字符串来自 `security/selinux/selinuxfs.c:174`，位于 `#ifdef CONFIG_ALWAYS_ENFORCE` 分支内：

```c
#ifdef CONFIG_ALWAYS_ENFORCE
	// If build is user build and enforce option is set, selinux is always enforcing
	new_value = 1;                        // 写什么都强制改回 1
	length = task_has_security(current, SECURITY__SETENFORCE);
	audit_log(..., "config_always_enforce - true; enforcing=%d old_enforcing=%d ...");
	selinux_enforcing = new_value;
	avc_ss_reset(0);
```

**② `avc.c:772` 同一宏下不读 `selinux_enforcing`**

```c
#ifdef CONFIG_ALWAYS_ENFORCE
	if (!(avd->flags & AVD_FLAGS_PERMISSIVE))
#else
	if (selinux_enforcing && !(avd->flags & AVD_FLAGS_PERMISSIVE))
#endif
		return -EACCES;
```

**③ 实测**：`w32 0xc0c4d490 0`（`dump` 回读 =0，`getenforce` 显示 Permissive）后，
root remount 仍 `exit=-13`，并产生新的 avc 记录（audit serial 281）。

### 重要修正：源码树是对的，`.config` 是错的

`/d/XboxGames/kernel_i9500` **是同一套代码**（ALWAYS_ENFORCE 分支与审计字符串都在），
只是本地 `.config` 没开这个宏（`grep -c CONFIG_ALWAYS_ENFORCE .config` = 0）。

> 教训：可以用这棵树读代码逻辑，**但不能用它的 `.config` 推断设备行为**。

### 推论：唯一有效通路

`permissive_map`（按域 permissive）→ 该标志在 `security_compute_av()` 里按
`policydb.permissive_map` **在 AVC 条目计算时烤进 `avd->flags`** →
所以改完 map 必须 `flush`，让条目按新 map 重算。

## 三、受控实验（/system remount，每步同 shell 内先校验 `uid=0`）

`/data/local/tmp/ktool root sh -c 'mount -o rw,remount /system'`：

| # | 前置状态 | 结果 |
|---|---|---|
| E0 | Enforcing，map=0，缓存有 denied | 失败 `rc=255`（audit：`filesystem:remount`，`tcontext=labeledfs`，`exit=-13`） |
| E2 | **全局 enforcing=0**（`getenforce`=Permissive） | **失败 `rc=255`**，新增 audiv serial 281 |
| E3 | `pwn`（map=1）+ `flush` | **成功 `rc=0`** |
| E4 | `enforce --noflush`（map=0，缓存保留） | **仍成功 `ro_rc=0`** ← 缓存里的授权压过当前 map |
| E5 | `flush`（map=0，缓存清空） | 失败 `rc=255` ← 重算后恢复强制 |

### 两条可操作的结论

1. **`enforce` 默认必须 flush**。E4 证明 `--noflush` 之后 remount 照样成功 ——
   即 `--noflush` **并没有真正恢复强制**，应视为诊断开关，不是“已还原”。
2. **切状态必须 flush**：map 从 0→1 要 flush 才能生效，从 1→0 也要 flush 才能撤销。

|---|---|---|
| `enforce [--noflush]`<br>别名 `unperm` / `restore` | 清 `permissive_map` + `avc_ss_reset` + 还原 `modprobe_path` | 完全可逆（E5 实测） |

## 五、不重启的完整复位流程（今日实测走通）

```
# 1) 若在本会话 promote 过
ktool unroot

# 2) 若用 kwrite_file 写过且要撤销
ktool undo

# 3) 撤 exec patch（单向门，最后做也行，但做了之后不能再 exec 新程序）
ktool unpatch

# 4) 清 permissive_map + flush + 还原 modprobe_path
ktool enforce

# 5) 卸模块（必须在 flush 之后——卸了就没有 avcflush 了）
ktool pwn /system/bin/sh -c 'true'      # 置 permissive map
ktool flush                              # 清缓存，让 sys_module 放行
ktool root /system/bin/sh -c 'rmmod ktool_mod; cat /proc/modules | grep -c ktool'

# 6) 若动过全局 enforcing（虽然对判定无效，但为了 getenforce 显示正确）
ktool w32 0xc0c4d490 1
```

### 顺序为什么不能乱

- **flush 必须在 rmmod 之前**：`flush` 走模块的 `avcflush`（`/dev/ktool`）；
  模块一卸，`enforce` 会打印 `avcflush unavailable` 而**跳过了 flush**，
  于是 map 清了但缓存里的旧授权还在 —— 机器看起来是 Enforcing，实际仍在放行。
- **rmmod 需要 permissive**：SELinux 拒绝的是 `capability:sys_module`（cap 16），
  与 `CAP_SYS_MODULE` 位无关（`CapEff=ffffffffffffffff` 也没用）。
  实测：Enforcing 下 `rmmod` → `errno 1`；`pwn`+`flush` 后 → `rc=0`。
- **`unpatch` 之后 exec 会被 KNOX 挡**，所以需要 exec 的动作（`rmmod`/`insmod`）
  必须放在 `unpatch` 之前。

### 模块重装（复位后要恢复常态时）

```
insmod /system/lib/modules/ktool_mod.ko ktool_enforce=1 ktool_target=ja3g:3.4.5-6264821
```

实测 `insmod_rc=0`，`/dev/ktool` 重建，`/proc/modules` 恢复 1。
模块 `ktool_exit()` 只做 `misc_deregister()`，不残留其他内核状态。

## 九、逐条核对旧结论「鸡生蛋」

旧说法（P4.88 §六 末段）：

> 安全地清 AVC 需要一个内核执行体（insmod 的模块，或 permissive 下的 shell），
> 而 restore 的最后一步恰恰是把这些关掉；撤了 exec patch 之后任何 root exec
> 都被 KNOX 挡掉，连"验证 restore 成没成功"都做不到；auditd 被杀了拉不回来
> （init 的活）；insmod 的模块卸不掉。

| # | 旧断言 | 判定 | 证据 |
|---|---|---|---|
| a | 清 AVC 需要"内核执行体（模块 或 permissive shell）" | **半对** | `flush` 走 `/dev/ktool`（模块），确实需要模块；但**不需要 permissive shell**，也不需要"先造一个执行体"——模块开机就由 init 装好，不存在引导难题 |
| b | restore 的最后一步恰恰把这些关掉 | **错** | `enforce` 内部顺序是 `do_unperm()` → `do_ctx("avcflush")`，flush 在同一条命令里完成；`enforce` 从不卸载模块、也不先关 permissive 再 flush |
| c | 撤 exec patch 后任何 root exec 都被挡，连验证都做不到 | **错** | 实测见下表：不是统一 EACCES；且 `dump/who/dis/fld/sym` 不 exec，照常可用；`patch` 是纯内核写，可随时重打，**不是单向门** |
| d | auditd 被杀拉不回来 | **未验证**，机制上成立 | auditd 由 init 拉起，shell 域起不来；但现在的路径都不杀 auditd，这条不再是阻塞项 |
| e | insmod 的模块卸不掉 | **错** | `pwn` + `flush` 后 `rmmod ktool_mod` → `rc=0`，`/dev/ktool` 消失。SELinux 拒的是 `capability:sys_module`，permissive map 能放行 |

### c 的实测明细（撤 patch 后）

| 命令 | 结果 |
|---|---|
| `ktool root /system/bin/sh -c 'id'` | `execvp: Permission denied`（EACCES，被拒） |
| `ktool root /system/bin/id` | exec 成功，但进程回落 **uid=2000**（root 丢失） |
| `ktool root /system/bin/ls /data` | exec 成功，`opendir failed, Permission denied`（已是普通 shell 权限） |
| `ktool dump 0xc0b79be0 8` | 正常 |
| `ktool who` | 正常（uid=2000，符合预期） |
| `ktool patch` | `0a000002 -> ea000047`，rc=0，root exec 立刻恢复 |

**准确表述**：撤 patch 不是"什么都干不了"，而是**特权能力没了**（要么被拒，要么降权）；
观测不受影响，且可随时重打 patch。

### 那段结论为什么塌了

它依赖两个前提：①flush 危险，②模块卸不掉。
P4.88 §七 推翻了 ①（消费者活着时 `avc_ss_reset` 无风暴），本轮推翻了 ②。
剩下的「auditd 拉不回来」只在"主动杀 auditd"这条已经废弃的路径里成立。

## 十、核实 `reload_stock_policy()` 是死代码

结论：**是死代码，且三条附带说明全部属实。**

| 断言 | 判定 | 证据 |
|---|---|---|
| 没有任何命令调用它 | **属实** | `grep -n reload_stock_policy ktool.c` 只有 1598 行定义；编译器直接报 `warning: 'reload_stock_policy' defined but not used [-Wunused-function]` |
| 写 `/sys/fs/selinux/load` 重载策略 | **属实** | 函数体 `open("/sys/fs/selinux/load", O_WRONLY)` + `write(policy_buf, total)`；策略来自 `/sepolicy`（设备上 399655 B，`-rw-r--r-- root root`，shell 可读） |
| 内部同样走 `avc_ss_reset` | **属实** | `security/selinux/selinuxfs.c:515 sel_write_load()` → `security_load_policy()`，后者在 `ss/services.c:1855 / 1936 / 2451` 三处调用 `avc_ss_reset(seqno)` |
| 同样需要 SELinux 放行 | **属实** | `selinuxfs.c:524 task_has_security(current, SECURITY__LOAD_POLICY)` → `avc_has_perm(sid, SECINITSID_SECURITY, SECCLASS_SECURITY, ...)` |

### ⚠ 实测否定：把它接成 `flush --policy` 会挂死

我一度把它接成 `flush --policy`（想当「模块卸载后 flush 的兜底」），**实测不可用**：

```
A) 没有 permissive_map 时：
   reload: write fail errno=13 (-1/399655)     ← load_policy 权限被拒
B) pwn 置 map 后：
   （无输出，进程卡在 D 状态，SIGKILL 无效）
   ps: root 14575 ... D /data/local/tmp/ktool
   dmesg:
     tima measure_verify_kernel: KERNEL VERIFICATION FAILED
     tima process_measure_kernel: SEAndroid verification succeeded
     tima generate_response_string: Kernel verification failure
     Tl_TIMA_PKM: ret = 0xffffffff = -1
```

**根因**：`security_load_policy` 被 Samsung 挂钩，加载策略时会触发 TIMA 对**内核**做完整性度量。
我们改过 `.text`（exec patch），度量必然失败；trustlet 返回 -1 后内核侧 `write` 永不返回，
进程卡死在内核态 D，还会永久占住 selinuxfs 的 `sel_mutex`（`selinuxfs.c:522`）。
副作用：`setenforce` 之类走 sel_mutex 的写操作从此阻塞（`w32` 直写 `selinux_enforcing` 不受影响）。

**代码已回退**：`reload_stock_policy()` 删除，`flush --policy` 删除，`enforce` 的 policy 兜底删除，
原位留下一段注释记录这次负面结论，防止以后重试。

**结论修正**：这台机器上**唯一**可用的 AVC 复位通路是模块的 `avcflush`（`/dev/ktool`）。
所以顺序只能是 **先 flush，再 rmmod**；模块一卸就再也清不了缓存，只能重启。
上次说「模块卸了也能靠 policy 重载兜底」是错的，实测直接挂死。

### 另一个必须知道的副作用

这次试验**主动触发了一次 TIMA 内核完整性度量并且失败**（`KERNEL VERIFICATION FAILED`）。
它是否会影响 Knox Warranty Bit 尚不确定，但可以确定：**不要为了清 AVC 去写 selinuxfs 的 load 节点**。

### 顺手修掉一个潜伏的坑

`dump/read` 是 `ktool_dispatch()` 的**最后一个分支**，代码结构是：

```c
if (!strcmp(argv[1], "dump")) { ...hexdump... }
else { ...raw read... }
```

也就是说**任何没匹配上的命令都会掉进 else，变成"读地址 0"**，输出一句莫名其妙的
`read failed`（rc=2）。删掉命令后 `ktool gate` 立刻暴露出这个行为。
已在前面加守卫：

```c
if (strcmp(argv[1], "dump") && strcmp(argv[1], "read")) {
	fprintf(stderr, "unknown command: %s（repl 里输 help 看用法）\n", argv[1]);
	return 1;
}
```

REPL 帮助同步重写，别名合并显示：`unperm`/`restore`→`enforce`，`x`/`rawexec`→`root`，
`shell`/`-i`→`repl`。新版已装 `/system/bin/ktool`（423044 B）。

## 十二、su 授权弹窗不出：`/data/local/tmp/sud` 缺失（2026-10-24 22:20）

现象：app（Amaze）请求 root 时不再弹授权框，`su` 直接失败。

### 排查（全部真机）

| 检查 | 结果 |
|---|---|
| `untrusted_app` 域能否 exec `su` | ✅ 能。`ctx` 切到 `u:r:untrusted_app:s0` 后执行 su，报的是 `su: ish failed` 而不是 `Permission denied` —— 说明 exec 成功，只是被我临时改的门禁拦在提权步 |
| 模块 `ish` 提权 | ✅ `echo -n ish > /dev/ktool` → `w=0`，域变 `u:r:init_shell:s0`，uid 0 |
| `/dev/ktool` 标签 | ✅ `u:object_r:null_device:s0`（与 /dev/null 一致） |
| `am start RequestActivity` | ✅ 两个 Activity 都进栈（`RequestActivity` + `MultitaskSuRequestActivity`） |
| phh 数据库 | 空（`uid_policy` 0 行）→ 必须走弹窗 |
| `/data/system/su_allow` | 只有 `99999`，Amaze 不在内 → 必须走弹窗 |

### 根因

`src/su_fork.c`：

```c
#define SOCK_DIR  "/data/local/tmp/sud"
#define SOCK_FMT  SOCK_DIR "/s%d"
```

`child_sock()` 只做 `unlink(sock_path)` + `bind()`，**没有任何 mkdir**。
而 `/data/local/tmp/sud` **不存在**（真机 `ls` 确认）。于是：

```
child bind → ENOENT → _exit
parent read → 空 → "su: socket not ready" → return 1
```

**根本走不到 `am start`，所以弹窗永远不出现**。这不是策略问题，是文件系统缺目录。

### 修复

1. **立即**：建目录（必须用 shell 身份 —— `/data/local/tmp` 是 `shell:shell 0771`，
   shell 是属主；用 uid 0 反而变成 other，需要 `dac_override`，会被
   `capability:dac_override` 拒掉）：

```
$ mkdir /data/local/tmp/sud && chmod 777 /data/local/tmp/sud
mk=0
drwxrwxrwx shell shell u:object_r:shell_data_file:s0 sud
```

2. **持久化**：在 `/system/etc/init.sec.boot.sh` 的 `ktool permissive` 之后加两行
   （该处 init_shell 已 permissive，可以建），已部署（4613 B，`sh -n` 通过）：

```sh
mkdir -p /data/local/tmp/sud && chmod 777 /data/local/tmp/sud
echo "sud_rc=$?"
```

### 附带纠正

- `ktool permissive` 只标 **init_shell** 一个 type，**不含 shell**。所以 uid 0 + 全 caps
  在 shell 域里仍然过不了 `capability:dac_override`（audit 里有实证）。要写 /data 这类
  `system:system 0771` 目录，得走 init_shell（`ktool sh`）或让属主身份来写。
- `su` 的 socket 目录为什么消失没有定论；`/data` 跨重启保留，可能是某次清理或开发期手工建的。
  开机补建是唯一稳妥的兜底。
