# P4.23 — permissive 从 1343 个 type 缩到 1 个

日期：2026-10-22 00:33–00:52
设备：GT-I9500 / 3.4.5-6264821

---

## 1. 结论

| 路径 | v5（全 type permissive） | **v7（只 init_shell）** |
|---|---|---|
| 模块加载（sec-sh 自己 insmod） | ✅ | ✅ |
| **app 调 su** | ✅ | ✅ |
| adb shell 调 su | ✅（靠 permissive） | ❌ 策略本来就不允许 |
| 写 /data/data、/system | ✅（靠 permissive） | ✅（init_shell 那 1 bit） |
| 其余 1342 个 type | permissive | **enforcing** |

```
$ sh -c 'echo "ctx u:r:untrusted_app:s0" > /dev/ktool; /system/xbin/su -c id'
uid=0(root) gid=0(root) context=u:r:init_shell:s0
```

---

## 2. 为什么能缩到 1 个

三个查询结果叠加出来的：

```
init_shell -> init_shell: [capability] chown,dac_override,...,sys_module,...   ← 有 CAP_SYS_MODULE
init_shell -> system_file: [file] execute,execute_no_trans,getattr,ioctl,lock,open,read
untrusted_app -> su_exec:   [file] execute,execute_no_trans,...                ← 真实规则
```

原来的流程要 `kernel` 域 + exec patch，是因为 `ktool pwn` 把进程切成 kernel 域，
而 kernel 域对 `system_file` 只有 `execute`、没有 `execute_no_trans`。

**但 `sec-sh` 本身就是 `init_shell`**，而 init_shell 两个都有。所以：

| 原来 | 现在 |
|---|---|
| `ktool pwn /system/bin/insmod`（切 kernel 域） | `/system/bin/insmod`（sec-sh 自己） |
| 必须先打 exec patch | 不需要（init_shell 有 execute_no_trans） |
| permissive 要标 kernel + init_shell | **只标 init_shell** |

而且 `/system/bin/insmod` 不在 `/data/` 下，KNOX 的 `sec_check_execpath` 不拦。

---

## 3. 但 su 提权后仍需要 exec patch

v6（只有 min，没 patch）的失败：

```
$ sh -c 'echo "ctx u:r:untrusted_app:s0" > /dev/ktool; /system/xbin/su -c id'
su: exec: Permission denied
```

原因：`ish` 把进程 uid 改成 0 之后，`sys_execve` 入口的 KNOX 检查块
（`c0012164: beq`，条件是 cred 六个 id 任一为 0）就会被命中。
虽然 `sec_check_execpath(mm, "/data/")` 本身不拦 `/system/bin/sh`，
但实际结果是 EACCES，所以 patch 仍是必需的。

**permissive 对此完全无效**——KNOX 那道检查不是 SELinux，改 permissive_map 不影响它。
这也说明 v5 时代 su 能跑，靠的是 exec patch，不是 permissive。

v7 的 boot 流程：

```sh
ktool w32 c0c0ae28 2      # bootmode = 2
ktool permissive          # 只置 bit 986 (init_shell)
ktool patch               # exec patch，为了 su 提权后能 exec
insmod /system/lib/modules/ktool_mod.ko
```

---

## 4. 实现

`do_permissive_min()`（ktool.c）：节点链结构和 highbit(1536) 都不动，
只把 8 个节点的 maps 清成 0，再单独置 `bits[] = {986}` 里那一位。

```c
static const unsigned int bits[] = { 986 };   /* init_shell */
...
for (i = 0; i < NNODES; i++) {
    memcpy(n, &nx, 4);
    memset(n + 4, 0, 24);      /* maps 全清 */
    memcpy(n + 28, &sb, 4);
}
/* 只置指定的 bit */
```

`ktool permissive` 命令改成调用 `do_permissive_min()`；
`sh` / `pwn` / `ls` / `cat` / `cp` 仍然用全开的 `do_permissive()`，调试用。

## 5. “两把钥匙”问题的完整解释（值得存档）

写别人的 app 数据（`/data/data/<pkg>`，0700）要同时过两关，而没有任何单一域同时有两把钥匙：

| 域 | DAC 关（`dac_override`） | SELinux 关（`app_data_file:file write`） |
|---|---|---|
| `init_shell` | ✅ 有 | ❌ 只有 read |
| `untrusted_app` | ❌ capability 规则为空 | ✅ 有 |

- uid 0 过 DAC 需要 `capable(CAP_DAC_OVERRIDE)`，而 SELinux 的 capability 钩子要求域里有 `dac_override` 规则
- `untrusted_app` 的 capability 规则是空的，所以它虽然 SELinux 能写，却过不了 0700 目录的 DAC

**备选方案（未实现）**：写某个 app 的数据时，把进程 fsuid 设成那个 app 的 uid、SID 设成 `untrusted_app`——
DAC 用 `fsuid == owner` 过，SELinux 用已有的 write。代价是每次写都要换身份，不划算，但证明这条路存在。
