## 一、两个严重问题

### 1) su 的 socket 没有校验连接方 → 任何 app 都能绕过授权弹窗

`child_sock()` 在 `/data/local/tmp/sud`（0777）里 listen，然后直接 `accept()`，
**不看连接方是谁**。而 su 判定授权的逻辑是"读到 `ALLOW` 就放行"。

于是任何 app 只要 `connect()` 到 `/data/local/tmp/sud/s<pid>`（目录 0777、
我们为弹窗加的 `sock_file { write }` 又刚好允许 connect），发一个 `ALLOW`，
就能让**自己那次 su 请求**直接通过——完全跳过授权弹窗。这比"permissive 放宽"
严重得多，因为它伪造的是"用户已同意"。

修复（`child_sock`）：

```c
for (i = 0; i < 3; i++) {
        cfd = accept(sfd, NULL, NULL);
        if (cfd < 0) continue;
        if (getsockopt(cfd, SOL_SOCKET, SO_PEERCRED, &cr, &cl) == 0 &&
            (int)cr.uid == admin_uid)      /* 只认管理 App 的 uid */
                break;
        close(cfd); cfd = -1;              /* 别人连上来直接丢弃，继续等 */
}
if (cfd < 0) { write_all(c2p_w, "ERR:PEER"); _exit(5); }
```

`admin_uid` 在 fork 之前算好传给子进程（父进程此时还是 caller 身份，能 stat）。

### 2) 开机脚本被写成 CRLF → 整脚本不执行（真实事故）

这一轮把脚本用 Python 在 Windows 上保存，写出了 CRLF。设备上的 mksh 直接报：

```
/system/etc/init.sec.boot.sh[66]: syntax error: 'do' unexpected
```

解析失败 = **一条语句都不执行**（重定向 `> /data/system/2a_v9g.log` 在脚本体内，
所以日志仍是上一次的）。后果连锁：

```
脚本没跑 → 没有 ktool patch → 没有 permissive → 没有 insmod
        → 没有 /dev/ktool → su 全程不可用
```

而且此时连 `mount -o rw,remount /system` 都进不去：`pwn` 虽然置了 permissive，
但 AVC 缓存里 `shell → filesystem { remount }` 的旧 deny 不会被重算，
`flush` 又依赖 `/dev/ktool`（模块没加载）——**死锁**。

破局手段：给 ktool 新增 `setsid` 命令，直接改当前进程内核里的
`cred->security->sid`（`current_sid()` 就是取这个），换成 `init_shell` 这个
**新 ssid**；首次判定会重新计算，permissive 立刻生效，于是 mount 成功。

```c
cred = *(u32 *)(kread(task + off_real_cred) + 4);
tsec = *(u32 *)kread(cred + 0x58);        /* struct cred->security */
pair[0] = osid;  pair[1] = 254;           /* init_shell */
kwrite_verify(tsec, pair, 8);             /* 必须 8 字节整写 */
```

（`target` 现在会打印 `cred.security=58`，偏移是从 `targets.h` 与实测共同确认的。）

修完把脚本转回 LF、`sh -n` 在**设备上**校验通过后重部署，冷启动一切正常。

## 四、脚本侧

**新增 `src/build_su.sh`**：su 的构建原来只存在于聊天记录里，现在固化成脚本
（`-static -O2 -s -DSQLITE_OMIT_LOAD_EXTENSION -DSQLITE_THREADSAFE=0 -DSQLITE_OMIT_WAL`）。

**重写 `src/deploy_su.sh`**（旧版是设备侧 sh，两处过时/危险）：

- 旧版无条件 `echo 2000 > /data/system/su_allow`，等于给 adb 永久免弹窗——
  现在四档由属性控制，不该再动白名单；新版不碰它。
- 旧版假设 `/data/local/tmp/su` 已就位、不校验版本；新版从 PC push、装完用
  `/system/xbin/su -v` 自检（`/data/local/tmp` 里的副本在 shell 域 exec 不出来，
  自检必须用装好后的路径）。
- 旧版不恢复 enforcing；新版按 `pwn → flush → rw → cp/chcon → ro → enforcing` 全流程。

**`init.sec.boot.v9g.sh` 增强**：

- 转 LF（这次事故的直接修复），并加注释说明为什么不能用 CRLF。
- `sud_rc` 失败时把 `ls -ldZ /data/local/tmp` 打到 kmsg（以前静默失败，
  表现只是"弹窗不出来"）。
- `restore` 返回非 0 时打 `KT_ENFORCE_FAIL`（4 = avcflush 不可用，
  看着 Enforcing 实际旧缓存仍放行）。
- 模块没起来时打 `KT_NO_MODULE: insmod failed, permissive left ON`。
- 记录 `avrule_applied` 与 `root_access`，便于事后核对。

## 六、遗留 / 仍可改进

1. **`setsid` 的写回校验不稳定**：第一次成功，之后连续 `sid write failed`
   （`kwrite_verify` 30 次都没过）。它是救援工具，不是常规路径；真要用就重试或
   改成"写完用 `dump` 复核"。模块在的时候优先用 `ctx`（uid0 例外）。
2. **`avrule_enable=0` 时没有替代方案**：应用侧弹窗会退回依赖 permissive。
3. **`sud` 目录仍是 0777**：任意 app 可创建/删除（可用性 DoS，不能提权，因为
   PEERCRED 已挡）。要更严格可改 1777，但 pid 复用时会 bind 失败。
4. **白名单 `/data/system/su_allow`** 仍在：命中即不问。它和四档是叠加关系
   （先看档位），留着自己用时方便。
