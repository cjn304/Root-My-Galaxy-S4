# P2.4 栈重塑方案设计（GT-I9500 / 3.4.5）

**日期：** 2026-10-17
**目标：** 在 A 线程的悬空 `pi_blocked_on` 地址处伪造 `rt_mutex_waiter`，把 chain-walk 的 `waiter->lock` 变成受控指针。

## 1. 目标地址与硬约束

- A 线程 `pi_blocked_on` = 触发时 `futex_wait_requeue_pi` 栈帧中的 `rt_waiter`
- 由反汇编推出：`rt_waiter = SP_entry - 0x1B0`
  - `sys_futex` frame 0x58（push 44 + sub 0x2c）
  - `do_futex` frame 0x88（push 44 + sub 0x5c）
  - `futex_wait_requeue_pi.constprop.16`: push 44，`fp = entry-4`，`rt_waiter = fp-0xcc` → 0xD0
- 需要控制该地址起 **48 字节**（0x00 list_entry / 0x14 pi_list_entry / 0x28 task / **0x2c lock**）

## 2. 公开方案不适用（关键结论）

| 喷雾源 | 缓冲区起始深度 D | 覆盖 waiter 范围 | 结论 |
|---|---|---|---|
| `pselect(nfds=320)` → `core_sys_select` stack_fds | 0x178 | 上方，未覆盖 | ✗ 浅 0x38 |
| `pselect6` | 0x190 | 上方，未覆盖 | ✗ 浅 0x20 |
| `poll`（stack_pps） | 0x3B4 | 下方深处，未覆盖 | ✗ 深 0x204 |
| `recvmmsg`（iovstack, ≤8 iovec=64B） | 0x1A0 | waiter+16..79 | 部分 ✓ |
| `sendmmsg`（iovstack 同源） | **0x1E0** | waiter 0..15 | 部分 ✓ |
| `fcntl64(F_GETLK64)` flock64 | 0x114 | 未触及 | ✗ |
| `ptrace` | ≤0x134 | 未触及 | ✗ |
| `process_vm_readv` | 0xD8 | 未触及 | ✗ |

> GhostLock-Galaxy 的 pselect 路线（shift ≤ 3 qwords）在本内核几何下不可行，必须自建喷雾组合。

## 3. 采用方案：sendmmsg + recvmmsg 双喷

两段缓冲**首尾相接、无重叠**，合计覆盖 waiter 0..79：

```
E-0x1E0 ── sendmmsg iovstack(64B) ── E-0x1A0 ── recvmmsg iovstack(64B) ── E-0x160
              ↑ waiter-0x30                ↑ waiter+0x10
                                          waiter = E-0x1B0
```

- `sendmmsg` 链：`sys_sendmmsg`(0x10) → `__sys_sendmmsg`(0xE0) → `___sys_sendmsg` iovstack `fp-0xec` → D=0x1E0
- `recvmmsg` 链：`sys_recvmmsg`(0x40) → `__sys_recvmmsg`(0x70) → `___sys_recvmsg` iovstack `fp-0xec` → D=0x1A0
- 各传 8 个 iovec（`UIO_FASTIOV`），触发 `copy_from_user(iovec[8], user_vec, 64)`
- recvmmsg 用非阻塞 socket，避免阻塞在 recv
- SELinux：shell 可 `create` unix_stream_socket ✓

### 字段布局（伪造 waiter）

| waiter 偏移 | 字段 | 来源 | 值 |
|---|---|---|---|
| 0x00 | list_entry.prio | sendmmsg | 任意 |
| 0x04..0x0b | prio_list next/prev | sendmmsg | 设成非空列表形式，精确控制 plist_del 分支 |
| 0x0c..0x13 | node_list next/prev | sendmmsg | 目标地址对（list_del_init 即 4 字节读写原语） |
| 0x14..0x27 | pi_list_entry | recvmmsg | 视 boost 分支而定 |
| 0x28 | task | recvmmsg | 任意（本路径不读） |
| **0x2c** | **lock** | recvmmsg | **用户态映射的假 rt_mutex** |

## 4. 消费链（触发条件与行为）

T 在 A 持有的 u3 上 `LOCK_PI` 阻塞 → `task_blocks_on_rt_mutex` 见 `A->pi_blocked_on != NULL` → `chain_walk=1` →
`rt_mutex_adjust_prio_chain(task=A, detect=1, orig_lock=u3_mutex, top_task=T)`：

1. `waiter = A->pi_blocked_on`（伪造）
2. `lock = waiter->lock` → 用户态假 rt_mutex
3. `raw_spin_trylock(&lock->wait_lock)` → 用户内存 ticket lock（ARMv7 无 PAN，可执行）
4. 死锁检查：`lock == orig_lock`（否）；`rt_mutex_owner(lock) == top_task`（假 owner 设 1，否）
5. `rt_mutex_top_waiter(lock)` → 读假 wait_list
6. **`plist_del(&waiter->list_entry, &lock->wait_list)`** ← 核心写原语
   - 若 prio_list 判空 → 只做 `list_del_init(node_list)`：两次受控 4 字节写（值=对侧指针）
   - 非空 → 额外 `list_del_init(prio_list)`，同样是受控写
7. `plist_add` → 写回假 wait_list（用户内存，无害）
8. `raw_spin_unlock(&A->pi_lock)`（真实 A）→ `put_task_struct(A)`
9. `task = rt_mutex_owner(lock)` ← **可指向任意地址**：`atomic_inc(task+8)`、`raw_spin_lock(task+0x39c)`、`rt_mutex_setprio(task, prio)`（读 sched_class 函数指针 → 潜在内核态任意调用）
10. `if (task->pi_blocked_on)` → 可续走下一轮（可控）

## 5. 风险与验证策略

| 风险 | 说明 |
|---|---|
| 栈底 clobber | `___sys_sendmsg` 在 iovec 拷贝后若再向 `[sp]` 写调用参数，会破坏 waiter 0..7 |
| 假 wait_list 语义 | 3.4 的 `plist_head` 无 `prio_list` 成员，`rt_mutex_top_waiter` 对空表返回 container_of(head)（读 head-12），需保证页内可读 |
| plist_del 分支 | prio_list 若被判非空，走额外 list 迭代 → 未映射地址 → oops |
| 崩溃 | 任一指针错误 = kernel oops/panic；dmesg 可能随重启丢失 |

**验证顺序（每步都可能 panic）：**
1. **控制权证明**：假 lock 指向未映射的 `0xDEAD0000` → 若 dmesg 出现 `Unable to handle kernel paging request at virtual address dead0000`，则证明 waiter 伪造成功
2. 通过后：假 lock 指向用户页，跑完整链走，确认无 oops
3. 末端：利用第 9 步的 `rt_mutex_setprio` 函数指针调用或第 6 步写原语改 cred
