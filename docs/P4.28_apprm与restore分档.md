## 二、apprm（新工具）

`/system/xbin/apprm`（700 root:root），和 appwrite 同一套双钥匙：

```
1. stat 目标父目录，拿到 owner uid/gid
2. 写 /dev/ktool: "ctx u:r:untrusted_app:s0 <uid> <gid>"
      → 模块换 sid + 内核直写 cred->fsuid/fsgid
3. 之后 unlink / rmdir / readdir 全部由 untrusted_app 的策略放行
```

用法：

```
apprm [-r] [-f] <path>...
   -r  递归删目录
   -f  忽略不存在的路径
```

**实测**（permissive 全关）：

```
$ ktool root /system/xbin/apprm $D/aw_x1 $D/aw_x2 ; echo $?     → 0
$ ktool root /system/xbin/apprm -r $D/aw_d ; echo $?            → 0   （含 s1/s2 两级子目录）
$ ktool root /system/xbin/ls .../aw_v1                          → No such file
```

**一个必须遵守的纪律**：`ctx` 之后不许再碰 stdio。切到 untrusted_app 后再写 shell 的 pty/pipe 会走
`security_file_permission` → 被拒 → 本内核审计路径 oops（`avc_audit_pre_callback` 里 `strnlen` 野指针），
进程直接 SIGSEGV。所以两个工具切域之后只用退出码报告（`_exit(rc)`）。

## 三、ktool sh 改造

旧 `sh` = `do_root` + `do_permissive()`（**全开** permissive_map）。

全开的代价：permissive 判定在**计算时**就烤进 AVC 条目的 `avd->flags`，之后即使清零也一直生效，
等于给整机留了个看不见的后门，只能重启清。

新实现：

```
ktool sh       = do_root → 写 /dev/ktool 切 init_shell（过同一个门禁）→ exec sh
                 模块不在（比如第一次 insmod 前）才退回 min permissive
ktool shfull   = 旧行为（do_root + 全开 permissive），保留作应急
```

实测：`ktool_v30 sh -c id` → `context=u:r:init_shell:s0`，且 permissive_map 没被碰。

## 四、restore 三档

```
ktool restore              关 permissive + 清 AVC 缓存（默认，root 仍可用）
ktool restore --noflush    只关 permissive，不清缓存（旧行为）
ktool restore --stock      连 exec patch / modprobe_path 一起还原成原始态
ktool flush                只清 AVC 缓存，permissive 状态不变
```

### 为什么 --stock 不能当默认

Samsung 在 `sys_execve` 入口的限制是「**6 个 cred id 全为 0 就进 KNOX 检查块**」。
patch 关掉之后：

```
$ ktool restore --stock
$ ktool root /system/bin/ls /system/bin
execvp: Permission denied          ← 连 ls 都 exec 不了
```

所以 `--stock` 一旦执行，root 就废了，只能重启恢复（重启时 boot 脚本会重新 patch）。
默认档保留 patch，只关 permissive —— 这才是"关提权面但不影响使用"的正确切法。

### AVC 缓存怎么清的

模块新增命令：

```c
static int ktool_avcflush(void)
{
	avc_reset = kallsyms_lookup_name("avc_ss_reset");
	avc_reset(0);        /* 内核自己的 API，按 slot 加锁 + call_rcu */
}
```

不能用"手工遍历链表"：无锁改活哈希表会造环链，`avc_search_node` 死循环 → 看门狗复位（P4.24 实测）。
`avc_ss_reset` 是 `security_load_policy` 自己用的函数，安全。

门禁：`avcflush` 和 `ctx` 一样，只放行 `exe=/system/xbin/su` 或**已 uid0** 的进程。app 到不了 uid0。

## 五、boot 脚本 v9e：permissive 收口

新增 3b 步（`insmod` 之后）：

```sh
  if [ -c /dev/ktool ]; then
    /system/bin/ktool restore
    echo "restore_rc=$?"
  fi
```

理由：`insmod` 需要 `CAP_SYS_MODULE`，这一步借的就是 init_shell 的 permissive bit；
模块进内存之后 permissive 没有存在必要了，立刻清零 + 清缓存。

真机开机日志（`/data/system/2a_v9e.log`）：

```
patch_rc=0
--- insmod attempt 0 (delay 0s) ---
insmod_rc=0
dev_ktool=ok
permissive_map cleared, modprobe_path restored
permissive off, modprobe_path restored
avc cache flushed: permissive 立即全部失效
restore_rc=0
ktool mode: -rwx------ root root 435316 ktool
--- su self test ---
uid=0(root) gid=0(root) context=u:r:init_shell:s0
```

**开机全程跑通，收口后 su 自检正常。**

## 六、顺带查清的两个老问题

### 1. permissive 为什么会"自己消失"

`mount -o rw,remount /system` 会触发 Samsung SEPF 重载策略：

```
Function: selinux_compare_spd_ram , priority [2] , priority version is VE=SEPF_GT-I9500_5.0.1-1_0039
SELinux: Loaded file_contexts from /file_contexts
```

策略一重载，`permissive_map` 就按策略文件重建，我们写进去的 bit 全没。
之前"重启后 permissive 没了/开机后能力消失"的根因就是它 —— 每次部署完 `mount -o ro,remount` 就中招一次。

### 2. 缓存里的拒绝不会因为"重新设 permissive"而复活

```
ktool permissive          → 写 bit 986 成功
mount -o rw,remount ...   → 仍然 Permission denied
ktool flush               → 之后 mount 才恢复
```

因为拒绝是**算过一次就缓存**的。所以"设 permissive"和"清缓存"必须配对使用，
`ktool flush` 就是为此加的。

## 八、遗留

1. **审计路径的 oops**（`avc_audit_pre_callback` → `strnlen` 野指针）：在"大量拒绝被审计 + 反复 rmmod/insmod"的
   会话里复现过两次，进程被 SIGSEGV 打死（不是整机崩）。干净启动 + permissive 收口的配置下 0 次复现。
   暂不处理，但要知道：**诊断时不要反复卸载/重载模块**。
2. **`--stock` 之后必须重启**：这是 Samsung exec 保护的硬约束，不是我们能绕的
   （除非把 patch 换成更精细的方式，比如只对非 su 路径放行）。
3. apprm 不做 ACL/xattr 处理，删不掉带 immutable 标记的文件。
