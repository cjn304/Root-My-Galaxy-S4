# P4.24 — /dev/ktool 门禁尝试与失败（已回滚）

日期：2026-10-22 00:50–01:50
状态：**门禁未生效，已回滚到 v7 行为**

---

## 1. 要解决的问题

```
allow domain null_device:chr_file {append,getattr,ioctl,lock,open,read,write}
/dev/ktool  crw-rw-rw-
```

任何 app 都能 `echo ish > /dev/ktool` 直接拿 uid 0 + init_shell，
**完全绕过 su 的授权弹窗**。v7 把 permissive 缩到 1 个 type，这个后门一点没变。

## 2. 尝试过的三条路，全失败

### 域门（判 `current` 的 SID 是不是 init_shell）—— 设备被打崩

三个版本依次试过，全部在 `echo ish` 时把设备打崩（需要重启恢复）：

| 版本 | 实现 | 结果 |
|---|---|---|
| v3 | `prepare_creds()` → 读 `cur->security` → `abort_creds()` | 崩（`abort_creds → selinux_cred_free`） |
| v4 | 同上 + `printk` 里二次调 `ktool_is_exe`（`d_path`） | 崩 |
| v5 | `d_path` 换成 dentry 指针比较，域门仍用 `prepare_creds` | 崩 |
| v6 | `rcu_read_lock()` + `rcu_dereference(current->cred)` | 崩 |
| v7 | `security_context_to_sid` 移到 init 缓存，read 里只比较 | 崩 |

**共同点：都在 write 上下文读 `cred->security`。**

这和 P4.16 的现象一致——模块的 `.config`（`ja3g_00_defconfig`）与设备内核实际 config 不一致，
`struct cred` 的编译期偏移不可信（当时 `cat /dev/ktool` 打印出 `0xc86fad68` 这种栈值）。

而 `ish`/`ctx` 命令用 `prepare_kernel_cred()` + `commit_creds()` 是成功的，
说明内核内部的分配/提交路径没问题，**只有模块自己按结构体偏移去读会错**。

### 路径门（判 `exe_file` 是不是 `/system/xbin/su`）—— 不生效 + 偶发崩

- 用 `d_path()`：write 上下文崩（v4）
- 换成 dentry 指针比较（模块 init 时 `kern_path` 缓存）：**`su` 自己的 ish 也被拒**
  （`su: ish failed`），说明 `current->mm->exe_file->f_path.dentry` 和 `kern_path` 拿到的不是同一个 dentry
- 且仍有偶发崩溃

### 节点权限 0600 —— 不可行

su 的 caller 是 app uid，写不了 root 0600 的节点。鸡生蛋，用户也已指出。

## 3. 回滚

`ktool_allow()` 恒返回 1，恢复到无门行为。实测恢复：

```
$ sh -c 'echo "ctx u:r:untrusted_app:s0" > /dev/ktool; /system/xbin/su -c id'
uid=0(root) gid=0(root) context=u:r:init_shell:s0
```

设备状态与 P4.23（v7）一致：permissive 1 个 type、exec patch 开、su 可用。

## 4. 当前真实的安全状态（不粉饰）

| 通道 | 状态 |
|---|---|
| app `echo ish > /dev/ktool` | ❌ **开放**（后门） |
| app `exec /system/bin/ktool sh` | ❌ **开放**（ktool 自带 exploit） |
| su 授权弹窗 | 可被上述两条完全绕过 |
| permissive | 1 个 type（init_shell） |
| enforcing | 其余 1342 个 type |

**结论：这套东西现在只适合装在你自己管理的机器上。** 装任何第三方 app 等于给它 root。

## 5. 还没试的一条路

模块里用**实测偏移**而不是编译期结构体去读 cred：

```c
struct task_struct *t = current;
u32 cred = *(u32 *)((char *)t + 0x2fc);      /* ktool find_self 实测 */
char *sec = *(char **)((char *)cred + 0x48); /* isec_off 实测 */
u32 sid = *(u32 *)(sec + 4);
```

ktool（用户态）用 `kread(p + 0x2f8, ...)` + 这套偏移读 cred 是成功的，
模块里有同等内存访问权，理论上可行。**没试，因为当晚已连续打崩设备 5 次。**

## 6. 短期可做的缓解（不解决根本问题）

1. **锁 ktool 二进制**：boot 脚本里 remount rw 后 `chmod 700 /system/bin/ktool`，再 remount ro。
   挡住 `app exec ktool` 这条路（owner root，app 是 other）。
   注意 sec-sh 自己 exec 时是 uid 0，不受影响。
2. 这条做完，`/dev/ktool` 的后门仍在，但攻击面从两条减到一条。
