# P3.2 越界自检（零内核地址）— 设计与运行

**目的**：证明「iovec 数组越界」在本机真实发生，且落点/越界量可控。
**安全边界**：所有 OOB 伪 iovec 的 `iov_base` 都指向**用户态** magic 数组，全程不出现任何内核地址。
最坏结果 = `writev` 返回 `-EFAULT`，不会 panic、不会重启。

---

## 1. 布局

`nr_segs = 257`（→ `kmalloc(2056)` → kmalloc-4096），写入 8192 字节 = 2 个 pipe buffer：

| iovec | base | len | 作用 |
|---|---|---|---|
| `iov[0]` | `ro_pg`（`PROT_READ`） | **16** | 让 `iov_fault_in_pages_write` 在第一条就 `break`，`iov[1]` 不被预取；同时决定越界量 W=16 |
| `iov[1]` | `race_pg`（被 mprotect 反复保护/放开） | 4080 | 制造 atomic 趟的确定性 EFAULT |
| `iov[2]` | `mid_pg`（常驻） | 4096 | 供重试消费，保证第一轮能写满 4096 |
| `iov[3..256]` | NULL | 0 | 填充 |
| 残留 `iov[257]/[258]` | `&magic[257] / &magic[258]` | 8/8 | 越界后真正被使用的两个条目 |

合计 16 + 4080 + 4096 = 8192。

### 无故障时（对照组）
```
轮 1: 16 + 4080 = 4096  →  iov[0].len=0, iov[1].len=0
轮 2: 4096 (iov[2])     →  正常写完 8192，无越界
```

### 有故障时（攻击组）
```
轮 1 atomic: 复制 16B（iov[0]）→ iov[1] 撞 PROT_NONE → EFAULT   (W=16)
轮 1 重试  : 跳过 iov[0] → iov[1] 4080 → iov[2] 16            (共 4096)
轮 2 atomic: iov[2] 剩 4080 → iov[3..256] 全 0 跳过
             → iov[257] 8B + iov[258] 8B  ← 越界 16B
```

管道第 8176..8191 字节 = `magic[257]`、`magic[258]`。

---

## 2. 残留（kmalloc-4096 复用）

`spray_once()` 每条 `sendmmsg`：

- `msg_iovlen = 512` → `sock_kmalloc(4096)` + `verify_iovec` **裸拷** 512 条 iovec（逐条不校验）
- `msg_controllen = 4096` → 再 `sock_kmalloc(4096)` + `copy_from_user`
- 返回前依次 `sock_kfree_s(ctl)`、`sock_kfree_s(iov)` → **最后压回 freelist 的是 iovec 对象**

紧接着的 `writev` 的 `kmalloc(2056)` 在同一个 CPU 上必然弹到这个对象，
前 2056B 被 257 条真 iovec 覆盖，后 2040B 保留 `siv[257..511]`。

`spray` 数组特意做成前 257 条长度为 0，所以每次 send 只读 2040 字节，开销很小。

## 3. 运行

```bash
adb push iov1805_test /data/local/tmp/
adb shell chmod 755 /data/local/tmp/iov1805_test
adb shell /data/local/tmp/iov1805_test 200000
```

参数 = 最大迭代次数。默认 20 万次，约 5–15 秒。

### 输出判读

| 输出 | 含义 |
|---|---|
| `warmup ret=8192` | 控制组正常（无 race 时不该越界） |
| `[+] HIT iter=... idx=257,258 val=dead...` | **越界成立**，且精确落在 257/258 |
| `[-] no hit. props: full=... part=... err=...` | 没撞上 race 窗口，看 full/err 比例调参 |
| 进程被 kill / 设备重启 | 理论上不应发生；若发生说明残留不是我们的（见 §4） |

`full` = 8192 的正常写入次数；`err` = `writev` 返回负值的次数；
一次成功越界的比例大约 = `err / (full + err)` 里能走到第二轮的那部分。

---

## 4. 已知风险与调参

1. **残留未命中**：若 `writev` 的 `kmalloc(2056)` 没拿到喷过的对象，`iov[257]` 是脏数据。
   最坏情况是当成长度非 0、base 是野指针 → 拷贝 EFAULT（只读，安全）；
   极小概率 base 恰好是可读用户地址 → 只会写回该对象内部 2 条 slot（≤4096 范围内），
   仍不跨对象。**建议先跑 1 万次看 `err` 比例，再放大。**
2. **race 不中**：把 `max_iter` 加到 100 万；或把 `toggle_thread` 的两次 `mprotect`
   改成 `munmap + mmap(MAP_FIXED)`（iovyroot 原版做法）。
3. **CPU 亲和**：writer 固定 CPU0，toggle 线程未固定（会跑到 CPU1-3）。
   若设备调度把两者挤到同一核，race 概率下降 —— 可以用 `taskset` 或改代码把 toggle 固定到 CPU1。
