# P4.7 不改内核代码的 root 方案（父子进程 + ptrace）

**时间**：2026-10-19 19:0x
**结论**：可行，实测 4/4 成功，**内核代码段一个字节都没动**。

---

## 1. 旧版为什么必须打补丁

`sys_execve @0xc0012118` 入口有 Samsung 加的分流：

```
cred 六个 ID（uid/gid/euid/egid/suid/sgid）任一为 0 → 进 KNOX 检查块
全非 0 → 直接 do_execve
```

检查块里两次 `sec_check_execpath`：

```c
// 第一次：看 exe 路径，命中 /sbin/adbd 就降权到 2000 再放行
if (sec_check_execpath(current->mm, "/sbin/adbd")) { 降权 }
// 第二次：命中 /data/ 就拒绝
if (sec_check_execpath(current->0x1ec, "/data/")) { printk("Restricted..."); return -EACCES; }
```

`ktool` 从 `/data/local/tmp` 启动、改完 cred 变 uid 0，一 exec 就命中第二次检查。
旧版解法是往 `0xc0012164` 写 4 字节（`beq` → `b`），跳过整块。

**问题**：ARMv7 的 I-cache 与 D-cache 不保证一致，改 text 不刷 I-cache 属于未定义行为（虽然实测最坏只是补丁不生效，不会崩）。

---

## 2. 新方案：让 exec 发生时 uid 还不是 0

关键观察：**检查块的触发条件只看 exec 那一刻的 cred**。

```
1. ktool 以 uid 2000 启动
2. do_permissive()            ← MAC 先放开
3. fork 子进程
   子进程：chdir("/")
           ptrace(PTRACE_TRACEME)
           execve("/system/bin/sh")     ← uid 仍是 2000，不进检查块，成功
4. 父进程 waitpid 收到 SIGTRAP（说明 exec 已完成，cred 已换成 exec 后的新副本）
5. 父进程遍历任务链表，按 parent 指针找到子进程
6. 把它的 cred 改成 uid 0 + caps 全满
7. ptrace(PTRACE_DETACH) → 子进程继续跑，已经是 root
8. 父进程 waitpid 等子进程退出（保持 adb 会话不断）
```

**为什么必须用 ptrace**：`execve` 内部会 `prepare_exec_creds()` 复制一份新 cred。如果父进程在 exec 之前改 cred，子进程的 exec 会命中检查块；如果在 exec 瞬间改，可能改到旧对象。`PTRACE_TRACEME` 让子进程在 exec 完成后停在入口处，父进程这时候改，改的一定是新 cred。

**为什么必须 chdir("/")**：见第 4 节。

---

## 3. 实测

设备：GT-I9500，shell 域，Enforcing。

| 命令 | 结果 |
|---|---|
| `ktool3 sh -c 'id'` | `uid=0(root) gid=0(root)` |
| `ktool3 sh -c 'id; /system/bin/date'` ×3 | 全部 uid=0，3/3 |
| `ktool3 sh -c 'id; pwd'` | uid=0，pwd=/ |
| 内核 `c0012164` | `0200000a` = 原值 `0x0a000002`（**没动过**） |

对照实验：

| 做法 | 结果 |
|---|---|
| 旧版（不 chdir），从 `/data/local/tmp` 启动 | `Permission denied` |
| 旧版（不 chdir），`cd /` 后启动（cwd=/） | `Permission denied` |
| 新版，子进程 `chdir("/")` | **成功** |

`dmesg` 里的失败证据：

```
Restricted making process. PID = 11463(sh) PPID = 11444(ktool2)
```

被拦的是 **sh 自己**（不是它要 exec 的 id），PID 与父进程打印的 `[+] child pid` 完全一致。

## 4. 尚未完全定论的环节：`chdir`

**事实**：
- 子进程不 `chdir` → 必失败（多轮验证）
- 子进程 `chdir("/")` → 必成功（4/4）
- 但把启动目录 `cd /` 后仍失败，说明**不是简单的路径前缀比较**

**已确认的**：第二次 `sec_check_execpath` 的第一个参数不是 `current->mm`，而是 `current->0x1ec`（检查块 `c0012308` 处 `ldr r0,[r0,#0x1ec]`）。这个字段与路径解析上下文有关，`chdir` 会重置它。

**未确认的**：`0x1ec` 究竟对应 `task_struct` 的哪个成员，以及 `chdir` 具体改变了它的什么内容。`init_task` 的该字段为 0（内核线程没有 fs），像是 `fs_struct *`，但无法解释"cwd 已是 / 仍失败"。

**工程取舍**：机制没吃透，但行为可复现。这一条如实记录，不编原因。

---

## 5. 与旧方案对比

| | 旧版（改 text） | 新版（父子进程） |
|---|---|---|
| 内核代码段 | 写 4 字节 | **不动** |
| I-cache 风险 | 有（补丁可能不生效） | 无 |
| 需要 ptrace | 否 | 是（`shell → shell:process ptrace` 已确认允许） |
| 需要 chdir | 否 | 是 |
| 进程模型 | 父进程直接 exec 成 sh | fork 子进程 sh + 父进程 wait |
| 交互式 shell | 支持 | 支持（父进程负责保活 adb 会话） |
| 稳定性 | 高 | 4/4（样本偏少） |
| ktool 退出后 | sh 就是原进程 | 父进程等 sh 退出后一起结束 |

## 6. 用法

```bash
adb push ktool /data/local/tmp/ktool
adb shell chmod 755 /data/local/tmp/ktool

adb shell /data/local/tmp/ktool sh                        # 交互式 root shell
adb shell "/data/local/tmp/ktool sh -c 'id; ls /data/data'"
```

注意：
- `chdir("/")` 是子进程做的，只影响那个 shell 的初始 cwd；要回原目录请自己 `cd`
- 每次运行都会重写一次 `permissive_map`（幂等）
- 内核 text、`selinux_enforcing` 全程不碰
- 彻底恢复仍然靠重启（`permissive_map` 清零后，已缓存的 permissive 决策要重启才失效）

## 7. SuperSU 的支持范围

| 项 | 事实 |
|---|---|
| 最后版本 | **2.82.1**，2018-01-02 |
| 完整支持 | Android 4.x – 7.1（Nougat） |
| 部分支持 | Android 8.0 – 9（Pie） |
| 不支持 | Android 10 及以上 |
| 归属变更 | 2015 年 Chainfire 卖给 CCMT；2017 年 Chainfire 退出开发；2018 年从 Play 商店下架 |

**对三星有专门处理**：SuperSU 自带 `supolicy` / `libsupol`，会在运行时往已加载的 `policydb` 注入规则，绕过 Samsung 的 SELinux 限制；2.82 的更新日志里也有"禁用三星 KNOX 弹窗"这类选项。

**但这台机器上仍然用不了**，三条独立原因：

1. `CONFIG_ALWAYS_ENFORCE` 让 `setenforce 0` 变成死代码（已实测），而 SuperSU 的安装脚本依赖这一步
2. 本机策略里**没有 `su` 进程域**，只有 `su_exec` 文件类型；`supolicy` 需要匹配 Samsung 的 policydb v26 格式，2015 年的 libsupol 大概率不认
3. 安装要写 `/system`（本机可以，无 verity）**或者改 boot ramdisk 做 systemless**（后者会烧 eFuse）

所以 SuperSU 的问题是"装不上、装上也起不来"，不是"版本不支持 5.0.1"——它支持 5.0，只是不支持这台机器被 Samsung 改过的策略模型。
