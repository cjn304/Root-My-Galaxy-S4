# P4.32 S4 的 WARN-%p 泄漏通道：实测否决

日期：2026-10-22
结论：**这条路不可行，而且不是"难"，是结构性的**。原因不是缺泄漏，而是**触发路径在
`pi_lock` 临界区里 BUG，线程一死这把真锁永久泄漏，约 27 秒后 softlockup 必 panic**。

---

## 一、先确认前提：打印机是真的

模块加 `warntest`（只 WARN，不杀进程），实测输出：

```
------------[ cut here ]------------
WARNING: at .../ktool_mod.c:241 ktool_write+0x560/0x84c [ktool_mod]()
ktool warntest: stack=d35e9ebc marker=feedface
Modules linked in: ktool_mod(O) [last unloaded: ktool_mod]
Backtrace:
...
```

要点：
- **正文完整落盘**，`%p` 打的是原始栈地址（3.4 只有 `%pK` 走 kptr_restrict）
- `dmesg_restrict` 在这台机不存在，shell 就能读
- `/proc/last_kmsg` 存在（root 可读），重启后能取证

再确认 BUG 的杀伤范围（模块 `bugtest`）：

```
ktool bugtest: stack=<addr>
kernel BUG at ...ktool_mod.c:241!
Internal error: Oops - BUG: 0 [#1] PREEMPT SMP ARM
→ 调用线程收到 SIGSEGV，内核 uptime 继续涨，taint=DIE
```

**process context 下的 BUG 只杀线程，机器能活** —— 前提 `panic_on_oops=0`。

到这里，引文的核心判断（"WARN 会打出 entry 地址，oops 只杀线程"）**成立**。

---

## 二、但是：链内 BUG 会带走一把真锁

用 NOSPRAY 模式做对照（**完全不喷伪造数据**，只让 futex 链走起来）：

```
[1901.005228] ------------[ cut here ]------------
[1901.005372] kernel BUG at kernel/rtmutex_common.h:74!
[1901.006416] PC is at rt_mutex_adjust_prio_chain+0x428/0x42c
[1901.007894] Flags: NzCv  IRQs off  ...  r4: ddec5940  r5: ddec5cdc

[1928.024893] BUG: soft lockup - CPU#0 stuck for 22s! [ms:9697]
[1928.025964] PC is at __raw_spin_lock_irqsave+0x9c/0xc0
[1928.026890] r4: e6906010        ← 同一个 pi_lock
[1928.11    ] Kernel panic - not syncing: softlockup: hung tasks
```

链条：

1. `rt_mutex_adjust_prio_chain()` 全程持 `task->pi_lock`（raw spinlock，IRQs off）
2. 链不一致 → `rtmutex_common.h:74` 的 `BUG_ON` 命中 → oops → **线程就地死掉**
3. `raw_spinlock` 没有 owner 记录，没人能替它解锁 → `e6906010` 永久锁死
4. 其它线程（这里是主线程）在同一个 pi_lock 上自旋 → 22 秒 softlockup → panic

**关键：这次连一字节伪造数据都没写（NOSPRAY）。** 说明挂的原因不是"spray 没落准"，
而是**这条 bug 的报错点本身就在锁里**。

---

## 三、地址复用：同启动成立，跨启动不成立

用 `warntest`（打印本线程内核栈地址）测：

| 场景 | 结果 |
|---|---|
| 干净线程退出 → 新线程 | 8 轮里 6 轮连续命中同址（`c79c1ebc`×3 → `e42fdebc`×5） |
| **oops 打死线程 → 新线程** | 3 轮里 2 轮命中同址（round1/2 都是 `d1643ebc`），机器存活 |
| **跨启动** | ❌ 三次启动分别 `c79c1ebc` / `d1643ebc` / `d364debc` —— 页号不同 |

所以：
- "同一次启动内，泄漏值给下一个线程用" —— 成立
- "泄漏一次（代价=重启），下次启动用这个地址" —— **不成立**

而第一节已经证明：每次触发都会在 27 秒内 panic。两者一叠加，**泄漏和复用无法接上**：
拿到地址的那次启动马上要死，下次启动地址又变了。

## 四、这推翻了什么、保留了什么

| 论断 | 原判断 | 实测后 |
|---|---|---|
| 格式串带 entry 的 %p | 成立 | ✅ 成立（kernel.raw 0x96a648 处原文） |
| `%p` 不打码 | 成立 | ✅ 成立 |
| 失败路径是 WARN + return | ❌ | 实际是 WARN 后紧跟 `BUG()`（`CONFIG_SEC_DEBUG_LIST_PANIC=y`） |
| "oops 只杀线程，A 的栈还在" | 部分 | 线程确实只死自己，但**内核栈已释放**；且链内 BUG 会泄漏 pi_lock → 整机 27s 后 panic |
| 泄漏值可复用 | 假设 | 同启动 ✅ / 跨启动 ❌ |
| 一小时能验证 | ❌ | 已用 40 分钟否掉；不需要 4-6 小时了 |

**P4.13 的"S4 死"结论不动，但死因要改写**：
不是"缺一个栈地址泄漏"，而是"**泄漏通道与致命锁泄漏绑在同一条指令流上**"。
换句话说，就算白送你一个栈地址，这条路也走不通——因为每次走到 `__list_del_entry`
的检查点，都已经在 `pi_lock` 里了，报错即锁死。

## 五、对后续目标（S5/S6 或别的机型）的判据补充

原来只看"目标机有没有编译 list 检查"。现在要加两条：

1. **报错点是否在持锁区内**：rtmutex 的全套路径（`adjust_prio_chain` /
   `task_blocks_on_rt_mutex`）都在 `pi_lock` 下，所以**任何 rtmutex 型的 bug，用
   "让它 BUG 来泄漏"都是自杀**。要换乘方（如 `rb_erase`，4.x 的 waiter）才可能避开。
2. **panic_on_oops 是否可置 0** 且 **oops 后锁状态是否可恢复**：光有 0 不够，
   raw spinlock 不跟踪 owner，死在临界区就是永久死锁。

## 六、副产品：一个交付态 bug

这次开机 `/dev/ktool` 的标签偶发变成 `u:r:platform_app:s0`（正常应是
`u:object_r:null_device:s0`），导致 `ctx`/`ish` 写不进去 —— **su 会静默失效到下次重启**。

原因：模块 init 在 13.7s 跑 `ktool_relabel()`，此时 `/dev/null` 的 security blob 可能
还没定型（策略刚加载完），拷过来的就是错的。

处置（待做）：`ktool_relabel()` 改成延迟重试（如 5s 后 workqueue 再来一次），
或 boot 脚本 insmod 后补一条 `chcon u:object_r:null_device:s0 /dev/ktool`。
