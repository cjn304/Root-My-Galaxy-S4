# P4.8 深挖 KNOX exec 检查：`0x1ec` 是什么，以及一个新的矛盾

**时间**：2026-10-19 19:30
**结论**：`0x1ec` 确认是 `mm`。但由此推下去，检查逻辑与实测结果对不上——这个矛盾没解开。同时发现不打补丁的方案**不稳定**。

---

## 1. `0x1ec` = `mm`，证据链

### 1.1 静态：检查块的第二次调用读的是它

```
c0012304  ldr  r0, [sl, #0xc]       ; sl = thread_info，[sl+0xc] = current
c0012308  movw r1, #0x1458
c001230c  movt r1, #0xc094          ; r1 = "/data/"
c0012310  ldr  r0, [r0, #0x1ec]     ; r0 = current->0x1ec
c0012318  bl   sec_check_execpath
```

### 1.2 动态：init 与 init_task 的对照

| 进程 | `+0x1ec` | `+0x1f0` |
|---|---|---|
| `init`（pid 1） | `0xe5842000` | `0xe5842000` |
| `init_task`（swapper） | `0` | `0` |

普通进程两者相同（`mm` 与 `active_mm` 指向同一对象），内核线程两者都是 NULL。**这是 `struct mm_struct *mm, *active_mm` 的典型形态。**

### 1.3 旁证：`get_mm_exe_file` 的偏移

```
c00328d0  T get_mm_exe_file
c00328dc  add r5, r0, #0x3c     ; &mm->exe_file_lock
c00328e8  bl  down_read
c00328ec  ldr r4, [r4, #0x188]  ; mm->exe_file
c00328f8  add r3, r4, #0x20     ; &file->f_count，atomic_inc
```

### 1.4 完整链路

```c
sec_check_execpath(mm, "/data/")
  → file = get_mm_exe_file(mm)          // mm->exe_file，持引用
  → if (!file) { printk("Cannot get exe from task->mm."); return 0; }   // 放行
  → d_path(&file->f_path, buf, 4096)    // file+8 是 f_path
  → strncmp(buf, "/data/", min(strlen(buf), 6))
  → 相等返回 1（拒绝），不等返回 0（放行）
```

`strncmp @0xc0253f48` 是标准实现（逐字节、最多 n 字节、相等返回 0），没有被改过。

---

## 2. 实测：`mm->exe_file` 指向的确实是 sh

在 `waitpid` 拿到 SIGTRAP 后、改 cred 之前，直接读子进程的内存：

```
self  mm=e56eba40 exe=c7cde840 | child mm=e56eb880 exe=e3b9da80
mnt=e6922310 dentry=e502b908 len=2 ptr=e502b92c name=sh
```

- 子进程 `mm->exe_file` 非 NULL，且与父进程的 file 对象**不同**（`e3b9da80` vs `c7cde840`）→ 不是继承来的
- `f_path.mnt` 有效，`f_path.dentry` 有效
- dentry 的 `d_name` 是 **"sh"**（len=2）

`/proc/<pid>/exe` 的 readlink 也返回 `/system/bin/sh`。

**按这条链路推，`d_path` 应该返回 `/system/bin/sh`，不含 `/data/`，检查应当放行。**

---

## 3. 矛盾：同一个 sh，`cat` 放行，`id`/`ls` 被拒

同一轮测试，三次都是 `ktoolc sh -c '<cmd>'`，三次都打印 `[+] child pid ... -> uid 0`：

| 命令 | 结果 | dmesg |
|---|---|---|
| `id` | `Permission denied` | `Restricted ... PID=12306(sh)` |
| `cat /proc/version` | **正常输出内核版本** | **无记录** |
| `ls /` | `Permission denied` | `Restricted ... PID=12362(sh)` |

三次的 `mm->exe_file` 都是同一个（dentry name = "sh"），`mm` 也没变。

**如果 `d_path` 返回 `/system/bin/sh`，三次都该放行。实测两次被拒。**

`dmesg` 里没有 `Cannot get exe from task->mm.`，也没有 `Error get path..`，说明 `get_mm_exe_file` 和 `d_path` 都"成功"了。

**唯一的解释是 `d_path` 拼出来的字符串确实以 `/data/` 开头——但从 dentry 名和 mnt 看又说不通。**

---

## 4. 还没排除的方向

`d_path` 走的是 `prepend_path(path, &root, ...)`，其中 `root` 来自 **`current->fs->root`**。如果 sh 的 `fs->root` 不是 `/`，路径拼接会受影响。

但要读 `fs` 得先知道它在 `task_struct` 里的偏移。试了 `+0x1f4`/`+0x1f8`，读出来都是 `1`，不是指针。`fs` 的偏移还没定位到。

另外，`d_path` 开头会检查 `dentry->d_op->d_dname`（`[dentry+0x54]`），伪文件系统会走自定义逻辑。`/system` 是 ext4，理论上没有 `d_dname`，但没实测。

**这两点是目前唯一没查的地方。**

---

## 5. 更重要的发现：不打补丁的方案不稳定

| 时间 | 版本 | chdir | 结果 |
|---|---|---|---|
| 19:04–19:06 | ktool3 | 有 | `sh -c 'id; ...'` **4/4 成功** |
| 19:15 | ktooln | 无 | 失败 |
| 19:15 | ktoolc | 有 | 失败 |
| 19:25–19:30 | ktoolc/ktoolx | 有 | 连续 6 次全失败 |

**同样的 chdir、同样的父进程模型，19:04 能过、19:15 之后过不了。**

这说明之前那次 4/4 不是"方案成立"，而是**当时的某个状态刚好让检查放行了**。可能是 AVC 缓存、内存布局，或者别的。

**结论：不打内核补丁的路线不可靠，不能作为主路径。**

---

## 6. 建议

| 方案 | 可靠性 | 代价 |
|---|---|---|
| **打 4 字节补丁**（旧方案） | 高（多轮实测） | 改内核 text，I-cache 未定义行为（最坏是补丁不生效，不崩） |
| 父子进程 + chdir（本报告） | **低**（同一份代码时好时坏） | 不改 text，但结果不可预测 |
| `ktool ls / cat / cp`（内置命令） | 高 | 不能执行任意程序，只能读写文件 |

**现阶段应该用第一条。** 第三条作为日常读文件的快捷方式。

如果要把第二条做可靠，必须先解开第 3 节那个矛盾——否则只是碰运气。

---

## 7. 顺带修正 P4.7 的两处结论

1. P4.7 说「`chdir("/")` 是必要条件，4/4 成功」——**不成立**。19:15 之后带 chdir 的版本连续失败。
2. P4.7 说「第二次检查看 cwd」——**不成立**。`0x1ec` 是 `mm`，不是 `fs`。
