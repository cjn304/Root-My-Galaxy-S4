# P2.6 infoleak 全量扫描报告

**目标**：为 CVE-2026-43499 寻找「同一次开机内的内核栈地址泄漏」，
用以补上 `plist_del(&waiter->list_entry)` 所缺的自指地址。

**结论：扫描完成，未找到可用的栈地址泄漏。CVE-2026-43499 在本机的链路正式判定为死。**

---

## 1. 扫描工具

`src/leakscan.c`（静态交叉编译，跑在设备上）：
- 递归遍历指定目录，读取每个普通文件（最大 256 KB，`O_NONBLOCK`）
- 提取所有 8 位十六进制串，筛选落入内核直接映射区 `[0xc0000000, 0xe7800000)` 的值
- 输出 `路径|地址|原始行`

跳过的危险文件：`mem` / `pagemap` / `kpagecount` / `kpageflags` / `kmsg` / `sysrq-trigger` / `clear_refs`。

## 3. 关键发现一：`%p` 与 `%pK` 行为不同

这是整轮扫描最重要的技术事实。

| 格式符 | 行为 | 证据 |
|---|---|---|
| `%p` | **打印真值，不做任何限制** | `binder/state` 输出 `d e3914300`、`buffer ecf00028`（真实内核地址） |
| `%pK` | **被清零** | `/proc/self/stack` 输出 `[<00000000>] save_stack_trace_tsk+0x0/0x98`；符号名保留、地址为 0 |

即 `kptr_restrict >= 1`，但 3.4 的 `%p` 走的是 `pointer()` 而非 `restricted_pointer()`，
不受 `kptr_restrict` 影响（哈希化 `%p` 是 4.15 才引入的）。

**这直接把问题收缩成一句话**：只要内核里存在一条用**裸 `%p`** 打印栈地址的 `printk`，就能拿到。

---

## 4. 关键发现二：debugfs 是完全打开的（大量堆地址）

`/sys/kernel/debug` 对 shell 可读，且泄漏真实内核堆地址。

### binder（最丰富）

| 文件 | 内容 | 示例 |
|---|---|---|
| `binder/state` | `ref N: desc N node N s N w N d %p` | `d e3914300`、`d c7127ac0` |
| `binder/proc/<pid>` | 同上（按进程） | `proc/3170` 单个文件 396 处 |
| `binder/transactions` | `buffer N: %p size ...` | `ecf00028`、`ec3000b8` |

其中 `%p` 是 `ref->node`（`struct binder_node *`），`buffer` 是 binder 的内核映射区地址。

**可利用性**：这些都能通过 shell 侧的 binder 操作**自己制造**——创建一个 node 就能在
debugfs 里看到它的内核地址。等于「可控对象的已知内核地址」。

### 其他子系统

- `pm_qos`：`c0c0546c`、`c1132030`（`.data` 段结构地址）
- `sync`：`e43c6400`、`c4ceb700`（sync fence 堆对象）

### 为什么这些不够

全部是**堆/静态数据地址**。本链缺的是**内核栈地址**（`waiter` 位于 A 线程的内核栈上）。
堆地址与栈地址之间没有任何可推导关系：内核栈由伙伴系统按 order-1 直接分配，
binder node / ref / buffer 分别来自 slab 与 vmalloc，三者互不相邻。

## 5. 关键发现三：tracing 被权限封死

| 文件 | 权限 | 可写 |
|---|---|---|
| `tracing/tracing_on` | `-rw-rw-r-- root:shell` | **是** |
| `tracing/trace` | `-rw-rw---- root:shell` | **是** |
| `tracing/trace_marker` | `--w--w--w-` | **是**（只能写） |
| `tracing/set_event` | `-rw-r--r-- root:root` | 否 |
| `tracing/current_tracer` | `-rw-r--r-- root:root` | 否 |
| `tracing/events/*/enable` | `-rw-r--r-- root:root` | 否 |

**矛盾点**：`tracing_on` / `trace` 给了 shell 组，但**唯一能选择记录哪些事件的开关**
（`set_event`、`events/*/enable`）全部是 root only。

实测：
- 扫描全部 `events/*/enable`，**没有一个默认启用**
- `trace` 缓冲区 `entries-in-buffer: 0/0`（空）
- 无法自行开启任何 tracepoint

所以即使 `events/kmem/mm_page_alloc` 存在（其 `print fmt` 会输出 `page=%p pfn=%lu order=%d`，
若能开启即可直接定位所有 order-1 分配 = 内核栈），也**开不起来**。

## 6. 关键发现四：唯一打印栈顶的路径被 panic 封死

从 `kernel.raw` 提取全部 545 个含裸 `%p` 的格式串，其中与栈相关的只有两条：

### (1) `Process %.*s (pid: %d, stack limit = 0x%p)` —— 唯一有价值的

位置：`arch/arm/kernel/traps.c:252`，在 `__die()` 内：

```c
printk(KERN_EMERG "Process %.*s (pid: %d, stack limit = 0x%p)\n",
	TASK_COMM_LEN, tsk->comm, task_pid_nr(tsk), thread + 1);
```

`thread + 1` = `thread_info + 1` = **内核栈顶**，正是 `waiter = 栈顶 - 0x208` 所需的唯一数值。
而且是**无条件打印**的（不受 `user_mode(regs)` 判断影响）。

**但 `__die()` 只被 `die()` 调用，而 `die()` 的结尾是：**

```c
#ifdef CONFIG_SEC_DEBUG
	if (in_interrupt())
		panic(...);
	if (panic_on_oops)          // ← 本机 = 1
		panic(...);
#endif
```

`panic_on_oops` 实测：

```
-rw-r--r-- root root  /proc/sys/kernel/panic_on_oops
值 = 1
echo 0 > ...  →  Permission denied
```

**结论**：触发 `__die` 必然 panic → 重启 → 栈地址重新随机化 → 打印出的那个地址失效。
且 `die()` 只在内核态异常时调用（用户态异常走 `arm_notify_die` 的 `force_sig_info` 分支，
不进 `__die`），无法用「用户态异常 + 捕获信号」的方式绕过。

### (2) `Backtrace aborted due to bad frame pointer <%p>`

`dump_stack()` 的路径，但 `dump_stack()` 自己先做 `verify_stack(fp)`，
fp 无效时打印的是 `invalid frame pointer 0x%08x` 并**不进入** `c_backtrace`；
能进这条分支时 fp 已通过校验，且打印的是回溯链上某一帧的 fp，
与栈顶的偏移随调用深度变化，**无法反推栈顶**。

### (3) WARN 不是出路

3.4 **没有 `panic_on_warn` 这个接口**（该功能 v4.0 才引入），所以 WARN 确实不 panic。
但 `WARN → warn_slowpath_common → dump_stack()` **不打印栈地址**，只打印返回地址链
（都是内核代码地址，而代码地址我们已有 kallsyms 全表）。
实测过 8 种 PI-futex 边界用法，也未触发任何 WARN。

## 7. 其他确认无效的路径

| 路径 | 结论 |
|---|---|
| `/proc/self/stack` | `%pK` 清零，符号名保留 |
| `/proc/self/stat` 的 kstkesp/kstkeip | 用户态 SP/PC（`0xBEEA…` / `0xB6F…`），非内核栈 |
| `/proc/self/wchan` | 输出 `0` |
| `/proc/vmcoreinfo`、`/sys/kernel/vmcoreinfo` | 不存在 |
| `/proc/<pid>/syscall` | 用户态寄存器 |
| `kptr_restrict` / `dmesg_restrict` | 文件本身读不了（权限被收紧） |
| `print-fatal-signals` | `root:root 0644`，不可写；且 `show_regs` 打印的是用户态寄存器 |
| SysV IPC stat 结构 | `msgctl_stat`/`shmctl_stat`/`semctl` 均有 `memset` |
| `statfs` 的 `f_spare` | `fs/statfs.c` 显式清零 |
| 3.4 的 `fdinfo` | 只有 `pos` / `flags`，不含 epoll 内部结构 |
| `tracing` 的 `printk_formats` | 空 |

## 8. 最终结论

**本机在同一次开机内，不存在任何 shell 可达的内核栈地址泄漏。**

推导链：

1. 需要 `waiter` 地址 → 需要 A 线程内核栈顶
2. 唯一直接输出栈顶的接口是 `__die` 的 `stack limit = 0x%p`
3. `__die` 只在 `die()` 里调用，`die()` 在 `panic_on_oops=1` 下必然 panic
4. `panic_on_oops` 是 `root:root 0644`，shell 改不了
5. panic = 重启 = 栈地址重随机化
6. 其余所有泄漏面（`/proc` 全量、debugfs、tracing、dmesg）都只给堆地址或代码地址

因此 **CVE-2026-43499 在这台 GT-I9500（3.4.5-6264821 + CONFIG_DEBUG_LIST + CONFIG_SEC_DEBUG_LIST_PANIC）
上确认无法提权**，此前的「两道门互补」结论由此得到闭环验证。

## 9. 本轮留下的可复用资产

虽然不是本链需要的，但以下能力已实测可用，将来若有 **需要堆地址** 的漏洞可以直接接上：

1. **`leakscan` 工具**（`src/leakscan.c`）：任意目录递归扫内核地址，静态 ARM 二进制。
2. **debugfs 堆地址泄漏面**：`/sys/kernel/debug/binder/*` 对本进程创建的
   `binder_node` 会直接打印其内核地址，等于「可控对象 + 已知地址」。
3. **`%p` vs `%pK` 的精确行为差异**（§3）：以后找泄漏时只看裸 `%p`，不必浪费时间在 `%pK` 上。
4. **`arch/arm/kernel/traps.c:252` 的 `stack limit = 0x%p`**：若某天能改 `panic_on_oops`
   （例如通过其他原语），这一行立刻变成可用的栈地址源。
5. **tracing 权限图谱**（§5）：`tracing_on`/`trace` shell 可写但事件开关 root only，
   这是一个容易被误判为「可用」的坑。
