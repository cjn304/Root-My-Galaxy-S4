## 2. 代码

```c
int main(int argc, char **argv)
{
	int caller = getuid();
	int fd, i;

	if (caller == 0)
		goto run;

	fd = open("/dev/ktool", O_WRONLY);
	if (fd < 0) { ... return 1; }
	if (write(fd, "ish", 3) != 3) { ... return 1; }
	close(fd);

	if (!is_allowed(caller)) {
		fprintf(stderr, "su: uid %d not in %s\n", caller, ALLOW_FILE);
		return 1;
	}

run:
	for (i = 3; i < 256; i++) close(i);

	if (argc >= 3 && strcmp(argv[1], "-c") == 0)
		execl("/system/bin/sh", "sh", "-c", argv[2], NULL);
	else if (argc >= 2)
		execvp(argv[1], argv + 1);
	else
		execl("/system/bin/sh", "sh", NULL);

	return 127;
}
```

`is_allowed()` 逐行读 `/data/system/su_allow`，每行一个 uid，`#` 开头忽略。

编译：`arm-none-linux-gnueabihf-gcc -static -O2 -s -o su su.c` → 332,880 B（glibc 静态）。

## 3. 部署

`src/deploy_su.sh`：

```sh
echo ish > /dev/ktool                     # 提权到 init_shell + uid0
mount -o rw,remount /system
cp /data/local/tmp/su /system/xbin/su
chmod 755 /system/xbin/su
chcon u:object_r:su_exec:s0 /system/xbin/su
mount -o ro,remount /system
echo 2000 > /data/system/su_allow
chmod 600 /data/system/su_allow
```

`chcon` 一次成功（`init_shell → su_exec:file {relabelto}` 在策略里）。

## 4. 实测输出

### 4.1 shell 域

```
$ /system/xbin/su -c id
uid=0(root) gid=0(root) context=u:r:init_shell:s0
su_rc=0
```

### 4.2 app 域（关键）

用模块的 `ctx` 把 shell 进程伪造成 `untrusted_app` 域，再调 su：

```
$ sh -c 'echo "ctx u:r:untrusted_app:s0" > /dev/ktool; \
         echo APP_CTX=$(cat /proc/self/attr/current); \
         /system/xbin/su -c id'

APP_CTX=u:r:untrusted_app:s0
uid=0(root) gid=0(root) context=u:r:init_shell:s0
app_su_rc=0
```

三件事同时被证明：
1. `untrusted_app → su_exec:file execute` —— 真的能 exec；
2. `untrusted_app → null_device:chr_file write` —— 真的能写 ktool；
3. 提权后是 `init_shell`，能读白名单、能 exec 命令。

### 4.3 白名单拒绝

```
$ su -c 'echo 99999 > /data/system/su_allow'    # 先把自己踢出名单
$ /system/xbin/su -c id
su: uid 2000 not in /data/system/su_allow
deny_rc=1
```

**注意一个操作性坑**：把 uid 踢出名单后，su 自己也就进不去了，无法用 su 改回来。
恢复要用 ish 直连：

```sh
sh -c 'echo ish > /dev/ktool; echo 2000 > /data/system/su_allow'
```

## 5. 踩到的坑：`ktool unperm` 会写坏 permissive_map

`ktool.c` 的常量注释与实际用途不一致：

```c
#define PERM_MAP	0xc0c4efccUL	/* 注释说 permissive_map */
#define PERM_BASE	0xc0b9ec3cUL	/* 注释说 modprobe_path */
```

但 `do_permissive()` 输出的是 `permissive_map: node=c0b9ec3c` —— **它一直在写 `PERM_BASE`**。
而 `do_unperm()` 把 `PERM_BASE` 那 256 字节填成字符串 `/sbin/modprobe`：

```c
memset(mp, 0, sizeof(mp));
strcpy((char *)mp, "/sbin/modprobe");
kwrite_verify(PERM_BASE, mp, 256);     // ← 把 ebitmap 节点写成了 ASCII
```

后果：`permissive_map` 的 ebitmap 结构被 ASCII 字节覆盖，之后：
- `cat /dev/ktool` 仍正常（读路径不受影响）；
- `echo x > /dev/ktool` 一律 `Permission denied`，**连重新 `ktool permissive` 也救不回来**；
- 必须重启。

**处置**：
1. 不要用 `ktool unperm`（这一版的实现有 bug）；
2. 需要 enforcing 就用重启，别在原地清；
3. 真要修，`do_unperm` 应该只清 `policydb.permissive_map` 的 ebitmap 头（`map`/`highbit` 两个 u32），
   而不是往节点里写字符串。

## 7. 接 Superuser APK 的改造点

现在的 `is_allowed()` 是白名单。换成 APK 只需改这一个函数 + 前面加一段弹窗逻辑：

```
main:
  caller = getuid()
  if (白名单命中)          → ish → exec        （快路径，不弹窗）
  else if (需要弹窗)
       fork 子进程 A（留在原域）
       A: am start -n me.phh.superuser/com.koushikdutta.superuser.RequestActivity \
              --ei uid <caller> --es command <cmd>
       主进程: ish
       主进程: 轮询 /data/data/me.phh.superuser/databases/su.sqlite
                select policy, until, command from uid_policy where uid=?
                5 秒超时 → deny
       allow → exec
```

三个待办：
1. sqlite 静态链接（用 phh 源码里的 `sqlite3/sqlite3.c`）；
2. `am start` 的参数与 APK 实际组件对齐（类全名仍是 `com.koushikdutta.superuser.RequestActivity`，
   applicationId 是 `me.phh.superuser`）；
3. 先确认那个 APK 能装上、能弹窗，再谈协议。
