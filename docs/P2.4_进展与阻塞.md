# P2.4 进展与当前阻塞（GT-I9500 / CVE-2026-43499）

> 结论先说：**悬空指针已经完全受控（三次独立复现已证实），但卡在 `CONFIG_DEBUG_LIST` 的
> 链表一致性校验上，需要知道 A 线程的内核栈绝对地址才能继续。**

---

## 一、已经证实的（都有设备实测证据）

| # | 结论 | 证据 |
|---|---|---|
| 1 | CVE 路径可稳定触发 | `CMP_REQUEUE_PI` 返回 `errno=35 (EDEADLK)`，且原子 trylock 未短路（u2 tid≠A tid） |
| 2 | **悬空 `pi_blocked_on` 在 A 返回后依然存在** | 崩溃时 A 的 task `state=0`(RUNNING) 但 `pi_blocked_on` 非空，指向 A 栈上已死帧 |
| 3 | waiter 绝对地址规律 | `waiter = kernel_stack_top - 0x208`，五次崩溃全部吻合（栈内偏移恒为 0x1DF8，栈基址每次启动不同） |
| 4 | syscall entry frame = 0x58 | 由 #3 与反汇编链长互相印证 |
| 5 | **链走真的读到了我们喷雾的 `waiter->lock`** | 崩溃寄存器 `r8` = 假锁地址：`0x20000100`、`0x3ffffbc7`(衍生)、`0x00010000`，三次不同载荷三次命中 |
| 6 | `_raw_spin_trylock` 在假锁上执行成功 | 崩溃点从 `trylock` 推进到 `plist_del`（`r6=0x00010008`=假 wait_list） |

## 二、喷雾几何（实测标定，可直接复用）

| syscall | 栈缓冲区绝对深度 | 覆盖 waiter 区间 | 副作用 |
|---|---|---|---|
| `recvmmsg` | `iovstack` = 0x1A0（64B） | `+0x10 … +0x4f` | 被调帧把 `+0x08/+0x0c` 抹成 0 |
| `sendmmsg` | `iovstack` = 0x1E0（64B） | `-0x30 … +0x0f` | 被调帧更深，不碰 waiter |
| `pselect6` | `stack_fds` = 0x190（6×size） | `+0x20 …` | `fd_set_bits` 6 指针压在 `+0x08…+0x1f` |
| `select` | 0x178 | `+0x38 …` | — |
| `poll` | 0x3B4 | 太深 | — |

`pselect6` 精确参数：`size = ((n+31)/32)*4`；`n=64 → size=8` → `in@+0x20`、`out@+0x28`，
因此 `out[0]=+0x28=task`、`out[1]=+0x2c=lock`（已验证 `r8=0x00010000`）。`n=65` 会变成 size=12，错位 4 字节。

## 三、阻塞点（硬墙）

链表重排代码在 `rt_mutex_adjust_prio_chain`：

```c
lock = waiter->lock;
if (!raw_spin_trylock(&lock->wait_lock)) { ... goto retry; }
if (lock == orig_lock || rt_mutex_owner(lock) == top_task) { ... goto out; }
top_waiter = rt_mutex_top_waiter(lock);        /* BUG_ON(w->lock != lock) —— 已通过 */
plist_del(&waiter->list_entry, &lock->wait_list);   /* ← 死在这里 */
```

`__list_del_entry` 的校验（`lib/list_debug.c:71`）：

```c
	if (WARN(prev->next != entry, ...) || WARN(next->prev != entry, ...)) {
		if (list_debug) BUG();
		return;
	}
```

`entry = &waiter->node_list = waiter + 0xc` 是**内核栈绝对地址**。

- `CONFIG_SEC_DEBUG_LIST_PANIC=y` → `list_debug = 0x100`（非 0）→ 任何不一致直接 `BUG()` → **panic**，没有"仅 WARN"的软路径
- `list_debug` 是 `static int`，无 `module_param`，用户态无法置 0
- `node->list_entry` 的自指残留（`+0x04/+0x08 = waiter+4`，`+0x0c/+0x10 = waiter+0xc`）本来是
  `remove_waiter` → `plist_del` → `list_del_init` 留下的、天然一致的，**但只要喷雾覆盖 `+0x28/+0x2c`，
  就必然会顺手破坏 `+0x04…+0x1f`**（帧布局决定），一致性随之丢失

## 四、可行的三条路

| 路 | 做法 | 成本 | 成功率 |
|---|---|---|---|
| **B（推荐先试）** | 找一个"用户栈拷贝起点恰好 = waiter+0x2c(深度0x184)"的阻塞 syscall —— 只写 `lock`，其余 44 字节保留内核自指残留 → `plist_del` 变纯空操作 → 进入 owner 分支拿到**双任意写** | 脚本扫描全部 syscall 的栈拷贝，1 次上车验证 | 中低（对齐很苛刻，但一旦命中即打通） |
| A | 先搞一个内核栈地址泄漏（本机 shell 无 `/proc/*/stack`、`kptr_restrict` 生效、无 perf/debugfs） | 需另找 infoleak 或三星私有接口，投入大 | 未知 |
| C | 停在"任意指针解引用 + 条件写 1"原语，不冲 root | 0 | 拿不到 root |

> 另外确认了可重复触发通道：`setpriority()` → `rt_mutex_adjust_pi(A)` →
> `rt_mutex_adjust_prio_chain(detect=0, orig_lock=NULL)`，不需要重建 futex 拓扑，
> 适合做高频标定实验（但同样撞 `plist_del`）。
