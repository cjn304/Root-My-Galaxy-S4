## 2. 第一次尝试失败：`cred check FAIL +4=0`

v3 段第一次跑，三次 insmod 全部失败：

```
cred check FAIL +4=0
insmod_try0_rc=3
insmod_try1_rc=3
insmod_try2_rc=3
```

根因在 `ktool.c` 的 `do_root()`：

```c
/* 旧版 */
for (i = 0; i < 8; i++) {
    uint32_t v = *(uint32_t *)(b + 4 + i * 4);
    if (v != 0x7d0) { printf("cred check FAIL +%x=%x\n", 4 + i*4, v); return -1; }
}
```

`0x7d0 = 2000`，是 adb shell 的 uid，用来防误改。但 **sec-sh 脚本本身跑在 uid 0**，
这个校验必然失败——P4.11 当时就踩过同一个坑（那次改用 `w32` 绕过，没修根因）。

**修复**：首个字段必须是 `0` 或 `0x7d0`，其余 7 个必须与它一致。

```c
uint32_t expect = *(uint32_t *)(b + 4);
if (expect != 0x7d0 && expect != 0) { ... return -1; }
for (i = 0; i < 8; i++)
    if (*(uint32_t *)(b + 4 + i * 4) != expect) { ... return -1; }
```

这样既保留了"8 个 uid/gid 必须一致"的防呆，又允许 uid 0 场景。
killed 后重编（431,220 B），先在 uid 0 的 shell 域里验证通过，再替换 `/system/bin/ktool`。

## 3. 开机顺序（顺序不可变）

```sh
# /system/etc/init.sec.boot.sh 末尾（sec-sh: uid 0 + u:r:init_shell:s0）

/system/bin/ktool w32 c0c0ae28 2      # 1. lkmauth_bootmode = 2（BSS，每次归零）
/system/bin/ktool permissive          # 2. permissive_map 全 1
/system/bin/ktool pwn /system/bin/insmod /system/lib/modules/ktool_mod.ko
                                      # 3. 必须在 kernel 域加载
```

三条约束各自独立，缺一不可：

| 步骤 | 为什么不能省 |
|---|---|
| bootmode=2 | `lkmauth` 只在 `bootmode != BOOTMODE_RECOVERY` 时调用；不写就过不了 TIMA 的模块校验 |
| permissive | 策略里 `load_module` 的 allow 规则数为 **0**，只能靠 permissive 放行 |
| kernel 域 insmod | shell/init_shell 域第一次失败会缓存 DENIED，permissive 不刷新旧节点，必须换全新三元组 |

第 3 条是这轮最反直觉的一条：`ktool pwn /system/bin/insmod` 之所以能过，
不是因为 kernel 域有权限，而是因为 `(kernel_t, kernel_t, security, load_module)`
这个三元组**从没被检查过**，新建节点时才读 permissive_map。

## 5. 开机代价

`ktool` 每次调用都会跑一遍 exploit。v3 段里有三次（w32 / permissive / pwn insmod），
加上原有 2a 段的两次，**一次开机约 5 次 exploit，累计 20–40 秒**。

`sec-sh` 是 `oneshot` + `class main`，不阻塞 `boot_completed`，所以只是后台多花时间，
用户感知不明显。若要压缩，可给 ktool 加一个 `boot` 子命令，一次 exploit 做完三件事。

## 6. v4：压成一次 exploit（已生效）

原来的 5 次：旧 2a 段 2 次（permissive + exec patch）+ v3 段 3 次（bootmode + permissive + pwn insmod）。

新增 `ktool boot <module>` 子命令，一次 `do_root()` 之后连着做完：

```c
ktool boot /system/lib/modules/ktool_mod.ko
  → do_root()              // 一次 exploit，进程变 kernel 域 + uid0
  → bootmode = 2           // 8 字节写（kwrite 要求 len&7==0）
  → do_permissive()
  → do_patch_exec(1)       // 必须！否则下面 exec 会 EACCES
  → execv("/system/bin/insmod", {insmod, module})
```

开机日志：

```
uid now: 0/0/0
bootmode=2 (was 0)
permissive_map: node=c0b9ec3c highbit=1536
exec patch applied (0a000002 -> ea000047)
exec patch on
boot: exec insmod /system/lib/modules/ktool_mod.ko
boot_rc=0
ktool_mod 3479 0 - Live
su self test: uid=0 ... init_shell
```

### 两个坑

| 坑 | 现象 | 原因 |
|---|---|---|
| bootmode 写失败 | `kwrite: bad len 4` / `bootmode write fail` | `kwrite()` 要求 `len & 7 == 0`，必须写 8 字节，不能写单个 u32 |
| exec insmod 被拒 | `execvp errno=13` | `kernel` 域对 `system_file` 只有 `execute`、没有 `execute_no_trans`；必须先打 `c0012164` 的 exec patch（KNOX 分支），否则 exec 过不去 |

第二个坑解释了 P4.16 当时为什么能成功——那次前面跑过 `ktool patch`/`ktool sh`，patch 已经在内存里。

### 顺带查清的一件事：shell 域不能 exec su

```
shell         -> su_exec: getattr,ioctl,lock,open,read    ← 无 execute
untrusted_app -> su_exec: execute,execute_no_trans,...
init_shell    -> su_exec: execute,execute_no_trans,...
```

- **app 调 su**：enforcing 下就能过（走 `untrusteddomain → exec_type`）
- **adb shell 调 su**：enforcing 下过不去，必须 permissive

所以 P4.17 里 "shell 域 su -c id 成功" 是 permissive 的功劳，不是策略允许。
但目标场景是 app 调 su，这一条在 enforcing 下是成立的。
