# P4.45 semtimedop 路径：waiter->lock 变成 32 位全可控

日期：2026-10-22 23:22
设备：GT-I9500 / ja3g / 3.4.5-6264821

---

## 一、缘起：semop 路径的硬约束

P4.44 跑通 plist_del 之后，剩下的限制是：`waiter->lock` 只能编码 `0xXXXX0000`
（低 16 位恒 0），所以 `fake_lock` 必须 64KB 对齐。这条约束来自
`lock = ops[10].sem_num | ops[10].sem_op<<16` 而 **`sem_num` 必须为 0**。

先排除了 `nsems` 这条路：

```
$ cat /proc/sys/kernel/sem
250	32000	32	128
  ↑ SEMMSL=250   ⇒  sem_num 最多 249，lock 低 16 位仍然接近 0
```

然后换了个思路：**换 syscall 路径，让数组落点相对 waiter 平移**，从而改变
`waiter+0x2C` 落在 sembuf 的哪个字节上。

---

## 二、两条路径的数组落点（都实测）

| syscall | `fast_sops` 基址 | 与 waiter(0x1DF8) 的关系 |
|---|---|---|
| `semop` | `stack + 0x1DE8` | 数组 = waiter − 0x10 |
| `semtimedop` | `stack + 0x1DF8` | **数组 = waiter + 0x00** |

semtimedop 的测量（`wfind16 <pid> 0101`，标记 = `ops[1].sem_op`，位于数组+8）：

```
ktool: wfind16 pid=8885 stack=e46ea000 pat=0101
ktool:   HIT16 off=1e00 abs=e46ebe00      ← 0x1e00 - 8 = 0x1df8
ktool: wfind16 done hits=3
```

`semtimedop` 比 `semop` 深 0x10：它多了 `struct sem_queue queue`、
`struct timespec _timeout`、`jiffies_left` 等局部量。

---

## 三、semtimedop 的完整字段映射（实测回读）

`build_sops_semt()` 里把每个字段填成可识别的常数，然后在 A 阻塞时用模块
`kread <waiter> 0x40` 回读（不需要触发链走，**零风险**）：

```
cd997df8: ffff0000    +0x00 prio           = 0xffff0000   (ops[0] 阻塞项固定)
cd997dfc: 00002000    +0x04 prio_list.next = 0x2000       (ops[0].sem_flg)
cd997e00: 00003000    +0x08 prio_list.prev = 0x3000       ★32 位
cd997e04: 00000000    +0x0C node_list.next = 0x00000000   (ops[2].sem_op<<16)
cd997e08: 00004000    +0x10 node_list.prev = 0x4000       (ops[2].sem_flg)
cd997e20: 00005000    +0x28 task           = 0x5000       (ops[6].sem_flg)
cd997e24: deadbeef    +0x2C lock           = 0xdeadbeef   ★★ 32 位全可控
```

字段表（数组基址 = waiter）：

| waiter 字段 | 数组偏移 | sembuf 编码 | 可控性 |
|---|---|---|---|
| `prio` +0x00 | 0x00 | `ops[0].sem_num(0) \| ops[0].sem_op<<16` | 固定 `0xffff0000`（阻塞项 sem_op=-1） |
| `prio_list.next` +0x04 | 0x04 | `ops[0].sem_flg \| ops[1].sem_num(0)<<16` | `0x0000XXXX` |
| `prio_list.prev` +0x08 | 0x08 | `ops[1].sem_op \| ops[1].sem_flg<<16` | **32 位全可控** |
| `node_list.next` +0x0C | 0x0C | `ops[2].sem_num(0) \| ops[2].sem_op<<16` | `0xXXXX0000` |
| `node_list.prev` +0x10 | 0x10 | `ops[2].sem_flg \| ops[3].sem_num(0)<<16` | `0x0000XXXX` |
| `pi_list_entry.prio` +0x14 | 0x14 | `ops[3].sem_op \| ops[3].sem_flg<<16` | **32 位全可控** |
| `pi_list_entry.node_list.next` +0x20 | 0x20 | `ops[5].sem_op \| ops[5].sem_flg<<16` | **32 位全可控** |
| `task` +0x28 | 0x28 | `ops[6].sem_flg \| ops[7].sem_num(0)<<16` | `0x0000XXXX` |
| `lock` +0x2C | 0x2C | `ops[7].sem_op \| ops[7].sem_flg<<16` | **32 位全可控** |

## 四、两条路径互补，正好拼齐

| 字段 | semop | semtimedop |
|---|---|---|
| `prio` | 低 16 位 | 固定 `0xffff0000` |
| `prio_list.next` | **32 位** | `0x0000XXXX` |
| `prio_list.prev` | `0xXXXX0000` | **32 位** |
| `node_list.next` | `0x0000XXXX` | `0xXXXX0000` |
| `node_list.prev` | **32 位** | `0x0000XXXX` |
| `task` | **32 位** | `0x0000XXXX` |
| `lock` | `0xXXXX0000` | **32 位** ★ |

**semtimedop 把 `lock` 从"必须 64KB 对齐"解放成"任意 32 位地址"。**
这是 endgame 的必要条件——只有 `lock` 能指向任意内核地址，才谈得上
把 waiter 插进别的内核等待队列。

代价：`node_list.next` 变成 `0xXXXX0000`，不能再指向 0x0000–0xFFFF 的
用户页。但这可以用一个**独立的 64KB 对齐用户页**（`fake_node`）解决：
`node_list.next = fake_node`，在该页 +0x00/+0x04 放 `entry_node`。

## 五、`prio` 固定成 0xffff0000 的影响

`rt_mutex_adjust_prio_chain` 里：

```c
	if (!detect_deadlock && waiter->list_entry.prio == task->prio)
		goto out_unlock_pi;
```

`0xffff0000` 作为有符号数是 **−65536**，正常任务的 prio 是 120 左右，
永远不会相等；`detect_deadlock` 一般也为真（`FUTEX_LOCK_PI` 路径传 1）。
所以这一关两重保险都能过。

副作用：`plist_add` 排序时 −65536 是最低优先级，会被插到链表末尾——
这恰好是我们想要的（不会成为 top waiter，避免触发 `wake_up_process`）。

## 六、下一步（endgame 设计，未实施）

唯一自然满足 `rt_mutex_top_waiter` 的 `BUG_ON(w->lock != lock)` 的内核对象，
是**一个当前有等待者的真实 `rt_mutex`**（空表时要求 `*(lock+0x28)==lock`，
自然对象几乎不可能满足）。

计划：

```
1. 主线程持 u5，线程 C 对 u5 做 FUTEX_LOCK_PI 而阻塞
2. 读 C->pi_blocked_on->lock（用模块 kread）→ 得到 u5 的 pi_state->pi_mutex 地址
3. A: futex 造 waiter → semtimedop 阻塞，lock 填该真实地址
   node_list.next = fake_node(64KB 对齐页，放 entry)
   prio_list 走 semtimedop 的编码（prev 32 位可控 → 用户页）
4. T 触发 → plist_add 把「指向 A 栈的 node」插进真实 rt_mutex 的 wait_list
5. 之后 u5 的 unlock / adjust 会把这个栈指针当 rt_mutex_waiter 用 → 类型混淆
```

风险：第 4 步之后系统处于不一致状态，随时可能 panic；每次实验等于一次重启。
另外第 3 步要求 `trylock(&pi_mutex->wait_lock)` 成功——C 阻塞期间该锁是空闲的，
理论上可以，但要实测。
