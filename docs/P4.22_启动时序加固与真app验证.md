## 1. 真 app 验证：Amaze File Manager

用户实测：装上 Amaze File Manager，**能顺利进 `/data/data`**。

这是第一个真实第三方 app 走完整条链的证据：

```
Amaze 请求 su
→ su 读 caller uid（10xxx，不在白名单）
→ 查 su.sqlite 的 uid_policy（无记录）
→ ish 提权 + fork 子进程建 socket
→ am start → APK 弹窗（显示 Amaze 的名字）
→ 用户点允许
→ su 以 uid0 + init_shell 执行 Amaze 的 shell 命令
→ Amaze 用 root 模式列出 /data/data
```

`/data/data` 能列出来，说明 `init_shell → app_data_file:dir {read,search}` 这条在真实场景下有效。

## 2. 启动时序的弱点

v4 的开机段是「一次 `ktool boot`，成功就成功，失败就没了」：

```sh
/system/bin/ktool boot /system/lib/modules/ktool_mod.ko
```

问题在于 **CVE-2015-1805 是竞态漏洞**——两个 spinner 线程和 pipe 的越界窗口需要抢。

- 抢到 → 一次成功
- 没抢到 → `do_root()` 返回 3，后面 bootmode / permissive / insmod **全都不执行**
- 结果：模块不加载，`/dev/ktool` 不存在，整套 root 不可用，直到下次重启

而且失败是**静默的**——用户只会发现"这次开机 su 用不了"。

## 3. v5 的改法：三次重试 + 设备节点判据

```sh
n=0
for d in 0 2 4; do
  if [ "$d" != "0" ]; then sleep "$d"; fi
  echo "--- attempt $n (delay ${d}s) ---"
  /system/bin/ktool boot /system/lib/modules/ktool_mod.ko
  echo "boot_rc=$?"
  if [ -c /dev/ktool ]; then
    echo "dev_ktool=ok"
    break
  fi
  echo "dev_ktool=missing"
  n=$((n+1))
done
```

三个设计点：

| 点 | 为什么 |
|---|---|
| **重试 3 次，间隔 0/2/4 秒** | 竞态失败有随机性，隔开时间重抢；递增延迟避开开机高峰 |
| **判据用 `[ -c /dev/ktool ]`，不看返回值** | `ktool boot` 返回的是 insmod 的返回值；模块已存在时 insmod 返回非 0，但设备节点在，实际是可用的 |
| **每次重试都是新进程** | 一次进程只能建立一次 exploit，重试必须在进程层面重来；`ktool boot` 每次调用都会重新抢窗口 |

代价：失败时最坏多花 6 秒 + 两次 exploit（各 5–10 秒）。成功时和 v4 完全一样，只跑一次。

## 5. 还能怎么加固（按性价比）

| 方案 | 成本 | 收益 |
|---|---|---|
| 重试次数加到 5、延迟拉到 0/3/6/10 秒 | 改一行 | 失败率再降一档，但最坏开机多花 20 秒 |
| 在 `sys.boot_completed=1` 后再查一次 | 需要改 init.rc 或加一个 service | 覆盖"sec-sh 跑太早"的场景 |
| 把模块编译进内核 | 改 boot.img | 彻底不依赖 exploit，但等于改机，warranty_bit 必翻 |
| 换用更稳的提权原语（如果有） | 未知 | — |

第三条是唯一的"根治"，但和这套方案的初衷（不刷机）冲突，所以现状已经是这个约束下的上限。

## 6. 失败时的诊断路径

`/data/system/2a_v5.log` 把三段分开记：

| 日志特征 | 失败点 | 处置 |
|---|---|---|
| 没有 `uid now: 0/0/0` | `do_root()` 失败 → exploit 没抢到 | 重试应该能救；连续 3 次失败说明窗口被系统负载挤掉 |
| 有 `uid now`，没 `bootmode=2` | `kwrite` 失败 | 检查 `kwrite` 的 8 字节对齐 |
| 有 bootmode，没 `boot: exec insmod` | permissive 或 patch 失败 | 看是否 `ktool` 版本不对 |
| 有 `boot: exec insmod`，没 `dev_ktool=ok` | insmod 被拒 | 大概率是 AVC 缓存（某个域先试过一次） |
