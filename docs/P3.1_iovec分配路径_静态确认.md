# P3.1 静态确认：`rw_copy_check_uvector` / `UIO_FASTIOV` / `kmalloc` 路径

**执行时间**：2026-10-18
**方法**：kernel.raw 反汇编（capstone）+ 3.4.67 源码树对照
**设备风险**：零（纯静态）
**结论**：**`nr_segs > 8` 的 kmalloc 路径是唯一可用的越界落点；栈路径（`iovstack[8]`）结构上不可用。**
**同时修正 P2.9 §8.3 的表述**（原文「越界后的 iov++ 落在内核栈或 kmalloc 区」——栈路径实际不成立）。

---

```
sys_writev @0xc00fd840        (type=WRITE)      sys_readv @0xc00fd7c0 (type=READ)
   └─ vfs_writev @0xc00fd748                     └─ vfs_readv @0xc00fd6d0

```

- `vfs_writev` 尾部：`mov r0,#1; bl 0xc00fd540`（type=1）
- `vfs_readv` 尾部：`mov r0,#0; bl 0xc00fd540`（type=0）
- 两者共用同一个 `do_readv_writev`，**只有 type 不同**，iovec 分配逻辑完全一致。
- `do_sync_readv_writev`：`blx r7` 时 `r1 = iov`、`r2 = nr_segs`（`c00fd32c/de/38`），**没有任何 iovec 数量二次处理**。

## 2. `rw_copy_check_uvector` 反汇编逐条对照

设备符号：`0xc00fd3f0`，长度 `0x150`（下一符号 `0xc00fd540`）。

### 2.1 签名：7 参数（含 `check_access`）

源码树 3.4.67 `fs/read_write.c:633`：

```c
ssize_t rw_copy_check_uvector(int type, const struct iovec __user *uvector,
                              unsigned long nr_segs, unsigned long fast_segs,
                              struct iovec *fast_pointer,
                              struct iovec **ret_pointer,
                              int check_access);
```

设备调用点 `c00fd570`–`c00fd590`：

```
c00fd570  mov  r1, r2              ; r1 = uvector
c00fd574  mov  r3, #1              ; 第 7 参数 check_access = 1
c00fd578  sub  r2, fp, #0x68       ; &iov
c00fd57c  str  r3, [sp, #8]        ; 第 7 参数入栈
c00fd580  str  r2, [sp, #4]        ; ret_pointer = &iov
c00fd584  mov  r3, #8              ; fast_segs = 8   ← UIO_FASTIOV
c00fd588  str  r6, [sp]            ; fast_pointer = iovstack

c00fd590  bl   0xc00fd3f0
```

被调方读 `sl = [fp,#0xc]` 即第 7 参数，之后 `cmp sl,#0; beq skip` —— **`check_access` 分支
与源码树完全一致，Samsung 只加了这一个背参，语义没变。**

### 2.2 四条硬性约束（逐条对应）

| 源码 | 设备指令 | 值 |

| `if (nr_segs > fast_segs) iov = kmalloc(nr_segs*8, GFP_KERNEL)` | `c00fd420 cmp r2,r3; lsl r8,r2,#3; bls skip; mov r0,r8; mov r1,#0xd0; bl __kmalloc` | **GFP_KERNEL = 0xd0** |
| `copy_from_user(iov, uvector, nr_segs*8)` | `c00fd498 mov r1,r4; mov r0,r7; mov r2,r8; bl __copy_from_user` | 整块拷贝 |
| `if (len < 0) -EINVAL` | `c00fd4d8 ldr r2,[r1,#4]; cmp r2,#0; blt → -EINVAL` | — |

| `if (len > MAX_RW_COUNT - ret) iov[seg].iov_len = len` | `mov r3,#0xf000; movt r3,#0x7fff; rsb r3,r0,r3; cmp r2,r3; movhi ip,r3; strhi ip,[r1,#4]` | **MAX_RW_COUNT = 0x7ffff000** |

### 2.3 `UIO_FASTIOV` 确认

`c00fd584  mov r3, #8` → **UIO_FASTIOV = 8**（与 3.4 主线一致，未被 Samsung 改动）。

`copy_from_user` 只拷 `nr_segs*8` 字节：**`nr_segs` 之外的数组元素永远不进入内核，
也永远不过 `access_ok`** —— 这是后面「假 iovec」能带内核地址进内核的前提。

## 3. 两条分配路径的几何

### 3.1 栈路径（`nr_segs ≤ 8`）：结构上不可用

`do_readv_writev` 序言：

```
c00fd540  mov ip, sp
c00fd544  push {r4,r5,r6,r7,r8,sb,fp,ip,lr,pc}   ; 10 个寄存器 = 40 字节
c00fd548  sub fp, ip, #4                           ; fp = sp0 - 4
c00fd54c  sub sp, sp, #0x58                        ; sp = sp0 - 128
c00fd554  sub r6, fp, #0x64                        ; iovstack = fp - 0x64 = sp0 - 104
```

`iovstack[8]` 覆盖 `[sp0-104, sp0-40)`，**紧邻其上的就是保存寄存器区**：

| 越界索引 | 地址 | 内容（进入 `do_readv_writev` 时的值） | 来源 |
|---|---|---|---|
| `iov[8]` | `sp0-40 / -36` | **`{nr_segs, uvector}`** | vfs_writev 的 `r4/r5` |
| `iov[9]` | `sp0-32 / -28` | `{file*, uvector}` | sys_writev 的 `r6/r7` |
| `iov[10]` | `sp0-24 / -20` | `{nr_segs, sb}` | `r8` / 未知 |
| `iov[11]` | `sp0-16 / -12` | `{fp, sp0}` | 帧指针 |
| `iov[12]` | `sp0-8 / -4` | **`{lr, pc}` ← 保存的返回地址** | — |

关键：**`iov[8].iov_base` 恒等于 `nr_segs`（≤ 8）**。
- 原子路径：`__copy_from_user_inatomic(to, (void*)8, n)` → 必然缺页 → `-EFAULT`
- 非原子路径：`access_ok(8, n)` 会通过（8 < addr_limit），但随后 `__copy_from_user` 仍缺页 → `-EFAULT`

也就是说，栈路径走到第 9 个 iovec 就**必然停在 `-EFAULT`**，永远到不了 `iov[9]` 里那个
`file*`（内核堆指针）。`mmap_min_addr` 若为 0 才有一线可能，但那也只能让越界继续走到
`iov[9]`，收益远小于代价 —— **不作为路线**。

> **修正 P2.9 §8.3**：越界落点是 **kmalloc 区**，不是「内核栈或 kmalloc 区」。

### 3.2 kmalloc 路径（`nr_segs > 8`）：唯一可用

`nr_segs = 257` 时：

```
size = 257 * 8 = 2056 (0x808)
```

`__kmalloc` → `get_slab.isra.43 @0xc00f4f5c`：

```
c00f4f68  cmp  r0, #0xc0        ; > 192 → 走 fls 分支
c00f4f90  sub  r0, r0, #1       ; 2055
c00f4f94  clz  r0, r0
c00f4f98  rsb  r0, r0, #0x20    ; = fls(size-1) = 12
c00f4f9c  ...
c00f4fa8  ldr  r0, [r3, #0xc]   ; kmalloc_caches[12]
```

**index 12 = 4096 字节对象**（`kmalloc-4096`）。也就是说：

- 请求 2056 字节，**实际拿到 4096 字节对象**
- 前 2056 字节 = 内核从用户态拷入的 257 个 iovec
- **后 2040 字节 = 该对象上一任主人的残留数据（不清零）**
- 越界 `iov[257]`、`iov[258]` 正好落在**同一对象的残留区**

这就是 iovyroot（dosomder，`IOVECS=512`）能工作的全部原因：
用 `sendmmsg` 的 4096 字节 `msg_control` 反复 `kmalloc-4096` + 填满 + 释放，
留下 512 个「假 iovec」的残留；随后 `readv` 的 `kmalloc(2056)` 复用同一个对象，
天然继承 `iovs[257]`/`iovs[258]` 作为越界项。

### 3.3 喷的对象：`sendmmsg` 的 iovec 拷贝（本机已确认）

`___sys_sendmsg`（3.4.67 源码 `net/socket.c:1930-1945`）：

```c
iov_size = msg_iovlen * sizeof(struct iovec);      // 512*8 = 4096
if (msg_iovlen > UIO_FASTIOV)
        iov = sock_kmalloc(sock->sk, iov_size, GFP_KERNEL);
err = verify_iovec(msg_sys, iov, &address, VERIFY_READ);
```

设备侧 `sock_kmalloc @0xc0581e58` 直接 `bl __kmalloc`（`c0581eb0`），
即 4096 → 同一个 `kmalloc-4096`。

设备侧 `verify_iovec @0xc058a258`：

```
c058a2a4  lsl   r2, r0, #3         ; size = msg_iovlen*8
c058a2ac  adds  ip, r1, r2         ; access_ok(msg_iov, size) —— 只校验数组本身
c058a310  ...                      ; sbcslo / cmp —— 单次范围检查
c058a334  bl    0xc02487fc         ; __copy_from_user(iov, msg_iov, size)
c058a2e0  ...                      ; 之后逐条只截断 iov_len > INT_MAX
```

**逐条元素完全不过 `access_ok`**。所以 512 个假 iovec 里
`iovs[258].iov_base = 内核地址` 可以被原样拷进 kmalloc-4096 对象，
不报 EFAULT。（`msg_control` 那条路 `copy_from_user` 是纯字节拷贝，同样不校验内容。）

## 4. 最关键的一条：atomic 路径不做 `access_ok`

这条决定了「假 iovec 里的内核地址能否生效」。

### 4.1 `pipe_write` 方向（任意读）

```
c0105c18  bl   iov_fault_in_pages_write     ; 返回值被丢弃（c0105c1c 立刻覆盖 r0）
c0105c20  bl   kmap_atomic
c0105c24  ldr  r1,[fp,#-0x38]               ; iov
c0105c28  mov  r2,r4                        ; chars
c0105c2c  mov  r3,#1                        ; atomic = 1（无条件）
c0105c34  bl   pipe_iov_copy_from_user
```

`pipe_iov_copy_from_user @0xc0105314`：

```
c0105368  cmp  r8, #0        ; atomic?
c010536c  bne  0xc01053a0    ; ← atomic 分支：直接 __copy_from_user，无 access_ok
c0105370  ...                ; 非 atomic 分支：c0105370-538c 是 access_ok 内联
c0105390  bl   __memzero     ; 失败时清零目标（copy_from_user 的内联语义）
c0105394  mvn  r0, #0xd      ; -EFAULT
c01053a0  mov  r0,r7; ldr r1,[r4]; mov r2,r5
c01053ac  bl   0xc02487fc    ; __copy_from_user
```

`__copy_from_user @0xc02487fc` 本体是**裸 `ldr`/`stm`**（不是 `ldrt`，无 DACR 切换）：
内核态执行，对内核地址完全可读。

### 4.2 `pipe_read` 方向（任意写）

```
c010579c  cmp  sb, #0
c01057a0  bne  0xc0105824         ; atomic 分支
c01057a4  ldr  r2,[r8,#8]         ; 非 atomic：addr_limit
c01057ac  adds r1,r0,r5; sbcslo ... ; access_ok 内联
c01057bc  beq  0xc0105990         ; 通过 → 拷贝
c0105824  ldr  r0,[r4]            ; atomic：iov->iov_base 直接用
c0105834  bl   0xc0248c20         ; __copy_to_user_std（裸 str，无 access_ok）
```

`__copy_to_user_std @0xc0248c20` 同样全是裸 `str`。

**结论**：只有**第一趟 atomic** 才允许越界 iovec 携带内核地址。非 atomic 重试会被
`access_ok` 挡下 —— 因此越界必须发生在 atomic 趟内。

---

## 5. 越界量是可控的（这是整条链的核心算术）

`pipe_*` 的调用方 `chars` 在重试时**不递减**，而 iovec 条目已被推进/清零，
所以「失败的那趟 atomic 已复制的字节数 W」会被重复计入一次：

```
第 1 趟 atomic：复制 W 字节 → 在 iov[k] 处缺页 → -EFAULT
重试 non-atomic：跳过已清零的条目，从 iov[k] 起再复制 chars 字节
净效果：数组消耗 = W + chars，但 total_len 只减 chars
→ 下一趟 chars 字节里，有 W 字节要从数组末尾之外去取
```

**W = 越界字节数 = 越界 iovec 条目数 × 8**，完全由 `iov[0].iov_len` 决定。

`pipe_write` 侧还有一个额外便利：`iov_fault_in_pages_write` 的返回值被丢弃（`c0105c18`），
即使预取失败也照样走 atomic。而 `fault_in_pages_writeable` 只摸首尾两个字节，
所以：

- `iov[0]` 指向**只读页**（`PROT_READ`）→ `__put_user` 失败 → 预取循环在 `iov[0]` 就 `break`
  → `iov[1]` 完全没被预取
- `iov[1]` 指向**非驻留页**（文件映射 + `MADV_DONTNEED`）→ atomic 拷贝在 `iov[1]` 首字节缺页
  → **W = iov[0].iov_len，精确可控，不需要竞态**

这比 iovyroot 的 mmap/munmap 竞态更稳（它靠 `usleep(50)` 反复撞）。

## 6. 判定汇总

| 项 | 判定 | 证据 |
|---|---|---|
| `UIO_FASTIOV` | **8** | `c00fd584 mov r3,#8` |
| `UIO_MAXIOV` | **1024** | `c00fd418 cmp r2,#0x400` |
| `nr_segs > 8` → `kmalloc(nr_segs*8)` | **成立** | `c00fd430-434` |
| `nr_segs = 257` → 4096 字节对象 | **成立** | `get_slab` fls(2055)=12 |
| 逐条 `access_ok`，仅限 `nr_segs` 内 | **成立** | `c00fd4e4-508` |
| 越界 iovec 不经校验 | **成立** | `copy_from_user` 只拷 `nr_segs*8` |
| 栈路径（≤8）可作为越界落点 | **不成立** | `iov[8].base = nr_segs ≤ 8`，必 EFAULT |
| atomic 路径无 `access_ok` | **成立（双向）** | `c01053ac` / `c0105834` 均为裸 `ldr`/`str` |
| 非 atomic 路径有 `access_ok` | **成立（双向）** | `c0105370` / `c01057a4` |
| 越界量 W 可控 | **成立** | W = `iov[0].iov_len`，只读页断预取 |
| 喷对象里的假 iovec 不被逐条校验 | **成立** | `verify_iovec` 只校验数组整体范围（`c058a2ac`） |

**一句话**：路线确定为 **`nr_segs = 257` + `kmalloc-4096` 残留喷 + 只读页断预取**，
不再考虑栈路径。

## 7. 下一步（待用户确认后执行）

1. **零风险自检**：`pipe_write` 方向，`iov[257] = {&user_canary, 8}`、`iov[258] = {&user_canary2, 8}`，
   目标全部是**用户地址**。若 pipe 里读出的 16 字节 == canary 内容，则证明：
   越界落点正确 + 残留继承成立 + W 精确。**全程不碰内核地址，最坏返回 EFAULT。**
2. 自检通过后，把 `iov[258].iov_base` 换成 `init_task`（`0xc0b79be0`）做一次内核读，
   验证 `__copy_from_user` 对内核地址确实放行。
3. 再设计写方向（`pipe_read`），目标先选只读区做「写入必崩」的对照，最后才碰 cred。

**遗留风险**：`slub_debug` 若开启会 poisoning 残留区 —— 需在设备侧确认
`/sys/kernel/slab/kmalloc-4096/` 存在且 `dmesg | grep -i slub` 无 `debug` 字样；
