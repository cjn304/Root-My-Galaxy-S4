## 1. 上一轮五连崩的真正根因（探针实测）

P4.24 的归因是错的。`kprobe` 探针（`kmod/kprobe.c`，零崩溃设计：每个指针先读成 u32、
过 `is_kaddr()` 才解引用）一次测出：

```
[off] task.cred=748(0x2EC)  real_cred=744(0x2E8)  comm=756(0x2F4)
[off] cred.security=88(0x58)  cap_eff=56(0x38)
[off] mm.exe_file=428(0x1AC)
cred hard(+0x2fc)=caa6b280  compiler=c3884b28  *** MISMATCH ***
cred uid=0 gid=0 euid=0                      ← 硬编码偏移读到的是对的
cand+0x48=00000001 (not kaddr, skip)
cand+0x4c=00000000 (not kaddr, skip)
cand+0x58=cb95ed40 osid=258 sid=258  <== MATCH init_shell
mm(compiler)=e56d6e00 kaddr=1 → exe_file=0    ← mm 指针是垃圾
```

结论：

| 结构 | 编译期偏移 | 设备实际 | 可信？ |
|---|---|---|---|
| `struct cred` | security=0x58 | 0x58（候选扫描 sid 命中） | ✅ 可信 |
| `struct task_struct` | cred=0x2EC, mm=0x1EC | cred=0x2FC | ❌ **整体错位 16 字节** |

- 五连崩的元凶：`current_cred()` = `*(task+0x2EC)` → 野指针 → `->security` → 崩。
- v3/v5 崩在路径门的 `current->mm->exe_file`（mm 偏移同样错位，读到 vmalloc 段垃圾）。
- **`new->security`（ish/ctx）一直能用**，因为 cred 布局是对的——这解释了为什么
  "ish/ctx 正常但一读 current->xxx 就崩"。

顺带：`panic_on_oops` 用 kallsyms+kwrite 置 0（proc 写被 Samsung 保护挡住），
`kallsyms` 地址 `c0c06504`，值 1→0。

## 2. 新门禁（路径门，砍掉域门）

设计三条原则：

1. **只用内核 API 取指针，不用任何编译期结构体偏移**
   - `get_task_mm(current)` —— EXPORT_SYMBOL_GPL，直接调
   - `get_mm_exe_file(mm)` —— 未导出，init 时 `kallsyms_lookup_name` 解析
   - `d_path(&exe->f_path, ...)` —— write 上下文实测正常（P4.24 的"d_path 崩"是野指针）
2. **比字符串不比 dentry**（P4.24 实测 dentry 比较对 su 失效）
3. **域门砍掉**：管理命令走 `ktool` 用户态（自带 do_root），根本不经过 `/dev/ktool`；
   过 `/dev/ktool` 的只有 su 发的 ish/ctx，所以只需要一道路径门

```c
static int ktool_allow(const char *kbuf)
{
	int priv = !strncmp(kbuf, "ish", 3) || !strncmp(kbuf, "ctx ", 4);
	int ok;

	if (!priv)
		return 0;              /* 其他命令一律拒绝 */
	ok = ktool_gate_ok();      /* 总是执行并打印 */
	if (!ktool_enforce)
		return 1;              /* 观察模式 */
	return ok;
}
```

模块参数：

```
insmod ktool_mod.ko ktool_enforce=1 [su_path=/system/xbin/su]
```

**注意参数名是 `ktool_enforce` 不是 `enforce`**——`module_param(ktool_enforce,...)`
用变量名做参数名，写成 `enforce=1` 会 ENOENT 加载失败（踩过）。

## 3. 实测（log-only → enforce）

先 `ktool_enforce=0` 部署，确认字符串：

```
ktool: gate exe=/system/xbin/su -> ALLOW (log-only)
ktool: gate exe=/system/bin/sh  -> DENY  (log-only)
```

再切 enforce：

| 测试 | 结果 |
|---|---|

| `ktool setuid 10198 su -c id` | 弹窗出现（ish 已过门）✅ |
| Amaze 启动 | `gate exe=/system/xbin/su -> ALLOW` + `ish -> uid0 sid=253` ✅ |

## 4. ktool 锁定（模块侧 i_mode）与一个 boot 期陷阱

`/system/bin/ktool` 是用户态 exploit（do_root 直改 cred），门禁管不到它。
必须 chmod 700，否则任何 app 都能 exec 它（`untrusted_app → system_file:file execute`
在策略里是允许的）。

**v9/v9b 在 boot 脚本里 chmod 是错的**：
- sec-sh 是 uid0+init_shell 但**没有 CAP_SYS_ADMIN** → `mount -o rw,remount /system`
  必 EPERM（日志里静默失败）→ chmod 撞 EROFS
- 借 `ktool sh` 的 caps 挂载 → 会把 `permissive_map` **全开且重启不还原**，
  直接毁掉"只有 1 个 type permissive"的设计

**v10 改为模块 init 直接写 i_mode**（`ktool_apply_ktool_mode`，和 `ktool_relabel`
改 /dev/ktool 同一个手段，无需挂载、不碰 permissive）：

```c
if (!kern_path("/data/local/tmp/ktool_dev", 0, &pflag)) want=0755;  /* dev flag */
else want=0700;
kern_path(KTOOL_BIN_PATH, LOOKUP_FOLLOW, &pkt);
pkt.dentry->d_inode->i_mode = (pkt.dentry->d_inode->i_mode & S_IFMT) | want;
```

**但发现 boot 期陷阱**：模块直写 i_mode **只在内存**（`/system` 只读挂载，
且直写不 mark_inode_dirty），开机后期 inode 被回收/重读后**磁盘上的旧值回来了**：

```
t=10s -rwx------ (700)   ← 模块写的内存值
t=20s -rwxr-xr-x (755)   ← inode 重读磁盘
```

**处置**：把磁盘上的模式真正改成 700（`mount rw; chmod 700; sync; mount ro`，
一次性，持久）。实测二次重启后稳定保持 700，120 秒轮询零回退。
模块的 init 写入保留作为兜底（每 boot 重写一次内存值）。

## 5. 最终交付态

| 项 | 值 |
|---|---|
| `/dev/ktool` | 0666，模块加载（enforce=1） |
| `/system/bin/ktool` | **700 root:root**（磁盘持久） |
| permissive | 只有 `init_shell` 1 个 type |
| gate | `exe=/system/xbin/su` 才放行 ish/ctx |

| `ktool` exec（sh/app） | 126 拒绝 |
| `su` exec（sh） | 126 拒绝（策略） |
| Amaze → su → root | ✅ 端到端 |

## 6. 调试通道（保留）

`/data/local/tmp/ktool`（ktool_min 副本，750 shell:shell）：
- adb shell（uid 2000）可 exec —— 我的调试入口
- app 不可 exec —— DAC（/data/local/tmp 是 drwxrwx--x shell:shell，other 仅 --x）
  + SELinux（`untrusted_app → shell_data_file` 无 execute）双保险
- **注意二进制必须叫 `ktool*`**：`find_self()` 按 comm 前缀匹配，改名成 `kt` 会
  "task not found"

dev 模式：`touch /data/local/tmp/ktool_dev` → 重启（或重载模块）→ 模块设 755。
flag 目录 app 建不了文件（同上 DAC），安全。

**v11 补记（04:25 发现并修复）**：v10 部署后，模块里的 flag 判定在最后一次编辑时丢了
（网络中断导致落盘的是简化版：无条件设 700），所以 v10 的 dev flag 实际是死的。
已在 v11 恢复并双向实测：

```
flag 存在 → ktool: /system/bin/ktool -> 755 (dev)   + adb shell 可执行 ktool ✅
flag 移除 → ktool: /system/bin/ktool -> 700 (locked) ✅
```

调试时若遇到 `kwrite caps fail`，是 exploit 竞态没抢到窗口，重跑即可（实测第 2 次成功）。

## 7. 剩余风险

1. 模块的 dev 模式 755 只在内存，inode 回收后回 700（**失败方向安全**），
   且 dev flag 不影响最终 700 的磁盘值
2. `init_shell → app_data_file:file` 只有 read 没有 write —— 写别人 app 数据
   仍依赖那 1 个 permissive bit（未变）
3. `/system` 被重刷/OTA 后 on-disk 模式会回到 cp 的 755，需要重新 chmod；
   模块 init 能覆盖到 inode 回收前
