## 一、B4 写事务（undo 日志 + 失败自动回滚）

### 原来的问题

`kwrite_buf` 逐块写、逐块校验，但**没有整体回退**：写到第 3 块失败时，前两块已经改完，
目标停在"一半新一半旧"的状态，比不写还危险。

### 现在

```
1. 先把整段原值读下来（快照）
2. 快照落盘 /data/local/tmp/ktool_undo.bin（magic + len + addr + data）
3. 逐块写；任一块失败 → 立刻用内存快照把已写的部分写回去
4. 回滚也失败 → 打印原值（≤64B）或提示用 `ktool undo`
```

- 目标不可读（快照失败）时**退化**为非事务写，并明确打印"无法快照"，
  不假装有保护；
- `kwrite_file <in> <addr> -n` 可跳过 undo 日志；
- 新增 `ktool undo`：从日志把上一次写入还原，用于"进程已经退出/回滚失败"的场合。

### 实测（真改真还原）

```
before : /sbin/modprobe
written: /sbin/zzzzzz        ← kwrite_file 生效
undone : /sbin/modprobe      ← undo 精确还原
```

三次 `kread_file` 各拉 64 字节回 PC 比对，`写入生效=True / undo还原=True`。

> 局限：**失败自动回滚这条分支没有做破坏性实测**——要造出"第 1 块成功、第 2 块失败"
> 需要一块"半可写"的内核内存，构造它的风险（写坏 .text 或页表）高于收益。
> 代码路径本身与 `kwrite_buf` 共用同一套写逻辑，undo 那半条已实测。

## 二、B5 cred 回滚（promote 前快照，unroot 还原）

### 关键认识

改的是**自己进程的 cred**，进程一退内核就把这个 cred 释放了。
所以"不可逆"只发生在**进程活着**的这段时间——也就是一次 `repl` 会话内。
跨会话去"还原"一个可能已被复用的地址是危险的，不做。

### 现在

`promote` 在动手前把 `cred+4` 起的 72 字节存进内存快照
（uid/gid×8 + securebits + 四组 cap，到 cap_bset 结束），`unroot` 用它写回。

**故意不存 `cred+0` 的 usage**：那是引用计数，是运行时值，
把旧值写回去会让 refcount 错乱。

`unroot` 写之前做两道校验：
1. `task+comm` 还是 `ktool`（确认这个 task 还是自己）；
2. `task+0x2f8` 解出来的 cred 指针与快照一致（防地址复用写错对象）。

### 实测

```
who: uid=2000 ...                      ← 提权前
promoted: uid=0 euid=0
who: uid=0 ... caps eff=ffffffff       ← 提权后
unroot: uid=2000 euid=2000 gid=2000
caps: eff=00000000 perm=00000000       ← 完整还原
who: uid=2000 ... caps eff=00000000
```

一次会话内 uid 2000 → 0 → 2000，caps 全 0 → 全满 → 全 0。

## 三、B7 竞态退避 + 竞态统计

### 问题

失败就立刻重试 300 次。连续失败说明"当前不在状态"，猛打只会把 loadavg 推高，
反过来更难赢；而且没有任何计数器，说不清一次读到底试了几次、慢在哪。

### 现在

```c
race_backoff():  连续失败 <=2 次不退避；之后每次 +200µs，封顶 2ms；成功一次清零
g_tries_sum:     累计 try 次数
bench:           ktool bench [addr] [n]   —— n 次 8B 读，打印 ok/耗时/平均 try
```

退避在**成功路径完全不起作用**（成功即清零），只在失败链上生效。
另有两处刻意关掉退避：`g_max_tries < 64`（探测模式）和 `g_quiet`（确认读）——
这两类读本来就预期会失败，退避只会把 15ms 的判决拖成 600ms。

### 实测

```
bench 50 x 8B @c0b79be0: ok=50  4 ms  0.1 ms/read  avg tries 1.7  backoff=on
bench 200 x 8B @c0b79be0: ok=200  74 ms  0.4 ms/read  avg tries 2.6  backoff=on
```

平均 1.7~2.6 次就命中，读原语本身很快（见下节）。

## 四、C8 吞吐：先测量，结论和原来的判断相反

### 原来的判断（P4.82）是错的

> "吞吐 ≈12KB/s（64KB 约 5.4s），1MB ≈ 90s"

实测：

| 操作 | 总耗时 | 扣掉 2s 固定启动 | 实际吞吐 |
|---|---|---|---|
| `kread_file` 64KB | 2.01 s | ~10 ms | ~6 MB/s |
| `kread_file` 1MB | 2.21 s | ~210 ms | **~4.8 MB/s** |
| `bench` 200×8B | 74 ms | — | 0.4 ms/读 |

12KB/s 是某次系统繁忙时测的（竞态难中 + 每条命令都要重付 2s 启动），
把"单进程启动成本"和"吞吐"混在一起了。**bulk 读根本不是瓶颈**，
真正的瓶颈是**空洞**。

### 空洞为什么贵

扫描时一次窗口读失败 → 退避把每次 try 拖到 2ms → 300 次 ≈ 600ms，
而失败后只前进 4KB，于是每 4KB 空洞都要重付 600ms。

```
scan 0xf0000000 0x10000 s:zzzz     14.23 s
```

### 改法（三层）

1. **探测模式**：扫描期间 `g_max_tries = 24`。实测平均 1.7~2.6 次命中，
   连续 24 次失败的概率约 3e-5，足够判定"读不到"；
2. **确认读防误判**：24 次失败后，再用 300 次读一个 8 字节——
   读得到说明只是竞态抖动（重试窗口），读不到才是真空洞。
   这一步是关键：**宁可多花 15ms，也不能把有数据的页当成空洞跳过去**；
3. **步长放大**：连续 3 次失败后，跳 4KB 改成跳 64KB。

### 实测（同一命令、同一区间）

```
scan 0xf0000000 0x10000 s:zzzz     2.06 s   （其中 2s 是固定启动，实际 ~60ms）
scan 0xc0b79000 0x2000 s:swapper   命中 0xc0b79ee4 = init_task+0x304 ✓
```

**14.23s → 2.06s，实际扫描耗时 14s → 60ms（约 230×）。**

### 没做：页表级跳过

原计划里的"读页表判断映射"没有实现——测量显示空洞代价已经降到一次判决 ~15ms，
再引入 ARM 两段页表 walker（要处理 section/coarse page table、TTBR 选择）
带来的复杂度和出错风险，与省下的几十毫秒不成比例。
