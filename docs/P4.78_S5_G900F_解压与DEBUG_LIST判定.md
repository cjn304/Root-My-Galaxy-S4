## 二、LZO 载荷的真实起点是 0x182B，不是 0x16E4

用户/外部建议定位到"内核段偏移 5860（0x16E4）有 LZO 标记"。实测该处**不是流起点**：

```
0x16DC: 0e f0 a0 e1                    mov pc, lr          ← 函数返回
0x16E4: 89 4c 5a 4f 00 0d 0a 1a 0a    lzop_magic[9]       ← 常量数组
0x16ED: 00 00 00 0a 0a 00 0a 0a        version=0x0000（lzop 应为 0x1030/0x0940）
0x16F5: " -- System halted"                                ← misc.c 字符串表
```

用同一套 lzop 解析器从 `0x16E4` 起解，第一块头读出 `usize=0x656C2E0A`（= 字符串 `"\n.el"`），立刻判定输出溢出、0 块解出。**证明 0x16E4 是解压器里的常量，不是数据。**

真实 lzop 头在 **0x182B**（字符串表结束后的第一个字节）：

```
89 4c 5a 4f 00 0d 0a 1a 0a   magic
10 30                        version = 0x1030  (lzop 1.03)
20 60                        lib_version = 0x2060
09 40                        version_needed = 0x0940
03                           method = 3 (M_LZO1X_999)
09                           level = 9
03 00 00 0d                  flags = ADLER32_D | STDIN | STDOUT, OS=Unix
00 00 00 00                  mode
5f bf 39 f2                  mtime_low = 1606371826 (2020-11-26)
00 00 00 00                  mtime_high
00                           filename_len = 0
29 54 03 6f                  header checksum (低16位不符 → 三星改过校验算法，未采纳)
[0x1851] 00 04 00 00 | 00 00 06 c0     第一块：usize=0x40000, csize=0x6C0
```

`csize=0x6C0=1728` 与 Unicorn 模拟 zImage stub 时截获的第一次 `__decompress(inlen=0x6c0)` **完全一致**，起点确认。

## 四、S5 的 list_debug 实现（指令级）

`__list_del_entry` 位于 **文件偏移 0x3F0284**（该内核文本段从 0x100000 起，故 VA≈0xC0308000+）：

```
0x3f0284  push  {r0, r1, r2, lr}
0x3f0288  mov   r3, r0
0x3f028c  ldm   r0, {r1, r2}          ; next / prev
0x3f0290  cmp   r1, #0x100
0x3f0294  bne   0x3f02b4
0x3f0298  ldr   r0, [pc,#0xa8]        ; "/home/dpi/.../lib/list_debug.c"
0x3f029c  str   r1, [sp]
0x3f02a0  mov   r1, #0x43             ; __LINE__ 67
0x3f02a4  ldr   r2, [pc,#0xa0]        ; "list_del corruption, %p->next is LIST_POISON1 (%p)\n"
0x3f02ac  add   r2, pc, r2
0x3f02b0  b     0x3f02d4
...
0x3f02d4  bl    0x19fc5c              ; warn_slowpath_fmt
0x3f02d8  ldr   r0, [pc,#0x78]        ; "list corruption during del"
0x3f02e0  bl    0xa82b28              ; ★ panic(...)
```

`0xa82b28` 的入口形态：`push {r4-r11,lr}` → `cpsid i`（关中断）→ `bl printk` ×2 → 末尾 `b .` 死循环。
**这是 `panic()`，不是 `printk()`。**

对照 S4（同一份 `lib/list_debug.c` 逻辑）：

```
S4 0xc025cde4  bl warn_slowpath_fmt
S4 0xc025cde8  udf #0x12                  ; ← if (list_debug) BUG();
```

差异根源：S4 的 `list_debug` 是 `static int list_debug = 0x100`（非 0，常量折叠成无条件 `BUG()`）；
S5 的版本没有这个标志位，直接在 `WARN` 后 `panic("list corruption during del")`。

`__list_add`（0x3F01F0 附近）同样：两条 `bl warn_slowpath_fmt` + 一条 `bl 0xa82b28`，无 udf。

## 五、为什么之前的扫描全部落空（重要方法论）

S5 的内核用 **text-relative 寻址**，典型序列：

```
0x100f04  ldr r0, [pc, #0x80]     ; r0 = 32 位“增量”
0x100f08  add r0, pc, r0          ; 目标 = (本条 pc=0x100f0c) + 增量
```

后果：
- 全镜像 `movt` 只有 **35** 条（S4 仅 `movt #0xc097` 一项就有 3178 条）；
- 字符串/全局变量的地址**不以绝对字面量出现**，所以"搜 `0xC0E3BDDF`"、"扫 movw/movt"、"扫 pc 字面量"三种方法全部返回 0 —— 这不是"没有引用"，是寻址模型不同；
- 正确判据：`ldr rD,[pc,#imm]` 取 32 位增量，再 `add rD,pc,rD`，目标按**文件偏移空间**计算。

用这个模型一扫就命中：`list_del` 四条格式串的引用点分别在 `0x3F02A4 / 0x3F02C8 / 0x3F02FC / 0x3F0318`。

## 六、附带确认

- S5 G900F 是 **高通 MSM8974**（ramdisk 全是 `init.qcom.*`），与 S4 的 Exynos 5410 不同分支。
- ramdisk 是标准 gzip，解出 4,751,360 字节 cpio（51 项）→ **boot.img 未整体加密**，只有 kernel 段是 LZO。
- `init.rc` 含 `write /proc/sys/kernel/panic_on_oops 1` → oops 即重启，与 S4 一致。
- 该镜像文本段起于 0x100000，前 1 MB 仅 0x0–0x100 有 ARM head 代码，其余为 0（1 MB 对齐填充）。

## 八、CVE-2015-1805 在 S5 上的判定：**FIXED**

### 8.1 判据（必须看二进制，不能看源码）

S4 就是反例：S4 的**源码树** `fs/pipe.c:113` 是 5 参已修形态
（`pipe_iov_copy_from_user(void *addr, int *offset, struct iovec *iov, size_t *remaining, int atomic)`），
但 S4 的**设备二进制**是 4 参未修形态。所以只能比机器码。

| 形态 | 参数 | 关键指令特征 |
|---|---|---|
| 未修（有洞） | `(void *addr, struct iovec *iov, unsigned long len, int atomic)` | `len` 存在寄存器里当局部变量，只回写 `iov_base` / `iov_len` |
| 已修 | `(void *addr, int *offset, struct iovec *iov, size_t *remaining, int atomic)` | 多两个指针参数，函数里 `*offset += copy` / `*remaining -= copy` |

### 8.2 S4 设备（对照，VULNERABLE）

```
0xc0105314  mov  ip, sp
0xc0105318  push {r4-r8, sb, fp, ip, lr, pc}
0xc0105320  subs r6, r2, #0      ; r6 = r2 = len（值传递，存局部）
0xc0105324  mov  r7, r0          ; addr
0xc0105328  mov  r4, r1          ; iov
0xc010532c  mov  r8, r3          ; atomic
0xc010535c  cmp  r1, r6
0xc0105360  movlo r5, r1         ; copy = min(len, iov_len)
0xc0105364  movhs r5, r6
```

只有 4 个参数，`len` 是值 → **未修**。

### 8.3 S5（FIXED）

`pipe_iov_copy_from_user` 入口 **0x26F3B8**：

```
0x26f3b8  push {r0, r4-r8, sb, sl, fp, lr}
0x26f3bc  mov  sl, r3            ; sl = remaining（第 4 参：指针）
0x26f3c0  ldr  sb, [sp, #0x28]   ; sb = atomic（第 5 参：栈上传入）
0x26f3c8  mov  r8, r0            ; addr
0x26f3d0  mov  r6, r1            ; offset（第 2 参：int *）
0x26f3d4  mov  r7, r2            ; iov（第 3 参）
0x26f3dc  ldr  ip, [sl]          ; while (*remaining > 0)
...
0x26f458  ldr  r3, [r6]
0x26f460  str  r3, [r6]          ; *offset += copy
0x26f464  ldr  r3, [sl]
0x26f46c  str  r3, [sl]          ; *remaining -= copy
0x26f470  ldr  r3, [r5]
0x26f478  str  r3, [r5]          ; iov->iov_base += copy
0x26f47c  ldr  r3, [r5, #4]
0x26f484  str  r4, [r5, #4]      ; iov->iov_len -= copy
```

**五个参数、offset/remaining 通过指针回写** → 已修。

两个调用点都在 `pipe_write`（入口 0x26F614）内，且都按 5 参布置：

```
0x26fb78  str r7, [sp]           ; atomic = 1
0x26fb80  bl  0x26f3b8

0x26fcfc  str r4, [sp]           ; atomic = 0
0x26fcf4  bl  0x1104b4           ; __copy_from_user 前置检查
0x26fcf8  str r9, [sp, #0x24]    ; &remaining 已就位
0x26fd10  bl  0x26f3b8
```

另外非原子路径内联了 `access_ok`，可作为「这是 from_user 而非 to_user」的旁证：

```
0x26f334  bic  fp, sp, #0x1fc0   ; fp = current_thread_info()
0x26f3d8  bic  fp, fp, #0x3f
0x26f430  ldr  ip, [fp, #8]      ; ti->addr_limit
0x26f434  adds r3, r1, r4
0x26f438  sbcslo r3, r3, ip
```

### 8.4 结论

| 机型 | `pipe_iov_copy_from_user` | CVE-2015-1805 |
|---|---|---|
| S4 GT-I9500（3.4.5-6264821） | 4 参（len 值传递） | **VULNERABLE**（已在用） |
| S5 G900F（3.4.0-14131106） | 5 参（offset/remaining 指针） | **FIXED** |

⇒ **S5 上 43499 链缺少"任意内核读"这一环**。而 S5 的 `CONFIG_DEBUG_LIST` 又是致命版（§四），
伪造 plist 节点必须自洽、必须知道栈地址 —— 两条前提同时不满足。

**S5 这条路就 43499 而言到此为止**，除非另有一个可用的内核读原语（binder / ION / 私有驱动）。

### 8.5 判据为什么要写成"比函数签名"而不是"比版本号"

- 同一个 CVE，S4 和 S5 都是 3.4 分支，结论却相反；
- S4 的源码树与设备二进制也不一致（源码已修、二进制未修）；
- 唯一可靠的做法是找到函数入口、看它吃几个参数、写不写回 `*remaining`。

## 九、附带：S5 的 ION 是 **msm 实现**，S4 的结论不能套用

### 9.1 静态证据

符号名区 `0xb2df40..0xb2e300` 出现 msm ION 全套：

```
ion_mmap / ion_buffer_create / ion_handle_add / ion_free_nolock
ion_phys / ion_map_kernel / ion_client_create / ion_share_dma_buf / ion_import_dma_buf
ion_device_add_heap / ion_heap_create / ion_chunk_heap_create
ion_secure_handle / ion_unsecure_handle
ion_secure_cma_mmap / ion_secure_cma_map_kernel / ion_secure_cma_allocate
msm_ion_get_base / msm_ion_parse_dt / msm_ion_populate_heap / msm_ion_allocate
msm_ion_heap_create / msm_ion_custom_ioctl        ← CUSTOM 面存在
ion_cp_change_mem_v2 / ion_cp_secure_buffer
```

源文件路径（`__FILE__`，0xE53213）：

```
/home/dpi/qb5_8814/workspace/P4_1716/android/kernel/drivers/gpu/ion/msm/msm_ion.c
```

DT 串：`qcom,ion-heap-type`、`qcom,default-prefetch-size`、`linux,contiguous`。

### 9.2 与 S4 的对照

| | S4 GT-I9500 | S5 G900F |
|---|---|---|
| ION 实现 | Samsung `drivers/gpu/ion/ion.c` | Qualcomm `drivers/gpu/ion/msm/msm_ion.c` |
| `ION_IOC_CUSTOM` | **空**（上机实测 cmd 0..8 全 `ENOTTY`） | **有**（`msm_ion_custom_ioctl` + cp/secure 一整套） |
| CVE-2016-6728 / 2017-0564 | 判 ABSENT 的唯一理由就是"没有 CUSTOM" | **该理由不成立**，需按 msm 代码重审 |
| 实测状态 | 可达、infoleak（handle=0xd8aed780）、占位型 spray、TOCTOU 只赢 refcount | 未上机、未审计 |

### 9.3 但对 43499 仍然无效（关键点）

ION 的 infoleak 给的是 **kernel heap 地址**；而 43499 在 plist 上缺的是
**目标线程的内核栈地址**（伪 waiter 的 `node_list` 必须自指 `waiter+0x0C`）。

**堆地址 ≠ 栈地址。** ION（无论哪个实现）都补不上这一环。
只有当 ION 存在**真正的任意读/写或内存破坏**缺陷时才有意义，infoleak 不够。

### 9.4 若仍要走 S5 ION 线，入口与判据

1. 定位 `msm_ion_custom_ioctl` 的地址
   （本镜像的符号名表是"只有名字指针的数组"，取不到 value；需解码 kallsyms 或按 cmd 常量定位）。
2. 审 custom cmd 的参数校验（msm 的 cp / secure 路径历史上出过 CVE）。
3. 判据只有一条：**它能不能读/写内核内存**。不能，就对 43499 没有价值。
