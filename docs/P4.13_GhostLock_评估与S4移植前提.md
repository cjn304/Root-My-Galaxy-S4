## 2. 设备级验证一：bug 在设备内核中确实存在

不按版本推断，直接反汇编设备 `kernel.raw`（kallsyms：`remove_waiter` c06f0b9c，区间 0x384 字节）：

```
c06f0bc4:  mov r3, sp
c06f0bc8:  bic r8, r3, #0x1fc0      ; current = sp & ~8191（THREAD_SIZE 对齐，两步 bic）
c06f0bcc:  bic sl, r8, #63
c06f0bdc:  ldr r0, [sl, #12]        ; current->task
c06f0c14:  str r7, [r0, #940]       ; current->pi_blocked_on = NULL（task+0x3ac）
```

**用的是 current，不是 waiter->task。**（修复版会从 waiter 参数 r1 的 +40 偏移取 task。）

设备版本串：`3.4.5-6264821 (dpi@SWDG2906) gcc 4.8 SMP PREEMPT` —— FUTEX/SMP/PREEMPT 前提齐备。

源码树（3.4.67）对应路径已读，与描述逐字一致：

```c
/* kernel/rtmutex.c */
static void remove_waiter(struct rt_mutex *lock, struct rt_mutex_waiter *waiter)
{
    raw_spin_lock_irqsave(&current->pi_lock, flags);   /* BUG: current */
    plist_del(&waiter->list_entry, &lock->wait_list);
    current->pi_blocked_on = NULL;                      /* BUG: current */
    ...
}

/* kernel/futex.c requeue 循环内 */
ret = rt_mutex_start_proxy_lock(&pi_state->pi_mutex,
                                this->rt_waiter,   /* waiter 在被挂起任务的栈上 */
                                this->task, 1);    /* current 是 requeue 发起者 */
if (ret) { /* -EDEADLK */ ... goto out_unlock; }     /* → remove_waiter(current) */
```

`futex_wait_requeue_pi` 确认 waiter 在**被挂起任务自己的内核栈**上：`struct rt_mutex_waiter rt_waiter; ... q.rt_waiter = &rt_waiter;`。

## 3. 设备级验证二：plist 路线的两个硬事实

### 3.1 waiter 布局（12 字，与长文算术一致）

```c
/* kernel/rtmutex_common.h:47 */
struct rt_mutex_waiter {
    struct plist_node list_entry;      /* 5 字: prio + prio_list(2) + node_list(2) */
    struct plist_node pi_list_entry;   /* 5 字 */
    struct task_struct *task;          /* 1 */
    struct rt_mutex *lock;             /* 1 */
};
```

`CONFIG_DEBUG_RT_MUTEXES is not set`（.config:3240）→ 无额外 3 字。**合计 12 字 = 48 字节** ✓

### 3.2 对齐：pselect6 在 3.4 上覆盖不到 waiter

`SELECT_STACK_ALLOC = FRONTEND_STACK_ALLOC = 256`（include/linux/poll.h:20-21）：

- `stack_fds` = 32 长字；每集合上限 `sizeof(stack_fds)/6` = 21 字节
- `FDS_LONGS(n) = (n+31)/32` → 栈路径要求 `n ≤ 160` → **size ≤ 5 长字/集合**
- 布局：`in`(0-4) / `out`(5-9) / `ex`(10-14) 用户可控（`get_fd_set` 拷贝）；`res_in`(15-19) / `res_out`(20-24) / `res_ex`(25-29) 由 `zero_fd_set` 清零
- **与 P2.4 实测完全吻合：用户可控 word 0–14，word 15–29 内核清零区**

而 P2.4 实测 waiter 在 word 30（偏移 0x78）：

- pselect6 的 `stack_fds` 只覆盖 word 0–29，waiter（48 字节，word 30–41）**在窗口之外**
- `n > 160` 走 kmalloc，离开栈，对栈回收无用

**→ 长文"硬性前提：对齐"成立且已量化：pselect6 这条 reclaim 在 3.4 几何下够不着 waiter。** 需要换 reclaim 系统调用（更深的调用链，或其缓冲区落在 waiter 深度），S5/S6 必须各自重测——不能照抄 6.x。

### 3.3 决定性发现：伪造 plist_del 在这台设备上 = 必 panic

设备 kallsyms 有 `__list_add`(c025cd2c) / `__list_del_entry`(c025cd68) / `list_del`(c025ce58) —— 这些符号只在 `CONFIG_DEBUG_LIST=y` 时存在（否则是 static inline）。**设备确认开启 DEBUG_LIST。**

反汇编设备 `__list_del_entry`：

```
c025cd78:  ldr r2, [r0]          ; next = entry->next
c025cd84:  ldr r3, [r0, #4]      ; prev = entry->prev
c025cd88:  cmp r2, #0x10001000   ; next == LIST_POISON1?
c025cd98:  cmp r3, #0x20000200   ; prev == LIST_POISON2?
c025cda0:  ldr r1, [r3]          ; prev->next
c025cda4:  cmp r0, r1            ; prev->next == entry?
c025cdac:  ldr r1, [r2, #4]      ; next->prev
c025cdb0:  cmp r0, r1            ; next->prev == entry?
c025cdb8:  str r3, [r2, #4]      ; next->prev = prev  ← 写原语本体
c025cdbc:  str r2, [r3]          ; prev->next = next  ← 写原语本体
; —— 四个检查任一失败 →——
c025cde4:  bl 0xc0034c8c         ; WARN: 打印 "list_del corruption"
c025cde8:  udf #18               ; 然后无条件 BUG()
c025ce0c/30: b 0xc025cde8        ; 其余失败分支全部跳到 BUG
```

`__list_add`（c025cd2c）同样：检查失败直接 `udf #18`，无 WARN 回退。

**结论：**

| 场景 | 主线 3.4 + DEBUG_LIST | **本设备（Samsung 补丁）** |
|---|---|---|
| 伪造 node 通过自指检查 | 获得 unlink 双写 | 同 |
| 伪造 node 检查失败 | WARN + 跳过（无写、不崩） | **WARN + BUG → panic_on_oops=1 → 重启** |

而通过检查需要 `prev->next == entry && next->prev == entry`，其中 `entry` 是伪造 waiter 的**绝对栈地址**——没有这个地址就填不出自指。**即：长文说的"自指死结"在设备上不仅仍然存在，失败代价还从"写不进去"升级为"必 panic"。**

## 5. 两个长文没提、但可能重要的点

1. **设备无 KASLR**：ktool 全套硬编码地址（c0c0ae28 等）跨开机有效，说明内核加载基址固定。那么 waiter 栈地址虽无直接泄漏，但落在确定性区域，**堆喷射/暴力枚举自指值有理论可能**——这是 P2.6"没有 infoleak"结论在新事实下的潜在松动点，值得单测。
2. **ktool 与 GhostLock 互补**：ktool 已有任意内核读——可以直接读出 waiter 的栈地址，补上自指所需的最后一个数。GhostLock 的增量价值在于一条**不依赖 lkmauth bootmode 的独立写原语**（模块路线若被堵死时的备份）。

## 6. 下一步（按优先级）

1. **换 reclaim 系统调用并重测对齐**：目标是让可控缓冲区覆盖 word 30–41。候选：`prctl(PR_SET_MM_MAP)`（3.4 的栈几何需实测）、`recvmsg`/`cmsghdr`、`set_robust_list` 等带栈拷贝的调用——先写一个栈深度探针（P2.4 方法）扫一遍。
2. **测栈地址可预测性**：无 KASLR 下反复起同构线程，读 `/proc/<pid>/stat` 的 kstkesp 或用 ktool 读 thread_info，看 waiter 栈地址的熵。若能预测 → 自指可构造 → plist 双写可用。
3. **验证触发**：3 线程 PI 环 + -EDEADLK 回滚，在设备上确认 dangling waiter（P1 已有分析，缺的是端到端复现）。
4. 以上任一通过后再谈写原语目标（modprobe_path / cred）。

# P4.13 续二 — 几何对平（设备反汇编重测，废止 §24/§25/§26 全部数字）

## 11. 用户指出的矛盾成立

「waiter = E−0x1B0」与「msgctl D=0x190 = waiter+0x20」不能同时成立——**§24 把 0x190 = 0x1B0 − 0x20 写成了 +0x20（符号错误）**。且三节各用一套几何。§26 整张表确实不该引用。

## 12. 根因：depthcalc 约定漏算每层 bl 的 4 字节返回地址

不复跑 depthcalc（它本身带这个 bug），改为**直接从设备 kernel.raw 反汇编实测**，统一约定：深度 D = 地址距 syscall 入口 SP 的偏移；每次 `bl` 压 4 字节；**结构体向浅层生长**（waiter+X 的深度 = depth(waiter) − X）。

| 链 | 实测 | 深度 |
|---|---|---|
| `sys_futex` 帧 | push 0x2C + sub 0x2C | 0x58 |
| → `do_futex` 帧 | push 0x2C + sub 0x5C | 0x88 |
| → `futex_wait_requeue_pi.constprop.16` | rt_waiter = fp−0xCC = entry−0xD0（`str ip,[fp,#-0xA4]` = rt_waiter.task=NULL 证实） | — |
| **waiter** | 0x58 + 4 + 0x88 + 4 + 0xD0 | **E−0x1B8** |
| `sys_msgctl` 帧 | push 0x2C + sub 0xA4 | 0xD0 |
| → `msgctl_down`（单 bl，c01f23cc 直调） | tbuf_old = fp−0xBC（`sub r0,fp,#0xbc` + `mov r2,#0x38` 证实） | **D=0x194** |
| `sys_semtimedop`（无嵌套调用） | fast_sops = fp−0x1AC（`sub r5,fp,#0x1ac` 证实） | **D=0x1B0** |

**waiter 字段深度**（结构体向浅层）：list_entry 0x1A5–0x1B8，pi_list_entry 0x191–0x1A4，task 0x190，lock 0x18C。设备 waiter 布局由 `adjust_prio_chain` 反汇编直接证实：`ldr r0,[r7]`=prio(+0x00)、`ldr r8,[r7,#0x2c]`=**lock@+0x2C**；`plist_first_entry` 的 `sub r2,r2,#0x20` 是 `pi_list_entry.node_list`（+0x14+0x0C）的偏移，不是 pi_list_entry 本身——我曾据此误判布局，实际设备就是标准 12 字结构。

**真机日志校准**（lk_m1）：栈基 0xc7246000 → E=0xc7247FB8 → waiter=0xc7247E00。

## 13. 对齐后的三喷雾源表（废止旧表）

| 喷雾源 | D | 拷贝区（深度） | 覆盖 waiter 字段 | 触碰 list_entry？ | 判定 |
|---|---|---|---|---|---|
| msgctl IPC_OLD | 0x194 | [0x15D, 0x194] | task(0x190)✓ lock(0x18C)✓ | ❌ 不碰 | **buf[0x04]→task、buf[0x08]→lock** |
| msgctl IPC_64 | 0x15C | [0x104, 0x15C] | 都够不着 | ❌ | 无用 |
| semtimedop | 0x1B0 | [D−6·nsops, 0x1B0] | task✓ lock✓ | **✅ 打烂 node_list(+0x0C/+0x10)** | 死（见下） |

**命中证据解释**：msgctl 拷贝覆盖 task/lock 且不碰 list_entry——§24 的定性结论成立，但字段映射是 buf[0x04]/buf[0x08]，不是它写的 0x08/0x0C。

**§25 的压栈结论成立**：`__copy_from_user` 序言 9 寄存器压栈区 = [S, S+0x24] = [0x19C, 0x1C4]，**整个 list_entry（0x1A5–0x1B8）被砸烂**——自指链表没了，DEBUG_LIST 检查必炸。这才是 msgctl 的真正死因（拷贝本身是干净的）。

**semtimedop 的死法（第三种）**：拷贝区 [D−6n, 0x1B0] 覆盖 node_list（0x1A5–0x1AC 中的 0x1A5–0x1B0 段）+ pi_list_entry + task + lock，但**不碰 prio(+0x00) 和 prio_list.next(+0x04)**——内核写的 `prio_list.next` 自指幸存，`list_empty(prio_list)` 为真跳过该分支；但 `list_del_init(node_list)` 的检查需要 node_list 自指 → 用户数据填不出 → BUG。不是“覆盖太多”也不是“够不着”，是**打烂 node_list**。

## 14. 修正后的几何窗口（替代 §26）

要写 lock(0x18C) 且不破坏 list_entry 自指（拷贝和压栈都不碰 0x1A5–0x1B8）：

```
拷贝基 D ≤ 0x1A4（拷贝区 [D−size, D] 整体浅于 list_entry）
调用点 sp S ≥ 0x1B9（压栈区 [S, S+0x24] 整体深于 list_entry）
⇒ S − D ≥ 0x15
```

- msgctl：D=0x194 ✓ 但 S−D=8 ✗（压栈砸 list_entry）
- semtimedop：D=0x1B0 ✗（拷贝本身砸 node_list）
- **两者都不满足；需重扫全部 syscall（修正约定下所有嵌套拷贝的 D 要 +4×层数）**

## 15. 残留 4 字节疑点（未决，需一次探针实测）

喷雾程序 `msgctl_spray.c:181-182` 用 **buf[0x08]→task、buf[0x0C]→lock**，与本表相差整整 4 字节（正好一个 bl 返回地址）。三种可能：①本表某处仍差 4；②程序注释偏移与实际写入不一致；③命中现场用的 Spray 版本与现存源码不同。

**一次探针即可裁决**：probe 模式下在 buf[0x08] 和 buf[0x0C] 放不同标记（如 0xAAAA0008 / 0xAAAA000C），看 `rtmutex_common.h:74` BUG 现场的 r8 是哪一个。r8=…0008 → 本表正确；r8=…000C → futex 链还差 4 字节（唯一嫌疑：do_futex→fwrp 的 `str lr,[sp]` 出参区算术）。

## 16. 结论

- §24/§25/§26 的数字全部作废，几何以第 12 节表为准（设备反汇编 + 真机日志双重来源）。
- msgctl 通道真实存在且写得到 task/lock——**但被自己的压栈帧否掉**；semtimedop 被拷贝本身否掉。两条路的死因不同，但都通向同一个结构性结论：**没有栈地址泄漏，list_entry 的自指无解**。
- 下一步不是重跑 depthcalc，而是：①探针裁决 4 字节疑点；②按修正约定的全 syscall 重扫（找 S−D ≥ 0x15 且 D ≤ 0x1A4 的拷贝点）。

**① 本设备 get_user 是 out-of-line 叶子 helper，不是内联。**
`sys_msgsnd` 反汇编：`bl __get_user_4` + `mvn r0,#13` 分支 + `str` 回栈。helper 本体（c0249bc0）无 push、无帧，`mov pc,lr` 返回——所以 helper 模式只压 4 字节返回地址，**等效于内联直写**（原计划中"get_user 无压栈问题"的假设成立，只是形态不同）。

**② syscall 树扫描有 blx 盲区。**
第一版从 324 个 syscall 入口递归 bl/b（`stepB_scan.py`，窗口命中 5264 个 str 但 get_user 判据 0），原因是 ioctl/socket 路径大量 `blx rX` 间接调用被截断——`do_ipv6_setsockopt.isra.7` 正是 blx 背后，树扫描永远走不到。

**③ 全内核扫（绕开盲区）才是终判。**
`stepB_full.py` 一次反汇编整个 text（c0008180–c0a3f000，263 万条指令），按 kallsyms 切分，找所有「bl __get_user_N(1/2/4/bad) 后 8 条内 str 到栈」的对：

```
全内核 get_user+str 对：共 18 个
相对深度分布：0x00-0x3f: 6 | 0x40-0x7f: 8 | 0x80-0xbf: 2
              0x100-0x13f: 1 | 0x140-0x17f: 1 | >=0x180: 0
```

**绝大多数 get_user 的结果用于比较/计算，不 str 回栈**——get_user 的典型用法如此，批量搬数据都走 copy_from_user（续四已扫空）。

## 29. 唯一临界候选的精确判定：setsockopt IPv6 差 12 字节

18 个对里只有两个相对深度值得追：`snd_rawmidi_info_select_user`（rel 0x12c，ALSA ioctl 间接链）和 `do_ipv6_setsockopt.isra.7`（rel 0x15c，源码 `ipv6_sockglue.c:955 get_user(len, optlen)` → `str r2,[fp,#-344]`）。

## 31. §30 的三条"封死"逐条失效

| §30 的判断 | 现状 | 错在哪 |
|---|---|---|
| 无几何窗口（13 个 copy 点 + 18 个 get_user 对全空） | **失效** | 前提错了：假设"必须用 spray **覆盖**一个已存在的 waiter"。实际可以**从头构造**——semtimedop 的 `fast_sops[64]` 起点就是 waiter+0x00，整块 0x30 字节全部由 `struct sembuf` 的 `sem_num/sem_op/sem_flg` 拼出来 |
| 无栈地址泄漏 ⇒ 自指无解 | **已补上** | 两条路：① 模块 `waiter <tid>` 读 `task->pi_blocked_on`；② 纯 ktool 遍历 `tasks` → `task+0x04`(stack)。后者不需要模块 |
| `SEC_DEBUG_LIST_PANIC` ⇒ 猜错即 BUG | **被满足，不是被绕过** | 拿到真实栈地址后可以**精确构造**自指（`prev->next == entry && next->prev == entry`）。四个崩点逐个填对后，检查自然通过 |

**最关键的认知反转**：§13 把 "semtimedop D=0x1B0" 当作否决理由（"整块 waiter 被覆盖 / 打烂 node_list"）。
但在 `sops = waiter + 0x00` 这个正确几何下，**"覆盖整块 waiter" 正是我们要的能力**——它不是破坏旧结构，而是**按我们的意愿重建整个结构**，包括三处自指。

§13/§14 的结论建立在"spray 只能覆盖部分字段、剩下的自指必须原样保留"这个假设上。一旦确认可以**全量重建 + 已知栈地址精确填自指**，整张窗口表就失去意义了。

## 32. 三处修正（P4.46 实测 → P4.47 复核）

| # | 原判断（§13/§14 及更早） | 实测/源码修正 |
|---|---|---|
| 1 | `prio = 0xffff0000(−65536)` 比所有真实 prio 小 ⇒ 永远不是 top waiter，不会被 wake | **反了**。`plist_add` 是**升序**插入（`if (node->prio < iter->prio)` 插到前面），`plist_first` 取**最小**值 ⇒ −65536 一插入就是 **top waiter**，unlock 时**立刻**被 wake |

| 3 | `sem_flg` 只能取 0 / 0x800 / 0x1000 / 0x1800 | **错**。3.4 `ipc/sem.c` 的校验循环只统计 `max sem_num` / `SEM_UNDO` / alter，**不检查 sem_flg 未知位** ⇒ 可填任意 16 位。这一条同时解放了 semop 的 `task` 和 semtimedop 的 `lock` |

## 33. P4.50：四个崩点连续内移

这一轮的价值在于**每次崩在更深的函数**——崩点内移就是进度。

| 轮次 | 崩点 | 根因 | 修法 |
|---|---|---|---|
| 1 | `do_futex+0x474 → __list_add` | `futex_lock_pi_atomic` 内联段把假 task 当 owner，`list_add(&pi_state->list, &task->pi_state_list)`，而 `task+0x3E0`（pi_state_list）为 NULL | 按 system_server 实测基准补自环 +0x3E0/+0x3E4，并把 `usage`(+0x08) 设为正数 |
| 2 | `do_futex+0x490 → rt_mutex_unlock → plist_del → __list_del_entry+0x38` | 内核删的是 **`pi_list_entry`(+0x14)**，金丝雀当时只填了 `list_entry`(+0x00) | 两组 plist_node 都填 |
| 3 | `rt_mutex_adjust_prio_chain+0x1ac → plist_del+0x2c` | 同因：`adjust_prio_chain` 走的是另一组节点 | 同上（两块不重叠，必须都给合法值） |
| 4 | `enqueue_task+0x6c` | `sched_class` 槽位偏移错 + `+0x04 enqueue_task` 未填 | 见 §34 |

配套确立的**硬几何**（与 `rtmutex_common.h:47` 源码逐字段吻合）：

```
struct rt_mutex_waiter {
    struct plist_node list_entry;     /* +0x00: prio@0, prio_list@+4/+8, node_list@+0xC/+0x10 */
    struct plist_node pi_list_entry;  /* +0x14: prio@0x14, prio_list@+0x18/+0x1C, node_list@+0x20/+0x24 */
    struct task_struct *task;         /* +0x28 */
    struct rt_mutex *lock;            /* +0x2C */
};                                    /* 合计 0x30 */
```

上一节 §12 写的 "lock@+0x2C / task@+0x28" 是对的；但当时把 `+0x14` 误当成 waiter 基址（其实是 `pi_list_entry`），导致只填了一组节点。

`sem_num` 恒 0（nsems=1）带来的硬约束：**高 16 位来自 sem_num 的字段，地址必须 < 0x10000；低 16 位来自 sem_num 的字段，地址必须 64KB 对齐**。这直接决定了 stub 页怎么分配（本机用 `0x8000/0xC000/0xD000/0xE000` 低位页 + `0x50000000` 高位 64KB 页）。

## 35. D 的重新评估：从 "<5%" 到 "可做，但要改三处"

入口既已证死，剩下的是"一页内存同时扮演 task 和 cred"的布局题。最省事形态：

```
task_waking(+0x2C) = commit_creds (0xc005af14，ksym 实测)
r0 = 假 task 页  ⇒  内核把这一页当成 struct cred
而 commit_creds 改的是 current —— 即"释放锁的那个线程"，也就是我们自己
```

**核心洞察**（成立）：提交进 `current->cred` 的内存是**我们自己的用户页**，所以返回用户态后可以随手改。这把"布局必须精确"降级为"布局必须安全"。

### 35.1 三处必须修正的硬伤（源码核实）

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| 1 | **`caps` 不可能在 commit 时全 1** | `task+0x30` = `sched_class`（必须指向用户页），`cred+0x30` = `cap_permitted` → 必然等于 `0xA000`；`task+0x38`(`se.load.inv_weight`) 与 `cred+0x38`(`cap_effective`) 同样冲突 | 只能事后改。好消息：`selinux_capable()` 先调 `cap_capable()`，`-EPERM` 就直接返回，**不走 AVC、不读 sid**，caps 不全反而更安全 |
| 2 | **`new->user` 必须有效** | `cred.c:518` `if (new->user != old->user) atomic_inc(&new->user->processes);` | 填 0 ⇒ `atomic_inc(&NULL->processes)` ⇒ Oops ⇒ panic_on_oops=1 重启。**必须从 old cred 拷**（且拷了还能让两个 atomic 分支都不走） |
| 3 | **`BUG_ON(atomic_read(&new->usage) < 1)`** | `cred.c:491`，而 `usage` = `cred+0x00` = `task+0x00` = **`state`** | `state` 必须是 1 或 2；`state=0` ⇒ usage=0 ⇒ **直接 panic** |

### 35.2 一个容易被漏掉的副作用

`ttwu_do_wakeup` 会执行 `p->state = TASK_RUNNING`(=0) → **把 `cred->usage` 清零**（同偏移）。
之后若有 get/put 配对，`atomic_dec_and_test` 1→0 → `__put_cred` → `call_rcu` → `kmem_cache_free(cred_jar, 用户页)` ⇒ **把用户页当 slab 释放**。

规避：返回用户态后**第一件事**把 usage 改成大数（假 task 使命已完成，state 无所谓）。

|---|---|---|
| **CVE-2026-43499**（GhostLock，Nebula Security VEGA） | 2026 年；引入 `8161239a8bcc`、修复 `3bfdc63936dd`；影响 **2.6.39 – 7.1-rc1**；只需 `CONFIG_FUTEX_PI` | **目标漏洞**：rt_mutex/futex PI waiter 生命周期缺陷 → 受控间接调用 |
| **CVE-2015-1805**（iovyroot） | 2015 年；pipe **iovec 数组越界** | **辅助原语**：任意内核读写（`ktool.c` 的 kread/kwrite 用的是它），用来补栈地址 / 改 cred |

本机方案 = 43499 的链 + 1805 的读。两者独立，"43499 什么时候修"与 "3.18.13" 无关。

#### 依赖关系随 waiter 形态而变（这是"换设备"判断的核心）

```
plist（3.4 / 3.10）：43499 链 = 43499 的调用能力 + 一个内核读原语（补栈地址）
rbtree（3.14+）    ：43499 链 = 43499 单独（rb_insert_color 重平衡写自带栈地址泄漏）
```

⇒ **"不需要 insmod" ≠ "不需要洞"。** 在 plist 上，若读原语也被回填修复，链同样跑不起来。
"唯一还站着的路"只在 **rbtree + 模块路被堵** 这个交集里成立（Root-My-Galaxy 的场景，不是 S4 的）。

#### 「不需要 insmod」这个价值的真实边界

先纠正一个常见误述：「su 依赖模块 + bootmode=2 + permissive 一位」**不准确**。代码核实：

`src/ktool.c` 全文只有**一处** `open("/dev/ktool")`，在 `do_ctx()` 里，且注释明写
"模块没加载时返回非 0，调用方自行兜底"：

| 功能 | 实际依赖 |
|---|---|
| `ktool root` / `pwn`（改 cred、permissive） | **1805**（writev + madvise + sendmmsg），不需要模块 |
| `ktool dump` / `find` | 同一套 1805 kread，不需要模块 |
| `do_ctx`（换 SELinux 域） | 模块，**可选** |
| `ktool boot`（insmod） | 模块 + `bootmode=2`，**只有这一步真依赖模块** |

⇒ 模块是**可选的加速层**（`waiter`/`ksym`/`ctx`/`avcflush`），不是 su 的前提。
"模块路断了"≠"su 没了"——`ktool root` 照样能跑。

#### 稀缺性判断：稀缺的不是"洞"，是"读原语"

43499 覆盖 2.6.39–7.1-rc1，**几乎全中，本身不稀缺**。真正稀缺的是能读内核内存的原语。
且读原语一旦存在，同一套机制通常连写也有（1805 就是读写同源）——**那时直接改 cred 比搭 43499 链省事得多**。

所以 43499 的独立价值只在两个条件的交集里：**读原语被修 + 43499 仍在 + 内核是 rbtree**。
在 S4（plist，1805 可用）上，它跑通的最大意义是**证明了链本身**、为移植到 rbtree 机器做准备，
而不是 S4 上的实用提权——§30 在"实用价值近零"这一点上的判断，仍然成立。

#### 附：那篇分析里的一处数字混用

"SID 必须提前填对（986 或 210）"——**986 不是 SID**。按实测记录，986 是 `init_shell` 的
**type value**（用于 `permissive_map` 位索引），210 是 `kernel` 的 **type 索引**，
而 `system_server` 实测 `sid = 332`。三个数被混成了两档。
⇒ 该分析适合当方向参考，数字必须实测（见 §35.3）。

### 36.2 rbtree 比 plist **更简单**（不是因为结构小，是因为没校验）

| | plist（3.4 / 3.10） | rbtree（3.14+ / 5.x / 6.x） |
|---|---|---|
| 校验 | `CONFIG_DEBUG_LIST=y` + `CONFIG_SEC_DEBUG_LIST_PANIC` ⇒ `list_debug = 0x100` 恒真 ⇒ `BUG_ON` **无条件执行**；反汇编 `__list_del_entry@0xc025cd68` 已证四条检查被优化成 `udf #0x12` | `lib/rbtree.c`（401 行）**无任何运行时校验**（无 `DEBUG_RBTREE` / `__rb_erase_valid`） |
| 失败后果 | 主动 BUG ⇒ panic ⇒ 重启 | 只解引用，指针有效就走下去 |

**决定性差异是"主动校验 vs 被动解引用"**，不是"旋转涉及多少节点"。

由此得到的移植判断：

| 目标 build | waiter 形态 | 需要外部读原语补栈地址？ | 难度 |
|---|---|---|---|
| 3.4 / 3.10 | plist + DEBUG_LIST 硬校验（udf） | **是**（本机靠 1805） | **最难**（三重叠加） |
| 3.14+ / 5.x / 6.x | rb_node，无校验 | **否**——`rb_insert_color` 的重平衡写自带栈地址泄漏 | 更简单（Root-My-Galaxy 走的就是这条；载荷用 KernelSU late-load，不碰 commit_creds） |

⇒ **S4/3.4 是这条链最难的版本**，不是最有代表性的版本。换到 rbtree 的机器反而省事。

**踩坑备忘**：
- `/dev/ktool` 在 rmmod 后被 devtmpfs 删除，此时 shell 重定向会**创建普通文件**，之后 insmod 注册的 misc 设备不覆盖它 ⇒ 命令静默写进普通文件。解法：重启。
