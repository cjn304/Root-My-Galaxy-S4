# P4.9 模块路线实证：lkmauth 是内容哈希，改 1 个字节都拒

**时间**：2026-10-19 19:27
**结论**：之前的「设计上锁死」措辞要收回（当时只是推断），但现在有实证了——**校验是按内容哈希，模块路线确定死亡**。

---

## 1. 两组实验

### 实验 A：追加 4 字节（按建议做）

```
cp /lib/modules/scsi_wait_scan.ko /data/local/tmp/t.ko
echo AAAA >> /data/local/tmp/t.ko        # printf 在 toolbox 里不存在
insmod /data/local/tmp/t.ko
```

结果：`Exec format error (RC=255)`，文件 1865 字节。

dmesg：

```
TIMA: lkmauth--verification failed 64
TIMA: lkmauth--unable to load kernel module; module len is 1865.
```

**但这一次 ENOEXEC 是 ELF 结构被破坏导致的**（3.4 的模块加载器会读文件尾部的 `struct module`，追加字节让偏移错位），**没走到哈希比较**。所以这个实验本身不能定性。

### 实验 B：改 `.comment` 段 1 个字节，长度不变

`scsi_wait_scan.ko` 的段布局：

```
.text                 off=   52  size=    0
.init.text            off=   52  size=   28
.modinfo              off=   96  size=  140
.gnu.linkonce.this_module off=236 size=340
.note.gnu.build-id    off=  576  size=   36
.comment              off=  612  size=   32     ← 改这里
.shstrtab             off=  691  size=  147
```

把 `.comment` 第一个字节 `0x00` 改成 `0xFF`，文件仍 1860 字节。

结果：`Exec format error (RC=255)`。

dmesg：

```
TIMA: lkmauth--launch the tl to check kernel module; module len is 1860
mcdrvkmod mcd: 901|Tl_TIMA_LKMAUTH::send_msg_tima_lkmauth_verify_module
mcdrvkmod mcd: 501|Err tima verify_module: Module Hash value does not match, addr:200000, len:744
TIMA: lkmauth--verification failed 64
TIMA: lkmauth--unable to load kernel module; module len is 1860.
```

**`Module Hash value does not match`**——这是 TrustZone trustlet 打印的，明确是**哈希比对**。

改的只是一个 `.comment` 段里的填充字节（`0x00`），加载器根本不读它，但哈希变了，直接拒。

---

## 2. 结论

| 之前的说法 | 现在的实证 |
|---|---|
| 「设计上锁死」 | 措辞收回——当时只是推断 |
| 可能是结构性检查（ELF 头 / vermagic） | **不是**，`.comment` 的填充字节都计入哈希 |
| 内容哈希白名单 | **确认**，`Module Hash value does not match` |

**模块路线死亡，这次是实证不是推断。**

顺带一个细节：哈希覆盖的长度是 **744 字节**（`len:744`），不是整个 1860 字节文件。`.comment`（offset 612）落在这个范围内。所以校验的是「可加载映像 + 段表之前的区域」，不是简单全文件 MD5。

## 3. 代价

- 产生 **2 条** TIMA 失败记录（`verification failed 64`）
- `ro.boot.warranty_bit` 仍为 **0**
- 未重启（uptime 02:03:43 连续）
- `/proc/modules` 空，无残留

属于运行期 dmesg 级记录，与之前那次 `SELinux verification failure` 同级。

## 4. 模块的收益到底是什么（假设能加载）

这是用户问的核心。如果 lkmauth 那道门能过，模块带来的是**质变**，不是量变：

### 4.1 能正确刷 I-cache——解决现有方案唯一的未定义行为

现在改 `sys_execve` 是用户态越界写内核 text，**不刷 I-cache**。ARMv7 的 I/D cache 不保证一致，这是未定义行为（实测最坏只是补丁不生效，但没保证）。

模块里可以：

```c
set_memory_rw((unsigned long)target & PAGE_MASK, 1);
*(u32 *)target = new_insn;
set_memory_ro((unsigned long)target & PAGE_MASK, 1);
flush_icache_range(target, target + 4);   // ← 关键
```

**这是标准做法，把"靠运气"变成"确定"。**

### 4.2 免竞态

现在每次 `ktool sh` 都要：
- `writev(pipe, iov, 257)` 触发越界
- `madvise(MADV_DONTNEED)` 抢「预取后、拷贝前」的窗口
- `sendmmsg` 喷 kmalloc-4096 残留
- 失败最多重试 300 次

模块加载是**一次性、确定性**的操作，没有窗口、没有喷雾、没有重试。

### 4.3 能力上限完全不同

| 现在（越界原语） | 模块 |
|---|---|
| 只能按地址读写 | 可以调用任意内核函数 |
| 改 cred 要遍历 task 链表 | 直接 `commit_creds(prepare_kernel_cred(0))` |
| 改 SELinux 要伪造 `permissive_map` + 清 AVC | 直接改 `selinux_enforcing` 或注册 hook |
| 无法观察内核行为 | 可以注册 kprobe，**能解决 P4.8 那个 `0x1ec` 矛盾** |
| 写死地址，换机型全废 | 用符号表/函数指针，可移植 |

### 4.4 本次开机内常驻

模块加载后一直有效，可以暴露一个 `/proc/ktool` 接口给用户态：

```
echo root > /proc/ktool     → 提权当前进程
echo patch > /proc/ktool    → 打 sys_execve 补丁
```

不需要每次重新跑 exploit。

### 4.5 但这些都是"如果"

**哈希校验挡在门口，上述收益一条都拿不到。**

唯一能合法加载的模块是原厂那三个，而它们的功能与我们无关。

## 5. 关于 2a / 2b 的拆分

| 形态 | 内容 | 验证成本 |
|---|---|---|
| **2a 自愈式** | 钩子跑 exploit → 内核补丁就位 → 本次开机内 `ktool sh` 可用 | 低 |
| 2b 常驻式 | 2a + 守护进程 + 文件 IPC | 高 |

**同意先做 2a。** 补充两点：

1. **`sec-sh` 的启动时机已核实**：`init.rc` 里没有 `start sec-sh`，只有 939 行的 service 定义；`class_start main` 在 675/676（`on nonencrypted`）、704/705（`trigger_restart_min_framework`）、707/708（`trigger_restart_framework`）三处，全部由 vold 解密后触发。**`/data` 必然已挂载。**

2. **2a 的真正难点不在 exploit 能不能跑，而在 `init_shell` 域能不能跑**。`init_shell` 有 `sys_admin`/`sys_module`/`net_admin` 等 14 项 caps，也有 `fifo_file`/`socket`，理论上够用。但 exploit 依赖的 `madvise` 竞态、`sendmmsg` 喷雾、`writev` 越界在 `init_shell` 域下是否都被允许，需要实测——这是 2a 唯一的未知数。

## 6. 顺带修正

1. **`rmmod` 成功不代表"模块能跑"**——`scsi_wait_scan` 是空模块（`init` 直接返回），只验证了加载/卸载通路。这一点之前没说清楚，接受。
2. **`/lib/modules` 在 ramdisk 里**，改它等于改 `boot.img`；自制模块只能放 `/data`（`insmod` 走路径参数）。这点之前没点明，接受。
3. **3.4.67 vs 3.4.5**：vermagic 可以手改，但 `struct module` 布局差异仍是风险——不过既然 lkmauth 在更前面拦，这些细节已无意义。
