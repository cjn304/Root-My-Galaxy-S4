# P4.88 ktool：restore 改名 enforce + 写原语的三个隐藏坑

日期：2026-10-24
对象：`src/ktool.c`、`src/targets.h`
触发：用户评审 restore 分档设计 + 顺带查模块解耦必要性

---

## 一、`restore` → `enforce`，删掉 `--stock`

用户评审的原意见（原文要点）：

> 关 permissive / 清 AVC / 撤 exec patch 三者可逆性不同，只有第三个是单向门。
> `--stock` 应该删掉——它的唯一效果是"在运行期主动把机器弄瘫，然后你还是得重启"，
> 它是"重启"的同义词。`--noflush` 保留但降级为诊断开关。命名要改：
> restore 名不副实，它没有"还原"任何东西，只是关掉了 permissive。

**结论：方向对，而且比原方案更该删**——`--stock` 本质是 `unpatch + enforce`，
而 `unpatch` 早就是独立命令，在 enforce 上再开一个"把机器弄瘫"的暗道纯属冗余。

落地：

| 命令 | 现状 |
|---|---|
| `enforce [--noflush]` | **主名**。关 permissive，默认清 AVC |
| `unperm` / `restore` | 保留为别名（`init.sec.boot.v9{e,f,g}.sh` 里有 3 处 `/system/bin/ktool restore`，不能静默改掉） |
| `--stock` | **删除**。传了只打印"已删除，它等于 unpatch + enforce" |
| `flush` | 独立命令不变，但加了运行时告警（见下） |
| `patch` / `unpatch` | 不变，`unpatch` 的单向门性质写进注释 |

`flush` 的告警直接写在命令里（原来只在 P4.12 文档里，操作的人看不到）：

```
! flush 会触发一波 avc denied 审计；实测可把 audit backlog 打爆导致复位（P4.12）
  确认系统静止后继续...（3s）
```

依据是 P4.12 §419-444 的实证：清 AVC + 清 permissive_map 后几秒内海量 denied →
`SecurityLogAgent` 已被禁用、没人消费 backlog → `audit: backlog limit exceeded` →
`RST_STAT=0x200` 复位（uptime 597s）。**所以 flush 要在系统静止时做。**

## 二、顺手抓到的栈溢出（`kwrite_verify`）

改完 enforce 一跑就段错误。定位：`kwrite_verify` 的读回缓冲是 `unsigned char b[64]`，
而 `do_unperm` 调它写 `modprobe_path` 时 len=256 → **读回 256 字节踩栈 192 字节**。

```c
-	unsigned char b[64];
-	if (len > MAXW) return -1;
+	unsigned char b[256];
+	if (len <= 0 || len > (int)sizeof(b)) return -1;
```

这条代码从 P4.28 起就在，只是 `restore` 那条路大概从来没在真机上跑通过
（一直段错误，被当成"模块没加载"之类的现象忽略掉了）。

## 三、最重要的发现：写原语的三个隐藏坑

做 B4（do_root 事务化）时连续踩到三个坑，全部用 `wtest`（在本进程自己的 cred 上
翻一个字节、写、读回、还原）实测定位。

### 坑 1：`kwrite` 永远返回成功，但字节不一定落地

（P4.87 已记录）每次独立一次 `kwrite` 的全落地率：
`len=8` 5/5、`16` 1/5、`32` 0/5、`48` 0/5、`72` 1/5。
→ 所以必须切 8 字节块。

### 坑 2：同一进程里**连着写**多块，第一块之后开始系统性失败

逐偏移单独写（每次一个新进程）：**9/9 全落地**。
但在一个进程里连写 9 块：uid/gid/eff 落地，euid/inh/perm/bset **每次都不落地**，
重试 6 次都一样——不是概率问题，是状态问题。

### 坑 3：写完立刻读回，读到的是污染数据

wtest 完整模式里，9 块写完后读回显示 bytes 16-19 = 0（即 euid=0），
而**同一时刻 `geteuid()` 返回 2000**。读回把结果整个判反。

先在 `iovyroot_write` 里加了 `drain()`（原来只在失败时抽），
10 次完整写从"几乎全错"变成 8/10 全对——**但 drain 不够**。

真正的解法是观察到的对比：

| 写法 | 结果 |
|---|---|
| 9 块连写，块间不读 | 大部分块不落地 |
| 9 块连写，**每块后穿插一次读**（`kwrite_verify_buf` 内部就有） | 8/10 全部落地 |

即：写完必须接一次读来"复位"管道状态。

### 因此 promote 的验证换成内核视角

```c
kt_write_rb()        /* 8 字节块 + kwrite_verify_buf（写+读+比），
                         但不轻信其返回值 */
+ 循环 6 次：
     kread_buf 读当前值 → 改 → kt_write_rb 写 9 块
     kt_caps_full() && getuid()==0 && geteuid()==0  → 成功，退出
+ 6 次都不成 → 按快照回滚 → 报失败
```

`kt_caps_full()` / `kt_cred_matches()` 用 `getuid/geteuid/getgid/capget`，
走内核的 `current_cred()`，**是唯一可信的地面真相**。
（`unroot` 最初只校验 uid，第 2 次测试就露出 euid 没还原；已改成 uid/euid/gid/egid/caps 全比对。）

实测 6/6：

```
promoted: uid=0 euid=0
unroot: uid=2000 euid=2000 gid=2000
```

## 四、模块解耦要不要做？

现状（`kmod/ktool_mod.c`）：偏移已经全部走 `targets.h` 的 `tgt->off_task_cred` 等，
只有 `ktool_is_uid0()` 里还有一个硬编码 `0x2FC`。也就是说**它已经是表驱动的**。

判断：**不值得为它单独做一轮**。

- 换机时真正的门槛是 **insmod 权限**（KNOX/TIMA 会不会拦），不是布局；
  布局问题用现有工具就能在设备上标定（`sym` 拿符号 → `scan4` 找引用 →
  `walk` 顺指针 → `fld` 读字段，P4.85 已闭环），然后改 targets.h 重编；
- 模块的独特价值（SELinux 实验、GhostLock waiter 几何）都跟具体内核强绑定，
  可移植性收益低；
- 优先级明显低于"找第二个读原语"。

要做也只做两件小事：把 `ktool_is_uid0` 里那个硬编码 0x2FC 换成 `TASK_CRED`，
以及把 `ktool_target` 模块参数改成可写（多目标时能运行时选）。各几行，但不急。

## 六、为什么做不到“不重启的完全干净 restore”

### 我们自己的改动几乎都能干净还原

| 改动 | 还原方式 | 干净 |
|---|---|---|
| `permissive_map` 位 | `enforce` 清零 | ✅ |
| `modprobe_path` | 写回 `/sbin/modprobe` | ✅ |
| `exec_br`（.text） | `unpatch` 写回原指令，可逐字节校验 | ✅ |
| cred（uid/caps） | 只动自己进程，退出即消失 | ✅ |

### 还原不了的只有一样：AVC 缓存里烤进去的 PERMISSIVE 标志

`kmod/ktool_mod.c` 的 avcflush 注释就是根因：AVC 条目在**计算时**就把
`AVD_FLAGS_PERMISSIVE` 烤进了 `avd->flags`，所以 `permissive_map` 清零后，
已缓存的三元组仍按 permissive 放行——内核没有逐条目失效的接口。

清它有两条路，都不干净：

1. **无锁改活哈希表** → 环链 → `avc_search_node` 死循环 → 看门狗复位（P4.24 实测）。
   等于重启，比不清还糟。
2. **`avc_ss_reset(0)`**（内核官方 API，`security_load_policy` 内部也调它，
   按 slot 加 spin_lock + `call_rcu` 回收）→ 安全，但清完的瞬间，之前被 permissive
   放过的所有真拒绝一次性变成拒绝，涌进审计。

### 洪水会不会变成复位，取决于有没有人消费 backlog

P4.12 §419-444 实测：模块 restore **先杀 auditd**（本意是防止它被海量事件压垮），
结果没人消费 → `audit: backlog limit exceeded` → `RST_STAT=0x200` 复位（uptime 597s）。
**即“清 AVC”这个动作本身就可能直接导致复位。**

### 还有一层鸡生蛋

- 安全地清 AVC 需要一个内核执行体（insmod 的模块，或 permissive 下的 shell）；
- 而 restore 的最后一步恰恰是把这些关掉（`unpatch` 关 exec 检查、`enforce` 关 permissive）；
- 撤了 exec patch 后**任何 root exec 都被 KNOX 挡掉**，连“验证 restore 成没成功”都做不到；
- auditd 被杀了拉不回来（init 的活，shell 域起不了）→ 审计残废到重启；
- insmod 的模块卸不掉（卸载要 `CAP_SYS_MODULE`，且卸完 exec 就被挡）→ 内核内存就是痕迹。

另有一条**没接线**的路：`reload_stock_policy()` 想写 `/sys/fs/selinux/load` 重载策略，
内核内部同样调 `avc_ss_reset`（同样有洪水），且写那个节点要 SELinux 放行
（init 域或 permissive）——还是鸡生蛋。该函数目前**无任何命令调用**（死代码）。

### 结论

`enforce` + `unpatch` 已把所有“能关的东西”关掉且不留半改状态（6/6 实测）；
唯一残留是 AVC 缓存里带 PERMISSIVE 的旧条目，会一直按 permissive 放行到重启。

> **⚠ 本节结论已被 P4.89 推翻（2026-10-24 19:30）**
>
> 上面“唯一残留到重启”的前提是“flush 不安全”，而 P4.88 §七已经实测 flush 安全。
> P4.89 的受控实验进一步证明：
>
> - `flush`（`avc_ss_reset`）之后，AVC 会按**当前** `permissive_map` 重算 ——
>   `enforce`（默认 flush）确实能把 permissive 效果彻底消掉（E5：flush 后 remount 重新变拒绝）。
> - 模块也能卸：`pwn` → `flush` → `rmmod ktool_mod`（rc=0，`/dev/ktool` 消失），
>   因为 SELinux 拒绝的是 `capability:sys_module`，permissive map 能放行。
> - 所以**内核状态可以 100% 复位、不需要重启**。真正不能消除的只有**审计/日志痕迹**
>   （记录本身不可删改），不是内核状态。
>
> 另：本文 §九 把根因归为“AVC 陈旧条目”，P4.89 证明更根本的原因是设备内核
> `CONFIG_ALWAYS_ENFORCE=true` —— 全局 `selinux_enforcing` 对权限判定完全无效，
> 只有 `permissive_map` 起作用，因此必须 flush 才能让 map 变更生效。

## 七、实验：消费者全活着时，AVC 刷新还会不会打死机器（2026-10-24 17:11）

背景：P4.12 把复位归因于“清 AVC + 清 permissive 造成审计风暴”，
而风暴致命的前提是“没人消费 backlog”。当时 `SecurityLogAgent` 是禁用状态，
于是先把它取消禁用（`enabled=3` → `enabled=1`，进程 pid 29583 自动拉起），
并确认 **auditd(4280) + kauditd(4281) 本来就活着**。

### 步骤与结果

```
基线：uptime 127967s，audit.log 3436B，auditd/kauditd/securitylogagent 全在
① ktool pwn sh -c '<30 × /data/data/* 的 ls 循环>'   # full permissive 下制造拒绝
   → audit.log 3436 → 4224B（+788B，约 8 条记录）
② ktool enforce                                      # 清 permissive + avc_ss_reset
   → 之后 12 秒连续采样：audit.log 停在 4224B 不变
   → uptime 128137 → 128148 连续，无复位，无掉线
终态：modprobe_path = "/sbin/modprobe"（已还原），三个消费者进程仍在
```

### 结论

**没有风暴，也没有复位。** 消费者全活着时，`avc_ss_reset` 是安全的。
P4.12 的复位根因因此可以重新定性：不是“清 AVC”本身致命，
而是 `ktool_restore()` 里的 `ktool_stop_auditd()` **主动杀了 auditd**，
把唯一的消费者干掉，backlog 才爆的。`ktool enforce` 不杀 auditd，所以安全。

### 实验局限（如实记录）

没能人工造出 P4.12 那种“几秒内海量事件”：**AVC 缓存按
(scontext, tcontext, tclass, perm) 去重，同样的检查只审计第一次**。
6000 次 `ls /data/data/*` 只产生 1 条 `dac_override` 记录（见 audit.log  serial 230）。
所以“>1024 条 distinct 记录在 auditd 排空之前灌满 backlog”这个阈值**没有被测到**，
只测到了“刷新本身不产生风暴”。

要真测阈值，得先搞出大量 *distinct* 的拒绝组合（不同 tcontext/tclass/perm），
而不是重复同一个访问——这正好是 AVC 缓存的设计目的，人工造不划算。

### 对操作的影响

- 想恢复强制：用 `ktool enforce`（不杀 auditd，安全）；
- **不要用模块的 `restore`**（它会杀 auditd，等于把 P4.12 的复位条件凑齐）；
- 真想复现 P4.12：`pm disable com.samsung.android.securitylogagent` + 杀 auditd，
  两个条件缺一不可。

## 八、restore 的改法与部署阻碍（2026-10-24 17:30）

按第七节的结论改了 `kmod/ktool_mod.c` 的 `ktool_restore()`：

```diff
-	/* 先杀掉 auditd，避免清 AVC 后海量事件把它压垮触发看门狗 */
-	ktool_stop_auditd();
+	/* P4.88：删掉 ktool_stop_auditd() —— 实测见 §七。
+	 * 杀 auditd 才是 P4.12 复位的直接原因；消费者活着时 avc_ss_reset 无风暴。
+	 * backlog 超限时内核的设计行为是丢记录（audit_log_lost），不是阻塞关键路径。 */
```

`ktool_stop_auditd()` 函数本身保留（`-Wno-unused-function`），注释写明它现在只用于
**复现 P4.12**（杀 auditd + 禁 SecurityLogAgent 两个条件之一），正常操作不要调。

### 部署阻碍：/system 装不进去

```
mount -o rw,remount /system        → Permission denied
ktool pwn sh -c 'mount -o rw...'   → Permission denied（root + full caps + permissive 也不行）
```

不是 SELinux（permissive 已开），是三星 KNOX/TIMA 对 system 分区的保护。
`/system/lib/modules/ktool_mod.ko` 和 `/system/etc/init.sec.boot.sh` 都在只读分区里，
**更新只能走 ODIN/recOVery 刷机**。顺带说明：这条保护一直是生效的，
也就是之前所有改动都没碰到过 Knox Warranty Bit。

### 所以实际上不需要等刷机

查了设备上的开机脚本 `/system/etc/init.sec.boot.sh`——**它根本不调用模块的 restore**
（整个文件没有 ktool / /dev/ktool 字样）。模块的 `restore` 只有手工
`echo restore > /dev/ktool` 才会触发，而用户态的 `enforce`/`unpatch` 走的是自己的
写路径，从来不碰 auditd。

**操作规范（现在就能执行，不用等新模块）：**

| 想做什么 | 用哪条 | 会不会杀 auditd |
|---|---|---|
| 恢复强制（关 permissive + 清 AVC） | `ktool enforce` | 不会 |
| 连 exec 检查一起还原（单向门） | `ktool unpatch` | 不会 |
| ~~全部一把梭~~ | ~~`echo restore > /dev/ktool`~~ | **会**（旧模块仍在设备上） |

新模块已编译好（`kmod/ktool_mod.ko`，136588 B，旧的备份为 `kmod/ktool_mod.ko.old`），
等下次刷机时一起进 /system 即可；在那之前只要不手工敲模块的 restore 就行。

## 九、/system 到底能不能写：AVC 缓存陈旧条目（2026-10-24 18:30）

### 我上一轮说错了

§八里我写“`mount -o rw,remount /system` EPERM 是三星 KNOX/TIMA 对 system 分区的保护，
不是 SELinux（开了 full permissive 再试照样 EPERM）”。**这个结论是错的**，
错在没意识到 AVC 缓存。

### 真相（内核源码 + 实测）

1. **拒绝来自 SELinux**。`security/selinux/hooks.c`：
   ```c
   static int selinux_mount(...)
   {
	if (flags & MS_REMOUNT)
		return superblock_has_perm(cred, path->dentry->d_sb,
					   FILESYSTEM__REMOUNT, NULL);
	...
   }
   ```
   `superblock_has_perm` 走的是**不带** `AVC_STRICT` 的 `avc_has_perm`，
   所以 permissive 本该放行——审计记录也对上了：
   `avc: denied { remount } scontext=u:r:shell:s0 tcontext=u:object_r:rootfs:s0 tclass=filesystem`

2. **挡路的是 AVC 缓存里的陈旧条目**。`avc_denied()` 判的是
   `avd->flags & AVD_FLAGS_PERMISSIVE`，而这个 flag 是**条目插入时**算出来烤进去的。
   早期某次真实拒绝插入了"shell × rootfs × filesystem = denied 且非 permissive"，
   之后开 permissive map、甚至把全局 `selinux_enforcing` 直接写成 0，
   **缓存里的旧条目依然返回 denied**——这就是"开了 permissive 还 EPERM"的原因。

3. **清缓存后立刻放行**。`ktool flush`（= 模块 `avc_ss_reset(0)`）冲掉旧条目，
   重新计算时带上 PERMISSIVE 标志：
   ```
   ktool pwn ...     # permissive map 全开
   ktool flush       # 关键：清 AVC 缓存
   → mount -o rw,remount /system   rc=0
   ```

### 可复用的 /system 写入步骤

```
ktool pwn /system/bin/echo on        # ① permissive map 全开
ktool flush                          # ② 清 AVC 缓存（关键，别省）
ktool root sh -c 'mount -o rw,remount /system && cp <new> /system/lib/modules/ && mount -o ro,remount /system'
ktool w32 $(ktool sym selinux_enforcing | cut -d" " -f1) 1   # ③ 还原全局 enforcing
ktool enforce                        # ④ 清 permissive map + 还原 modprobe_path + 清缓存
```

已用这套把新模块（136588 B）装进 `/system/lib/modules/ktool_mod.ko`，
`/system` 已恢复 ro，`selinux_enforcing` 已还原为 1，auditd/kauditd 都在。
**下次重启生效**（开机脚本 insmod 它）。

### 附带发现

`selinux_enforcing` 在符号表里（`B selinux_enforcing` @ `0xc0c4d490`），
可以用 `w32` 直接写——比 `setenforce 0`（要写 selinuxfs，shell 域没权限）可靠。
`getenforce` 会跟着变。

### 对"之前怎么装的"的回答

就是 `apply2a_v3.sh` 那一套：`mount -o rw,remount /system && cp`。
那时候能成，是因为 AVC 缓存里还没有那条陈旧拒绝条目。
**之后每一次失败的 remount 尝试都会把它重新烤成非 permissive**，
于是越来越装不进去——典型的"缓存把一次性状态变成了永久状态"。
