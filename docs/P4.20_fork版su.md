# P4.20 — fork 版 su：socket 交给 app 域子进程持有

## 1. 结论

```
$ su -c id            # caller = uid 2000，库为空，需弹窗
Starting: Intent { cmp=me.phh.superuser/...RequestActivity (has extras) }
→ APK 弹窗 → 点"允许"
uid=0(root) gid=0(root) context=u:r:init_shell:s0
```

**弹窗、授权、提权、执行，全链路通过。**

---

## 2. 为什么必须 fork

unix socket 的 SELinux 标签是**创建者的域**（`sockcreate` / `current_sid`），不是文件路径的标签。

所以：

| 谁建 socket | socket 的 sid | APK（untrusted_app）能连吗 |
|---|---|---|
| su 提权后自己建 | `init_shell` | ❌ `untrusted_app → init_shell:unix_stream_socket` 无 connectto |
| su 提权前 fork 的子进程建 | 调用方的域 | ✅ 同域或 `untrusted_app → shell`（有 connectto） |

**这是 su_apk 版能跑只是因为 permissive 的根本原因**——它的 socket 由 init_shell 建。

---

## 3. 策略依据：为什么管道可以、socket 不行

```
init_shell    -> untrusted_app:unix_stream_socket = 无
init_shell    -> untrusted_app:fifo_file = append,getattr,ioctl,lock,open,read,write   ← 有
untrusted_app -> untrusted_app:unix_stream_socket = accept,acceptfrom,bind,connect,
                                                    connectto,create,listen,read,write,…
```

匿名 pipe 在 SELinux 里按 `fifo_file` 算，而 init_shell 对 untrusted_app 的 fifo 有完整读写。
所以**提权后的父进程可以用 pipe 和 app 域的子进程通信**。

---

## 4. 结构

```
su (caller 域, uid=caller)
 ├─ pipe(p2c), pipe(c2p)
 ├─ fork A（保持 caller 域）
 │    A: 读 p2c → 建 /data/local/tmp/sud/s → listen
 │       写 c2p "READY"
 │       accept → 写 13 帧协议 → 读结果 → 写 c2p "ALLOW"/"DENY"
 └─ 父进程
      close 多余 fd → 写 /dev/ktool "ish" → uid0 + init_shell
      白名单命中 / 数据库命中 → 写 p2c "x" 让 A 退出 → exec
      需要弹窗 → 写 p2c "go" → 读 c2p "READY"
                → fork 一个 am start（uid 0 才能拉起 exported=false 的 Activity）
                → 读 c2p "ALLOW"/"DENY" → exec 或退出
```

预建目录：`/data/local/tmp/sud`（0777，部署时建一次，`/data/local` 不是 tmpfs，重启保留）。

## 5. 实测中的一个假故障

第一次测弹窗失败，`su: denied (uid 2000, DENY)`，UI 里找不到 allow 按钮。排查了半天协议，最后发现是**屏幕熄灭了**——之前为了点按钮把 `svc power stayon false` 恢复了，测试时屏幕黑着，`uiautomator dump` 抓不到 Activity。

唤醒后立刻正常：

```
$ input keyevent 224; input swipe 360 800 360 100
$ uiautomator dump → grep 'id/allow' = 1
$ input tap 810 1848
→ uid=0(root) ... init_shell
```

**教训**：自动化点按钮前先确认 `dumpsys power | grep mWakefulness = Awake`。

## 6. 一个必须说清的边界：fork 没有去掉 permissive

fork 解决的是 **socket 跨域**，不是"让整套东西不依赖 permissive"。

permissive 仍然是必需的，原因在模块加载：

```
策略里 "load_module" 的 allow 规则数：0
```

没有任何域被允许加载内核模块，只能靠 permissive 放行新三元组。
所以 `ktool boot` 必须 `do_permissive()` 之后才能 insmod。

**fork 的真实收益**：socket 那条链现在走的是**真实 allow 规则**
（`untrusted_app → shell:unix_stream_socket connectto` 确实存在），
不再依赖 permissive 的"新三元组放行"。

换句话说：

| 环节 | 依赖 permissive 吗 |
|---|---|
| 模块加载 | **是**（load_module 零规则） |
| su 提权（写 /dev/ktool → init_shell） | 否（走 `domain → null_device`） |
| APK socket（fork 版） | **否**（走 `untrusted_app → shell`） |
| APK socket（su_apk 版） | 是（init_shell 的 socket 无人能连） |
| 写 /system、写 /data/data | 是（init_shell 只有 read） |

## 7. 并发修复：socket 路径带 pid

第一版把 socket 固定成 `/data/local/tmp/sud/s`，两个 app 同时调 su 会互相踩——后启动的 `unlink` 掉前一个的 socket。

改成 `SOCK_FMT = SOCK_DIR "/s%d"`，用 `getpid()` 做后缀：

```c
snprintf(sock_path, sizeof(sock_path), SOCK_FMT, (int)getpid());
```

父子进程各自持有同一个 `sock_path` 变量（fork 前算好），`am start` 的 extra 也传它。

实测：

```
$ ls /data/local/tmp/sud/
s10194
```

## 8. 真 app uid 测试

真 app（`me.phh.superuser`）的 uid 是 10198。用 ktool 的 `setuid` 把调用方 uid 改成它，模拟真 app 调 su：

```
$ ktool setuid 10198 /system/xbin/su -c 'id; cat /proc/self/attr/current'
uid=10198 euid=10198                       ← 调用方已经是 app 的 uid
Starting: Intent { ...RequestActivity (has extras) }
→ 弹窗（APK 显示 u0_a198）→ 允许
uid=0(root) gid=0(root) context=u:r:init_shell:s0
u:r:init_shell:s0
```

这一层验证的是 **uid 路径**（白名单/数据库都用 uid 查）。
域那一层在 P4.17 用 `ctx` 验过（`untrusted_app → su_exec:file execute`）。
两块拼起来，真 app 调 su 的路径是通的。
