# P4.4 临时 root：成果、限制与风险

**设备**：GT-I9500（Exynos 5410 / Android 5.0.1 / 内核 3.4.5-6264821）
**入口**：CVE-2015-1805（pipe iovec 越界），纯 syscall，shell 可达
**状态**：root 级**文件访问**已打通；**root 级 exec（起 root shell）被内核拒绝**，原因已定位到阶段但未定位到具体检查点

---

## 1. 已实测成立的能力

| 能力 | 状态 | 证据 |
|---|---|---|
| 任意内核读 | ✅ | 读 `linux_banner` → `"Linux ve"` |
| 任意内核写 | ✅ | `selinux_enforcing` 1→0，`getenforce` 变化 |
| uid=0 | ✅ | `getuid()=0`，`cred.uid` 回读为 0，持续 5s 不回滚 |
| capability 全满 | ✅ | `capget` 返回 eff/perm/inh = 0xffffffff |

**全程未重启、未写盘、未刷机、未碰 bootloader。**

## 2. 关键实现

### 2.1 MAC：伪造 policydb.permissive_map

`CONFIG_ALWAYS_ENFORCE` 只删掉了 `selinux_enforcing` 判断，`avc_denied()` 仍保留：

```c
#ifdef CONFIG_ALWAYS_ENFORCE
	if (!(avd->flags & AVD_FLAGS_PERMISSIVE))
		return -EACCES;
```

而 `security_compute_av()` 会读 `policydb.permissive_map`（设备上 `0xc0c4efcc`，实测 `{node=0, highbit=0}` 为空）。

做法：把 `modprobe_path`（`0xc0b9ec3c`，256B 可写 .data）改写成 8 个全 1 的 `ebitmap_node`
（`{next, maps[6]=~0, startbit=i*192}`），再把 `permissive_map = {node=0xc0b9ec3c, highbit=1536}`。
内核直接解引用用户/内核指针均可（ARMv7 无 PAN），所以这里用内核 .data 最稳。

### 2.2 AVC 缓存必须清

旧缓存节点的 `avd.flags` 里没有 PERMISSIVE，命中即拒绝。`avc_cache.slots` 基址 `0xc0c4bc70`、
512 桶（`ubfx #0,#9`），整块清零即可强制全部重新计算。

### 2.3 cred 布局（设备实测，非猜测）

用 `capget()` 逐字段标定：

| 偏移 | 字段 |
|---|---|
| +0x00 | usage |
| +0x04..+0x20 | uid,gid,suid,sgid,euid,egid,fsuid,fsgid |
| +0x24 | securebits |
| +0x28 | cap_inheritable |
| +0x30 | cap_permitted |
| +0x38 | cap_effective |
| +0x58 | security（task_security_struct{osid,sid}） |

task_struct：`tasks=0x1d0`、`real_cred=0x2f8`、`cred=0x2fc`、`comm=0x304`。

## 3. 未解决：uid=0 时 execve 返回 EACCES

### 3.1 现象

| uid / euid | exec 结果 |
|---|---|
| 2000 / 2000 | 正常 |
| 1000 / 1000 | 正常 |
| 1 / 1 | 正常 |
| **0 / 任意** | **EACCES(13)** |
| **任意 / 0** | **EACCES(13)** |

### 3.2 关键判据：失败发生在路径解析之前

- `open("/system/bin/zzz_nope")` → **ENOENT(2)**（路径遍历正常）
- `execve("/system/bin/zzz_nope")` → **EACCES(13)**（本应是 ENOENT）
- 换 `syscall(__NR_execve, ...)` 裸调用，结果一致 → 不是 libc 问题
- 停掉喷雾线程（单线程）、SECURE_NOROOT、file_caps_enabled=0、清 AVC 缓存，均无改善

即：只要 uid 或 euid 为 0，`execve` 在 `open_exec()` 之前就失败。

### 3.3 已排除

- SELinux `selinux_cred_prepare`（设备 `0xc0205ba0`，只返回 0 / -ENOMEM）
- `cap_bprm_set_creds` 的 root 分支（SECURE_NOROOT 跳过仍失败）
- `get_file_caps` / file_caps_enabled
- AVC 缓存陈旧
- 多线程 `LSM_UNSAFE_SHARE`
- DEFEX / 内核里的 knox 字符串（镜像中不存在）

### 3.4 结论

这是一条**非 LSM、与 uid==0 强绑定**的内核检查，位置在 `do_execve` 中 `open_exec()` 之前或
`open_exec()` 的路径解析阶段。`do_execve` 本身没有 `-EACCES` 常量，`prepare_bprm_creds` 只可能返回
`-ENOMEM`，因此剩下两个候选：
1. `open_exec()` 内 `do_filp_open()` 对 uid 0 的路径遍历返回 EACCES（与 `open()` 行为不一致）
2. 某个未在 kallsyms 暴露的钩子

**影响**：无法拿到 root shell（`sh`、`id` 都起不来）。

**规避**：把需要的操作做进工具本身 —— `ktool ls / cat / cp` 以 uid0+caps+permissive 直接做文件 I/O，
已验证可读取任意 app 私有数据。

## 4. 风险：TIMA 已检测到 SELinux 改动

P4.2 写入 `selinux_enforcing=0` 后，内核日志出现：

```
mcdrvkmod mcd: 801|SELinux enabled: 1, SELinux Enforcing: 0
mcdrvkmod mcd: 501|Err tima process_measure_kernel: SELinux turned off
mcdrvkmod mcd: 501|Err tima generate_response_string: SELinux verification failure
```

即 **TrustZone 侧 TIMA 在运行期做了内核完整性度量，并判定失败**。

- 该失败**不是** Knox Warranty Bit（eFuse），`ro.boot.warranty_bit` 仍为 0，未刷机、未改 boot
- 但 TIMA 失败记录属于 Knox 体系，是否影响后续 OTA/Knox 应用**未验证**
- **已把 `selinux_enforcing` 写回 1**，避免持续告警；但 TIMA 的失败记录不会因此消失
- 后续若继续测试，**不要**再改 `selinux_enforcing`；permissive_map 方案不需要它

## 5. 工具用法

```bash
adb push ktool /data/local/tmp/ && adb shell chmod 755 /data/local/tmp/ktool

ktool ls  /data/data                     # root 列目录
ktool cat /data/data/<pkg>/<file>        # root 读文件到 stdout
ktool cp  /data/data/<pkg>/<file> /data/local/tmp/x   # root 复制
ktool dump <hexaddr> <len>               # 任意内核读
ktool w32  <hexaddr> <val>               # 任意内核写
ktool permissive                         # 仅打开 MAC 放行
ktool root                               # 仅提权（uid0+caps）
```
