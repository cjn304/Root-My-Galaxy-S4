# P4.29 机型/build 适配表：换目标要动哪几处

日期：2026-10-22
产物：`src/targets.h`（用户态 ktool 与内核模块**共用同一张表**）

---

## 一、表怎么选目标

```
主键 = 机型(ro.product.device) + 内核 version 串(/proc/version 第二段)
例：  ja3g : 3.4.5-6264821
```

**为什么不用 ROM build id 当主键**：表里的地址全部来自**内核镜像**（vmlinux 的
`.text/.data/.bss` 布局）。同一个内核被不同 ROM 复用时地址完全一样；反过来
同一个 build id 换内核后地址必然不同。build id 只作记录和人工对照。

**匹配不到会怎样**：`ktool` 拒绝执行**所有地址类命令**（root/sh/permissive/patch/
restore/flush 都不干），只打印支持列表和本机 `device/kernel`。绝不按机型猜地址。

```
$ ktool target
device=ja3g kernel=3.4.5-6264821
supported targets:
  GT-I9500    device=ja3g        kernel=3.4.5-6264821    [verified]
              build=LRX22C.I9500ZSSHQD1
加目标见 P4.29_机型build适配表.md（只需推 6 个地址，逻辑不动）
```

模块侧由开机脚本传 `ktool_target="<device>:<kernel>"`；不给参数时，表里只有
一个目标才退回它，多个目标就禁用地址类操作。开机日志会打：

```
ktool: target ja3g/3.4.5-6264821 build=LRX22C.I9500ZSSHQD1
```

## 二、字段分三类

| 类 | 含义 | 换 build | 换近亲机型 |
|---|---|---|---|
| **[A] build 相关地址** | 内核镜像布局 | **必改** | **必改** |
| **[A2] 策略相关** | perm_bit（init_shell 的 type value） | 策略没变就不用 | **必改** |
| **[B] 内核配置偏移** | `struct task_struct` / `struct cred` 字段偏移 | 一般不动 | 通常照抄，要用探针复核 |
| **[C] 逻辑** | ish/ctx/门禁/双钥匙/restore 分档/AVC flush | 不动 | 不动 |

### [A] 六个地址（每个内核镜像都不同）

| 字段 | 是什么 | 用在哪 |
|---|---|---|
| `init_task` | `init_task` 地址 | `find_self()` 扫任务链表的锚点 |
| `modprobe_path` | 256 字节可写 `.data` | 借来放 8 个假 `ebitmap_node`（min permissive 用） |
| `permissive_map` | `policydb.permissive_map`（`struct ebitmap`） | min permissive / restore |
| `avc_slots` | `avc_cache.slots[512]` | 仅调试命令 |
| `exec_br` + `exec_br_orig/patch` | `sys_execve` 里 KNOX 检查块的 `beq` | root 态 exec（su 依赖它） |
| `lkmauth_bootmode` | BSS 里的启动模式变量 | 开机写成 2 |

### [A2] 策略相关

| 字段 | 说明 |
|---|---|
| `perm_bit` | **init_shell 的 type value（不是 SID！）**，min permissive 就设这一位。本机 986。换机型/换策略必变，用 `sepolicy_parse.py` 数出来 |

`ktool permissive [bit]` 支持临时覆盖，便于在不改表的情况下试：

```
$ ktool permissive          → bits=[986] (min)
$ ktool permissive 1018     → bits=[1018] (min) [override]
```

### [B] 七个偏移

```
task.tasks=0x1d0  real_cred=0x2f8  cred=0x2fc  comm=0x304
cred.uid=0x04     caps=0x28     security=0x58
```

这些由**内核 defconfig** 决定（不是 build id）。同 SoC 同 defconfig 基本一致；
如果目标机型的内核选项不同（`CONFIG_KEYS`、`CONFIG_DEBUG_CREDENTIALS` 等），
偏移会整体平移——用现成的 `kmod/kprobe.c` 探针复核（它会打印实测偏移）。

## 三、换 build（同机型）

**只改 [A] 六项**，`perm_bit` 和 [B] 通常不动。步骤：

1. 拿到该 build 的内核镜像（`boot.img` 解出 kernel，或官方源码编出的 vmlinux）
2. 定位符号（有镜像时 `nm`/`objdump` 最省事）：

```bash
nm vmlinux | grep -E ' (init_task|modprobe_path|lkmauth_bootmode)$'
# permissive_map 在 policydb 里，是 .bss 里的一个 struct ebitmap
# exec_br：反汇编 sys_execve，找「连续比较 cred 的 6 个 id」之后的 beq
```

3. 没有镜像时，用现成的 **kread 原语**扫（只读、可验证）：
   - `modprobe_path`：在 `.data` 范围搜字符串 `/sbin/modprobe`
   - `permissive_map`：搜 `{node 指针, highbit>=987}` 且 node 链 `startbit` 递增的结构
   - `exec_br`：读 `sys_execve` 附近，找 `... 0a0000xx`（beq）且下一段会调
     `sec_check_execpath` 的位置
4. 表里加一行，`verified = 0`，先跑只读命令（`ktool target` / `ktool dump`），
   确认读出来的东西对（`init_task` 附近能读到 `swapper/0`），**再**跑写命令。

**风险**：地址错 = 往内核里随便写 → 直接 panic 或变砖。所以流程必须是
「只读校验 → 单命令写 → 立刻验证回读」，不要一上来跑 `sh`/`restore`。

## 四、换机型：只考虑"近亲"

**判定近亲的三条硬指标**（缺一条就别试）：

1. `ro.build.version.release` = 5.0.1（或同为 SEPF 5.x 时代）
2. `/proc/version` 以 `3.4.5` 开头
3. 策略里存在 `untrusted_app → system_file: file execute`
   （这条决定 ktool 必须 700，否则任何 app 都能 exec 它拿 root）

**大概率可行（同 Exynos 5410 + 同 SEPF + 同内核 3.4.5）**：

| 机型 | 说明 | 状态 |
|---|---|---|
| GT-I9500 | 本机，`ja3g` | ✅ 已全链路验证 |
| GT-I9502 | 双卡国行，同 SoC | 候选，需推 6 地址 + 复核策略 |
| GT-I9508 | 移动版，同 SoC | 候选 |
| GT-I959 / SCH-I959 | 电信版，同 SoC | 候选 |
| SHV-E300S/K/L | 韩版 S4（Exynos Octa） | 候选 |

> 具体 `ro.product.device` 一定要从设备上 `getprop` 读，不要照抄文章里的代号。

**明确不要试**：

| 机型 | 原因 |
|---|---|
| GT-I9505 / I9506 / I9515 | Snapdragon 600，内核完全是另一套 |
| Note 3 (`hlte`) | Snapdragon 800 |
| Note 3 Exynos (`ha3g`) | Exynos 5420，内核接近但偏移/地址全变，且是另一套 SEPF |
| 任何 Android 6+ 三星 | 没有这个 KNOX 分支形态；CVE-2015-1805 也早修了 |

### 换近亲机型要动的地方

1. **[A] 六个地址** —— 全推
2. **[A2] `perm_bit`** —— 用该机型 `sepolicy` 数 init_shell 的 type value
3. **策略四项复核**（决定能力边界，不是地址）：
   ```
   untrusted_app → app_data_file: dir{create,add_name,remove_name,search,write}
                                  file{create,write,append}   ← appwrite/apprm 靠它
   untrusted_app → system_file:  file execute                   ← ktool 必须 700
   init_shell    → （capability setuid/setgid/chown/dac_override 是否存在）
   init_shell    → app_data_file: 是否仍缺 write（缺才对，说明双钥匙仍必要）
   ```
4. **交付物重做**：ktool 落盘 700、模块部署、boot 脚本部署、su APK 重新授权
5. **[C] 逻辑一行不用改** —— 这是这次重构的目的

## 五、代码里还有哪些不是"表"能覆盖的

诚实列一下，换目标时容易漏：

| 位置 | 内容 | 说明 |
|---|---|---|
| `kmod/ktool_mod.c` `ktool_relabel()` | 把 `/dev/ktool` 的 security blob 指向 `/dev/null` 的 | 依赖该机型存在 `/dev/null` 且标签可用；几乎不变 |
| `ktool` 门禁 `su_path` | `/system/xbin/su` | 路径不同（有的机型在 `/system/bin/su`）要改参数 |
| `su_fork.c` | phh 协议 + `17` 版本常量 | 与 APK 绑定，换机型不用改 |
| boot 脚本 | `/data/local/tmp` 调试通道、`/system/lib/modules` | 路径基本通用 |
| `cred.securebits` 0x24 | 由 `off_cred_uid + 0x20` 推导 | 不需要单列 |
| `list_head` 的 `{next,prev}` 布局 | 内核 ABI 级稳定 | 不需要参数化 |

**已知待办**：`perm_bit` 现在进表了，但 `sepolicy_parse.py` 的"数 type value"还没
自动接进构建流程——换机型时得手动跑一次（见该脚本头部注释）。

## 六、加完新目标的验收清单

全部通过才算这个 target 可用：

```
[ ] 1. ktool target               显示新目标，verified 状态符合预期
[ ] 2. ktool dump <init_task+0x2f8-4> 64   能读到 swapper/0 的 comm
[ ] 3. ktool root /system/bin/ls 成功（说明 find_self/do_root 偏移对）
[ ] 4. ktool sh -c id             context=u:r:init_shell:s0
[ ] 5. ktool permissive           打印 bits=[该机型 perm_bit]
[ ] 6. insmod 成功 + /dev/ktool 出现
[ ] 7. ktool flush                avc cache flushed
[ ] 8. appwrite 写 app 数据       rc=0，文件 owner = 该 app uid
[ ] 9. apprm 删掉它               rc=0
[ ] 10. sh -c 'echo ish > /dev/ktool'  rc=1（门禁有效）
[ ] 11. 重启后：ktool 700、模块 target 日志正确、restore_rc=0
[ ] 12. Amaze 等真实 app 走 su    gate ALLOW + ish uid0
```
