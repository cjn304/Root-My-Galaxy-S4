# P4.5 KNOX exec 限制的机制与破解（root shell 打通）

**结论**：找到并绕过了 Samsung 在 `sys_execve` 里加的 root 限制，`uid=0(root)` shell 已跑通。

---

## 1. 根因：`sec_check_execpath`

设备上 `sys_execve @0xc0012118` 不是原生实现，Samsung 在入口处插了一段：

```asm
c0012158  ldr r3, [r3, #0x2fc]     ; current->cred
c001215c  ldr r2, [r3, #4]         ; cred->uid
c0012160  cmp r2, #0
c0012164  beq c0012174             ; uid==0 → 走检查块
c0012168  ldr r2, [r3, #8]         ; cred->gid
c0012170  bne c00122b4             ; uid!=0 && gid!=0 → 再看 euid/egid/suid/sgid
...
c00122e0  bne c0012288             ; 六个 ID 全非 0 → 直接 do_execve（完全不检查）
```

**只要 uid/gid/euid/egid/suid/sgid 里有任意一个是 0，就会进入检查块**；普通 app/shell（全 2000）直接跳过，所以它们 exec 一切正常。

检查块逻辑（还原后）：

```c
if (root_ish()) {
    if (sec_check_execpath(current->mm, "/sbin/adbd")) {
        /* adbd 特例：把 cred 改成 2000 再放行 */
        new = prepare_creds();
        new->uid = new->gid = new->euid = new->egid = 2000;
        commit_creds(new);
    }
    if (sec_check_execpath(current->mm, "/data/")) {
        printk("<3>Restricted making process. PID = %d(%s) PPID = %d(%s)\n", ...);
        return -EACCES;                  /* ← 我们一直撞的就是这里 */
    }
    ...
}
```

`sec_check_execpath(mm, prefix)` 的实现（`0xc0011ee0`）：

```c
file = get_mm_exe_file(mm);          // 注意：取的是**当前正在运行的可执行文件**
if (!file) return 0;
d_path(&file->f_path, buf, 4096);
return strncmp(buf, prefix, min(strlen(buf), strlen(prefix))) == 0;
```

**关键点：它比较的是「当前进程的可执行文件路径」，不是要 exec 的目标路径。**

所以：只要你的入口程序在 `/data/` 下（比如 `/data/local/tmp/ktool`），这个进程一旦 uid=0，就**永远**不能 exec 任何东西——连 `/system/bin/id` 都不行。这就解释了之前所有反常现象：`stat`/`open` 正常（ENOENT），只有 `execve` 返回 EACCES；uid=1000/2000 正常。

**dmesg 实证**：

```
<3>[ 1432.273960] L0 8527 Restricted making process. PID = 8527(ktool) PPID = 8524(sh)
```

## 2. 绕过

### 2.1 先确认内核 text 可写

用「幂等写入」验证（把原值写回原地址，成功即代表该页可写，失败也不会崩——`copy_to_user` 有 fixup，只返回 EFAULT）：

```
ktool w32 c0012324 0x0a000001
→ c0012324 <= 0a000001 (was 0a000001)     成功
```

结论：**没有 CONFIG_STRICT_MEMORY_RWX，内核代码段可写**。

### 2.2 补丁

把 `c0012164` 的 `beq c0012174`（uid==0 进入检查块）改成 `b c0012288`（直接去 do_execve）：

| 项 | 值 |
|---|---|
| 地址 | `0xc0012164` |
| 原指令 | `0x0A000002` (`beq`) |
| 新指令 | `0xEA000047` (`b 0xc0012288`) |
| 计算 | `(0xc0012288 - 0xc001216c) >> 2 = 0x47` |

```
ktool w32 c0012164 0xea000047
→ c0012164 <= ea000047 (was 0a000002)
```

## 4. 使用

```bash
adb push ktool /data/local/tmp/ && adb shell chmod 755 /data/local/tmp/ktool

# 一条命令拿 root shell（内部：打补丁 → uid0+caps → permissive → exec sh）
adb shell /data/local/tmp/ktool sh
adb shell "/data/local/tmp/ktool sh -c 'id; ls /data/data'"
```

`ktool sh` 内部顺序：
1. `find_self()` → 找到自己的 task
2. 补 caps（inheritable/permitted/effective/bset = 0xffffffff）
3. uid/gid/euid/egid/suid/sgid/fsuid/fsgid = 0
4. 伪造 `policydb.permissive_map` + 清 AVC 桶
5. `execve("/system/bin/sh", ...)`

**注意**：`ktool sh` 本身**不打** exec 补丁（补丁是一次性的内核改动）。要恢复干净状态就重启。

## 5. 风险与回滚

| 项 | 说明 |
|---|---|
| 补丁范围 | 只影响 `uid==0` 的 exec；普通 app/shell 走另一条分支，行为不变 |
| 回滚 | 重启即恢复原状（纯 RAM 修改） |
| 写坏的可能 | 若指令编码错误会导致 exec 崩溃 → `panic_on_oops=1` → 重启（40–60s），不变砖 |
| Knox | 不碰 boot/recovery/分区，warranty_bit 仍为 0 |
| TIMA | 该补丁不涉及 `selinux_enforced/enabled` 两个被 PKM 监控的变量 |
| 已知代价 | 每次重启后需重跑 `ktool sh`；补丁非持久 |

**原始字节备份**：`kernel_full.bin` 中 `0xc0012164` = `02 00 00 0a`，需要还原时执行
`ktool w32 c0012164 0x0a000002`。
